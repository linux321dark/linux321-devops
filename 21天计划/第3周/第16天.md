# 第 16 天 · 中间件云原生化（Operator）

## 一、今日目标（结论先行）
用 **StatefulSet + Operator（Redis/Strimzi ES）** 把中间件跑上 K8s，实现故障自动转移——对应三岗共同要求的"中间件高可用"，复用你 2.6 中间件实战。

## 二、企业真实需求背景
- **行业B**："负责中间件、消息队列、缓存、日志系统组件运维，保障业务中间件集群高可用"。
- **行业C**：多中间件高可用。
- 你已熟 Nginx/Tomcat/MySQL/Oracle/Redis/Kafka/ES 部署，今日只补"K8s 上有状态部署"一层，性价比高。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜为什么中间件是最难上 K8s 的一类（也是你的差异化优势）
无状态应用挂了重建就行，中间件不行——它有三个硬约束：

| 约束 | 具体表现 | K8s 的解法 |
|---|---|---|
| **数据不能丢** | Pod 重建后本地数据消失 | PVC + `volumeClaimTemplates`，存储独立于 Pod 生命周期 |
| **身份不能变** | 集群成员要互相认识（Kafka broker id、ES 节点名、Redis 主从关系） | Headless Service + StatefulSet 有序命名 `xxx-0/xxx-1` |
| **启动顺序有讲究** | 主节点先起、从节点后加入；成员变更要按序 | StatefulSet 有序启停 + Operator 的 readiness 逻辑 |
| **故障要能自动处理** | 主库挂了要选主、副本落后要重建 | Operator 把 DBA 的处置经验写成代码 |

**这就是行业B"保障业务中间件集群高可用"的真实含义**：不是让你会 `helm install redis`，是让你在 Pod 被驱逐、节点故障、存储挂掉时知道会发生什么、怎么恢复。

### 场景 B｜真实事故现场
1. **Pod 重建数据没了**：用了 `emptyDir` 或没配 PVC，或者 StorageClass 是本地盘（节点漂移后数据在新节点上不存在）。正确：生产用网络存储（阿里云云盘/ NAS），并确认 StorageClass 的 `reclaimPolicy` 不是 Delete。
2. **Kafka 脑裂 / 数据丢失**：`replication.factor=1`（副本只 1 份）、`min.insync.replicas` 没配、`unclean.leader.election` 开着。正确：至少 3 broker + RF=3 + `min.insync.replicas=2` + 关闭 unclean 选举。
3. **ES 单节点 OOM 或无法启动**：`vm.max_map_count` 太小、`node.store.allow_mmap` 没关。正确：宿主机调内核参数，或按 ECK 文档关 mmap。
4. **Redis 主从切换后应用连不上**：应用连的是具体 Pod IP 而不是 Service，或者没配哨兵/代理。正确：客户端走 Service 或 Sentinel/Cluster 代理，不直连 Pod。
5. **Operator 升级把中间件搞崩**：CRD 版本不兼容、Operator 和 K8s 版本错配。正确：先看兼容矩阵，在非生产环境验证，生产 Operator 与中间件版本都钉死。

### 场景 C｜面试官的真实痛点
行业B明确写"中间件、消息队列、缓存、日志系统组件运维"——他们要的是**能处理中间件故障的人**，不是能装中间件的人。面试会直击：
- "Kafka 消息丢了怎么排查？"（答案：看 ISR、看 ack 配置、看 min.insync.replicas）
- "Redis 主从延迟大怎么办？"（答案：看 `INFO replication` 的 offset 差、看网络、看大 key）
- "ES 集群变黄/变红怎么处理？"（答案：黄=副本未分配，红=主分片缺失，看 `_cluster/allocation/explain`）

**你的优势**：裸机时代你是真踩过这些坑的，现在只是把部署形态换成 K8s，**排障逻辑没变**——这一点一定要在面试里讲出来，这是纯云原生新人没有的。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 存储 | emptyDir / 本地盘 | 网络存储 PVC + 保留策略 |
| 副本数 | Kafka 单 broker 图省事 | ≥3 broker，RF=3，min ISR=2 |
| 客户端连接 | 直连 Pod IP | 走 Service / Sentinel / 代理 |
| 版本管理 | Operator 跟着 latest 升 | 兼容矩阵核对 + 钉版本 |
| 备份 | 有 PVC 就以为安全 | PVC ≠ 备份，定期快照/逻辑备份 |

- **原理**：有状态需稳定网络标识(Headless Service)+持久存储(PVC)；Operator 封装领域运维知识(CRD+Controller)。
- **理论**：有状态 vs 无状态；Operator 模式。
- **核心易忘点**：`StatefulSet` 有序启停；`volumeClaimTemplates`；Redis Operator / Strimzi(Kafka) / ECK(ES)。
- **横向对比**：裸机部署（你熟）vs StatefulSet 裸跑 vs Operator（生产推荐）。
- **常见问题**：Pod 重建数据丢→PVC+正确 StorageClass；Kafka 脑裂→`replication.factor`+`min.insync.replicas`。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 Redis Operator 部署主从 + PVC
```bash
helm repo add redis-operator https://ot-container-kit.github.io/helm-charts
helm install redis redis-operator/redis-operator -n middleware --create-namespace
kubectl apply -n middleware -f - <<'EOF'
apiVersion: redis.redis.opstreelabs.org/v1beta2
kind: Redis
metadata: { name: redis-standalone }
spec:
  kubernetesConfig: { image: redis:7.4.1-alpine }
  storage: { volumeClaimTemplate: { spec: { resources: { requests: { storage: 1Gi } } } } }
EOF
kubectl get pods -n middleware
```

### 5.2 模拟 Pod 删除 → 观察自动重建
```bash
POD=$(kubectl get pods -n middleware -l redis=redis-standalone -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod $POD -n middleware
kubectl get pods -n middleware -w     # 新 Pod 重建且数据保留（PVC）
```

### 5.3 ES Operator / Kafka(Strimzi) 选一
```bash
# ECK
kubectl apply -f https://download.elastic.co/downloads/eck/3.0.0/crds.yaml -f https://download.elastic.co/downloads/eck/3.0.0/operator.yaml
kubectl apply -f - <<'EOF'
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata: { name: quickstart }
spec:
  version: 8.15.0
  nodeSets: [{ name: default, count: 1, config: { "node.store.allow_mmap": false } }]
EOF
```

## 六、成果验证方式
1. Redis Pod Running，PVC 绑定（数据持久）。
2. 删 Pod 后新 Pod 重建，数据不丢（验证 PVC 生效）。
3. ECK/Kafka 其一部署成功，`kubectl get elasticsearch/strimzi` 显示就绪。

## 七、常见坑与排错
- StorageClass 不对致 PVC Pending；Operator 版本与 K8s 版本错配。
- Kafka 脑裂靠副本因子；ES 单节点关 mmap（资源受限）。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：中间件高可用你怎么保障？（你的强项，答扎实）
> "分两层说：**故障发生前靠架构，故障发生后靠排障经验**。
> 架构上，Kafka 至少 3 broker、副本因子 3、`min.insync.replicas=2`，关闭 unclean 选举——这样挂一台不丢数据也不选脏主；Redis 用主从加 Sentinel 或 Cluster，客户端走 Sentinel 拿主节点地址，不直连 Pod；ES 按角色分节点，主节点不和数据节点混部；MySQL 主备异步复制，配半同步降低丢数据风险。
> 排障上，这几类问题我都实际处理过：Kafka 消息丢，先看 ISR 是否收缩、再看 producer 的 acks 是不是 1、再看 min ISR 配置；Redis 主从延迟，看 `INFO replication` 的 offset 差和网络；ES 索引变红，看 `_cluster/allocation/explain` 定位是主分片未分配还是节点丢失。
> K8s 上只是把部署形态换成 StatefulSet + PVC + Operator，**排障逻辑没变**——这是我相对纯云原生背景的人的优势。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| StatefulSet 和无状态 Deployment 区别？ | "三点：稳定网络标识（Headless Service 给每个 Pod 固定 DNS）、稳定存储（volumeClaimTemplates 每个 Pod 独立 PVC）、有序启停（`-0` 起完才起 `-1`）。中间件全靠这三条。" |
| Operator 到底解决什么？ | "把运维专家的处置逻辑写成控制器。比如 Redis 主挂了，不用人半夜登上去敲 `slaveof`，Operator 检测到就自动提升从库、重建旧主、重新同步。CRD 描述期望状态，Controller 负责收敛。" |
| PVC 就是备份吗？ | "不是，这是常见误解。PVC 保证 Pod 重建数据还在，但误删数据、逻辑损坏、存储故障照样丢。备份要单独做——逻辑备份或存储快照，并且要定期演练恢复。" |
| Kafka 副本不全会不会阻塞生产？ | "取决于 `acks` 和 `min.insync.replicas`。`acks=all` + `min.insync.replicas=2` 时，ISR 不足会直接拒绝写入，保护数据一致性但牺牲可用性；要按业务取舍——交易类必须这样，日志类可以放宽。" |
| ES 集群变黄要紧吗？ | "黄是副本未分配，数据完整但没冗余，要查；红是主分片缺失，部分数据不可读，必须立刻处理。处理顺序是 `_cluster/health` → `_cluster/allocation/explain` → 看磁盘水位和节点状态。" |

### 数字锚点
`Kafka RF=3 / min ISR=2`｜`StatefulSet 三要素`｜`PVC ≠ 备份`｜`ES 黄=缺副本 / 红=缺主分片`

### 禁忌
- ✗ "中间件直接 helm install 就行" —— 会被立刻追问故障处理。
- ✗ 把 PVC 当备份 —— 数据安全认知错误。
- ✗ 只说 K8s 部署方式，不说排障 —— 丢掉了你最大的优势。
