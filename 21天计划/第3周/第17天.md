## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜等保测评现场到底在查什么（不是背条款，是拿证据）
测评师进场的动作是"要材料 + 登系统验"，逐条对应你要准备的东西：

| 控制点 | 测评师会做什么 | 你要准备的证据 | 落到 K8s 是什么 |
|---|---|---|---|
| 身份鉴别 | 看是否唯一标识、口令复杂度、是否多因素 | 账号清单、密码策略截图、堡垒机日志 | apiserver 接 OIDC/企业 IDP，禁用匿名访问 |
| 访问控制 | 抽一个账号看它能访问什么 | RBAC 清单、权限矩阵、审批记录 | Role/RoleBinding 最小权限，一岗一角色 |
| 安全审计 | 要求调某天的操作记录 | 审计日志（≥6 个月）、日志完整性证明 | apiserver audit log → Filebeat → ES，禁止篡改 |
| 入侵防范 | 看漏洞扫描记录和补丁记录 | 扫描报告 + 整改工单 + 复测记录 | Trivy 接 CI，报告归档 90 天以上 |
| 数据完整性/保密性 | 看传输加密、存储加密 | TLS 配置、KMS 加密证明 | Ingress TLS、etcd 加密、PVC 加密 |
| 数据备份恢复 | 要求现场恢复一次 | 备份策略 + 恢复演练记录 | Velero 备份 + 定期演练记录 |
| 剩余信息保护 | 看数据删除是否彻底 | 数据销毁流程 | PVC 回收策略、镜像/日志清理 |

**这就是你证书之外真正值钱的东西**：多数人只有证，没有"证据链怎么造"的经验。你在金融项目做过一次三级测评，这套流程你是真跑过的。

### 场景 B｜真实事故现场（合规最容易在这里翻车）
1. **审计日志没开或保留不够**：默认 apiserver 审计策略很弱，甚至没开。测评时"调三个月前的操作记录"拿不出来 → 直接判不符合。正确：显式配 AuditPolicy（Metadata 级别起步），日志集中存储并设保留期 ≥6 个月。
2. **密钥硬编码到处飞**：Git 里有、镜像里有、ConfigMap 里有。这是等保和个保法的双重红线，也是最高频整改项。正确：External Secrets + KMS + Git 历史清洗。
3. **NetworkPolicy 写了但没生效**：CNI 不支持（kind 默认的 kindnet 不支持 NetworkPolicy）。正确：Calico/Cilium/Terway，部署后必须实测"默认拒绝后是不是真的不通"，不能只看对象存在。
4. **镜像漏洞有扫描没闭环**：扫了，报告没人看，高危照样上线。正确：门禁阻断 + 工单闭环 + 复测记录，三段证据齐全。
5. **特权容器 / root 运行**：为了省事加 `privileged: true`。这在等保里是明确的"入侵防范"不符合项。正确：PodSecurity Admission 限制到 baseline/restricted，非 root + 只读根文件系统。

### 场景 C｜面试官的真实痛点
行业A 的 JD 写"理解 HIPAA、个保法、等保对基础设施的合规硬约束"——他要的是**你能在架构设计阶段就把合规嵌进去，而不是上线后被测评打回来重做**。这决定了两件事：
- 你能不能在设计评审时说出"这个方案过不了等保，因为审计日志没设计"；
- 你知不知道合规改造的真实成本（往往比功能开发还高）。

### 场景 D｜信创环境和通用环境，到底差在哪（你的老本行，别浪费）
你已经在信创上做过 多类技术栈交付，但缺一个"信创 + 云原生"的合起来讲法。真实差异只有这四条，记住就够用：

| 差异点 | 通用环境 | 信创环境 | 对 K8s 的实际影响 |
|---|---|---|---|
| CPU 架构 | x86_64 一统 | **鲲鹏/飞腾（ARM64）+ 龙芯（LoongArch）** 多架构并存 | 镜像必须**多架构构建**（`docker buildx --platform linux/arm64,linux/amd64`），否则拉起来就 `exec format error` |
| 操作系统 | CentOS/Ubuntu | **麒麟 V10 / 统信 UOS**（内核版本与 systemd 行为有差异） | kubelet/containerd 需对应版本；SELinux/安全加固策略可能拦截容器挂载 |
| 数据库 | MySQL/PG | **达梦 / 人大金仓 / GaussDB / OceanBase** | 有状态服务的 Operator 基本没有国产库适配版，得自己写或用 StatefulSet + 手工高可用 |
| 中间件 | Nginx/Tomcat | **东方通 TONGWeb / 宝兰德 / 金蝶 Apusic** | 官方镜像往往不存在，需自建基础镜像；JDK 需用国产发行版（如毕昇 JDK / 龙井 JDK） |

**这才是"信创 + K8s"的真实门槛**：不是会不会装 K8s，是**你的镜像、Chart、Operator 在 ARM64 + 国产 OS 上还能不能跑**。你原来的信创经验解决的是"单机部署能不能跑"，现在补的是"容器化 + 编排后能不能跑"——这两件事的难点完全不同，讲清这个差别，面试官会认为你真做过信创。

**一句话概括（可直接背）**：**信创迁移的难点不在换操作系统，在换 CPU 架构之后的整条制品链——基础镜像、依赖库、JVM、数据库驱动、Operator 全部要重新验证一遍。** 这句话只有真做过信创的人才说得出来。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 审计 | 上线后再补日志 | 架构阶段就设计 audit + 集中存储 + 保留期 |
| 密钥 | 环境变量/ConfigMap | External Secrets + KMS + 轮换 |

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: prod }
spec: { podSelector: {}, policyTypes: [Ingress, Egress] }
EOF
```

## 七、常见坑与排错
- 审计日志缺失是等保高频扣分项；弱口令/高危端口暴露；未定期渗透。
- NetworkPolicy 需 CNI 支持（Calico/Cilium），kind 默认无→用 Cilium 或仅演示 manifest。
- **信创侧 `exec format error`**：镜像架构不符。先 `docker manifest inspect` 看有没有 arm64，没有就 buildx 重构建；有但 Pod 仍报错，查节点架构 `kubectl get node -o wide` 是不是混部了两种架构（需 `nodeSelector: kubernetes.io/arch` 亲和）。
- **信创侧 `libssl.so.1.1: cannot open shared object file`**：基础镜像里的 openssl 版本与目标 OS 不匹配，麒麟 V10 与 UOS 20 的默认版本不同。正确做法是**基于目标国产 OS 的官方基础镜像**重构建，不要在 alpine 上打补丁硬凑。
- **国产库容器化后字符集/大小写问题**：达梦默认大小写敏感、分页语法与 MySQL 不同，迁移后应用 SQL 报错。这类问题必须在适配清单里单列，不能归到"应用 bug"。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：等保三级在 K8s 上怎么做？（你的差异化王牌，务必答满）
> "我持等保 2.0 证书，也在上一家完整支撑过一次三级测评，所以这块我能说到落地层。
> 三级是'一个中心、三重防护'——安全管理中心，加计算环境、区域边界、通信网络三层防护。落到 K8s 上是这样对应的：
> **身份鉴别**接企业 IDP 走 OIDC，不让人拿静态 kubeconfig 到处跑；**访问控制**用 RBAC 做到一岗一角色，开发只能看自己命名空间的 Pod 日志，不能 exec；**安全审计**开 apiserver audit，日志经 Filebeat 收进 ES，保留半年以上，测评师要调三个月前的操作记录我直接给；**入侵防范**用 PodSecurity Admission 卡住特权容器和 root 运行，镜像走 Trivy 门禁，CRITICAL 直接阻断；**数据保密性**是 Ingress TLS + etcd 加密 + PV 加密；**备份恢复**用 Velero，并且每季度真演练一次恢复，不是只写方案。
> 最关键的一点：**合规不是上线后补，是设计评审阶段就要嵌进去**。我见过最常见的返工是审计日志没设计，测评前两周才发现要重做日志链路。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 等保三级和二级差在哪？ | "三级多了一整套集中管控和更严的审计要求：二级主要看基本防护，三级要求安全管理中心统一管控、审计记录集中留存、还要定期渗透测试和每年测评。三级在实际执行上是要'拿得出证据'，二级更多是'有没有做'。" |
| 审计日志怎么设计？ | "apiserver 配 AuditPolicy，先上 Metadata 级别（记录 who/what/when，不记请求体，避免日志爆量和泄敏），关键资源可以开 Request 级别；日志落到文件，Filebeat 采集进 ES，Kibana 做查询，保留 6 个月以上，存储侧设只增不改。" |
| 密钥合规怎么保证？ | "三层：密钥不进 Git、不进镜像，Git 里只有 ExternalSecret 声明；运行时从 KMS 拉，走 RAM 角色鉴权；KMS 有调用日志，谁在什么时候取过什么密钥可查。这是等保要的证据链。" |
| NetworkPolicy 怎么验证真的生效？ | "写默认拒绝之后，必须实测——同命名空间跨 Pod 能不能通、跨命名空间能不能通、能不能出公网。只看 YAML apply 成功不算，因为 CNI 不支持的时候策略会被静默忽略，这是最坑的地方。" |
| 个保法和等保有冲突吗？ | "不冲突但侧重点不同。等保管'系统安全'，个保法管'个人信息处理的合法性'，比如数据最小化、告知同意、跨境传输限制。医疗数据两边都管，所以除了安全措施，还要有数据分类分级、访问留痕、脱敏策略。" |
| 你在信创方面做过什么？ | "做过 多类技术栈的信创交付，覆盖麒麟/统信 UOS 操作系统、鲲鹏/飞腾 CPU、达梦/人大金仓数据库、东方通/宝兰德中间件。转到容器化之后要补的是另一层——**镜像和制品链的适配**：基础镜像有没有 arm64 版本、国产 JDK 的依赖库齐不齐、国产库有没有 Operator。我现在做的是多架构构建（buildx 一次出 amd64 + arm64 manifest）加自建国产中间件基础镜像。**信创迁移的难点不在换操作系统，在换 CPU 架构之后的整条制品链全部要重新验证一遍**，这个判断是我踩过坑才有的。" |
| 信创环境的 K8s 和通用环境有什么不同？ | "三个层面：① **架构**——x86 变 ARM64/LoongArch，所有镜像要重建，节点要按 arch 做亲和，混部会直接起不来；② **操作系统**——麒麟/UOS 的内核和 systemd 行为与 CentOS 有差异，kubelet/containerd 版本要匹配，安全加固策略可能拦容器挂载；③ **生态缺失**——国产库基本没有官方 Operator，国产中间件没有官方镜像，这两块得自己补。所以我一般先做一份适配清单逐条验，而不是直接上生产试。" |

### 数字锚点
`一个中心三重防护`｜`审计保留 ≥6 个月`｜`CRITICAL 阻断`｜`每季度恢复演练`｜`最小权限一岗一角色`｜`多类技术栈信创交付`｜`多架构 amd64+arm64 单 manifest`

### 禁忌
- ✗ 只背条款不讲落地 —— 面试官要的是"证据怎么造"。
- ✗ "合规是安全部门的事" —— 行业A 岗位直接排除。
- ✗ 说 NetworkPolicy 配了就行 —— 不验证等于没配。
- ✗ 把信创说成"装过麒麟系统" —— 那是桌面运维，不是信创交付。要说制品链。
