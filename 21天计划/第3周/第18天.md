## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜CKA 的四个考点，正好对应运维每天的四件事
CKA 考纲看着像考试，其实是**值班时最常遇到的四类任务**：

| 考点 | 考试形式 | 真实工作对应 | 常见触发场景 |
|---|---|---|---|
| **网络策略** | 给一组 Pod 写隔离规则 | 等保整改、微服务隔离、多租户 | 测评要求"业务区与数据区隔离" |
| **存储** | PV/PVC 绑定、挂载、扩容 | 中间件持久化、日志落盘 | 磁盘写满要扩容、Pod 换了节点数据丢 |
| **调度** | nodeSelector / 亲和 / 污点容忍 | 让 GPU 任务去 GPU 节点、核心业务隔离到专有节点池 | 有状态服务被调度到错误节点 |
| **ETCD 备份恢复** | 做快照、恢复集群 | **集群级灾难恢复的最后一道防线** | 升级前备份、误删资源、控制面故障 |

**最该重视的是 ETCD**：前三个错了是单个服务受影响，ETCD 恢复失败是**整个集群没了**。这也是面试里最能区分"玩过"和"管过"的问题。

### 场景 B｜真实事故现场
1. **升级前没备份 ETCD，升级失败集群起不来**：这是最致命的一类。正确：任何控制面变更（升级、证书轮换、etcd 参数调整）前必须做快照 + **验证快照可用**（`snapshot status`），并把快照拷到别的机器（本地快照跟着机器一起挂）。
2. **NetworkPolicy 写了不生效，以为配置错了**：CNI 不支持。正确：先确认 CNI 类型（Calico/Cilium 支持，kindnet/flannel 部分支持），再看策略是否在正确的命名空间、`podSelector` 是否匹配到 Pod。
3. **PVC 一直 Pending**：没有匹配的 PV，或 StorageClass 不存在，或 `accessModes` 不匹配（RWO vs RWX），或容量不够。正确：`kubectl describe pvc` 看 Events，四个原因逐个排。
4. **Pod 一直 Pending 但不报错**：资源不足 / 节点亲和无法满足 / 污点没容忍 / PDB 阻塞。正确：`kubectl describe pod` 看 Events 里的 `FailedScheduling` 原因，一句话就定位。
5. **`kubectl drain` 把业务搞挂**：drain 驱逐 Pod 但没有 PDB 保护，一次性全赶走。正确：配 PDB（`minAvailable` / `maxUnavailable`）+ 分批 drain + 确认业务副本在其他节点可用。

### 场景 C｜面试官的真实痛点
面试官不太在乎你有没有证，在乎的是：**① 你敢不敢在生产做 etcd 恢复（很多人不敢）；② 集群出问题时你能不能从上往下定位（节点 → 控制面 → 网络 → 应用）；③ 你知不知道 `drain` 之前要先看 PDB**。三条都是"管过集群"才会有的直觉。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 变更前 | 直接升级 | 备份 ETCD + 验证快照 + 异地存放 |
| 排障顺序 | 先看应用日志 | 节点 → 控制面 → 网络 → 应用，自上而下 |
| 驱逐节点 | `drain --force --ignore-daemonsets` 一把梭 | 先查 PDB，分批驱逐，观察副本 |
| 网络隔离 | 只写 policy | 写 + 实测（同 ns / 跨 ns / 出网三个方向） |

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 网络策略
```bash
# 允许 app 访问 db 的 5432，拒绝其他
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-app-db, namespace: prod }
spec:
  podSelector: { matchLabels: { app: db } }
  policyTypes: [Ingress]
  ingress:
  - from: [{ podSelector: { matchLabels: { app: app } } }]
    ports: [{ protocol: TCP, port: 5432 }]
EOF
```

### 5.2 存储（PV/PVC）
```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolume
metadata: { name: pv-demo }
spec:
  capacity: { storage: 1Gi }
  accessModes: [ReadWriteOnce]
  hostPath: { path: /data/pv-demo }
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pvc-demo }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
EOF
kubectl get pv,pvc
```

### 5.3 调度（nodeSelector / 污点容忍）
```bash
kubectl label nodes <node> disktype=ssd
kubectl apply -f - <<'EOF'
spec:
  nodeSelector: { disktype: ssd }
EOF
kubectl taint nodes <node> dedicated=special:NoSchedule
kubectl apply -f - <<'EOF'
spec: { tolerations: [{ key: dedicated, operator: Equal, value: special, effect: NoSchedule }] }
EOF
```

### 5.4 ETCD 备份
```bash
ETCDCTL_API=3 etcdctl snapshot save snap.db \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key \
  --endpoints https://127.0.0.1:2379
ETCDCTL_API=3 etcdctl --write-out=table snapshot status snap.db
```

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：集群出问题你怎么定位？（上机题 + 口述题双高频）
> "我按自上而下四层：**节点 → 控制面 → 网络 → 应用**。
> 先 `kubectl get nodes` 看节点是不是 Ready，NotReady 就看 kubelet 和容器运行时；节点都正常再看控制面，apiserver、etcd、scheduler、controller-manager 四个组件是否健康，`kubectl get componentstatuses` 或直接看静态 Pod；控制面没问题再看网络，Pod 之间能不能通、DNS 解析对不对、NetworkPolicy 有没有挡；最后才看应用本身，日志、探针、资源限制。
> 这个顺序的理由是：**下层问题会在上层表现为各种症状**，先查应用容易误判。比如节点磁盘满了，应用表现为写日志失败；比如 DNS 挂了，应用表现为数据库连不上。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| etcd 备份和恢复怎么做？ | "`etcdctl snapshot save` 带三个证书参数（cacert/cert/key）和 endpoints，存完必须 `snapshot status` 验证完整性，然后把快照传到别的机器——跟集群放一起等于没备份。恢复是 `snapshot restore` 到新目录，改 etcd 静态 Pod 的 `--data-dir` 指过去，然后重启 apiserver。生产上我建议先在测试集群演练一遍再动真的。" |
| NetworkPolicy 怎么确认生效？ | "三个方向实测：同命名空间内通、跨命名空间不通、出公网不通。前提是 CNI 支持策略——Calico、Cilium 支持，flannel 原生不支持。很多人 policy 写完就以为生效，其实 CNI 压根没实现。" |
| Pod Pending 怎么快速定位？ | "`kubectl describe pod` 看 Events，九成能直接看出原因：`Insufficient cpu` 是资源不足，`node(s) had taint` 是污点，`didn't match node selector` 是标签，`persistentvolumeclaim not found` 是存储。不需要猜。" |
| 为什么生产不建议随便 drain？ | "drain 会驱逐所有 Pod，如果没 PDB，一个服务的所有副本可能同时被赶走，造成中断。正确做法是配 PDB 限制不可用数量，再分批 drain，每批观察业务。" |
| CKA 有用吗？ | "我的定位是：CKA 是标准化能力的证明，不是经验替代品。它能证明我能独立完成集群运维的标准动作，但生产上的容量规划、故障处置还是靠实际做过。我现在是把它当查缺补漏的清单在刷，不是为了考而考。" |

### 数字锚点
`排障四层：节点→控制面→网络→应用`｜`ETCD 快照必验证 + 异地存`｜`NetworkPolicy 三方向实测`｜`drain 先看 PDB`
