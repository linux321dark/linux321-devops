## 1. 概念

### 1.1 registry 是什么

> **一句话**：**registry 是镜像的存储与分发服务**——一个"按名字存镜像、按名字取镜像"的服务端。

用一句话区分三个东西：

| 概念 | 是什么 | 在哪 | 类比 |
|---|---|---|---|
| **Dockerfile** | 镜像的**构建说明书** | 你的代码仓库 | 菜谱 |
| **镜像 image** | 构建出来的**只读分层模板** | 本地 Docker 存储 / registry | 菜 |
| **registry** | **存镜像并对外提供 pull/push 的服务** | 服务器 | 冰箱 + 柜台 |

registry 干三件事：

1. **存**：接收 `push` 上传的镜像内容
2. **分发**：响应 `pull`，按内容哈希把层传下去
3. **记账与管控**：谁能推、谁能拉、推过什么、有没有漏洞

**registry 里的镜像不是一个文件，而是一组对象**（这一节的 2.1 会展开）：

```
manifest（清单，JSON）
│   描述这个镜像由哪些层组成、每层的压缩摘要、平台信息
├── config（镜像配置 JSON）
│   记录 ENV / CMD / ENTRYPOINT / USER / 架构
├── layer 1（blob，gzip tar）
├── layer 2（blob）
└── layer 3（blob）
```

> **关键认知**：registry 存的是**内容寻址（content-addressed）**的数据。**层和 manifest 都按内容的 SHA256 摘要寻址**，所以同一个内容在 registry 里只存一份，多个镜像可以共享基础层。**这条设计是后面 digest 不可变的物理基础**——内容变了，摘要就变了。

### 1.2 没有 registry 会怎样

先看反面。假设公司只有一台开发机，镜像只存在本地：

| 问题 | 具体表现 |
|---|---|
| **K8s 节点拉不到** | 节点上有自己的 containerd，**不共享开发机的镜像层**。Deployment 起来就是 `ErrImagePull` / `ImagePullBackOff` |
| **多环境无法交付** | 测试环境的镜像怎么"给"到生产？靠 `docker save` 传 tar 再 `docker load`？**这不是交付，是手工搬运** |
| **没有唯一版本** | 三个人构建出三个都叫 `app:latest` 的镜像，内容不同，**谁也说不清线上跑的是哪份** |
| **无法回滚** | 没有版本历史，回滚只能"重新构建一个的" |
| **权限失控** | 谁都能推，生产仓库和测试仓库一个门禁都没有 |

> **所以 registry 不是"存镜像的地方"，它是"交付链路上的信任锚点"。** 后面的四道防线全部建在这个锚点上。

### 1.3 Docker Hub vs 阿里云 ACR vs Harbor：三种定位

这三个常被混为一谈，但它们解决的是**完全不同层级**的问题。

| 维度 | Docker Hub | 阿里云 ACR | Harbor |
|---|---|---|---|
| **是什么** | Docker 官方的**公有镜像托管平台** | 阿里云的**云上镜像仓库服务** | 开源的**企业级自建镜像仓库** |
| **谁运维** | Docker 公司 | 阿里云（云服务） | **你自己**（K8s 里跑一组 Pod） |
| **镜像放哪** | Docker 的机房 | 阿里云同地域机房 | **你自己的服务器/云主机** |
| **典型用途** | 拉公开基础镜像（alpine/nginx） | **国内生产的镜像仓库**（推自己的业务镜像） | 有合规/离线/多集群要求的团队自建 |
| **权限模型** | 公开读 + 命名空间写 | 企业版支持 RAM 权限、命名空间隔离 | **细粒度 RBAC + 项目（Project）隔离** |
| **扫描能力** | Docker Scout（需订阅/登录） | 内置镜像安全扫描 | 内置 Trivy 扫描器 |
| **高可用/备份** | 平台负责 | 平台负责 | **自己负责**（生产必须做备份与副本） |
| **成本结构** | 免费额度 + 付费加速 | 按量/包年 | **机器 + 存储 + 人力运维成本** |
| **拉取速度（国内）** | **慢，直连常超时** | **快（同地域内网）** | 取决于自建位置 |

**三者的正确关系不是"选一个"，而是"分工"**：

```
公开基础镜像（alpine / nginx / openjdk）
        │  ← 走国内加速器，或直接用 ACR 的镜像加速地址
        ▼
   Docker Hub  （只读拉取）

自己的业务镜像
        │  ← 必须推到自己有权限控制的地方
        ▼
   ACR（云上） 或 Harbor（自建）   ← 二选一或并存
```

> **面试这么答**："Docker Hub 是公有平台，我们只用来拉公开基础镜像；自己的业务镜像一律推阿里云 ACR——**理由是内网拉取速度与国内网络可达性，同时能用 RAM 控制谁能推**。Harbor 是自建方案，适合有等保、数据不出域、多集群统一治理要求的团队；**它的代价是可用性、备份、升级全要自己扛**，所以我们没有自建。"

## 2. 机制

### 2.1 push / pull 的实际过程（传的是什么）

**pull 的完整过程**：

```
docker pull registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1
  │
  ├─ 1. 认证：请求头带 X-Registry-Auth（凭据助手提供）
  │
  ├─ 2. 取 manifest：GET /v2/<repo>/manifests/v1
  │       └─ registry 返回 manifest（JSON），内含每个层的 digest + 大小
  │
  ├─ 3. 取 config：GET /v2/<repo>/blobs/sha256:<config digest>
  │       └─ 拿到 ENV / CMD / ENTRYPOINT / 架构等元数据
  │
  ├─ 4. 逐层取 blob（可并行）：
  │       GET /v2/<repo>/blobs/sha256:<layer digest>
  │       └─ 已经存在的层直接跳过（本地已有 digest 就不重复下载）
  │
  └─ 5. 解压叠加成本地镜像层，校验每层 digest → 打上本地 tag
```

**push 的完整过程**（与 pull 镜像对称但顺序相反）：

```
docker push registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1
  │
  ├─ 1. 逐个 blob 检查：HEAD /v2/<repo>/blobs/sha256:<digest>
  │       └─ 已存在（内容相同）→ 跳过，不重复上传
  │
  ├─ 2. 缺失的 blob 走分块上传：
  │       POST /v2/<repo>/blobs/uploads/ → 得到上传会话 URL
  │       PATCH/PUT 分块写入 → 最后 PUT 提交
  │
  ├─ 3. 上传 config blob（同 blob 流程）
  │
  └─ 4. 上传 manifest 并打 tag：
        PUT /v2/<repo>/manifests/v1
        └─ ★ 关键一步：registry 把 tag「v1」这个指针指向这个 manifest
           ★ tag 是指针不是内容 → 同名再 push 一次，指针被改写
```

> **从这段流程能直接推出两个结论**：
> 1. **pull 快不快，取决于"有多少层是本地没有的"**。基础层如果本地已有，只拉你改过的那几层——这解释了为什么"第一次拉慢，第二次秒开"。
> 2. **tag 被覆盖不是 bug，是设计**。`PUT /manifests/v1` 就是"把指针 v1 改指向新 manifest"，**registry 不做任何"这个 tag 已被使用"的检查**。

### 2.2 docker login 的凭据存哪（是不是加密的）

`docker login` 之后凭据写在**当前用户家目录**的 `~/.docker/config.json`：

```json
{
  "auths": {
    "registry.cn-hangzhou.aliyuncs.com": {
      "auth": "ZG9uZ3p6cGFzc3dvcmQ="
    }
  }
}
```

**`auth` 字段是 `username:password` 的 base64 编码。**

> **base64 是编码，不是加密。** 任何人都能一条命令还原：
> ```bash
> echo "ZG9uZ3p6cGFzc3dvcmQ=" | base64 -d
> ```
> **所以"docker login 之后密码就安全了"是错的。** 这条要背下来，面试官问"怎么保护镜像仓库凭据"时，这一句是分水岭。

**真正的保护手段有三条**：

| 手段 | 做法 | 保护强度 |
|---|---|---|
| **credential helper**（推荐） | 配置 `credsStore` 或 `credHelpers`，凭据交给**系统钥匙串**（macOS Keychain / Windows Credential Manager / Linux secret-service） | **高**：文件里只剩一个句柄，明文在系统受保护存储里 |
| **最小权限的访问令牌** | Docker Hub 用 **Personal Access Token**（PAT）而不是账号密码；ACR 用 RAM 子账号/访问凭证 | 中高：**泄露了也只是这个 token 的权限**，可单独吊销 |
| **CI 里用 `--password-stdin`** | 把 token 用管道喂给 `docker login --password-stdin`（完整写法见下方代码块） | 关键在 CI：**不把密码写在命令行**（命令行会进进程表 `ps`）和 shell 历史里 |

**CI 里绝对不要这么写**（D4 日课那段 `docker login -u $REGISTRY_USER -p $REGISTRY_PASS` 就是反例）：

```bash
# ❌ 密码进进程表、可能进 CI 日志（GitLab 会掩码变量值，但 echo 出来的还是会露）
docker login -u "$REGISTRY_USER" -p "$REGISTRY_PASS" "$REGISTRY"

# ✅ 正确：密码走 stdin，不进命令行
echo "$REGISTRY_PASS" | docker login --password-stdin -u "$REGISTRY_USER" "$REGISTRY"
```

> **配套的 K8s 侧**：私有仓库在集群里拉取，靠的是 **imagePullSecret**（`kubernetes.io/dockerconfigjson` 类型），它本质上是同一份 `config.json` 的 base64 编码。**K8s 里的 401 和本节的"凭据明文"是同一个问题的两个面**——见 6.1 踩坑表。

### 2.3 国内镜像加速器：`registry-mirrors` 的作用边界

**问题**：国内直连 Docker Hub 极慢或直接超时。**本机实测拉 `alpine:3.20` 就是超时**（L1 踩坑表第 1 行已记）。

**解法**：在 Docker 守护进程配置里加**镜像加速器**。

```json
// /etc/docker/daemon.json （Linux）
{
  "registry-mirrors": ["https://<你的ID>.mirror.aliyuncs.com"]
}
```

```json
// macOS / Windows：Docker Desktop → Settings → Docker Engine，同一段 JSON
{
  "registry-mirrors": ["https://<你的ID>.mirror.aliyuncs.com"]
}
```

改完**必须重启守护进程**才生效（Linux：`systemctl restart docker`）。

**加速器的三个关键性质（面试常被追问）**：

| 性质 | 说明 |
|---|---|
| **只作用于拉取** | 加速器是**pull-through 缓存**（拉的时候代你回源并缓存）。**push 不走加速器**——推 Docker Hub 依然直连，依然慢/失败 |
| **默认只代理 Docker Hub** | `registry-mirrors` 影响的默认是 `docker.io`。**推 ACR、拉 ACR 完全不经过它** |
| **是缓存不是永久副本** | 加速器上的镜像是**按需回源拉下来的副本**，上游删了、版本被覆盖了，缓存不一致 → **生产镜像永远不要依赖加速器** |

> **一句话记住加速器的定位**：**加速器解决的是"拉公开基础镜像慢"，不是"交付自己的业务镜像"。业务镜像的交付问题只能靠 ACR / Harbor 解决。** 这两件事在面试里经常被混为一谈。

### 2.4 tag 与 digest 的本质区别（本篇最重要的一节）

| | **tag** | **digest** |
|---|---|---|
| 形态 | 字符串，如 `v1.2.0` / `latest` | `sha256:` + 64 位十六进制 |
| 指向 | **可变指针**，指向某个 manifest | **就是 manifest 自身的内容哈希** |
| 能否被改写 | ✅ **能**（再 push 同名即改写） | ❌ **不能**（内容变了哈希就变，这是哈希的性质） |
| 语义 | 人写的、给人看的 | 机器算的、给机器用的 |
| 相同 tag 在不同仓库 | 是完全不同的内容 | digest 全局唯一（同一 manifest 在任何仓库哈希都一样） |
| 生产部署用 | ❌ 不应单独使用 | ✅ **应固定** |

**怎么拿到 digest**：

```bash
# 本地镜像的 RepoDigests（第一项就是仓库@sha256:...）
docker inspect --format='{{index .RepoDigests 0}}' <image>:<tag>

# 远端某个 tag 当前指向的 digest（不需要先把镜像拉下来）
docker manifest inspect --verbose registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1
```

**用 digest 拉取**：

```bash
docker pull registry.cn-hangzhou.aliyuncs.com/linux321-devops/app@sha256:<64位摘要>
```

**生产为什么要固定 digest**：

> **因为 tag 是可变指针。** 你的 Deployment 里写着 `image: .../app:v1`，那么在**任何时刻**，`v1` 这个名字指向的都可以是任何人 push 上去的新内容。**K8s 每次拉取时（imagePullPolicy: Always，或节点上没这个镜像时）都可能拿到不同的内容。**
>
> 更糟的场景：**镜像被覆盖后，HPA 扩出一个新 Pod，新 Pod 拉到的就是新内容**——**同一个 Deployment 的不同 Pod 跑着不同代码**，而且没有任何报错。

固定 digest 之后：

```yaml
image: registry.cn-hangzhou.aliyuncs.com/linux321-devops/app@sha256:<64位摘要>
```

**K8s 看到 digest 就知道这个镜像是不可变的** → 不会去"检查有没有更新"，行为等价于 `imagePullPolicy: IfNotPresent`，**集群里每个 Pod 拿到的必然是同一份字节**。

> **这和 GitOps 的"不可变基础设施"是同一条原则**：
> - GitOps：声明式配置进 Git，**Git 的 commit 是不可变的**，变更必须有新 commit
> - 镜像供应链：**digest 是不可变的**，变更必须有新 digest
>
> **两条都指向同一件事：可变指针不能作为部署依据。** 你在 K8s 里用 tag、在 GitOps 里用 `latest`、在 CI 里推 `latest`——**是同一种错误的三个马甲。**

**代价与配套**：固定 digest 后，"升级镜像"变成了一件需要显式触发的事（改 YAML 里的摘要）。**这是故意的**——升级必须留痕、必须能审计、必须能回滚。工程上通常配合一条流水线：**构建 → 拿到 digest → 把 digest 写回 values.yaml / 部署清单 → 提交 Git → ArgoCD 同步**，用 Git 的变更历史代替 tag 的模糊性。

### 2.5 多架构镜像与 buildx

**问题**：你的 Mac 是 arm64，生产集群节点是 amd64。构建出来的镜像架构不对，节点拉下来直接 `exec format error`。

**解法**：**一份镜像，同时包含多个平台的实现**。

```
manifest list（顶层索引，OCI image index）
├── manifest (linux/amd64)  → config + layers
├── manifest (linux/arm64)  → config + layers
└── manifest (linux/s390x)  → config + layers
```

**构建命令**：

```bash
docker buildx create --use --name multiarch
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1 \
  --push .
```

**三个必须理解的点**：

| 点 | 说明 |
|---|---|
| **必须有 buildx** | 经典 `docker build` 只能构建当前平台。`buildx` 是 BuildKit 的多平台前端 |
| **不能加载到本地** | 多架构产物**没法 `docker load` 进本地镜像库**（本地镜像存储一次只能有一种平台）。所以多架构构建**必须 `--push`**（或 `--output type=oci,dest=app.tar`） |
| **索引节点会变多** | 每个平台一份 manifest + config。**这是 `--provenance=false --sbom=false` 存在的原因** |

**`--provenance=false --sbom=false` 为什么必须加**：

新版 BuildKit 默认会在构建产物上**附加证明（provenance attestation）与 SBOM attestation**——也就是**索引里除了各平台的 manifest，还多出 attestation 相关的条目**。部分较旧的 registry 或运行时**不认这些新的 manifest media type**，表现为：

- push 成功但 `docker pull` 报错
- 或者多架构索引拉取时解析失败
- 或者节点上的 containerd 拉不下来（`failed to resolve reference`）

> **所以**：构建多架构镜像时加 `--provenance=false --sbom=false`，把索引收敛成"只有平台 manifest"的干净结构。**L2 的踩坑表最后几行已经记了这条**（"多架构构建推上去后拉不下来"），本节补上原因。

**验证双架构是否真的推上去了**：

```bash
docker manifest inspect registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1
```

**看到两个平台的 manifest 条目，才叫推成功了。**

### 2.6 镜像扫描：Trivy 的两类扫描

Trivy 是一个**单文件、无依赖**的开源扫描器，能扫容器镜像、文件系统、Git 仓库、K8s 集群。

**两类扫描必须分清**：

| 类型 | 扫什么 | 典型命令 | 发现的问题 |
|---|---|---|---|
| **漏洞扫描**（vuln） | 镜像/依赖里各组件的**已知 CVE** | `trivy image <image>` | 组件版本带 CVE（log4j 那种） |
| **配置扫描**（misconfig） | **Dockerfile / K8s YAML / Terraform 里的不安全写法** | `trivy config ./k8s` | `latest` 标签、以 root 运行、缺资源限制、挂载 hostPath |

**在 CI 里当门禁用**：

```bash
# 只看高危和严重；发现漏洞时退出码为 1 → 流水线红
trivy image --severity HIGH,CRITICAL --exit-code 1 \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1

# 扫 Dockerfile 与 K8s 清单本身
trivy config --exit-code 1 ./k8s
```

> **`--exit-code 1` 是门禁的开关**。不加这个参数，Trivy 扫出漏洞也只是打印出来、退出码仍是 0，**流水线照样绿**——这是"以为有门禁其实没有"最常见的一种。

**误伤与阈值策略（工程现实）**：

| 问题 | 表现 | 处理 |
|---|---|---|
| **基线太严** | 基础镜像带几十个 HIGH，全公司没人能合并 | **先跑一轮全量，生成"已知可接受漏洞"基线**，之后只卡新增 |
| **只卡 CRITICAL** | HIGH 全放行 | 分级：CRITICAL 必须 0；HIGH 设"不超过基线数量" |
| **数据库滞后** | CVE 公开了但本地库还没更新 | 定期 `trivy image --download-db-only` 更新漏洞库；CI 里固定更新步骤 |

**ACR 内置扫描**：阿里云 ACR 控制台也提供镜像安全扫描能力（依赖漏洞 + 基线检查），**但把它当门禁要谨慎**——控制台扫描是"事后看报告"，CI 门禁需要**退出码可判定**，所以流水线里通常仍用 Trivy 跑在 job 里。

### 2.7 SBOM：软件物料清单到底解决什么问题

> **SBOM（Software Bill of Materials，软件物料清单）= 镜像里所有组件的名字、版本、依赖关系的清单文件。**

**没有 SBOM 时，CVE 爆出来的那一天会怎样**：

```
某天 CVE-2026-XXXX 爆了，影响组件 log4j-core 2.14.x
  ↓
问："我们线上哪些镜像里有它？"
  ↓
没有人答得上来 → 逐个镜像扫一遍（几百个镜像 × 几分钟）→ 几小时到几天
  ↓
期间新漏洞持续爆出来，排查是重复劳动
```

**有了 SBOM**：

```
问："我们线上哪些镜像里有 log4j-core 2.14.x？"
  ↓
grep 一份 SBOM 清单 → 秒级列出全部受影响镜像 + 精确版本
```

**SBOM 的三类用途**：

| 用途 | 说明 |
|---|---|
| **应急响应** | 新 CVE 出来时，**秒级定位受影响资产**，而不是重新全量扫描 |
| **持续检测** | 漏洞库更新时，**拿 SBOM 去比对**，而不是重新拉镜像扫 |
| **合规审计** | 等保/行业监管要求"能说清你的软件成分"，SBOM 是直接证据 |

**格式**：两大标准 —— **SPDX**（Linux 基金会主导）和 **CycloneDX**（OWASP 主导）。

**用 Trivy 生成**：

```bash
trivy image --format cyclonedx --output sbom.json \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:v1
```

> **关键认知**：**SBOM 不是"扫描报告"，它是"资产清单"。** 扫描报告告诉你"现在有什么问题"（会过期），SBOM 告诉你"我里面有什么"（是事实）。**SBOM + 漏洞库 = 持续检测能力**，这个组合是供应链安全的核心资产。

### 2.8 签名与验签：解决的是"谁构建的"

**先说清楚要防什么**：

前面所有机制防的是"**这个镜像内容对不对**"（漏洞、可追溯）。签名防的是另一个问题：

> **"这个镜像是不是我们自己构建的？"**

**攻击场景**：

1. 有人拿到 registry 的 push 权限（或凭据泄露），**push 了一个内容完全不同的镜像，但仍用 `v1` 这个 tag**
2. CI 里有人改了构建脚本，**产物里塞了后门**，但流程看上去全绿
3. 镜像在**第三方 registry 之间被搬运/篡改**

**签名怎么解决**：给镜像的 **digest** 打一个密码学签名。私钥在你手里（KMS / HSM / OIDC 身份），**公钥可以公开分发**。

```
构建完成 → 拿到 digest（sha256:xxx）
        → 用私钥对这个 digest 签名 → 生成签名对象（signature）
        → 签名对象随镜像推到 registry

部署前 → 用公钥验证签名 → 通过才允许部署
```

**两套主流方案**：

| 方案 | 归属 | 签名方式 | 特点 |
|---|---|---|---|
| **cosign** | Sigstore 生态 | **keyless**（用 OIDC 身份，如 CI 的工作负载身份，**不存私钥**）或 KMS 密钥 | 新项目首选；**keyless 模式在 CI 里最省心**，签名身份直接绑定到流水线 |
| **Notary / Notation** | Docker 生态 → CNCF Notation | 密钥或证书 | 早期 Docker 生态方案；Harbor 有集成；v2 形态由 **CNCF Notation** 承接 |

**验签怎么落到生产**：

| 层次 | 做法 |
|---|---|
| **流水线里** | deploy job 前加一步 `cosign verify`，验不过就不部署 |
| **集群准入** | 用准入控制器（Admission Controller）在 Pod 创建时强制验签，**没签名的镜像直接拒绝创建 Pod** |

> **准入层验签才是"真门禁"**：流水线验签防的是"我方流程出错"，准入验签防的是"**任何路径**（包括有人手动 kubectl apply）想跑没签名的镜像"。**面试讲到这里，层次就出来了。**
>
> **注意成本**：Notary/Notation 体系里密钥管理（生成、分发、轮换、吊销）本身是门工程活。**面试能讲"我们选了 cosign keyless 因为不用自己管私钥"，比只会说"我们签名了"实在得多。**

### 2.9 Docker Scout 是什么

**Docker Scout** 是 **Docker 官方自己提供的镜像分析服务**，跟 Docker Desktop / Docker CLI 集成：

| 能力 | 说明 |
|---|---|
| **SBOM 生成** | `docker scout sbom <image>` 直接出一份清单 |
| **漏洞查询** | `docker scout cves <image>` 列出已知漏洞及修复版本 |
| **修复建议** | `docker scout recommendations` 给基线加固建议 |
| **多架构感知** | 扫描的是**指定平台的实现**，不是所有平台的并集 |

**它的定位**：把"官方出品、一条命令、不用装额外东西"。**适合个人/小团队快速自查**。

**但要清楚它的边界**：

- 需要 Docker Hub 账号并登录（免费额度有限）
- 漏洞库是 Docker 侧的（**与 Trivy 的库不同**——同一镜像两个工具报的漏洞条数不一样）
- **不适合做生产门禁**：依赖外部服务与账号状态，CI 里失败了你分不清是"真有漏洞"还是"服务不可用"

> **所以本篇的门禁方案用 Trivy**（开源、单二进制、可离线、可自建、退出码可判定），**Scout 留作开发期自查工具**。两者的详细对比见 5.4。

### 2.10 供应链安全的四道防线

把前面所有机制收拢成一张可复述的框架（**面试直接背这个结构**）：

```
┌─ 防线一：来源可信 ────────────────────────────────────────┐
│  私有仓库 + 最小权限（谁能推）+ 镜像签名（cosign）            │
│  解决："这个镜像是谁构建/推送的？"                          │
└──────────────────────────────────────────────────────────┘
┌─ 防线二：内容可查 ────────────────────────────────────────┐
│  漏洞扫描（Trivy vuln）+ 配置扫描（Trivy misconfig）        │
│  + SBOM（成分清单）                                          │
│  解决："这个镜像里有什么、有什么已知问题？"                   │
└──────────────────────────────────────────────────────────┘
┌─ 防线三：不可变 ──────────────────────────────────────────┐
│  生产用 digest 不用 tag + 禁推 latest + 保护分支禁止覆盖    │
│  解决："今天拉的和上个月拉的是不是同一份？"                   │
└──────────────────────────────────────────────────────────┘
┌─ 防线四：可追溯 ──────────────────────────────────────────┐
│  镜像 label 记录源码仓库/commit/构建时间 + tag 用 commit SHA │
│  + registry 审计日志 + SBOM 归档                             │
│  解决："线上跑的这份代码，对应仓库里的哪次提交？"               │
└──────────────────────────────────────────────────────────┘
```

**四道防线对应到具体动作**：

| 防线 | 落地动作 | 本篇讲过的位置 |
|---|---|---|
| 来源可信 | 私有仓库 + RAM/RBAC + `cosign sign` | 2.8 |
| 内容可查 | `trivy image --exit-code 1` + `trivy config` + SBOM | 2.6 / 2.7 |
| 不可变 | `image: repo@sha256:...` + 禁 `latest` | 2.4 |
| 可追溯 | `docker build --label` + tag 用 commit SHA + 审计日志 | 3.5 |

> **必须说清这四道不是"堆料"，是有先后逻辑的**：
> **不可变（防线三）是前提**——如果 tag 会被覆盖，前三道防线全部失效，因为你扫过的和线上跑的不是同一份东西。
> **内容可查（防线二）需要防线一和防线三托底**——你得先知道扫的是可信的、且是最终上线的那份。
> **可追溯（防线四）是把前三道串起来的线**——出事时能把"这份 digest → 这个 CVE → 这个 commit → 这个人"串成一条链。

### 3.1 登录与推送（本地 → ACR）

```bash
# ① 确认本地镜像在（沿用 D1 的产物）
docker images --format "{{.Repository}}:{{.Tag}}  {{.Size}}"
# 看到：
#   registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-java-demo:v20261018  A
#   registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018   B

# ② 登录（凭据用环境变量拿，不写命令行明文）
export ACR_USER='<你的 RAM 子账号>'
export ACR_PASS='<你的访问凭证>'
echo "$ACR_PASS" | docker login --password-stdin \
  -u "$ACR_USER" registry.cn-hangzhou.aliyuncs.com

# ③ 看凭据落在哪（验证 2.2 的结论：base64，不是加密）
cat ~/.docker/config.json
# 看到 "auths" → "registry.cn-hangzhou.aliyuncs.com" → "auth": "<一串 base64>"
echo "<那串 base64>" | base64 -d
# 能还原出 用户名:密码 → 证明它没有加密

# ④ 推送（tag 用 commit SHA，不用 latest —— 防线三 + 防线四）
docker push registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:$(git rev-parse --short HEAD)
```

**看到什么算对**：
- ② 之后 `docker info` 的登录段出现该 registry 名字 → 登录成功
- ④ 的输出里每一层都是 `Layer already exists`（说明本地已有层没重复上传）→ **push 走的是增量**
- ④ 结尾出现 `digest: sha256:... size: ...` → **这一行就是生产要固定的那个摘要**

> **★ 把 digest 记下来**：`docker push` 输出的 `digest:` 那行，就是你后面写进 K8s 清单里的值。**这是"构建 → 固定 digest"这条链的物理交接点。**

### 3.2 拉取与 digest 验证

```bash
# ① 远端查 tag 当前指向的 digest（不拉镜像）
docker manifest inspect --verbose \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018 | head -20
# 看到 "Descriptor" → "digest": "sha256:..." 且与 push 时一致

# ② 记录 digest 变量，后面所有地方都用它
export DIGEST=$(docker manifest inspect \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018 \
  | grep -m1 '"digest"' | cut -d'"' -f4)
echo "$DIGEST"
# 看到 sha256: 开头 + 64 位十六进制

# ③ 按 digest 拉（不可变引用）
docker pull registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo@$DIGEST

# ④ 本地镜像的 RepoDigests 里能对上
docker inspect --format='{{index .RepoDigests 0}}' \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018
# 应该等于 $DIGEST
```

**看到什么算对**：③ 不报 `invalid reference format`；④ 输出的摘要与 ② 一致。

**反向验证"tag 可被覆盖"（只读操作，安全）**：

```bash
# 同一个 tag 在不同时间的 digest 会变 —— 因为 tag 是指针
# 所以不能用 tag 当"这次构建的唯一标识"，必须用 commit SHA 或 digest
docker manifest inspect --verbose \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018 \
  | grep -m1 '"digest"'
```

### 3.5 生产清单改 digest 固定

**改之前**（危险写法）：

```yaml
# ❌ 用 tag：同名可被覆盖，扩出的新 Pod 可能拿到不同内容
apiVersion: apps/v1
kind: Deployment
metadata:
  name: day1-go-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: day1-go-demo
  template:
    metadata:
      labels:
        app: day1-go-demo
    spec:
      containers:
        - name: app
          image: registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo:v20261018
          imagePullPolicy: Always      # ← 每次都查 tag，配合可变 tag = 内容变
```

**改之后**（固定 digest）：

```yaml
# ✅ digest 固定：每个 Pod 拿到的必然是同一份字节
apiVersion: apps/v1
kind: Deployment
metadata:
  name: day1-go-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: day1-go-demo
  template:
    metadata:
      labels:
        app: day1-go-demo
    spec:
      containers:
        - name: app
          image: registry.cn-hangzhou.aliyuncs.com/linux321-devops/day1-go-demo@sha256:<64位摘要>
          imagePullPolicy: IfNotPresent   # ← digest 天然不可变，无需 Always
```

**配套：让镜像可追溯（防线四）**——构建时打 label：

```bash
docker build \
  --label "org.opencontainers.image.source=https://gitee.com/<你的仓库>" \
  --label "org.opencontainers.image.revision=$(git rev-parse HEAD)" \
  --label "org.opencontainers.image.created=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -t registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:$(git rev-parse --short HEAD) .
```

**看到什么算对**：

```bash
docker inspect --format='{{json .Config.Labels}}' \
  registry.cn-hangzhou.aliyuncs.com/linux321-devops/app:<sha>
# 看到 org.opencontainers.image.revision 与你的 commit 一致
```

> **这三个 label 是 OCI 约定的标准 label**，不是自定义的——**统一用标准 key**，别的工具（Trivy、Scout、GitOps）才能自动识别。这是"可追溯"从口号变成机器可读事实的关键一步。

## 4. 逐字段表

### 4.1 镜像引用与安全属性对照表

> **这张表的用法**：拿到一个镜像引用（YAML 里的 `image:` 字段），对着表逐行判断它**安全属性如何、哪里有风险**。

| 引用形态 | 示例 | 类型 | 指向语义 | 可变性 | 安全属性 | 写错的后果 |
|---|---|---|---|---|---|---|
| **仓库名** | `alpine` | 隐式引用 | `docker.io/library/alpine:latest` | 完全可变 | ❌ 最弱 | 拉到的是"某个叫 alpine 的东西"，内容随上游变化 |
| **仓库名 + `latest`** | `alpine:latest` | 隐式 tag | 指向 `latest` 这个可变指针 | **可变** | ❌ 弱 | **生产事故高发**：今天和明天不是同一份；上游重新发布即变 |
| **仓库名 + 语义 tag** | `app:v1.2.0` | tag 引用 | 指向 `v1.2.0` 这个可变指针 | **可变** | ⚠️ 中 | 别人 push 同名 tag 即被改写；**本意是版本号，实际是变量名** |
| **仓库名 + commit SHA** | `app:a1b2c3d` | tag 引用（SHA 作 tag） | 指向该 SHA 命名的 tag | 可变（但**实践中不会变**） | ✅ 较好 | SHA 作 tag 极难撞名，**比语义 tag 安全得多**；仍非绝对（理论上可被推同名） |
| **仓库名 @ digest** | `app@sha256:<64位>` | **digest 引用** | 直接指向那一份 manifest | ✅ **不可变** | ✅ **最强** | 写错摘要 → 拉不到（`manifest unknown`）；**这是唯一真正不可变的引用** |
| **仓库名 + tag + digest** | `app:v1@sha256:<64位>` | digest 引用（附 tag 提示） | **仍以 digest 为准**，tag 只作人类可读注释 | ✅ 不可变 | ✅ 最强 | 部分运行时对"tag 与 digest 不一致"报错；**建议只用纯 digest** |
| **无仓库前缀的短名** | `app` | 隐式引用 | 默认补 `docker.io/library/app` | 完全可变 | ❌ 弱 | **本地同名镜像会被顶替**；公共库里被抢注名字则拉到别人的镜像 |
| **含 tag 关键字的短名** | `nginx:alpine` | tag 引用 | `docker.io/library/nginx:alpine` | 可变 | ⚠️ 中 | 同上；**生产里连 `alpine` 这种"看起来很具体"的 tag 也不要单独依赖** |
| **私有仓库短名** | `myreg.io/app:v1` | tag 引用 | 私有 registry 里的指针 | 可变 | ⚠️ 中 | K8s 拉取时 **401**（缺 imagePullSecret）；不是安全问题但会阻塞部署 |

**速判规则**：

| 引用里含 | 判定 |
|---|---|
| `@sha256:` | ✅ 不可变，**生产可用** |
| `:latest` | ❌ **生产禁用** |
| `:v1` / `:1.0` 等语义 tag | ⚠️ **生产要配合 digest 用** |
| `:$(git rev-parse --short HEAD)` | ✅ **推荐做法**（tag 与 commit 一一对应，人也能读懂） |
| 完全没有仓库域名（短名） | ⚠️ 只在开发期用 |

### 4.2 digest 固定写法对照表

> **这张表的用法**：想在某个环节固定镜像引用，**该写成什么样**。

| 场景 | 写法 | 固定强度 | 前提/注意 | 写错的后果 |
|---|---|---|---|---|
| **K8s Deployment** | `image: <repo>@sha256:<64位>` | ✅ 绝对不可变 | 摘要在构建后确定，需回填 | 摘要写错 → `ErrImagePull: manifest unknown`；Pod 起不来 |
| **K8s Deployment（保留人类可读性）** | `image: <repo>:v1@sha256:<64位>` | ✅ 不可变 | 运行时若不支持"tag+digest"会报错 | 部分运行时解析失败 → **优先用纯 digest** |
| **K8s `imagePullPolicy`** | 配 digest 时用 `IfNotPresent` | — | digest 天然不可变，**Always 无意义还多一次 registry 查询** | 用 `Always` + 固定 digest：慢，且每次都去问 registry |
| **`docker pull`** | `docker pull <repo>@sha256:<64位>` | ✅ | 摘要必须是完整 64 位 | 截断/多字符 → `invalid reference format` |
| **`docker run`** | `docker run <repo>@sha256:<64位> ...` | ✅ | 同上 | 同上 |
| **Helm values** | 拆成 `image.repository` + `image.digest`（**tag 只留作注释**） | ✅ | 模板里用 `{{ .Values.image.repository }}@{{ .Values.image.digest }}` | 模板里仍写 `{{ .Values.image.tag }}` → **digest 形同虚设** |
| **ArgoCD Application** | `spec.source` 或目标清单里用 digest | ✅ | 镜像更新要改 Git 里的摘要 → ArgoCD 感知变更 | 直接在集群里改 Deployment → ArgoCD 会**漂移纠正回去** |
| **CI 变量** | `IMAGE_REF="${REPO}@${DIGEST}"`，digest 从 `docker push` 输出或 `docker inspect` 取 | ✅ | 取 digest 的时机在 push 之后 | 在 push 之前取 → 拿到的是旧摘要 → 部署了旧镜像 |
| **CI tag 命名** | `IMAGE_TAG="${CI_COMMIT_SHORT_SHA}"`（tag 用 SHA，内容用 digest） | ✅ | **tag 给人看，digest 给机器用** | tag 用 `latest` → 无法回滚、无法追溯 |
| **本地验证** | `docker inspect --format='{{index .RepoDigests 0}}' <image>` | — | 本地镜像的 RepoDigests 才是真实摘要 | — |

### 5.2 tag vs digest

| 维度 | tag | digest |
|---|---|---|
| **本质** | 可变指针（名字 → manifest） | manifest 的内容哈希 |
| **能否被改写** | ✅ 能（同名再 push 即改写） | ❌ 不能 |
| **可读性** | ✅ 人读 | ❌ 机器读 |
| **能否唯一标识一次构建** | ❌ 不能 | ✅ 能 |
| **能否回滚到指定版本** | ⚠️ 靠"不覆盖 tag"的约定 | ✅ 天然可以 |
| **K8s 行为** | `imagePullPolicy: Always` 时每次查 tag | 视为不可变，不会去查更新 |
| **节点缓存** | tag 变了要重新拉 | 同一个 digest 复用本地层 |
| **审计友好度** | ❌ 事后无从查证 | ✅ 可反查构建记录 |
| **生产推荐** | ❌ 单独使用 | ✅ **生产默认** |

> **两者不是二选一，是分工**：**tag 用 commit SHA（人可读、可追溯），digest 写进部署清单（机器用、不可变）。** 生产环境同时用两者，是当前最佳实践。

### 5.3 Dockerfile vs `docker commit`

> **问题**：能不能在容器里改完直接 `docker commit` 一个镜像推到仓库，绕过写 Dockerfile？

**技术上能。工程上绝对不能。** 对比：

| 维度 | Dockerfile 构建 | `docker commit` |
|---|---|---|
| **可复现** | ✅ 同一份 Dockerfile → 同一个 digest | ❌ **不可能复现**（中间状态没记录） |
| **可审计** | ✅ 每一行都在 Git 里 | ❌ 只有"一个最终状态"，**中间干了什么完全不可知** |
| **体积** | ✅ 多阶段可控（A → B） | ❌ **构建工具链全留在镜像里**（跑过 mvn/gradle 就带着 Maven） |
| **分层与缓存** | ✅ 层可缓存、顺序可优化 | ❌ 一坨大层，**没有任何缓存可言** |
| **可溯源** | ✅ 有构建过程、可打 label | ❌ 说不清谁改了什么 |
| **密钥泄露风险** | ✅ 密钥可用 `RUN --mount=type=secret` 只在构建期可见 | ❌ **在容器里 `export PASSWORD=xxx` 后再 commit，密码进镜像层，`docker history` 一看就有** |
| **安全扫描** | ✅ 配 Dockerfile 规则可扫 | ⚠️ 扫不出问题来源 |
| **多架构** | ✅ buildx 一条命令 | ❌ 一个 commit 就是一个架构 |

**`docker commit` 唯一的合理用途**：**临时调试快照**——复现线上问题时把容器状态存下来供分析。

> **面试这么答**："`docker commit` 只能做调试快照，不能做交付。**最致命的三条**——不可复现、不可审计、体积失控；再加一条**安全风险**：容器里设过的环境变量会进镜像层，`docker history` 直接可见。**交付用的镜像必须由 Dockerfile 构建，因为 Dockerfile 才是可审计、可复现的构建说明书。**"

### 5.4 Docker Scout vs Trivy

| 维度 | Docker Scout | Trivy |
|---|---|---|
| **归属** | Docker 官方 | **开源**（Aqua Security） |
| **形态** | 官方服务 + CLI 插件 | **单文件二进制**，可离线可自建 |
| **安装** | Docker Desktop 自带 / CLI 插件 | 下载二进制 / 容器跑 / CI 镜像 |
| **账号要求** | ⚠️ **需登录 Docker Hub** | ❌ 不需要 |
| **漏洞库** | Docker 侧数据库 | **自维护的漏洞库**（GHSA / NVD 等聚合） |
| **离线可用** | ❌ | ✅ |
| **CI 门禁友好度** | ⚠️ 依赖外部服务与账号 | ✅ **退出码可判定**（`--exit-code 1`） |
| **扫描范围** | 镜像（Docker 相关） | **镜像 / 文件系统 / Git 仓库 / K8s 集群 / IaC** |
| **配置扫描** | 有基线建议 | ✅ **Trivy config**（Dockerfile / K8s / Terraform） |
| **SBOM 生成** | ✅ `docker scout sbom` | ✅ `--format cyclonedx/spdx` |
| **多架构处理** | 扫指定平台 | 支持 `--platform` |
| **典型位置** | **开发机自查** | **CI 门禁 + 自建扫描服务** |

> **选型结论**：**Scout 是"开箱即用的自查"，Trivy 是"能进流水线的门禁"。**
> 两者报的漏洞**条数不一致**（库不同）——**这本身是个要注意的点**：安全基线要以**团队统一的工具和库**为准，别一会儿 Scout 一会儿 Trivy 两套基线。

## 6. 踩坑与排障

| 你看到的（症状） | 状态 | 真实原因 | 怎么修 | 下次怎么防 |
|---|---|---|---|---|
| `docker push` 报 `unauthorized: incorrect username or password` | 命令退出码 1，push 完全没开始 | ① 登录的 registry 域名与 push 的目标不一致（**登录了 Docker Hub 却推 ACR**，最常见）；② 凭据过期/被改；③ ACR 用了 RAM 主账号密码而该账号没被授权 | ① 确认 `docker login` 的地址**和 push 地址完全一致**（都带 `registry.cn-hangzhou.aliyuncs.com`）；② 重新用**访问凭证/PAT** 登录；③ 用 RAM 子账号并授予目标命名空间的 push 权限 | 在流水线里把 registry 域名抽成**一个变量**（`$ACR_REGISTRY`），登录和 push 都引用它，杜绝写两处不一致的地址 |
| `docker pull` 卡住 / `i/o timeout`（**本机实测拉 `alpine:3.20` 超时**） | 命令挂住直到超时 | 国内**直连 Docker Hub** 网络不可达或极慢 | 在 `/etc/docker/daemon.json`（或 Docker Desktop → Docker Engine）加 `registry-mirrors`，**重启守护进程** | 开发机初始化脚本里就配好加速器；**业务镜像一律走 ACR，不依赖加速器** |
| `docker pull <repo>@sha256:xxx` 报 `invalid reference format` | 语法解析阶段就失败 | ① digest 不完整（**必须 64 位十六进制**）；② 多写了 `@` 或把 tag 和 digest 混写；③ 摘要是 `sha512:` 等不支持的算法 | 从 `docker push` 输出或 `docker inspect --format='{{index .RepoDigests 0}}'` **复制粘贴**，不要手敲 | 摘要**由脚本从 push 输出里取**，不手写、不入库手改 |
| K8s 里 Pod 卡 `ImagePullBackOff`，事件里是 `401 Unauthorized` | Pod 一直 `Pending`，`kubectl describe pod` 能看到 401 | 私有仓库**没有 imagePullSecret**；或 secret 类型不对（要 `kubernetes.io/dockerconfigjson`）；或 secret 里的 registry 域名与镜像地址不匹配 | 建 `kubernetes.io/dockerconfigjson` 类型的 Secret 并挂到 `serviceAccount` 或 Pod 的 `imagePullSecrets` | 私有仓库**必须**配 imagePullSecret；域名拼写与镜像地址**逐字符一致**（尾部斜杠、`https://` 前缀都会导致不匹配） |
| 同一 Deployment 里不同 Pod 跑着不同代码，**且没有任何报错** | Pod 全部 Running，无告警 | 镜像用的是**可变 tag**（尤其 `latest`）+ `imagePullPolicy: Always`；期间 tag 被重新 push 覆盖 | 生产改用 **digest 固定**：`image: <repo>@sha256:<64位>` | **CI 里禁止推送 `latest`**；tag 一律用 commit SHA；生产清单只接受 digest（可用准入策略校验） |
| `docker manifest inspect` 只看到**一个**平台 | 命令正常返回，但 manifest list 里只有一条 | ① 只 `docker build` 没走 buildx；② buildx 构建时用了 `--load`（**多架构产物无法 load 到本地**）；③ 构建时没加 `--platform` | 用 `docker buildx build --platform linux/amd64,linux/arm64 --push` | 多架构构建固化成一条命令，写进 Makefile / CI 变量，**不要手敲** |
| 多架构镜像 **push 成功但 pull 失败**（`failed to resolve reference` 之类） | registry 里有对象，但拉取解析失败 | BuildKit 默认附加的 **provenance / SBOM attestation** 条目不被旧 registry 或旧 containerd 识别 | 构建时加 `--provenance=false --sbom=false` | **多架构构建命令固定带这两个参数**；升级 registry / containerd 也要跟进 |
| 容器里 `export PASSWORD=xxx` 后 `docker commit`，**`docker history` 里能看到密码** | 密码明文出现在历史里 | commit 把可写层原样封成镜像层，**含运行时环境变量** | 用 Dockerfile 构建；密钥用 K8s Secret 或 `--mount=type=secret` | **禁止 `docker commit` 做交付镜像**；CI 里加一步扫 `docker history` 输出 |
| `~/.docker/config.json` 里的 `auth` 被同事一眼看懂 | base64 直接还原出账号密码 | base64 是**编码不是加密** | 配 `credsStore`/`credHelpers` 交给系统钥匙串；并**轮换一次该凭据** | 用**最小权限的访问令牌**而非账号密码；凭据泄露当密码泄露处理，**立即吊销** |
| Trivy 扫出 30 个 HIGH 漏洞，**流水线全红，没人能合并** | 门禁确实生效了，但阈值不可用 | 基线太严：基础镜像自带的低危/中危漏洞也计入 | 先跑一轮全量，把"已知可接受"的写进**基线文件**；之后只卡**新增** | 门禁分级：CRITICAL 必须 0；HIGH 对比基线；**定期评审基线** |
| Trivy 报 `database update failed` / 漏洞库一直是旧的 | 拉不到最新漏洞库 | 漏洞库需要联网更新，国内不通 | `trivy image --download-db-only`；在 CI 里**单独一步更新并缓存** | CI 缓存漏洞库目录；**别依赖运行时在线更新** |
| 加了 `--exit-code 1` 但流水线仍然绿 | 退出码 0 | ① 命令后接了管道（如 `tee`），**退出码被管道末端命令覆盖**；② 扫描目标名写错（扫了个不存在的镜像，Trivy 直接报错退出） | 用 `set -o pipefail`；先单独跑一次确认扫描有输出 | 门禁命令**单独一行**，失败即中断；配合 `allow_failure: false` 语义 |
| `docker login` 在 CI 里成功，但**换个 job 就失效** | 每个 job 独立容器 | 凭据写在 `~/.docker/config.json`，**不跨 job 共享**（也不该跨 job 共享） | 每个需要 push/pull 的 job **各自 login**；或把 `config.json` 作为 artifact 传（**安全性差，不推荐**） | 用 **CI 内置的 `CI_REGISTRY_*` 变量**（GitLab 内置 registry）免登录；自建仓库用 masked 变量 |

## 8. 自测三问

1. **能说清输入输出吗？** —— 输入：一个本地镜像（分层内容）；输出：一个**内容寻址**的 registry 条目（manifest + config + blobs）+ 一个可变的 tag 指针。中间经过：blob 增量上传 → manifest 上传 → tag 指针改写。**关键因果**：因为 manifest 按内容哈希寻址，所以 digest 天然不可变；因为 tag 只是指针，所以 tag 可被覆盖。

2. **能故意改坏再倒推吗？** —— 五个具体实验（每个都能看出明确现象）：
   - **实验 A（tag 可变）**：把同一个 tag 推两次**不同内容**（改一行代码重新构建再 push 同名 tag），然后 `docker manifest inspect --verbose <repo>:<tag>` 比较两次的 `digest` —— **会看到 digest 变了，而 tag 名字没变**。这就是"tag 被覆盖"的直接证据。
   - **实验 B（base64 不是加密）**：`cat ~/.docker/config.json` 取出 `auth` 值，`echo "<值>" | base64 -d` —— **会直接还原出账号密码**。
   - **实验 C（digest 引用更安全）**：Deployment 里写 `image: <repo>:v1` 与 `image: <repo>@sha256:<64位>` 各起一个 Pod，`kubectl get pod -o jsonpath='{..image}'` 对比 —— **一个会随 tag 变，一个永远不变**；再故意把 digest 改错一位 → **Pod 卡 `ImagePullBackOff`，事件报 `manifest unknown`**。
   - **实验 D（凭据明文进镜像层）**：容器里 `export PASSWORD=secret123`，`docker commit` 出来，`docker history` —— **会看到 `ENV PASSWORD=secret123` 明文出现在历史里**。
   - **实验 E（门禁真的会红）**：拿一个**故意带高危漏洞的旧版本基础镜像**跑 `trivy image --severity HIGH,CRITICAL --exit-code 1 <image>` —— **会看到退出码为 1**；去掉 `--exit-code 1` 再跑 —— **退出码变 0，输出里漏洞还在**。这一条说明"以为有门禁其实没有"是怎么发生的。

3. **能画上下游吗？** —— 画出这条链并标出每一步的失败表现：
   ```
   Dockerfile ──docker build/buildx──► 本地镜像（分层）
        │                                │
        │                          docker push（blob 增量上传 + manifest + tag 指针）
        │                                ▼
        │                        registry（ACR / Harbor）
        │                          ├── manifest（按内容哈希 → digest 不可变）
        │                          ├── blob（分层，可共享）
        │                          └── tag（可变指针 → 可被覆盖）
        │                                │
        │        docker pull（认证 → 取 manifest → 逐层取 blob → 校验 digest）
        │                                ▼
        │                        节点本地镜像（层缓存命中 → 决定拉取快慢）
        │                                │
        │        Trivy image（漏洞扫描）/ trivy config（配置扫描）/ --format cyclonedx（SBOM）
        │                                ▼
        │                        门禁判定（--exit-code 1 → 流水线红）
        │                                │
        │        cosign sign（对 digest 签名）/ cosign verify（验签）
        │                                ▼
        └────────► K8s Deployment（image: repo@sha256:...  ← digest 固定，不可变）
                     │
                     └── label（source / revision / created）──► 可追溯
   ```
   **每一步的失败表现**：push → `unauthorized`；pull → `i/o timeout`（国内直连）；digest 写错 → `invalid reference format` / `manifest unknown`；K8s 私有仓库 → `401 Unauthorized` + `ImagePullBackOff`；门禁 → 退出码 1；tag 被覆盖 → **无报错，只是内容悄悄变了**。
