# 第 06 天 · Helm 封装 + 多环境

## 一、今日目标（结论先行）
把 D1–D5 的手写 YAML 封装成 Helm Chart，用 values-dev/values-prod 实现多环境参数化与一键回滚——Helm 是本地民企 K8s 应用交付事实标准，Chart 多存 **Harbor**。

## 二、企业真实需求背景
- **行业B/行业C**：多应用多环境，手写 YAML 易漂移；Helm 模板化是工程化标配。
- 本地民企镜像/Chart 仓现实：阿里云 ACR 同时存镜像和 Helm Chart；大厂自建 Harbor。
- 你已有 Apollo 多环境经验，可迁移到 Helm values 多环境注入。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜为什么民企最终都会上 Helm（不是因为它时髦）
一家 200 人研发的公司，K8s 上跑 60–150 个应用，每个应用 3–4 套环境：

| 不用 Helm 的真实状态 | 用 Helm 之后 |
|---|---|
| 每个应用 × 每套环境一份 YAML，共 150×3 ≈ 450 份几乎相同的文件 | 一份 Chart + 每环境一份 values（150×3 份，但每份只有 10–30 行差异） |
| 改一个公共字段（比如加 `securityContext`）要改 450 个文件 | 改模板一次，全应用生效 |
| 环境间配置漂移，dev 能跑 prod 不能跑 | 差异被显式收敛在 values 里，可 diff |
| 回滚靠 `kubectl rollout undo` 或 Git revert，不知道"上次发了什么" | `helm history` + `helm rollback` 精确到 revision |
| 新人不知道要配哪些字段 | `values.yaml` 就是配置说明书 |

**这就是行业B/行业C"多应用多环境交付"的真实痛点**——不是不会写 YAML，是 YAML 太多、太像、改不动。

### 场景 B｜真实事故现场
1. **改了 values 但部署没变**：`--set` 优先级高于 `-f`，且多个 `-f` 是后者覆盖前者。写反了就是"改了没生效"。排查：`helm get values <release>` 看最终合并结果，别猜。
2. **模板 nil 指针 panic**：`{{ .Values.xxx.yyy }}` 在某个环境没配就报 `nil pointer evaluating interface {}.yyy`。正确：`{{ .Values.xxx.yyy | default "v" }}` 或 `required` 显式报错。
3. **回滚"回到了错误版本"**：`helm rollback` 不指定 revision 时回退到上一个，但如果中间失败过几次，revision 号会乱。正确：先 `helm history` 看清楚，再 `helm rollback <rel> <明确revision>`。
4. **Chart 版本没升，仓库里被覆盖**：`helm push` 同版本号会被拒或覆盖，导致"发的是哪版"说不清。正确：Chart version 与 appVersion 分开管理，每次发布必升 version。
5. **ConfigMap 改了但 Pod 没重启**：Helm upgrade 更新了 ConfigMap，但 Deployment 的 Pod template 没变，Pod 不会滚动。正确：用 `checksum/config` 注解触发滚动。

### 场景 C｜面试官的真实痛点
面试官关心：**① 你会不会把 Helm 用成"更复杂的 YAML 生成器"（只做模板替换，不懂 release 管理）；② 回滚到底靠不靠得住；③ 你的 Chart 能不能给别人复用（有没有写成通用 Chart 而不是硬编码自己公司）**。第三点最区分水平——能写通用 Chart 的人，才懂平台化。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 多环境 | 复制 Chart 三份 | 一个 Chart + 多 values，差异收敛 |
| 镜像 tag | values 里写死具体版本 | 部署时 `--set image.tag=$CI_COMMIT_SHA` 注入 |
| 回滚 | 只靠 Git revert | `helm history` 定位 + `helm rollback` 精确 revision |
| 敏感信息 | 写进 values.yaml 提交 Git | values 只放引用，密钥走 External Secrets |
| 配置变更 | 改 ConfigMap 后以为自动生效 | Pod template 加 checksum 注解触发滚动 |

- **原理**：Go template 渲染；release + ConfigMap(Secret) 记录版本支持回滚。
- **理论**：配置即代码；环境差异化注入。
- **核心易忘点**：Chart 结构（`Chart.yaml/values.yaml/templates/`）；`--values` 顺序覆盖；`helm lint/install/upgrade/rollback/history`。
- **横向对比**：Helm（模板渲染，主流）vs Kustomize（overlay，无模板）vs Jsonnet。**选择口径（JD 高频并列要求"Helm/Kustomize"）**：自研应用走 Helm（要 release 历史）；改第三方 Chart / 只补丁不改结构走 Kustomize（不进 Chart 仓库、不产生新 release）；两者可叠加（Helm 渲染 → Kustomize 打补丁）。
- **常见问题**：values 覆盖不生效→查 `--values` 顺序与 `{{ .Values.xxx }}`；回滚→`helm rollback <rel> <rev>`。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 创建 Chart 骨架
```bash
helm create myapp
tree myapp
# myapp/
# ├── Chart.yaml
# ├── values.yaml
# └── templates/
#     ├── deployment.yaml
#     ├── service.yaml
#     └── _helpers.tpl
```

### 5.2 改造 templates 用 values
`templates/deployment.yaml` 关键段：
```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
resources:
  requests:
    cpu: {{ .Values.resources.requests.cpu }}
replicas: {{ .Values.replicaCount }}
```
`values.yaml`：
```yaml
replicaCount: 1
image: { repository: registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo, tag: go-v1 }
resources: { requests: { cpu: "100m" } }
```

### 5.3 多环境 values + 安装/升级/回滚
```bash
# dev / prod 分离
cat > values-dev.yaml <<'EOF'
replicaCount: 1
image: { tag: go-dev }
EOF
cat > values-prod.yaml <<'EOF'
replicaCount: 3
image: { tag: go-v1 }
EOF

helm lint myapp
helm install myapp-dev ./myapp -f values-dev.yaml --namespace dev --create-namespace
helm install myapp-prod ./myapp -f values-prod.yaml --namespace prod --create-namespace

# 改 tag 后升级
helm upgrade myapp-prod ./myapp -f values-prod.yaml --set image.tag=go-v2
helm history myapp-prod
# 异常回滚
helm rollback myapp-prod <上一个REVISION>
```

### 5.4 打包 + 推 ACR（Chart 仓库）
```bash
helm package myapp
helm push myapp-0.1.0.tgz oci://registry.cn-hangzhou.aliyuncs.com/devops-journey/charts
```

### 5.5 Kustomize 打补丁（15 分钟，JD 高频并列项，必须能上手）
场景：公司用社区 Chart 或别人给的 base，你只想改副本数、加个注解、换镜像仓库——**不要 fork 整个 Chart**。
```bash
kubectl create ns dev --dry-run=client -o yaml > base/ns.yaml   # 示例 base
mkdir -p overlays/prod
cat > overlays/prod/kustomization.yaml <<'EOF'
resources:
  - ../../base
namespace: prod
namePrefix: prod-
images:
  - name: myapp
    newName: registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo
    newTag: go-v2
replicas:
  - name: myapp
    count: 3
patches:
  - target: { kind: Deployment, name: myapp }
    patch: |-
      - op: add
        path: /spec/template/metadata/annotations
        value: { prometheus.io/scrape: "true" }
EOF
kubectl kustomize overlays/prod        # 只渲染，不落地——先看输出对不对
kubectl apply -k overlays/prod         # 真正下发
kubectl diff -k overlays/prod          # 下发前看差异，这是 Kustomize 的最大价值
```
**关键认知（面试会问）**：`kubectl diff -k` 能告诉你"这次到底改了什么"，而 `kubectl apply -f` 不能。这是 Kustomize 在**审计留痕**场景的真实优势，也是等保/变更管控里的加分项。
```bash
# 三层叠加顺序（Helm 渲染 → Kustomize 补丁）
helm template myapp ./myapp -f values-prod.yaml > /tmp/rendered.yaml
# 把 rendered.yaml 放进 base，再用 overlay 打补丁，即可同时拥有 release 历史 + 环境补丁
```

## 六、成果验证方式
1. `helm install` 后 `kubectl get pods -n dev/myapp-dev` Running。
2. `helm upgrade --set image.tag=go-v2` 后 Pod 镜像更新；`helm history` 出现 v2。
3. `helm rollback` 后镜像回退到旧 tag，Pod 重建。
4. `helm package` + `helm push oci://...` 成功（Chart 入 ACR）。
5. `kubectl kustomize overlays/prod` 渲染出预期 YAML；`kubectl diff -k overlays/prod` 能列出待改字段。

## 七、常见坑与排错
- values 覆盖顺序：后 `--values` 覆盖前；`--set` 优先级最高。
- 模板 nil 指针→`{{ .Values.x | default "val" }}`。
- rollback 后 release 版本号递增，注意 `--version` 指向目标 revision。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：多环境怎么管的？为什么用 Helm 不用 Kustomize？（高频对比题）
> "我用 Helm，核心原因是**多环境差异要能收敛在声明里，同时要有 release 版本概念**。
> 一个 Chart 加三份 values，模板只写结构，环境差异全部落到 values，dev 和 prod 的差别打开文件就能 diff。更关键的是 Helm 有 release 和 revision，`helm history` 能看到每次发布了什么、用的哪个镜像 tag，出问题 `helm rollback` 回到任意一版，这是 Kustomize 给不了的——Kustomize 只管渲染，不管发布历史。
> Kustomize 我也有用，适合'别人的 Chart 我只想打补丁'的场景，比如改个副本数、加个注解，不想 fork 整个 Chart。所以我的结论是：**自己写的应用用 Helm，二次修改第三方清单用 Kustomize**，两者不冲突。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| Helm 的 release 和 revision 是什么？ | "release 是一个 Chart 在集群里的一次安装实例，revision 是它的每次变更版本号。每次 install/upgrade/rollback 都会生成新 revision，历史存在集群的 Secret（或 ConfigMap）里，所以回滚不依赖 Git。" |
| 改了 values 没生效怎么查？ | "先 `helm get values <rel>` 看最终合并值，再看优先级：`--set` > 后面的 `-f` > 前面的 `-f` > Chart 自带 values.yaml。九成是优先级写反或者 key 拼错。" |
| 生产回滚要注意什么？ | "两点：一是回滚会连带 ConfigMap、Secret 一起回，如果中间有数据库变更，代码回滚了 schema 没回，会二次故障，所以回滚要配合发布策略（先兼容后切换）；二是回滚本身也是一次新 revision，不是'撤销'，要记录。" |
| Chart 版本怎么管？ | "`version` 管 Chart 结构变更，`appVersion` 管应用版本，两者独立升。同一个 version 不允许推两次，否则仓库里到底哪份是最终版说不清。" |
| 怎么让 Chart 通用可复用？ | "所有环境相关的东西一律不许硬编码：名字用 `_helpers.tpl` 生成，镜像、副本、资源、探针全走 values，可选组件用 `enabled` 开关。做完之后别人拿去改 values 就能跑，这才叫能进平台。" |

### 数字锚点
`1 Chart + N values`｜`rollback 到任意 revision`｜`版本双轨（version/appVersion）`

### 禁忌
- ✗ "多环境就复制三份 YAML" —— 直接暴露没做过规模化交付。
- ✗ 只会 `helm install`，说不出 release/revision —— 等于用 Helm 当模板引擎。
- ✗ 说"回滚就是 Git revert" —— 混淆了制品回滚和代码回退。
