# 第 05 天 · 多环境门禁 + 质量扫描

## 一、今日目标（结论先行）
在流水线上加**质量门禁**：SonarQube 代码扫描 + Trivy 镜像漏洞扫描接门禁，dev 自动、prod 手动审批——直接命中行业A"安全左移"和行业B"交付流程优化"。

## 二、企业真实需求背景
- **行业A**："合规经验：熟悉等保对基础设施的合规硬约束"——漏洞镜像上线是等保红线。
- **行业B**："交付流程优化"。
- 本地民企 DevSecOps 现实：SonarQube（代码质量）+ Trivy（镜像漏洞）+ 钉钉告警是标配，而非境外 Snyk/Datadog。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜门禁的真实设计：三层拦截点
门禁不是"加个扫描"，而是在交付链路上选**三个必须拦住的点**：

| 拦截点 | 拦什么 | 阈值怎么定 | 拦不住的后果 |
|---|---|---|---|
| MR 合并前（代码层） | 新增代码的坏味道、硬编码密钥、高危依赖 | 只扫**增量**，覆盖率/重复率卡"新增代码"，不卡全量 | 老代码债务导致门禁永远红，最后所有人绕过门禁 |
| 镜像推送后（制品层） | 基础镜像 CVE、系统包漏洞 | CRITICAL 阻断、HIGH 出报告不阻断 | 全量 HIGH 阻断 → 没人能发布 → 被迫关闭门禁 |
| 生产发布前（流程层） | 未审批发布、非 tag 发布 | 保护分支 + 手动审批 + 审批人白名单 | 误发布、审计无留痕，等保测评扣分 |

**关键认知**：门禁设计失败的头号原因不是工具不好，是**阈值定太严导致全红，团队干脆绕过**。所以一律"新代码严格、老代码宽松"。

### 场景 B｜真实事故现场
1. **SonarQube 一上来卡全量，门禁永远红**：老项目几千个 bug，任何 MR 都过不去，最后 Leader 关掉门禁。正确：Quality Gate 只卡"New Code"（新增代码），老债务单独排期清理。
2. **Trivy 扫出 300 个 HIGH 导致没人能发版**：根因是基础镜像太旧（如 `openjdk:8` 三年没更新）。正确：先统一基础镜像升级（这一步能砍掉 80% 的 CVE），再把阻断级别定在 CRITICAL。
3. **Trivy 数据库拉不下来，扫描超时**：默认从 ghcr 拉，国内不稳。正确：配 `TRIVY_DB_REPOSITORY` 国内镜像或离线 OCI 包，DB 缓存进 CI cache。
4. **钉钉告警刷屏，最后被全员静音**：每条失败都推、每个 job 都推。正确：只推 main 分支失败 + 生产发布失败，其余进日报。
5. **等保测评要"漏洞闭环证据"，拿不出来**：扫描结果没留存、修复没记录。正确：扫描报告作为 CI artifact 保留 90 天，修复单关联到工单，测评时直接导证据链。

### 场景 C｜面试官的真实痛点
- **行业A"等保对基础设施的合规硬约束"**：他们要的不是"我装过 Trivy"，而是"**漏洞从发现到修复到复测的闭环怎么留痕**"——测评师会查这个。
- **行业B"交付流程优化"**：门禁不能拖慢交付，必须"拦住该拦的、放过该放的"。
- 面试官必问：**"门禁太严研发造反怎么办？"** 这题答得好不好，直接区分"装过工具"和"落地过制度"。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 扫描范围 | 全量卡死 | 只卡新增代码（New Code） |
| 阻断级别 | 全部 HIGH 都阻断 | CRITICAL 阻断，HIGH 出报告+限期整改 |
| 例外处理 | 手动改 YAML 绕过 | 走白名单流程 + 到期自动失效 + 留审批记录 |
| 证据留存 | 结果不存 | 报告存 artifact 90 天，关联工单形成闭环 |

- **原理**：SonarQube 静态分析；Trivy 扫描镜像层 CVE；门禁=流水线 `allow_failure:false` 阻断。
- **理论**：DevSecOps 安全左移；质量门禁；不可变制品。
- **核心易忘点**：SonarQube Quality Gate；Trivy `--severity CRITICAL` 退出码；钉钉 webhook 机器人。
- **横向对比**：SonarQube（代码）vs Trivy（镜像）vs Dependency-Check（依赖）；钉钉（本地标配）vs Slack/PagerDuty（境外）。
- **常见问题**：Trivy 数据库更新慢→配国内源（`TRIVY_DB_REPOSITORY`）；扫描阻断误报→白名单；钉钉告警频率爆→分组/抑制。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 起 SonarQube（docker compose 本地）
```bash
docker run -d --name sonarqube -p 9000:9000 sonarqube:community
# 浏览器开 http://localhost:9000，默认 admin/admin，建 token
```
`.gitlab-ci.yml` 增加 scan 段：
```yaml
sonarqube:
  stage: scan
  image: sonarsource/sonar-scanner-cli:latest
  script:
    - sonar-scanner -Dsonar.host.url=$SONAR_URL -Dsonar.token=$SONAR_TOKEN \
        -Dsonar.projectKey=day1-demo -Dsonar.sources=.
```

### 5.2 Trivy 镜像扫描接门禁
```bash
# 本机先验证
trivy image --severity CRITICAL,HIGH --exit-code 1 \
  registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1
```
```yaml
trivy:
  stage: scan
  image: aquasec/trivy:latest
  variables:
    TRIVY_DB_REPOSITORY: "ghcr.io/aquasecurity/trivy-db:2"   # 国内加速
  script:
    - trivy image --severity CRITICAL --exit-code 1 --no-progress $IMAGE
```

### 5.3 钉钉机器人告警
```bash
# 流水线失败时调用钉钉
notify_fail:
  stage: .post
  when: on_failure
  script:
    - |
      curl -s -X POST $DINGTALK_WEBHOOK -H 'Content-Type: application/json' -d '{
        "msgtype":"text","text":{"content":"CI 失败：'$CI_PROJECT_NAME' #'$CI_PIPELINE_ID'"}}'
```

### 5.4 多环境策略
```yaml
deploy_prod:
  stage: deploy
  environment: { name: prod }
  rules: [{ if: '$CI_COMMIT_TAG' }]
  when: manual          # prod 手动审批
```

## 六、成果验证方式
1. SonarQube 项目页出现 day1-demo 的分析结果（bug/vulnerability 数）。
2. Trivy 对含高危 CVE 的镜像返回退出码 1，流水线 `scan` 标红阻断。
3. 故意让 build 失败 → 钉钉收到失败通知。
4. `deploy_prod` 在未打 tag 时不触发、打 tag 后需手动点。

## 七、常见坑与排错
- Trivy DB 国内源：`export TRIVY_DB_REPOSITORY="ghcr.io/aquasecurity/trivy-db:2"`。
- SonarQube 首次启动 ES 内存不足→`-e SONAR_ES_BOOTSTRAP_PASSWORD=admin` 并调 JVM。
- `when: manual` 卡 prod；钉钉 webhook 频率限制。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：门禁怎么落地的？研发会不会绕过？（最能体现落地能力）
> "门禁我按三层设计：代码层、制品层、流程层。
> 代码层是 SonarQube，但我**只卡新增代码**——老项目几千个历史问题，如果卡全量，门禁永远是红的，最后团队会集体绕过。所以 Quality Gate 配成 New Code 口径，新增代码的覆盖率和重复率必须达标。
> 制品层是 Trivy 扫镜像。我先做了一轮基础镜像治理，把三年没更新的 JDK 基础镜像统一升级，这一步就砍掉了 80% 的 CVE，然后阻断线定在 CRITICAL——HIGH 出报告、限期整改、不阻断合并。**门禁的阻断线必须匹配团队当前的修复能力，定太严等于自废门禁**。
> 流程层是生产发布必须 tag 触发 + 手动审批，审批人白名单，留审计记录。
> 例外走白名单流程，带到期时间和审批人，不能直接改 YAML 绕过——这是等保要的"变更可追溯"。整套下来交付没有变慢，因为阻断发生在合并前而不是发布时。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 为什么只卡 CRITICAL 不卡 HIGH？ | "因为基础镜像的 HIGH 有几百个，全阻断等于停摆。我的做法是先治理基础镜像把存量降下来，再逐步把阻断线提到 HIGH。门禁是拿来落地的，不是拿来好看的。" |
| 扫描结果怎么留证？ | "Trivy 的 JSON 报告作为 CI artifact 保留 90 天，SonarQube 有历史趋势。等保测的时候要的是'发现—整改—复测'的闭环，所以每个高危要关联工单号，复测通过才关闭。" |
| 误报怎么处理？ | "Trivy 有 `.trivyignore` 可以抑制，但必须写清原因和有效期，我一般要求带 CVE 编号和复核日期，到期自动失效重新暴露，不允许永久忽略。" |
| 扫描会不会拖慢流水线？ | "会，所以要错位。代码扫描放 MR 阶段、只扫增量，1 分钟内；镜像扫描放构建之后、部署之前，30 秒左右，Trivy DB 走缓存和国内源。整体增加不到 2 分钟，换来的是上线不带高危。" |
| 门禁和等保什么关系？ | "等保三级要求漏洞及时修补和变更留痕，门禁正好是这两个控制的落地手段：扫描管'发现'，审批和工单管'闭环'，artifact 管'证据'。测评师问起来我直接导记录。" |

### 数字锚点
`三层门禁`｜`只卡 New Code`｜`CRITICAL 阻断 / HIGH 限期`｜`报告留存 90 天`｜`增量 <2min`

### 禁忌
- ✗ "全部 HIGH 都阻断，一个都不放过" —— 没落地过才会这么说。
- ✗ "研发绕过就批评教育" —— 制度问题不能用态度解决。
- ✗ 只讲工具不讲阈值定法 —— 面试官要的是判断力。
