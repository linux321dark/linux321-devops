# 第 04 天 · GitLab CI 云原生化

## 一、今日目标（结论先行）
把你的核心资产 GitLab CI 升级成"提交→扫描→构建→推镜像→部署 K8s"全链路 YAML 流水线——本地民企偏好 GitLab CI（YAML 即代码），阿里云对标产品是**云效**。

## 二、企业真实需求背景
- **你 多年 DevOps 资产**：CI T1→T2、N+ 仓库——面试最强卖点，但要把"会用"讲成"原理清晰"。
- **行业B**："主导 CI/CD 流水线规划、落地与迭代优化"。
- **行业A**："CI/CD 全链路：App/Web/Agent/数据"。
- 本地民企现实：GitLab CI（YAML 即代码）比 Jenkins 脚本更受新公司偏好；大厂用阿里云**云效**做类似闭环。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜一条流水线的真实形态（不是三段 YAML，是七段带门禁的链）
中型研发团队（100–500 人）的标准流水线，大概率需要重建或优化：

| 阶段          | 干什么                        | 耗时预算     | 失败率最高的原因           |
| ----------- | -------------------------- | -------- | ------------------ |
| 1. 触发       | push/MR/tag 触发，`rules` 分流  | <5s      | rules 写宽了，每个分支都跑全量 |
| 2. 静态检查     | lint + 代码规范 + 敏感信息扫描       | 30–60s   | 工具版本不固定，规则随升级变动    |
| 3. 单测 + 覆盖率 | 并行分片跑                      | 1–3min   | 没有依赖缓存，每次重装依赖      |
| 4. 构建镜像     | DinD/Kaniko，多阶段            | 1.5–3min | 无 layer 缓存、镜像源不通   |
| 5. 安全扫描     | Trivy 镜像扫描 + 依赖漏洞          | 30–60s   | 阈值定太严，全量阻断导致没人能合并  |
| 6. 推送制品     | 推 ACR，tag 用 commit SHA     | 30–90s   | 推 latest，回滚时找不到版本  |
| 7. 部署       | dev 自动 / test 自动 / prod 手动 | 1–2min   | 生产无审批，误发布          |

**面试里你要能说出"每个阶段的时间预算"**——这证明你调过，不是搭过。

### 场景 B｜真实事故现场
1. **流水线从 T1 降到 T2，怎么做到的？** 不是换工具，是三件事：阶段 DAG 并行（`needs` 打破 stage 强串行）、依赖缓存命中（`cache:key` 按 lockfile 哈希）、制品复用（编译一次，测试/部署共用同一镜像，不重复构建）。
2. **缓存投毒**：`cache:key` 只写分支名，不同依赖版本共用缓存，A 分支的 `node_modules` 被 B 分支复用，出现"本地能跑 CI 不能跑"。正确：key 用 `lockfile` 哈希。
3. **DinD 在 K8s runner 上起不来**：`privileged: true` 被集群策略禁掉。正确：换 Kaniko（无需 daemon）或 BuildKit rootless。
4. **生产被误发布**：MR 合并即部署生产。正确：`when: manual` + `environment: prod` + 保护分支 + 只有 release tag 触发。
5. **CI 变量泄露**：把 AK 写进 `.gitlab-ci.yml` 或 echo 到日志。正确：Masked + Protected 变量，且只在保护分支可用。

### 场景 C｜面试官的真实痛点
- **行业B"主导 CI/CD 流水线规划、落地与迭代优化"**：他要的是"规划"能力——阶段划分、时间预算、门禁策略、多环境推进节奏，不是会写 YAML。
- **行业A"CI/CD 全链路：App/Web/Agent/数据"**：四类制品（移动端包、前端静态资源、Agent 服务、数据任务）流水线形态不同，要能分别说。
- 面试官必问：**"T1 怎么压到 T2？"** 答不出具体手段 = 数字是编的。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 触发策略 | 所有分支跑全量 | MR 跑"检查+单测+构建"，main 跑全量+部署 dev，tag 跑生产 |
| 制品 | 每次重新构建 | 编译一次，全阶段复用同一 image digest |
| 审批 | 生产自动发 | `when: manual` + 保护分支 + 双人审批 |
| 密钥 | 写在 YAML / 日志 echo | Masked+Protected CI 变量，严禁 echo |

- **原理**：Pipeline = 有向无环图（stage 串行、job 并行）；runner 拉取执行；制品不可变。
- **理论**：持续集成/交付；质量左移；流水线即代码。
- **核心易忘点**：`.gitlab-ci.yml` 的 `stages/rules/cache/artifacts/needs`；DinD 须 `privileged:true`+`docker:dind`；`rules:` 控制分支触发。
- **横向对比**：GitLab CI（YAML 即代码，本地偏好）vs Jenkins（你熟，Groovy）vs GitHub Actions（境外）。
- **常见问题**：缓存 key 设计错致命中错误；DinD 在 K8s runner 权限；Apollo 配置与代码不同步致环境错乱。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 写 `.gitlab-ci.yml`（基础三段）
```yaml
stages: [build, scan, deploy]
variables:
  IMAGE: registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:ci-$CI_COMMIT_SHORT_SHA
build:
  stage: build
  image: docker:25-cli
  services: [docker:25-dind]
  variables: { DOCKER_TLS_CERTDIR: "/certs" }
  script:
    - docker build -t $IMAGE .
    - docker login -u $REGISTRY_USER -p $REGISTRY_PASS registry.cn-hangzhou.aliyuncs.com
    - docker push $IMAGE
scan:
  stage: scan
  image: aquasec/trivy:latest
  script:
    - trivy image --severity CRITICAL --exit-code 1 $IMAGE   # 高危阻断
deploy:
  stage: deploy
  image: bitnami/kubectl:latest
  rules: [{ if: '$CI_COMMIT_BRANCH == "main"' }]            # 仅 main 部署
  script:
    - kubectl set image deployment/web web=$IMAGE --namespace demo
```
> 在 jihulab 建仓库推送；CI 变量 `REGISTRY_USER/REGISTRY_PASS` 在 Settings→CI/CD→Variables 配置（不写进仓库）。

### 5.2 本地用 gitlab-runner 验证（无共享 runner 时）
```bash
# 本机起一个 docker runner 跑流水线
docker run -d --name gitlab-runner --restart always \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest
gitlab-runner register --url <你的jihulab> --token <project-token> --executor docker --docker-image docker:25-cli
```

### 5.3 缓存与多环境
```yaml
# 加速：Maven/npm 依赖缓存
cache:
  key: $CI_COMMIT_REF_SLUG
  paths: [node_modules/, ~/.m2/repository/]
# 多环境：用 environment + rules 区分
deploy_prod:
  stage: deploy
  environment: { name: prod }
  rules: [{ if: '$CI_COMMIT_TAG' }]      # 打 tag 才生产发布（手动审批）
  when: manual
```

## 六、成果验证方式
1. push 到 jihulab → Pipelines 页看到 build→scan→deploy 三段均绿色。
2. `scan` 阶段对高危 CVE 返回非零退出码（故意引入漏洞镜像验证阻断生效）。
3. `deploy` 后 `kubectl get deployment web` 镜像 tag = `$CI_COMMIT_SHORT_SHA`。
4. `when: manual` 的 prod 任务需手动点才执行。

## 七、常见坑与排错
- DinD 需 `privileged:true` + `DOCKER_TLS_CERTDIR`；K8s runner 无特权时改用 `kaniko` 构建。
- 缓存 `cache:key` 错致命中错误版本 → key 含 ref slug。
- `docker:25-dind` 镜像拉取慢 → 配 registry-mirrors。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：T1 压到 T2，具体怎么做的？（最高频，必须答得实）
> "不是换工具，是三件事叠加。
> 第一，**拆串行为并行**。原来是一条链串到底，编译完才跑测试，测试完才构建镜像。我把它拆成 DAG，静态检查和单测并行，多个服务的构建并行，用 `needs` 打破 stage 的强制顺序，这一步就砍掉了一半时间。
> 第二，**缓存命中**。以前每次全新装依赖，Maven 和 npm 各要 3–5 分钟。我给缓存 key 绑 lockfile 的哈希，依赖没变就直接命中，只有改依赖才重装，又省下 3 分钟左右。
> 第三，**制品只构建一次**。原来测试阶段构建一遍、部署阶段又构建一遍，镜像还不一定一致。改成构建一次产出 image digest，后面所有环境复用同一个 digest，既提速又保证"测的就是发的"。
> 再叠加镜像本身的瘦身——多阶段把 A 压到 B，拉取和推送也快了一截。最终从 T1 到 T2，N+ 个仓库统一迁移到 GitLab CI。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| `needs` 和 `stages` 什么关系？ | "`stages` 定义默认串行顺序，`needs` 可以显式声明某个 job 依赖谁，从而跳过中间 stage 直接开跑，本质是把流水线从链变成 DAG。用错会破坏依赖关系，比如测试没等编译就跑了。" |
| 缓存为什么有时不生效？ | "三种情况：key 写成分支名导致跨分支命中脏缓存；路径写错（`~/.m2` 在容器里是 `/root/.m2`）；runner 类型不一致（docker executor 的缓存要落在卷上，shell executor 是本地目录）。所以 key 我用 lockfile 哈希，路径写绝对路径。" |
| 生产怎么防误发？ | "三道：保护分支只允许 MR 合入、生产 job 设 `when: manual`、只有 `v*` tag 才允许触发生产部署。另外环境级加审批人，AK 变量设为 Protected 只在保护分支可用。" |
| DinD 和 Kaniko 选哪个？ | "有特权就能用 DinD，简单快；但 K8s 集群一般禁 privileged，这时用 Kaniko，不需要 daemon，用普通 Pod 就能构建。我给客户环境的方案是 Kaniko + 缓存层，规避权限审批。" |
| 四类制品（App/Web/Agent/数据）流水线有什么不同？ | "App 要出签名包走应用市场；Web 是静态资源，构建完直接推 OSS+CDN 刷新；Agent 服务是镜像推 ACR 走 K8s 发布；数据任务重点是调度依赖和幂等。所以不能一套模板全用，要按制品类型分模板。" |
| 怎么衡量流水线好坏？ | "四个指标：单次时长（P50/P90）、失败率（区分环境性问题还是代码问题）、平均修复时间、排队等待时长。我每周看一次 P90，因为均值掩盖长尾。" |

### 数字锚点
`T1→T2`｜`N+ 仓库`｜`镜像 A → B`｜`制品只构建一次`

### 禁忌
- ✗ "换了个更快的 runner" —— 硬件提速不算能力。
- ✗ 只讲 YAML 语法不讲时间收益 —— 面试官要的是数字归因。
- ✗ 说"我们没统计过流水线时长" —— 等于没做过优化。
