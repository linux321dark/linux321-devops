## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜谁在真的用弹性，峰谷长什么样
本地民企的流量不是均匀的，HPA 的价值全在"峰谷差"上：

| 业务形态 | 峰谷特征（真实口径） | 不弹性会怎样 | 弹性后省什么 |
|---|---|---|---|
| 行业B·车联网/APP 后端 | 早晚通勤双峰（7:30–9:00、18:00–20:00）约为谷时 3–5 倍；OTA 推送/发布会瞬时 5–8 倍 | 按峰值常年备机器，成本翻 3 倍；或按均值备，高峰 502 | 谷时缩到 1/3，ACK 节点费直降 |
| 行业A·在线问诊 | 上午 9–11 点、晚间 20–22 点双峰；夜间近乎空载 | GPU/推理节点单价高，空转最烧钱 | 夜间缩容是最直接的降本项（FinOps 考核点） |
| 行业C·政企 SaaS | 工作日 9–18 点为主，周末低 | 周末空转 | 按工作时段收缩 |

你的岗位动作不是"配个 HPA"，而是**给出峰谷画像 → 定阈值 → 定上下限 → 验证 → 出成本对比**这一整条。面试官要听的是这条链，不是 `kubectl autoscale` 一行命令。

### 场景 B｜真实事故现场（HPA 的坑全在"不生效"和"乱生效"）
1. **大促不扩容，HPA 一直 `<unknown>/50%`**：Deployment 漏写 `resources.requests.cpu`。HPA 的利用率分母是 request，没有分母就算不出百分比，控制器直接放弃。**这是生产最高频的 HPA 失效原因**，且不报错、不告警，只能靠看 `kubectl get hpa` 发现。
2. **HPA 扩了，Pod 全 `Pending`**：集群节点没资源了。HPA 只管 Pod 数量，不管节点。要让节点也跟着扩，需要 **cluster-autoscaler（ACK 弹性伸缩组）** 配合，且 Pod 的 request 必须真实，否则调度器误判。
3. **扩容慢半拍，高峰已经过去了**：指标采集 `--metric-resolution=15s` + HPA 默认 15s 同步 + 拉镜像/启动耗时，实测扩容生效 1–2 分钟。靠 HPA 救秒级尖峰是错的，秒级要靠预留副本（minReplicas）+ 限流。
4. **缩容把长连接打断，用户看到 502**：缩容默认 300s 稳定窗口，但 Pod 终止时若没有 `preStop` + `terminationGracePeriodSeconds`，正在处理的请求被硬切。正确做法：`preStop: sleep 15` + 优雅停机 + `PodDisruptionBudget`。
5. **副本数来回抖（flapping）**：阈值卡在业务均值上，负载一波动就 1→3→1→3。用 `behavior.scaleDown.stabilizationWindowSeconds: 300` 抑制，并把阈值放在"高于日常峰值 20%"的位置。
6. **CPU 打满了却扩不动**：容器 `limits.cpu` 太低被 cgroup 节流（throttling）——**CPU 超限不会杀容器，只会把它变慢**。被节流后采集到的用量顶到 limit，**分母是 requests 时利用率反而偏高、照样触发扩容，但每个新 Pod 同样被限死，扩了也没用**。真正让 HPA「有值但不扩」的是**分母被撑大**（只写 limits 而 limits 远大于实际用量）、命中 10% 容差、已达 maxReplicas、或指标没采到。

### 场景 C｜面试官的真实痛点
面试官关心三件事：**① 你们线上到底有没有真弹性（还是常年固定副本假装云原生）；② 扩不出来的时候你怎么定位（能不能分清 HPA 没触发 / 触发了但调度不上 / 调度上了但起不来）；③ 缩容会不会把业务搞挂**。这三问答得干脆，比背 API 字段有用得多。

### 标准动作 vs 反例
| 环节     | 反例（会被当场问倒）        | 标准动作（直接说这个）                               |
| ------ | ----------------- | ----------------------------------------- |
| 阈值设定   | 拍脑袋写 80%          | 看历史 CPU 曲线，取"日常峰值 × 1.2"对应的利用率，通常 50–70%  |
| 上下限    | min=1 max=100 图省事 | max 按"单 Pod 承载 QPS × 副本数 ≤ 集群余量"反推，避免打爆节点 |

### 4.1 今天的命令，先按"三态"归位

K8s 只有三个状态：**期望态**（你写的 yaml）→ **实际态**（集群真实跑的）→ **协调**（controller 死循环把前者拉成后者）。今天的命令全部落在这三类里：

| 命令                       | 属于哪类   | 具体在干什么                                                        |
| ------------------------ | ------ | ------------------------------------------------------------- |
| `kind create cluster`    | 造环境    | 不是 K8s 命令，是拿 Docker 起一个容器当"节点"，里面跑 kubelet + containerd + 控制面 |
| `kind load docker-image` | 造环境    | 把宿主机 Docker 的镜像**灌进 kind 节点容器**，绕开 registry                   |
| `kubectl apply -f`       | 改期望态   | 把 yaml 写进 etcd，然后 controller 开始干活                             |
| `kubectl get / describe` | 看实际态   | 看协调到哪一步了                                                      |
| `kubectl rollout status` | 看协调进度  | 死等"实际态 = 期望态"，等不到就报超时                                         |
| `kubectl exec`           | 摸真实运行态 | 进容器内部，绕开 K8s                                                  |

> **排障顺序由这个模型定死**：`apply` 之后没起来，第一件事不是重装，是 `describe` 看 Events 卡在哪一步（调度？拉镜像？探针？）。

### 4.2 `go-demo.yaml` 每个字段为什么这么写

| 字段 | 为什么必须有 | 写错的后果 |
|---|---|---|
| `selector.matchLabels` 与 `template.metadata.labels` | 两者**必须一致**。Deployment 靠它找到"哪些 Pod 归我管" | 不一致 → `apply` 直接报错 `selector does not match template labels` |
| `replicas: 1` | 期望的 Pod 数，HPA 之后会改它 | — |
| `resources.requests.cpu: 100m` | **HPA 的分母**。100m = 0.1 核 | 漏写 → HPA 永远 `<unknown>/50%`，一个都不扩，且**不报错不告警** |
| `resources.limits.cpu: 500m` | 上限，超了被 cgroup 节流（**不杀容器，只变慢**） | limits 太低 → 采集值顶到 limit → **分母是 requests 时利用率反而偏高、照样扩但每个新 Pod 同样被限死**；真正「有值但不扩」的是分母被撑大（场景 B 第 6 条） |
| `imagePullPolicy: IfNotPresent` | 节点本地有镜像就不联网拉 | 写 `Always` → 每次都去 registry，私有仓库无凭据直接 `ImagePullBackOff` |
| `containerPort: 8080` | 声明容器监听 8080（**只是声明，不做限制**） | 写错不报错，但 Service 的 `targetPort` 会对不上 |
| Service `selector` | 选后端 Pod，**必须等于** Pod 的 label | 写错 → `get endpoints` 为空，访问 503 |

**两条能自己验证的推论**：

```bash
kubectl get deploy day1-go -o yaml | sed -n '/status:/,$p'   # 看 status，这才是"实际态"
kubectl get endpoints day1-go-svc                            # Service 到底挂上没有，看这个最准
```

### 4.3 `rollout status` 凭什么判断"成功"

它不看日志、不探测业务，只比 Deployment 的 `status` 里三个数字：

| 字段 | 含义 |
|---|---|
| `replicas` | 当前总 Pod 数（含旧的） |
| `updatedReplicas` | 已经是新版本的 Pod 数 |
| `readyReplicas` / `availableReplicas` | **Ready 且可用**的 Pod 数 |

`rollout status` 等的就是 `updatedReplicas == replicas == availableReplicas == 期望副本数`。今天报的 `0 of 1 updated replicas are available`，说明 1 个 Pod 创建了但**没有一个进入 Ready**。

> 所以"超时"这个报错本身**零信息量**——它只是"等够了没等到"。原因必须去 Pod 的 Events 里找。
> **默认等 600 秒**（`spec.progressDeadlineSeconds`），这 10 分钟里它什么都没干，只是在等。

### 4.4 HPA 的 `TARGETS` 那个百分比是怎么算出来的

```
利用率 = 当前 Pod 的 CPU 实际用量 ÷ requests.cpu
```

以你的 yaml 为例：`requests.cpu: 100m`。若单个 Pod 实际用量 30m → `30m/100m = 30%`，显示 `30%/50%`，没到 50% 不扩。

扩容公式：

```
期望副本数 = ceil( 当前副本数 × (当前利用率 / 目标利用率) )
```

1 个 Pod、利用率 120%、目标 50% → `ceil(1 × 120/50) = ceil(2.4) = 3` → 扩到 3 个。

**这就是为什么 requests 不能乱写**：写 100m 意味着"50% = 50m 就开始扩"，写 500m 意味着"要烧到 250m 才扩"。**分母定多少，直接决定扩不扩、什么时候扩。**

### 4.5 metrics-server 那 6 个对象为什么缺一不可

按"输入从哪来 → 输出给谁用"串一遍，整段 yaml 就通了：

```
kubelet 的 cAdvisor（每节点）→ 暴露 /stats 接口
   ↓
metrics-server（Deployment 跑的普通容器）→ 拉取并聚合
   ↓
APIService v1beta1.metrics.k8s.io → 注册进 apiserver 的 API 目录
   ↓
kubectl top / HPA 才能"像查内置资源一样"查它
```

| 对象 | 缺了会怎样 |
|---|---|
| ServiceAccount + ClusterRole + ClusterRoleBinding | 读 `nodes/stats`+`nodes/metrics` 要权限，**缺了就是 403**：容器 Running 但 `kubectl top` 报错 |
| Deployment | 没人跑它 |
| Service | APIService 靠 `service.name/namespace` 找它，缺了注册不上 |
| **APIService** | 缺了它，`kubectl top` 和 HPA **根本不知道有这个数据源**——这一步是"接进 K8s"的关卡 |
| `--kubelet-insecure-tls` | kind 的 kubelet 用自签证书，不加这个连不上。**生产 ACK 上不需要** |
| `--metric-resolution=15s` | 采集间隔，直接决定 HPA 反应速度（话术里"扩容延迟 1-2 分钟"的第一段） |

> **可迁移的规律**：任何外部组件要变成"K8s 的资源"，必须三件套——**① 有 Pod 跑 ② 有 Service 让 apiserver 找得到 ③ 有 APIService 注册成 API 组**。以后遇到 Prometheus Adapter、KEDA、任何 custom metrics 组件，都是同一个套路。**这才是今天真正该带走的东西。**

### 5.2 写 Deployment + Service（必须含 requests.cpu）
`go-demo.yaml`：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: day1-go, labels: { app: day1-go } }
spec:
  replicas: 1
  selector: { matchLabels: { app: day1-go } }
  template:
    metadata: { labels: { app: day1-go } }
    spec:
      containers:
      - name: day1-go
        image: registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1
        imagePullPolicy: IfNotPresent
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "100m", memory: "128Mi" }   # ← HPA 分母，缺了就 /50%
          limits:   { cpu: "500m", memory: "256Mi" }
---
apiVersion: v1
kind: Service
metadata: { name: day1-go-svc }
spec:
  selector: { app: day1-go }
  ports: [{ port: 80, targetPort: 8080 }]
  type: ClusterIP
```
```bash
kubectl apply -f go-demo.yaml
kubectl rollout status deployment/day1-go
kubectl get pods -l app=day1-go          # 期望 Running 1/1
```

### 5.3 装 metrics-server（kind 必踩：阿里云镜像 + v0.7.2 + --kubelet-insecure-tls）
```bash
kubectl delete apiservice v1beta1.metrics.k8s.io --ignore-not-found
kubectl -n kube-system delete deployment/metrics-server service/metrics-server serviceaccount/metrics-server --ignore-not-found
cat > ~/metrics-server.yaml <<'EOF'
apiVersion: v1
kind: ServiceAccount
metadata: { name: metrics-server, namespace: kube-system }
---
apiVersion: v1
kind: Service
metadata: { name: metrics-server, namespace: kube-system, labels: { kubernetes.io/name: Metrics-server } }
spec: { selector: { k8s-app: metrics-server }, ports: [{ port: 443, targetPort: https }] }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: metrics-server, namespace: kube-system, labels: { k8s-app: metrics-server } }
spec:
  selector: { matchLabels: { k8s-app: metrics-server } }
  template:
    metadata: { labels: { k8s-app: metrics-server } }
    spec:
      priorityClassName: system-cluster-critical
      serviceAccountName: metrics-server
      containers:
      - name: metrics-server
        image: registry.cn-hangzhou.aliyuncs.com/google_containers/metrics-server:v0.7.2
        args: [--cert-dir=/tmp, --secure-port=10250, --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname,
               --kubelet-use-node-status-port, --metric-resolution=15s, --kubelet-insecure-tls]
        ports: [{ name: https, containerPort: 10250 }]
        readinessProbe: { httpGet: { path: /livez, port: https, scheme: HTTPS }, initialDelaySeconds: 5, periodSeconds: 10 }
        livenessProbe:  { httpGet: { path: /livez, port: https, scheme: HTTPS }, initialDelaySeconds: 5, periodSeconds: 10 }
      tolerations:
      - { key: CriticalAddonsOnly, operator: Exists }
      - { key: node-role.kubernetes.io/master, effect: NoSchedule }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: system:metrics-server, labels: { kubernetes.io/cluster-service: "true" } }
rules:
- apiGroups: [""]
  resources: ["pods","nodes","nodes/stats","nodes/metrics","namespaces","configmaps"]
  verbs: ["get","list","watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: system:metrics-server }
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: system:metrics-server }
subjects: [{ kind: ServiceAccount, name: metrics-server, namespace: kube-system }]
---
apiVersion: apiregistration.k8s.io/v1
kind: APIService
metadata: { name: v1beta1.metrics.k8s.io }
spec: { service: { name: metrics-server, namespace: kube-system }, group: metrics.k8s.io, version: v1beta1, insecureSkipTLSVerify: true, groupPriorityMinimum: 100, versionPriority: 100 }
EOF
kubectl apply -f ~/metrics-server.yaml
kubectl rollout status deployment/metrics-server -n kube-system --timeout=120s
sleep 30 && kubectl top nodes && kubectl top pods -l app=day1-go   # 必须返回真实数值
```

### 5.4 配 HPA（CPU 50%）
```bash
kubectl autoscale deployment day1-go --cpu-percent=50 --min=1 --max=5
# 或写 manifest：
cat > hpa.yaml <<'EOF'
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: day1-go }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: day1-go }
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 50 } }
EOF
kubectl apply -f hpa.yaml
kubectl get hpa day1-go        # 期望 TARGETS 形如 0%/50%（非 <unknown>/50%）
```

## 七、常见坑与排错
- **`top` 报错 / HPA `<unknown>`**：metrics-server 没装或漏 `--kubelet-insecure-tls` → 重跑 5.3（坑24/29）。
- **`TARGETS /50%` 分母缺失**：Deployment 漏 `resources.requests.cpu`（坑25）。
- **`ErrImagePull`**：忘了 `kind load` 或 `imagePullPolicy` 是 `Always` → 改 `IfNotPresent`（坑26）。
- **`exec format error`**：Mac(arm64) 跑 kind 拉 amd64 镜像 → 回 ECS(amd64) 跑（坑27）。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：HPA 你们怎么用的？说说原理和踩过的坑（75–90 秒逐字稿）
> "HPA 本质是一个控制器循环：它每 15 秒左右从 metrics-server 拉一次 Pod 的实际用量，除以 `resources.requests.cpu` 得到利用率，再按公式 `期望副本数 = 当前副本数 × (当前利用率 / 目标利用率)` 算出目标副本，写回 Deployment 的 replicas。
> 所以有两个死点：一是**分母必须存在**，Deployment 不写 `requests.cpu`，HPA 就永远是 `<unknown>/50%`，一个副本都不会扩，而且不报错；二是**它只改 Pod 数、不管节点**，节点没余量就全 Pending，得靠 cluster-autoscaler 或者 ACK 的伸缩组接着扩节点。
> 我踩过最典型的是第一类：上线后大促没扩，查 `kubectl get hpa` 发现 TARGETS 是 `<unknown>`，补上 requests 之后立刻正常。另外扩容不是实时的，指标 15 秒一次 + 调度 + 拉镜像，实测生效要 1–2 分钟，所以秒级尖峰我们会用 minReplicas 预留 + 网关限流兜底，不指望 HPA 救瞬时流量。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 指标数据从哪来？ | "kubelet 的 cAdvisor 采容器资源用量，metrics-server 通过 Summary API 拉聚合，注册成 `metrics.k8s.io/v1beta1` 的 APIService 提供给 HPA。所以 `kubectl top` 没数据 = metrics-server 这条链断了，HPA 一定跟着瞎。" |
| 为什么缩容要等 300 秒？ | "默认 `scaleDown.stabilizationWindowSeconds=300`，取窗口同行资料荐副本数的最大值，防止负载一抖就缩、缩完又扩。扩容窗口默认 0，是故意不对称设计的——扩要快、缩要慢。" |
| 扩容延迟具体卡在哪几步？ | "四段：指标采集 15s 粒度 → HPA 同步周期 → 调度 + 拉镜像（镜像大就是主要耗时，这也是 Day1 压体积的意义）→ 应用就绪探针通过。所以镜像 A 和 B，扩容速度完全不同。" |
| HPA 能不能按 QPS 扩？ | "能，autoscaling/v2 支持 Pods/External 类型指标，QPS 一般通过 Prometheus Adapter 把指标暴露成 custom metrics。CPU 是替代指标，QPS 才是业务真相；但 Adapter 链路更长、排障成本高，我一般先上 CPU，业务对延迟敏感再补 QPS。" |
| HPA 和 VPA 什么关系？ | "HPA 调副本数（横向），VPA 调单个 Pod 的 requests/limits（纵向）。VPA 改 request 需要重建 Pod，和 HPA 同时用会打架，通常二选一；我们选 HPA + 人工定期校准 request。" |
| 有状态服务能 HPA 吗？ | "技术上能，但缩容要保证数据安全：StatefulSet 有稳定网络标识，缩容会删最高序号的 Pod，配合 PDB 和数据副本策略才安全。生产上数据库这类我倾向固定副本 + 垂直扩容，HPA 只给无状态服务用。" |
| 你怎么证明 HPA 真的生效了？ | "压测留三样证据：`kubectl get hpa -w` 的 TARGETS 爬升过程、`kubectl get pods -w` 的副本数变化、`kubectl describe hpa` 里 Events 的 `SuccessfulRescale` 记录。有这三样才叫验证过，不是配完就完。" |

### 数字锚点
`metrics 15s`｜`扩容生效 1–2min`｜`缩容窗口 300s`｜`HPA 目标 50%`｜`min1→max5`
