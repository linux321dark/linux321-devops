## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜这不是练习，是一家民企真实的"云原生交付链从 0 到 1"项目
这类项目的真实推进节奏如下（用 7 天走完一遍，是为了之后能直接接手）：

| 阶段 | 真实周期 | 你要交付的东西 | 谁验收 |
|---|---|---|---|
| 现状盘点 | 第 1–2 周 | 应用清单、环境清单、当前构建耗时基线、镜像体积基线、漏洞基线 | 技术负责人 |
| 镜像治理 | 第 3–4 周 | 统一基础镜像、多阶段 Dockerfile 模板、.dockerignore 规范 | 研发组长 |
| 流水线重建 | 第 5–7 周 | `.gitlab-ci.yml` 模板库、阶段时间预算、门禁阈值 | 研发 + 测试 |
| 制品与环境 | 第 8–9 周 | ACR/Harbor 仓库规划、tag 规范、Helm Chart、多环境 values | 运维 |
| 弹性与可观测 | 第 10–12 周 | HPA 策略、监控大盘、告警规则与分级 | SRE / Leader |
| 交付验收 | 第 13 周 | 一份"改造前后对比"报告（时长、体积、漏洞数、故障率） | 管理层 |

**关键认知**：这条链里每一环都有"改造前基线 → 改造后数字"。你在 D1–D6 做的每一步，都对应一个可汇报的数字。**没有基线的改造，汇报时等于没做。**

### 场景 B｜整合时最容易崩的四个衔接点
1. **CI 构建的镜像和 Helm 部署的 tag 对不上**：CI 用 `ci-$CI_COMMIT_SHORT_SHA`，values 里写死 `go-v1`，部署上去永远是旧镜像。正确：部署时 `--set image.tag=ci-$CI_COMMIT_SHORT_SHA` 由流水线注入，values 里只放默认值。
2. **kind 里拉不到 ACR 私有镜像**：集群没有 imagePullSecret。正确：`kubectl create secret docker-registry` 并挂到 `imagePullSecrets`，或本地用 `kind load` 绕过。
3. **Helm 装完 Pod 没起来，但 `helm install` 显示成功**：Helm 默认不等就绪。正确：加 `--wait --timeout 5m`，让它等到 Ready 才算成功，否则"部署成功"是谎报。
4. **HPA 和 Helm 打架**：Helm upgrade 会把 replicas 重置回 values 里的值，HPA 又改回去，来回抖。正确：HPA 管的 Deployment，Helm 里**不设 replicas 或设为 null**，副本数交给 HPA 独占。

### 场景 C｜面试官的真实痛点
面试官问"你做过最完整的交付链路是什么"，本质在验证三件事：**① 你是真的端到端跑通过，还是各环节都碰过一点；② 你有没有遇到过环节之间的冲突（比如上面 HPA 与 Helm 打架）；③ 你能不能把它讲成一条 90 秒的线，而不是一堆碎片。** 第三点是表达能力，前两点是真实经历——D7 就是把它们缝合起来。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 镜像 tag | values 写死 / 用 latest | 流水线注入 commit SHA |
| 部署成功判定 | `helm install` 返回即成功 | `--wait --timeout` + 就绪探针 |
| 副本数归属 | Helm 和 HPA 都管 | HPA 独占，Helm 不设 replicas |
| 项目汇报 | 讲"我用了什么技术" | 讲"改造前后四个数字" |

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 项目串讲（从零部署一遍）
```bash
# 1) 构建+推送
cd ~/devops-day1/go-demo
docker buildx build --provenance=false --sbom=false \
  -t registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:week1 --push .

# 2) kind 起集群 + 装 metrics-server（复用 D2 的 ~/metrics-server.yaml）
kind create cluster --name week1
kubectl apply -f ~/metrics-server.yaml
kubectl rollout status deployment/metrics-server -n kube-system --timeout=120s
sleep 30 && kubectl top nodes

# 3) Helm 部署 + HPA
helm install myapp ./myapp -f values-prod.yaml --namespace demo --create-namespace
kubectl autoscale deployment myapp --cpu-percent=50 --min=1 --max=5 -n demo
kubectl get pods,hpa -n demo
```

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：讲一个你做过最完整的交付链路（90 秒结构性逐字稿，这是终面必问题）
> "我拿一条端到端的链路说，从代码提交到线上可观测，五段。
> **第一段，提交触发**。研发提 MR，GitLab CI 按 rules 分流：MR 只跑检查、单测和构建，合并到 main 才跑完整链路，打 tag 才允许上生产。
> **第二段，构建制品**。多阶段 Dockerfile，builder 编译、runtime 只留 jre 或 scratch，Java 从 A 压到 B，Go 做到 V；构建完立刻 Trivy 扫，CRITICAL 直接阻断，不让带高危的镜像进仓库。
> **第三段，制品入库**。推阿里云 ACR，tag 用 commit SHA，不用 latest，保证任何一次发布都能精确找回当时的镜像。
> **第四段，部署**。Helm 一个 Chart 管多环境，dev 自动、prod 手动审批，`--wait` 等到 Pod 真正 Ready 才算成功；出问题 `helm rollback` 回任意一版。
> **第五段，运行态**。HPA 按 CPU 50% 弹性，压测验证过 1 到 5 副本；Prometheus 采集、Grafana 出盘、钉钉分级告警。
> 整条链路改造前 CI T1、镜像 A、发布靠手工；改造后 T2、B、一键发布可回滚。**这就是我多年 DevOps 经验在云原生栈上的落地版本。**"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 这条链路里最难的是哪一步？ | "最难的不是工具，是 HPA 和 Helm 抢副本数——Helm upgrade 会把 replicas 重置回 values，HPA 又调回去，来回抖。解决办法是把副本数所有权明确给 HPA，Helm 模板里不设 replicas。这类'两个工具都认为自己该管'的冲突，是平台建设里最耗时间的部分。" |
| 这套东西在你们生产规模下撑得住吗？ | "单集群百级应用没问题，我这次是单节点 kind 验证的，生产在 ACK 上控制面和 etcd 是托管的。真正要注意的是 HPA 的 maxReplicas 和节点容量匹配，别一次扩到调度不上。" |
| 如果让你从零给一家公司重建这条链，多久？ | "分三期：第一期两周做基线盘点和镜像治理，效果最快、阻力最小；第二期一个月重建流水线和门禁；第三期一个月做弹性与可观测。总共三个月能出一个可汇报的对比报告。我在这一周把它完整走通了一遍，路径是验证过的。" |
| 你这些是练手的还是生产跑过的？ | 诚实回答："K8s 这块是我为了转云原生系统补齐的，kind 和 ACK 短跑都验证过；CI/CD、阿里云运维、等保这些是我在金融项目里真实跑过四年的。所以我强在流水线体系和合规落地，K8s 生产深度是我正在补的部分。"（**不夸大是底线，被追问穿帮的代价远大于承认缺口**） |
