# 第 01 天 · Docker 多阶段构建达生产级

> 参考仓库素材：`docs/day1-evening-practice.md`（七语言实操）、`docs/docker-multistage-allstacks.md`（全栈手册）、`docs/learning-resources-nav.md`（资源导航）。本日命令来自上述已验证 SOP。

## 一、今日目标（结论先行）
为 1–2 门目标岗位最相关的语言（本地优先 **Java / Go / Node**）写出**带真实依赖的多阶段 Dockerfile**，压到目标体积（Go 10–30MB / Java 150–200MB / Node 150–250MB），非 root 运行，并用 `buildx --provenance=false` 推 ACR 个人版验证——这是 CI/CD 提速第一关，也是行业B/行业A/行业C 容器化交付的共同入场券。

## 二、企业真实需求背景
- **行业B**（应用运维 J18133）："支撑研发交付效率提升"——镜像体积是研发自助构建的痛点。
- **行业A（行业A）**："CI/CD 全链路：从代码到生产"——镜像作为不可变制品贯穿流水线。
- **行业C**：多应用多环境交付，镜像越大拉取越慢、ACK 存储越贵。
- 本地民企现状：研发用 Mac(arm64) 本地构建，生产 ECS/ACK 是 amd64，跨架构是高频坑；镜像仓多用**阿里云 ACR**，部分大厂自建 **Harbor**。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜岗位日常：研发每天在跑的这条链路
本地民企研发规模 100–500 人，日均代码提交 80–300 次，每次提交触发一次镜像构建。你的岗位不是"帮人构建"，而是**保证这条链路的时长、体积、安全性三项指标不掉线**：

| 环节      | 不治理时的真实数字                    | 治理后                | 谁在为此付钱                        |
| ------- | ---------------------------- | ------------------ | ----------------------------- |
| CI 构建时长 | Java 单服务 5–7 分钟              | 1.5–2 分钟           | runner 机时费 + 研发排队等待           |
| 镜像推送    | A 推到 ACR 需 3–5 分钟        | 60–90 秒            | 带宽 + 每次发布耗时                   |
| 节点拉取    | 700MB × 10 节点 ≈ 7GB/次发布      | B × 10 ≈ 1.8GB | ACK 存储/流量费 + 滚动发布卡在 ImagePull |
| 镜像漏洞数   | 含 JDK/编译器的镜像 CRITICAL 常 N+ | 20–40              | 等保测评不过 → 上线卡死                 |
| 回滚速度    | 拉大镜像 3 分钟，回滚窗口超时             | 30 秒内              | 故障时长 = 钱                      |

**这就是行业B JD 写的"支撑研发交付效率提升"的具体含义**——它不是让你写脚本，是让你把上表五个数字压下去，并且拿得出前后对比。

### 场景 B｜真实事故现场（不做到位会炸在哪）
1. **Mac M 系列 → Linux 服务器**：研发在本地 `docker build` 推上去，Pod 起来 `CrashLoopBackOff`，日志首行 `exec format error`。根因：arm64 镜像跑在 amd64 节点。正确动作：CI 里统一 `buildx --platform linux/amd64`，禁止研发本地构建作为制品来源。
2. **推 ACR 报 `oci.empty` / `manifest invalid`**：Docker 23+ 默认给镜像附 provenance/SBOM 附件，ACR 个人版不认。正确动作：`--provenance=false --sbom=false`，并在 CI 里固化环境变量 `BUILDX_PROVENANCE=false`，而不是每次手敲。
3. **scratch 镜像启动即 panic**：`x509: certificate signed by unknown authority`（没带 CA）、或 `fork/exec: no such file`（漏了 `CGO_ENABLED=0`，二进制仍动态链接 glibc）。正确动作：静态编译 + 显式 `COPY ca-certificates.crt`。
4. **镜像 1.2GB**：新人把整个项目目录 `COPY . .`，把 `target/`、`node_modules/`、`.git/` 全塞进去；且没写 `.dockerignore`。正确动作：先 `COPY` 依赖清单再装依赖，最后 `COPY` 源码，并维护 `.dockerignore`。

### 场景 C｜面试官的真实痛点（他们为什么必须招一个懂这个的）
面试官（基础设施/运维负责人）脑子里想的是三件事：**① 我们的镜像是不是在裸奔（安全扫描一堆 HIGH）；② 新人会不会又把构建搞成 10 分钟；③ 等保/审计来查，我拿不拿得出镜像可追溯的证据**。你只要能对这三件事各给一个具体做法 + 一个数字，这轮就过了。

### 标准动作 vs 反例
| 环节    | 反例（会被当场问倒）            | 标准动作（直接说这个）                                    |
| ----- | --------------------- | ---------------------------------------------- |
| 基础镜像  | `FROM openjdk:latest` | `FROM eclipse-temurin:17-jre-alpine`，并锁 digest |
| 依赖缓存  | 先 COPY 全部源码再 mvn      | 先 `COPY pom.xml` + `go-offline`，再 COPY src     |
| 构建架构  | 本地 build 后 push       | CI 内 `buildx --platform linux/amd64` 单点构建      |
| 镜像内用户 | 默认 root               | `USER 1000` / `USER 65532:65532`               |
| 制品可信  | 覆盖 tag `latest`       | 语义化 tag + git commit SHA，禁止 latest 上生产         |
|       |                       |                                                |

- **原理**：镜像=只读层叠加(UnionFS)；容器=镜像+可写层+namespace/cgroup 隔离；多阶段靠多 `FROM` 阶段，`COPY --from=` 只搬产物阶段。
- **理论**：不可变基础设施；12-Factor（依赖显式声明）；最小攻击面。
- **核心易忘点**：`COPY --from=` 引用阶段名或序号（0 起）；体积杠杆排序＝**不装多余东西 > 多阶段 > 小基础镜像 > 钉版本 > 清缓存**；Go 必须 `CGO_ENABLED=0` 才能跑 scratch；Java runtime 用 `*-jre-*` 而非 JDK；Node 用 `npm ci`（锁 lockfile）。
- **横向对比**：Docker（通用）vs Buildah（Rootless）vs Kaniko（K8s 内构建无 daemon）。
- **常见问题**：镜像过大→多阶段+alpine；Mac(arm64)→ECS(amd64) `exec format error`→`buildx --platform linux/amd64`；推 ACR `oci.empty`→`buildx --provenance=false --sbom=false`；拉取超时→registry-mirrors（坑8）。

### 5.1 前置确认（ECS 登录后）
```bash
ssh root@<你的ECS公网IP>
docker info | grep -i "server version"         # 应显示 29.9.1
docker info | grep -A2 "Registry Mirrors"      # 应看到你的 *.mirror.aliyuncs.com（阿里云专属首位）
mkdir -p ~/devops-day1 && cd ~/devops-day1
```
> 若 `Registry Mirrors` 为空/含第三方死源(xuanyuan/daocloud/nju)/公共 `mirror.aliyuncs.com`，先改 `/etc/docker/daemon.json` 只留实例专属地址并 `sudo systemctl restart docker`，否则 `FROM` 报 **not found**。

### 5.2 写 Java（Spring Boot）多阶段 Dockerfile
`java-demo/Dockerfile`：
```dockerfile
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
RUN mkdir -p /root/.m2 && printf '%s' \
  '<settings><mirrors><mirror><id>aliyun</id><mirrorOf>central</mirrorOf><name>aliyun maven</name><url>https://maven.aliyun.com/repository/public</url></mirror></mirrors></settings>' \
  > /root/.m2/settings.xml
COPY pom.xml .
RUN mvn dependency:go-offline -q
COPY src ./src
RUN mvn package -DskipTests -q
FROM eclipse-temurin:17-jre-alpine AS runtime
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
USER 1000
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app.jar"]
```
```bash
cd java-demo && docker build -t day1-java . && docker images day1-java --format "{{.Size}}  java"  # 期望 150–200MB
```

### 5.3 写 Go 多阶段（压到 scratch）
`go-demo/Dockerfile`：
```dockerfile
FROM golang:1.26.0 AS build
ENV GOPROXY=https://mirrors.aliyun.com/goproxy/,https://goproxy.cn,direct
ENV GOSUMDB=sum.golang.google.cn
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /bin/app .
FROM scratch
COPY --from=build /bin/app /bin/app
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
USER 65532:65532
EXPOSE 8080
CMD ["/bin/app"]
```
```bash
cd go-demo && docker build -t day1-go . && docker images day1-go --format "{{.Size}}  go"  # 期望 10–30MB
```

### 5.4 推 ACR 个人版（必须用 buildx 关 provenance）
```bash
echo '你的ACR访问凭证固定密码' | docker login --username=学徒321 registry.cn-hangzhou.aliyuncs.com
cd ~/devops-day1/go-demo
docker buildx build --provenance=false --sbom=false \
  -t registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1 --push .
docker pull registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1
```
> 一劳永逸：`echo 'export BUILDX_PROVENANCE=false' >> ~/.bashrc && source ~/.bashrc`。

## 六、成果验证方式
1. `docker images day1-java/day1-go` 体积达目标区间（Java 150–200MB / Go 10–30MB）。
2. `docker run --rm <镜像> id -u` 返回非 0（非 root 生效）。
3. `docker history <镜像>` 最终阶段无 JDK/SDK/编译器。
4. ACR 拉回成功：`docker pull registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1` 不报 manifest 错误。
5. 产出已 `git push`。

## 七、常见坑与排错
- **`not found`(404)**：镜像源坏了（daemon.json 含死源）→ 只留实例专属地址 + restart docker（坑8/16）。
- **`oci.empty` 拒收**：Docker 29 默认附 provenance → 必须 `buildx --provenance=false --sbom=false --push`（坑18）。
- **Go scratch panic**：漏 `CGO_ENABLED=0` 或需出网没带 `ca-certificates.crt`。
- **`insufficient_scope`**：ACR 命名空间/仓库未建或登录态错位（坑23）。
- **超时**：语言级包源未配国内镜像（见 `day1-evening-practice.md` §0.5）。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：你们镜像这块做过什么优化？（60–75 秒逐字稿）
> "我接手的时候，流水线里 Java 镜像平均 A，单次构建 6 分钟左右，推送还要 3–4 分钟。我做了三件事。
> 第一，**多阶段构建**：builder 阶段用 maven 镜像编译，runtime 只留 `jre-alpine`，用 `COPY --from` 只搬 jar，编译工具链一点不进最终镜像。
> 第二，**依赖分层缓存**：先 `COPY pom.xml` 跑 `dependency:go-offline`，再 COPY 源码。这样改业务代码不会击穿依赖缓存，单次构建从 6 分钟压到 1 分 40。
> 第三，**基础镜像统一治理**：所有服务钉到 alpine/slim 并锁 digest，禁止 `latest` 上生产，同时容器内统一非 root。
> 结果：Java A→B，Go 服务用 scratch 做到 V，CI 整体从 T1 降到 T2，ACK 节点拉取流量明显下降。"

### 追问应对（准备好被连着问 3 层）
| 追问 | 你的回答（要点，别背成念稿） |
|---|---|
| Go 怎么能做到 V？ | "`CGO_ENABLED=0` 静态编译，`-ldflags='-s -w'` 去符号表和调试信息，最终 `FROM scratch` 空基础镜像，只放二进制 + CA 证书。" |
| scratch 里没有 shell，出问题怎么排查？ | "平时同时构建一个 `-debug` 变体（同一二进制 + alpine + busybox），生产用 scratch；应急还能 `kubectl debug` 挂临时容器进 Pod 网络排查。两条路都有，不会因为没 shell 就瞎。" |
| 非 root 起不来 80 端口怎么办？ | "容器内监听 8080，不用特权端口，Service 把 80 映射到 8080。这样不需要 `NET_BIND_SERVICE`，安全上下文最干净。" |
| 为什么不直接用 distroless？ | "distroless 更彻底，但调试成本高、团队接受度低。我的取舍是：对等保/医疗这类合规硬的场景用 distroless 或 scratch，普通业务用 alpine 收敛即可，先保证能落地。" |
| 镜像漏洞扫出来一堆 HIGH 怎么处理？ | "Trivy 进 CI 门禁，CRITICAL 阻断合并、HIGH 出报告不阻断；基础镜像统一走升级通道，每月跟一次 patch tag，而不是每个服务各自升。" |
| alpine 的 musl 有没有踩过坑？ | "踩过——某些依赖 glibc 的 native 库在 alpine 上会崩。这种情况我换 `-slim`（debian 系）而不是硬改，选基础镜像要跟业务技术栈对齐，不能一律 alpine。" |

### 数字锚点（背这 5 个，别多背）
`A → B`｜`Go V`｜`构建耗时明显下降`｜`CI T1→T2`｜`拉取流量明显下降`

### 禁忌（说了就掉分）
- ✗ "用 alpine 就行" —— 会被追问 musl/glibc 差异，答不出就是背话术。
- ✗ "我们镜像不大，没统计过" —— 没有基线数字等于没做过。
- ✗ 把多阶段说成"删掉缓存" —— 暴露只懂 `docker system prune`。
