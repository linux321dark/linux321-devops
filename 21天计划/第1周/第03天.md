# 第 03 天 · K8s 网络 Service / Ingress / Secret

## 一、今日目标（结论先行）
用 Service（ClusterIP/NodePort/LoadBalancer）+ Ingress 打通集群内外访问，用 ConfigMap/Secret（含 External Secrets 接 KMS 思路）管配置与密钥——对应行业B"故障治理"与行业A"多环境一致性"。

## 二、企业真实需求背景
- **行业B**："故障治理、容量管理、告警治理、可观测性"——服务发现与流量入口是故障治理第一环。
- **行业A**："多环境一致性"——配置/密钥管不好，dev/prod 串环境是高频事故源。
- 本地民企合规趋严：密钥硬编码进镜像/ConfigMap 是**等保红线**，须走 External Secrets Operator 接 KMS/Vault。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜一条请求到底怎么进到 Pod（这是面试最常被要求画图的题）
本地民企的标准链路（以 ACK 为例）：

```
用户 → 域名(DNS) → 云 SLB / ALB Ingress → Ingress Controller(nginx/ALB) → Service(ClusterIP)
     → kube-proxy/ipvs → Pod(8080) ；Pod 之间互调走 Service DNS（东西向）
```

每一跳对应一个你能落地的职责：
- **DNS**：域名解析到 SLB，HTTPS 证书在哪挂（SLB 还是 Ingress）。
- **Ingress**：多域名/多路径路由规则、限流、灰度权重（金丝雀通常在这一层切流）。
- **Service**：ClusterIP 提供稳定虚拟 IP，Pod 重建 IP 变了也不影响调用方。
- **Endpoint/EndpointsSlice**：Service 靠 selector 自动维护后端 Pod 列表，**Pod 没 Ready 就不进 Endpoint**——这是"为什么 502"的第一排查点。

### 场景 B｜真实事故现场（K8s 网络/配置的坑最集中在这五类）
1. **`404` 但 Pod 明明活着**：Ingress 没装 Controller（只 apply 了 Ingress 资源，没人执行）、或 `ingressClassName` 写错、或 `pathType` 用了 `Exact` 匹配不上。排查顺序：Controller Pod 是否 Running → `kubectl get ingress` 有无 ADDRESS → `kubectl describe ingress` 看 Events → Controller 日志。
2. **`503` / 后端全不通**：Service 的 selector 和 Pod label 对不上，Endpoint 为空。`kubectl get endpoints <svc>` 一看就清楚。
3. **跨命名空间调不通**：写了 `http://user-svc` 而不是 `http://user-svc.other-ns.svc.cluster.local`，DNS 只在同 ns 内补全。
4. **密码进了 Git**：研发 `kubectl create secret ... -o yaml` 直接提交，base64 只是编码不是加密，`base64 -d` 秒还原。**这是等保测评的必查项，也是真实高频事故**（审计一看 Git 历史就命中）。
5. **dev 环境的配置打到 prod**：ConfigMap 同名不同 ns 混用，或镜像里打包了 `application-prod.yml` 被误用。正确做法是"配置全部外部化 + 环境由部署清单注入"。

### 场景 C｜面试官的真实痛点
- **行业B"故障治理"**：他们要的是"给你一个 502，你 3 分钟内定位到是 Ingress 还是 Service 还是 Pod"，不是背 Service 三种类型。
- **行业A"多环境一致性"+"等保合规"**：密钥不能进 Git、不能进镜像，且要能审计"谁在什么时候取了什么密钥"。这就是 External Secrets + KMS 的动因——**不是为了炫技，是为了过测评**。
- 面试官会追问的一句：**"你们密钥怎么管的？"** 答"放 ConfigMap 里"直接出局。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 密钥来源 | 写进 ConfigMap / 打进镜像 / 提交 Git | External Secrets Operator 从 KMS/Vault 拉，Git 里只留 ExternalSecret 声明 |
| 多环境 | 一个 ConfigMap 改来改去 | 每环境独立 ns + 独立 ConfigMap，同名不同值，清单随环境目录分离 |
| 外部暴露 | 图省事用 NodePort 开一堆端口 | 统一 Ingress/ALB 入口，NodePort 只用于临时调试 |
| Service 类型 | 内部服务也用 LoadBalancer | 内部用 ClusterIP，只有入口层用 LoadBalancer/Ingress（每个 LB 都在花钱） |

- **原理**：ClusterIP（集群内）/NodePort（节点端口）/LoadBalancer（云 SLB）/Ingress（七层路由）；Secret 经 base64（非加密！）存储，需配合 KMS 加密 etcd。
- **理论**：服务发现（DNS/kube-dns）；南北向(Ingress) vs 东西向(Service)流量。
- **核心易忘点**：Ingress 需 Ingress Controller（nginx/ALB）；`externalName`；Secret 类型 `Opaque/dockerconfigjson/tls`；跨 ns 访问用 `svc.ns.svc.cluster.local`。
- **横向对比**：NodePort（简单）vs LoadBalancer（云原生、本地用 ACK ALB Ingress）vs Ingress（多域名路由）。
- **常见问题**：Ingress 不生效→Controller 没装/注解错；Secret 明文风险→External Secrets + KMS；跨命名空间访问→Service 域名带 ns。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 三种 Service 类型
```bash
kubectl create deployment web --image=registry.cn-hangzhou.aliyuncs.com/devops-journey/day1-demo:go-v1 --port=8080
kubectl expose deployment web --name web-clusterip --port=80 --target-port=8080 --type=ClusterIP
kubectl expose deployment web --name web-nodeport --port=80 --target-port=8080 --type=NodePort
kubectl get svc web-clusterip web-nodeport
kubectl run client --rm -it --image=busybox --restart=Never -- wget -qO- http://web-clusterip   # 集群内 DNS 解析验证
```

### 5.2 Ingress（装 nginx controller + 路由）
```bash
# 装 ingress-nginx（kind 本地；镜像若拉不动先 export https_proxy=127.0.0.1:7897 或 kind load）
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx -n ingress-nginx --create-namespace \
  --set controller.service.type=NodePort
kubectl get pods -n ingress-nginx

cat > web-ingress.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: web-ingress, namespace: default, annotations: { nginx.ingress.kubernetes.io/rewrite-target: / } }
spec:
  ingressClassName: nginx
  rules:
  - host: demo.local
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend: { service: { name: web-clusterip, port: { number: 80 } } }
EOF
kubectl apply -f web-ingress.yaml
kubectl get ingress web-ingress
curl -H "Host: demo.local" http://<节点IP>:<NodePort>/api   # 外部访问验证
```

### 5.3 ConfigMap + Secret（含 KMS 思路）
```bash
# 多环境配置
kubectl create configmap app-config --from-literal=env=prod --from-literal=log_level=info
kubectl get configmap app-config -o yaml

# 密钥（base64 非加密，仅为演示；生产走 External Secrets）
kubectl create secret generic db-secret --from-literal=password='S3cr3t!' --dry-run=client -o yaml > db-secret.yaml
kubectl apply -f db-secret.yaml
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d; echo

# External Secrets 接 KMS 设计（等保合规，不写进 Git）
cat > externalsecret.yaml <<'EOF'
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: db-secret }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aliyun-kms, kind: ClusterSecretStore }
  target: { name: db-secret, creationPolicy: Owner }
  data:
  - secretKey: password
    remoteRef: { key: kms-db-pass, property: password }
EOF
```

## 六、成果验证方式
1. `kubectl get svc` 三类型均 Ready；`client` Pod 经 ClusterIP 拿到 HTTP 响应。
2. Ingress `ADDRESS` 分配；`curl -H "Host: demo.local"` 命中 `/api` 路由返回 200。
3. `kubectl get configmap app-config` 含 env/log_level；`db-secret` 能 `base64 -d` 还原（演示用）。
4. 画出"前端→Ingress→Service→Pod"流量图，标注 External Secrets 接 KMS 的合规改造点。

## 七、常见坑与排错
- Ingress 注解/Class 配错→404；Secret base64 非加密须配 KMS；跨 ns 服务发现用 `svc.ns.svc.cluster.local`。
- ingress-nginx 镜像来自 registry.k8s.io 国内易卡→`export https_proxy` 或 `kind load`。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：一个请求从外网进到 Pod，中间经过什么？（画图 + 40 秒讲清）
> "域名解析到云上的 SLB 或者 ALB Ingress，七层入口做路由和证书终止；Ingress 按 host + path 把流量分到对应的 Service；Service 是 ClusterIP 的虚拟 IP，靠 selector 自动维护后端的 Endpoint 列表，只有 Ready 的 Pod 才会被挂进去；kube-proxy 用 ipvs 把请求转发到 Pod 的 8080。
> 这套链路的好处是 Pod 重建、IP 变了调用方完全无感。出问题时我按这个顺序反推：Ingress 有没有 ADDRESS → Endpoint 是不是空的 → Pod 是不是 Ready → 最后才看应用日志。"

### 主问 2：密钥怎么管的？（等保场景必问）
> "分三层。第一层，密钥绝不进 Git、不进镜像，Git 里只有 ExternalSecret 这个声明对象，里面写的是 KMS 里的 key 名，不是值。第二层，运行时由 External Secrets Operator 用 RAM 角色去阿里云 KMS 拉值，写进集群内的 Secret，定时 refresh，KMS 侧轮换密码集群自动跟着更新。第三层，审计，KMS 有调用日志，谁在什么时候取了哪个密钥可查，这是等保测评要的证据链。
> 顺手补一句：K8s 原生 Secret 只是 base64 编码，不是加密，etcd 不加密的话拿到备份就等于拿到明文，所以 ACK 上还要把 etcd 的 KMS 加密打开。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| NodePort / LoadBalancer / Ingress 怎么选？ | "内部服务一律 ClusterIP；对外统一走 Ingress（ACK 上就是 ALB Ingress），因为一个 LB 能承载多个域名、共用证书和限流策略；NodePort 只在临时调试或没有 LB 的环境用，它端口范围固定、不好管。" |
| Ingress 配了但 404 怎么查？ | "先确认 Controller 在跑（`kubectl get pods -n ingress-nginx`），再看 `kubectl get ingress` 有没有 ADDRESS，没有就是 Controller 没接管；有 ADDRESS 还 404 就看 `ingressClassName`、`pathType`（Prefix 和 Exact 差别很大）和 rewrite 注解，最后看 Controller 日志里的 upstream。" |
| Service 通但时好时坏？ | "八成是 Endpoint 里混进了没 Ready 的 Pod，或者 readinessProbe 配得太宽松导致流量过早进来。先 `kubectl get endpoints` 看列表，再看探针的 initialDelay 和失败阈值。" |
| 配置热更新怎么做？ | "ConfigMap 挂成 volume 时，kubelet 会异步同步文件，应用要能监听文件变化重载；挂成环境变量则不会更新，必须重启 Pod。所以对需要热更的配置我用 volume + 应用侧 reload，不重要的直接用 env。" |
| External Secrets 挂了会不会把业务搞死？ | "它只负责把值写进集群内 Secret，运行中的 Pod 用的是本地 Secret，Operator 短时不可用不影响存量 Pod。我还会设 `creationPolicy: Owner` 让 Secret 随 ExternalSecret 生命周期走，避免残留。" |

### 数字锚点
`Service 三类型`｜`Endpoint 只挂 Ready Pod`｜`ExternalSecret refresh 1h`｜`Secret=base64≠加密`

### 禁忌
- ✗ "密钥放 ConfigMap / 环境变量里" —— 等保场景直接判不合格。
- ✗ "用 NodePort 暴露给用户" —— 暴露不懂入口层治理。
- ✗ 说不清 404 与 503 的区别（一个是路由没命中，一个是后端没端点）。
