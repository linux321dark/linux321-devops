## 一、每篇的固定骨架（八段，不许少）

```markdown
# Lx · 标题

> **本篇定位**：……（学完能做什么）
> **前置**：L? ……
> **学完能做什么**：……（可验证的动作，不是"理解了"）
> **在 21 天里**：D?（对应哪一天的哪个环节）
> **环境/版本基准**：……（实测值；没有实测就写"以官方文档为准"）
> **配套方法**：[授渔篇] · **来源规范**：[参考索引]

## 0. 知识图谱          ← 树状图，一眼看清本篇分支
## 1. 概念              ← 是什么 / 为什么需要 / 术语表（中英对照）
## 2. 机制              ← 内部怎么工作；关键参数与默认值表
## 3. 动手              ← 最小可运行示例；每步写清"看到什么算对"
## 4. 逐字段表          ← 清单/参数逐项：字段 | 类型 | 必填 | 含义 | 写错的后果
## 5. 横向对比          ← 同一问题的几种解法，给选择依据
## 6. 踩坑与排障        ← 症状 | 状态 | 真实原因 | 怎么修 | 怎么防
## 7. 参考来源          ← 编号来源表（见第三节）
## 8. 自测三问          ← ①输入输出 ②故意改坏再倒推 ③画上下游
```

**附加要求**：
- **第 4 段必须有"写错的后果"这一列**——这是 L1/L2/L0 的共同特征，也是最有价值的部分。
- **第 6 段必须是表格**，五列齐全：`你看到的（症状）| 状态 | 真实原因 | 怎么修 | 下次怎么防`。
- **第 8 段的第 ② 问必须给出具体可执行的破坏实验**（改哪个字段、会看到什么报错）。

## 二、讲解深度基线（对标尚硅谷教学文档）

| 维度 | 标准 | 达标的样子 |
|---|---|---|
| **概念** | 先讲"为什么需要它"，再讲"它是什么" | "没有它会怎样"要能落到具体事故上 |
| **机制** | 讲清内部流程，不是只列名词 | 能画出流程图，能说出每一步失败会看到什么 |
| **清单** | **逐字段**，带类型与写错后果 | `requests.cpu` → 漏写 → HPA `<unknown>/50%`（不报错不告警） |
| **默认值** | 表格列出，并标来源 | `progressDeadlineSeconds=600`、`HPA 缩容窗口=300s` |
| **对比** | 给选择依据，不只列优缺点 | "生产不用 NodePort，因为端口固定易冲突、无健康检查联动" |
| **踩坑** | 报错原文照录 | 用真实报错原文，不用"可能会失败" |
| **面试** | 能讲原理 + 能讲取舍 | "distroless 的代价是没有 shell，排障要靠 kubectl debug" |

**绝对禁止的三种写法**：
1. ❌ "这里需要注意…" / "可能会遇到各种问题" —— **空话，删掉**
2. ❌ 罗列名词不给因果 —— "X 功能强大、Y 灵活、Z 简单"
3. ❌ 假大空结论 —— "能大大提升效率"（提升多少？哪个环节？）

## 三、来源规范（硬约束）

### 3.1 只能用已实测的链接

**所有 URL 必须来自 [`09-参考索引/README.md`](09-参考索引/README.md) 里已标注 ✅ 的条目。**

- 不许自己拼 URL（`docs.docker.com/zh-cn/*` 全是 404 这类坑已经踩过）
- 需要某个具体章节时，**在已验证的页面 URL 后标注章节名**，不要自己造深层链接
- 如果某个知识点确实没有对应的已验证链接 → **在来源表里标 `⚠️ 单源待补`**，并写清缺的是什么

### 3.2 每个知识点 ≥ 2 个来源

- A（官方）+ B（中文）或 C（云厂商）**二者缺一不可**
- 版本敏感的内容必须标版本（如 K8s 字段行为、Helm 3 vs 2、Terraform 1.x）

### 3.3 来源表格式

```markdown
## 7. 参考来源

| 编号 | 类型 | 文档 | 本篇用到的章节 | 访问状态 |
|---|---|---|---|---|
| S1 | 官方 | `kubernetes.io/zh-cn/docs/concepts/workloads/controllers/deployment/` | Deployment 滚动更新策略 | ✅ 2026-10-24 |
| S2 | 官方 | `kubernetes.io/docs/reference/using-api/` | 字段语义交叉验证 | ✅ 2026-10-24 |
| S3 | 云厂商 | `help.aliyun.com/zh/ack/user-guide/` | ACK 托管版差异 | ✅ 2026-10-24 |
```

### 3.4 篇目之间的引用：占位一律写真链接

**凡是提到同库其他篇目（无论正文、表格还是「下一篇」），一律写成 markdown 链接**，不要用纯文本：

```markdown
✅ [`L3-镜像仓库与供应链安全.md`](01-基础篇/L3-镜像仓库与供应链安全.md)   ← 读者能点开
❌ `L3-镜像仓库与供应链安全.md`                                        ← 读者按名字找不到
```

**为什么这是硬要求**：纯文本形式的篇目引用**不是链接**，既不会被链接检查发现，也无法点开。规模化写作时它会变成"过期导航"——目标文件改名或改了编号，读者却毫无察觉。**链接会失效，读者至少知道；纯文本会沉默地骗人。**

**写作过程中的常见来源**：先写"待写"的占位、后补正文时忘了改成链接。收尾检查用验收脚本的「过期导航」项（会扫反引号包裹的 `.md` 纯文本引用，并排除已经是链接的写法）。

### 3.5 冲突处理

中文来源与官方冲突时：**以官方为准**，正文写一行标注「中文来源说 X，官方为 Y，以官方为准」。

## 四、数据纪律（最高优先级）

| 规则 | 说明 |
|---|---|
| **不编数字** | 体积、耗时、默认值、端口范围、样本量——**要么实测，要么标"官方文档标称"** |
| **不编报错** | 报错原文要么实测，要么标「典型报错（来自官方 issue/社区）」，不许自己编 |
| **不编命令输出** | 不许写"输出应该是 xxx"这种想象出来的结果 |
| **不确定就留空** | 拿不准的写 `⚠️ 待验证`，并在文末列"待验证清单" |
| **版本要对齐** | 本地是 v1.37，文中就不要引用 v1.26 的行为差异当默认 |

**允许做的实测**：读取本机已有资源（`docker images` / `docker history` / `kubectl get` / `kubectl explain`），**不新建环境、不拉新镜像**。

**禁止做的实测**：拉取新镜像、创建容器/集群、修改用户已有资源。

> 理由：写文档不需要动环境；改环境会污染用户的实验环境且可能引入网络等待。

## 五、跨篇一致性（避免自相矛盾）

| 项 | 统一口径 |
|---|---|
| K8s 版本 | 本地实测 v1.37.x；引用行为差异时必须标版本 |
| 市场数据（版本采用率等） | **只回官方发布说明 / 社区实测**，禁引报告聚合站 |
| HPA 公式 | `期望副本数 = ceil(当前副本数 × 当前利用率 / 目标利用率)` |
| HPA 分母 | `requests.cpu`（省略时退化为 limits，两者都不写则无分母） |
| QoS 三档 | BestEffort → Burstable → Guaranteed（驱逐顺序） |
| 探针语义 | liveness 失败→重启；readiness 失败→摘出端点**不重启** |
| 缩容窗口 | `scaleDown.stabilizationWindowSeconds` 默认 **300s**，扩容默认 0 |
| 优雅停机 | shell 形式 ENTRYPOINT 不转发 SIGTERM → 必须 exec 形式 |
| 本地环境 | kind 集群名 `day2`，节点 `day2-control-plane`，镜像仓库 `registry.cn-hangzhou.aliyuncs.com/linux321-devops/` |
| **面试话术里的数字** | **必须与简历原文逐字一致**（N+ 仓库 / M+ 次 / K+ 起 / T1→T2 / S+ 台 / 配置类故障显著下降）。**教学资料里的实测值（如 D1 镜像 A、B）不得写进话术**——那是学习过程产物，不是项目成果，混用会被面试官当场问住 |
| **两套数字的关系** | 简历口径 = 项目成果（可对外讲）；实测口径 = 教学演示（只在教材与截图里出现）。**两者可以同时存在，但同一句话里不许混用** |

### 校验脚本（提交前必跑）

**唯一权威实现是 [`00-验收脚本.py`](00-验收脚本.py)。不要在别处再复制粘贴脚本副本**——两份实现一旦漂移，验收数字就不可信（本次重构中就出现过「规范内嵌版」与「独立版」给出不同结果的情况）。

```bash
cd "/Users/dengzz/Desktop/学习简历/21天计划"
python3 00-验收脚本.py                            # 全量验收
python3 00-验收脚本.py 02-K8s核心 05-可观测性      # 只验指定目录
```

它一次性检查 7 项：

| # | 检查项 | 判据要点 |
|---|---|---|
| 1 | **表格列数一致性** | 列分隔符数 = 去掉**转义竖线 `\|`** 后剩余的裸竖线数。**代码段内的裸竖线照样切列**（GFM 规范要求转义），见第六节 bug 5 |
| 2 | **内部链接有效性** | 只认真链接 `[文字](路径)`；**先剔除 ``` 围栏代码块**（块内是示例文本，不是链接） |
| 3 | **未登记外链** | 只扫「## 7. 参考来源」段内的 URL；正文示例里的地址（maven 镜像、127.0.0.1 等）不算 |
| 4 | **八段骨架** | `## 0.` 到 `## 8.` 齐全且顺序一致；**只检查 `L+数字` 命名的教材篇目**（`baseline/` 下的可填模板不是教材） |
| 5 | **来源表格式** | 第 7 段存在且含「访问状态」列 |
| 6 | **模糊词** | 问题级：`大概` / `也许` / `大致上`（**提示级**：`应该是` / `差不多` / `估计`，不判失败）。**引述豁免**：被成对引号或反引号包裹时判为引用反例，不报错 |
| 7 | **过期导航** | 扫反引号包裹的 `.md` **纯文本**引用（先剥掉 markdown 链接语法与围栏代码块），同目录不存在即报——**这类问题链接检查抓不到，读者却按名字找不到文件** |

> **写完必须用构造用例回归**（见下方回归用例段）：造一个含「代码块里的假死链 / 假表格 / 假引用」+「真链接」+「真过期导航」的测试篇，要求前三项各报一次、真链接不误报。
> **校验脚本会把"示例"当"真实内容"、把"真链接"当"过期占位"，两头抵消后会给出虚假的 0**——数字不可信时，先怀疑脚本。


> **本脚本自身的五个已修 bug（2026-10-24 晚）**：
> 1. **原守卫 `if "](" in name: continue` 永远为假**（general-purpose-3 修）——`name` 是正则捕获的**反引号内部**内容，而链接语法里的 `](` 在反引号**外面**，所以这个判断恒为 False。**后果：真链接（反引号包裹篇目名 + 紧跟 `](` 路径）被误报成"过期纯文本占位"。** 正确判据是看**反引号右边界之后**是否为 `](`。
> 2. **未剔除 ``` 代码块**（general-purpose-3 修）——`00-写作规范.md` 第 89 行的**规范示例本身**在代码块内（渲染后不是链接），却被当成真链接参与死链统计，产生误报。
> 3. **表格脚本未剔除转义竖线 `\|`**（general-purpose-9 修）——Markdown 表格里 `\|` 是表示字面 `|` 的**标准正确写法**，原脚本直接 `l.count("|")` 会把它算成列分隔符，**误报 `01-基础篇/L0` 等正确写法为"表格异常"**。正确做法是先 `l.replace("\\|","")` 再计数。**注意：这类要改的是脚本，不是文档**——把 L0 改掉反而会破坏正确写法。
> 4. **表格脚本错误地剥离了反引号代码段**（general-purpose-3 修）——**这一条是上一条的反面，也是本轮最容易犯的"想当然"**。当时的假设是"GFM 渲染时 cmark 先剥离代码段再切分，所以代码段内的竖线不算列分隔符"。**这个前提是错的**，GFM 规范（Tables 扩展）原文是：
> > "Include a pipe in a cell's content by escaping it, **including inside other inline spans**"
> > 配套示例：\| b `\|` az \| → \`<td>b <code>|</code> az</td>\`
>
> **即：代码段内的竖线照样切列，必须写成 `\|` 才能留在格子里。** 已用 **GitLab 自己的渲染器**（`api.github.com/markdown`，`mode=gfm`，即 GitHub 用的 cmark-gfm）实测对照：转义 `\|` → 第三格完整；不转义 → 第三格被截断成 \`` `{{ .Values.tag ``\`，**模板语法断裂、整表错位**。
> **后果**：错误地剥离代码段 → 少算分隔符 → **把"代码段内未转义竖线"这个真 bug 当成没问题放过去**（`04-交付与GitOps/L1-Helm-模板化封装.md` 因此有 18 行表格在 GitHub 上渲染错位）。**修法：回到 GFM 规范——只剔除 `\|`，不剥离代码段。**
> **教训**：**"判据必须与渲染器一致"这句话是对的，但"与渲染器一致"不等于"我想当然的模型"。** 这次的错误前提是"先剥离代码段"，而规范说的是"代码段内也要转义"。**唯一能定案的方式是拿渲染器本身验证**——`pandoc -f gfm` 或 GitHub 的 markdown API 都行，**别靠推理定判据**。
>
> **回归用例（改脚本后必须逐条验，防"修好一个坏掉另一个"）**：
> ```
> | a | b | c |                                  → 3 列
> | a | `x \| y` | c |                          → 3 列（转义竖线不算）
> | a | `{code=~"200|201"}` | c |                → 3 列（代码段内竖线不算）
> | a | b |                                      → 2 列（真的少一列，要能抓到）
> | a | b | c | d |                              → 4 列（真的多一列，要能抓到）
> | a | `x` 和 `y|z` | c |                       → 4 列（代码段内裸竖线照样切列 —— GFM 规范要求转义）
> ```
>
> ⚠️ **断言时注意口径**（general-purpose-3 实测踩过一次）：脚本的 `ncols()` 返回的是**分隔符数**，不是列数——`分隔符数 = 列数 + 1`（首尾各一个边界竖线）。**同一张表所有行的分隔符数相等，所以用它互相比对与用列数互相比对完全等价**，脚本逻辑没问题；但如果你照着用例写 `assert ncols(line) == 3` 会**全部失败**（实际是 4）。**要么断言分隔符数，要么在期望值上 +1，别混用。**
>
> **教训**：**校验脚本本身也会有 bug，会误报。** 看到"死链"或"表格异常"先问一句"**这是真问题还是脚本误报**"——**和索引第 1b 条是同一条方法论：断言某物是问题之前，先确认它到底是不是问题。** 修脚本优先于改文档，除非文档确实写错了。
>
> **推论**：**改完校验脚本，必须补一组回归用例。** 本轮四个 bug 里有三个是"脚本把正确写法判成错误"，如果只跑全库看"还有没有报错"，无法区分"修好了"和"把真问题也一起藏起来了"。
>
> **推论二（2026-10-24 晚，general-purpose-9）**：**脚本自己的运行输出也必须干净。** 本轮 `00-验收脚本.py` 出现两类警告：
> - `SyntaxWarning: invalid escape sequence '\|'`——docstring 里的 `\|` 被 Python 当无效转义序列，**每次跑都刷一条**；
> - `ResourceWarning: unclosed file` × 74——`io.open(...).read()` 未关闭文件句柄（`-W all` 下才可见）。
>
> 两者都不影响功能，**但会让真正重要的警告被淹没**——这违背了"脚本输出要可信"的初衷。**验收脚本自己刷警告，等于让狼来了没人喊。** 修法：docstring 用 `r"""..."""` raw string；文件读取一律用 `with io.open(...) as f:`。**现在 `python3 -W all 00-验收脚本.py` 的警告数为 0。**
>
> **推论三（2026-10-24 晚，general-purpose-3）**：**脚本报了问题 ≠ 验收会失败——退出码才是 CI 看的那个数。**
> 本轮实测：`00-验收脚本.py` 的 `return` 只看 `total_issues`（教材篇目），**共享文件（`00-*.md` / `09-参考索引`）的 `shared_issues` 只被 print、没进退出码**。
> **后果**：共享文件被并发编辑搞坏时（例如本轮「跨篇一致性」表格被交叉插入挤错列数），**脚本报出了、但退出码仍是 0**——CI 判定"通过"，损坏留在原地，下一个读第五节口径表的人读到的是错位的表格。
> **这正好补上了前面那句话的另一半**：「跑一遍规范自身的三脚本复核」是**人工纪律**（靠人记得跑）；**把共享文件的问题计入退出码**才是**机制保障**（靠脚本自己挡住）。**人工纪律会被忘记，机制不会。**
> **修法**：`return 0 if (total_issues + shared_issues) == 0 else 1`，并把合计行拆成「教材 N + 共享文件 M」。
> **验证方式（构造用例回归）**：往 `00-写作规范.md` 的口径表里**故意插一行少一列的脏行** → 脚本报出该行且**退出码变为 1** → 撤掉脏行 → 退出码回到 0。**没有这个构造用例，就无法区分"退出码真的会挡住"和"我只是改了个数字"。**
>
> **推论四（2026-10-24 晚，general-purpose-9）**：**读-改之间有窗口——共享文件被并发编辑时，"我 Read 完准备 Edit"到"实际写入"之间，别人可能已经改过同一处。**
> 本轮实测两例：① 我 Read `00-验收脚本.py` 后、Edit 前，第 49 行的 `"""` 已变成 `r"""`（有人先改了）；② 有人往「本地环境」这一行**中间**插入两行新内容，把原行内容挤到新行末尾，**跨篇一致性表被挤成 3 列**——两边都以为自己在追加。
> **两条纪律**：
> 1. **改共享文件前先看 mtime**（`ls -lT <file>`），若与自己上次读的时间不符，说明期间有人改过 → **重新 Read 再改**；
> 2. **改完共享文件立刻读回自己写的那一段**（不要只信 Edit 返回成功），并跑一遍 `python3 00-验收脚本.py`——**现在共享文件损坏会直接让退出码变 1（推论三），不再依赖人记得复核**。
>
> **推论五（2026-10-24 晚，general-purpose-9）**：**「共享文件有问题」要区分"真问题"与"待写篇目的正常等待"。**
> 例如 `L9-安全RBAC与合规.md` → `L10-排障方法论.md` 的死链：**L10 是待写篇目，链接等它落盘正是"占位一律写成真链接"的设计意图**，不是缺陷。**修链接前先问"这个目标是待写还是写错了名字"**——把待写链接改成纯文本占位，反而会退回"静默腐烂"的老问题。
> **判据**：目标文件在 `00-学习地图与前置依赖.md` 的目录规划里 → 是待写，**保留链接**；不在规划里 → 才是写错了名字，要改。
