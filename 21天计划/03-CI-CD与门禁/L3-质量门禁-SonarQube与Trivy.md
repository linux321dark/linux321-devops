## 1. 概念

### 1.1 门禁的定义

> **一句话**：质量门禁是**一个能判定"这次变更是否达标"的自动化检查，并且它的结论会改变流水线的走向**。

拆成两个必须同时成立的要件：

| 要件 | 含义 | 缺了会怎样 |
|---|---|---|
| **① 有判定** | 有一组事先写死的**条件**（阈值、规则集、严重级别） | 变成"扫完给个报告"——报告给人看，人可以不看 |
| **② 有阻断** | 判定不通过时，**后续流程不执行** | 变成"告警"——事情照做，只是有人收到一条消息 |

**只有①没有②，叫"扫描"；只有②没有①，叫"拦路"。** 真正的门禁是"按事先定好的条件，自动地拦路"。

这一条区分在面试里很值钱，因为大量候选人会把"我们接了 SonarQube"说成"我们有质量门禁"。**接了工具 ≠ 有门禁。** 有门禁的判定标准只有一条：

> **把阈值调到"必然不通过"，这次变更还能不能发出去？**
> 能发出去 → 你没有门禁，你有一个仪表盘。

### 1.2 三种门禁形态（成熟度从低到高）

| 形态 | 结论去哪 | 谁看 | 阻断力 | 典型实现 |
|---|---|---|---|---|
| **报表** | Web UI / 邮件 | 没人主动看 | ❌ 无 | 每周导出一次质量报告 |
| **告警** | 钉钉 / 企微机器人 | 值班同学 | ⚠️ 弱（依赖人响应） | `when: on_failure` 推一条消息 |
| **阻断** | **流水线状态** | 机器 | ✅ **强** | 扫描 job 退出码非 0 → 后续 stage 不跑 |

**三种形态不是替代关系，是叠加关系**：阻断是底线，告警是阻断之后的补充通知。

> **一个真实事故**：某团队接了 Trivy，扫描结果推送到群里，开发同学收到消息看一眼，回复"这个我知道了"，然后照常发布。**从合规角度看，这套扫描等于没做**——因为漏洞从未被阻止进入生产，且没有留下"被阻止过"的记录。**等保测评要的是后者。**

### 1.3 术语表（中英对照）

| 英文 | 中文 | 一句话 |
|---|---|---|
| Quality Gate | 质量门禁 | **一组达标条件**，全过才 OK；SonarQube 里的正式概念 |
| Quality Profile | 质量配置 | **一组启用的规则**，决定"哪些问题会被报出来" |
| New Code | 新代码 | 本次变更涉及的代码；**门禁应该卡它，而不是卡全部历史代码** |
| Overall Code | 全部代码 | 项目所有代码，含历史债；**卡它 = 卡死** |
| Issue | 问题 | SonarQube 的问题统称：漏洞 / 缺陷 / 异味 |
| Vulnerability | 漏洞 | 有真实安全影响的问题（SQL 注入、XSS 等） |
| Bug | 缺陷 | 逻辑上一定会出错的代码 |
| Code Smell | 代码异味 | 不会立刻出错，但会埋雷（重复、深层嵌套） |
| Hotspot | 热点 | 安全性存疑但需人工判断的地方（不直接算漏洞） |
| Scanner | 扫描器 | **跑在 CI 里的客户端**，负责拉代码、跑规则、上传结果 |
| SonarQube Server | 服务端 | **长期运行的服务**，负责存结果、算指标、算 Quality Gate |
| Misconfiguration | 配置不合规 | 镜像/编排写错了（如容器跑 root、开了 privileged） |
| SCA | 软件成分分析 | 专门扫**第三方依赖**漏洞的工具类 |
| SBOM | 软件物料清单 | 制品里到底有哪些包/组件的**机器可读清单** |
| SARIF | — | 静态分析结果的**标准化交换格式**，GitHub / GitLab 原生支持 |
| Exit Code | 退出码 | **门禁阻断的物理机制**：非 0 → 进程失败 → job 失败 |
| `allow_failure` | 允许失败 | GitLab CI 关键字；**为 true 时 job 失败不阻断 pipeline** |

## 2. 机制

### 2.1 三道拦截点（本章的骨架）

门禁不是"加一个扫描"，而是在交付链路上**选三个必须拦住的点**。每个点的**拦截对象、判定时机、失败代价**都不一样：

| 拦截点 | 拦什么 | 工具 | 判定发生在 | 拦不住的后果 | 成本（误伤风险） |
|---|---|---|---|---|---|
| **① 代码提交前**（本地） | 格式错误、硬编码密钥、明显 bug | pre-commit 钩子 / IDE | **开发者本机**，秒级 | 无（只是本机检查） | 低——只提示不阻断 |
| **② 代码合并前**（MR 检查） | 新增代码的质量、重复、覆盖率 | **SonarQube** | **CI 里**，分钟级 | 脏代码进主干，全量质量持续恶化 | **高**——卡太严会卡死所有人 |
| **③ 制品发布前** | 镜像里的 CVE、编排配置错误 | **Trivy** | **CI 里，构建产物上**，秒级到分钟级 | 高危漏洞进生产 | 中——存量漏洞会一次性爆雷 |

**为什么是三个而不是一个**：

- **只做①**：能挡住"手滑"，挡不住"不知道怎么写"。
- **只做②**：能挡住代码质量，**挡不住运行时装出来的问题**（基础镜像的 CVE 不在代码里）。
- **只做③**：能挡住制品，**挡不住代码债累积**（覆盖率从 80% 掉到 20% 也没人拦）。

**还有一个第四层——流程层**：生产发布必须打 tag 触发 + 手动审批 + 审批人白名单。**这一层不靠工具，靠流水线规则**，它的产出是**审计记录**（谁在什么时候批的），这是等保测评会查的东西。

> **关键认知**：三层拦截点里，**②最容易失败**。因为它的判定对象是"人写的东西"，误报会直接打到人脸上。**③最容易生效**，因为它判定的对象是"已经构建出来的字节"，没有主观性。**所以真实项目的落地顺序通常是：先把③做硬（无争议），再慢慢调②的阈值。**

### 2.2 SonarQube 的四个组件

```
┌────────────────────────────────────────────────────────────┐
│  ① Scanner（客户端）        ← 跑在 CI 里，**一次性的**        │
│     sonarsource/sonar-scanner-cli                           │
│     职责：拉代码 → 跑分析器 → 跑规则 → 打包 → 上传          │
│     它**不算** Quality Gate                                 │
└───────────────────────┬────────────────────────────────────┘
                        │ HTTP 上传分析结果（.sarif-like 报告体）
                        ▼
┌────────────────────────────────────────────────────────────┐
│  ② SonarQube Server（服务端）← **长期运行**                 │
│     · 接收并存储分析结果                                    │
│     · 计算度量（metrics）：覆盖率、重复率、复杂度            │
│     · 计算 Quality Gate 状态（OK / ERROR）                  │
│     · 提供 API 与 Web UI                                   │
└───────────────┬──────────────────────────┬─────────────────┘
                │                          │
                ▼                          ▼
┌────────────────────────────┐  ┌──────────────────────────────┐
│ ③ 数据库                    │  │ ④ Web UI                     │
│   · 搜索引擎索引（代码、   │  │   · 看问题列表、按文件定位   │
│     规则、度量）            │  │   · 配 Quality Gate 条件     │
│   · 关系型库（项目配置、   │  │   · 看历史趋势               │
│     用户、权限、门禁定义）  │  │   · 看"New Code 趋势图"     │
└────────────────────────────┘  └──────────────────────────────┘
```

**四个组件的分工，一句话各一条**：

| 组件 | 一句话 | 生命周期 | 谁拥有它 |
|---|---|---|---|
| **Scanner** | "**去把代码读一遍并报告问题**" | **一次性的**，每个 CI job 跑一遍就结束 | CI（Docker image 或 runner 里的包） |
| **Server** | "**把结果存起来，算出门禁结论**" | **长期运行**，要 HA、要数据库、要升级维护 | 平台组 / 运维 |
| **数据库** | "**让趋势有历史可查**" | 长期 | 平台组（备份、扩容） |
| **Web UI** | "**人看和改的地方**" | 长期 | 产品 / 架构师改规则与门禁 |

### 2.3 谁产出结果、谁算门禁（本文最重要的一张图）

> **这是很多人对 SonarQube 误解最深的地方，也是面试高频。**

```
Scanner（CI 里跑）
  ├─ 拉代码（scanner 自己管 SCM，或者由 CI 先 checkout）
  ├─ 跑分析器：解析出语法树、符号表、覆盖率数据
  ├─ 跑规则：判断每个规则条件是否命中 → 产出 Issue
  ├─ 跑指标：覆盖率 / 重复行 / 复杂度 / 债务
  └─ 上传结果到 Server  ← **它到这里就结束了**
                                              │
                                              ▼
Server（算门禁）
  ├─ 存结果
  ├─ 关联到分支 / PR
  ├─ 计算 **New Code 范围**（新代码怎么定义 → 见 2.4）
  ├─ 计算 **Overall Code** 范围
  ├─ 按 Quality Gate 上配置的**条件逐条比对**
  │    ├─ 覆盖率 ≥ X？        → 条件 1
  │    ├─ New Issues = 0？    → 条件 2
  │    ├─ 重复率 ≤ Y？        → 条件 3
  │    └─ ...
  └─ 输出 **Quality Gate Status = OK / ERROR**
                    │
                    ▼
CI 侧怎么拿到这个结论？（两条路）
  ├─ 路线 A：scanner 上传完就退出（**默认**）→ CI 什么都不知道 → **门禁形同虚设**
  └─ 路线 B：让 scanner **等** Server 算完，并按结论返回退出码
             （`sonar.qualitygate.wait=true`）→ **门禁真正生效**
```

**结论（务必背下来）**：

> **SonarQube 的 Scanner 只负责"发现问题并上报"，Server 才负责"判定达标与否"。**
> 所以**"扫描器跑完没报错"≠"质量门禁通过了"**。
> 要让 CI 拿到门禁结论，必须让 scanner 显式等待 Server 的判定结果。

**这条机制的直接推论**（也是最常见的"假门禁"）：

| 做法 | 发生了什么 | 结果 |
|---|---|---|
| 只跑 `sonar-scanner`，不配等待参数 | scanner 上传完立刻退出 0 | **门禁只是"打了个分"，流水线照常绿** |
| 配了 `sonar.qualitygate.wait=true` | scanner 等 Server 算完，门禁 ERROR 时退出码非 0 | **门禁真的会挡住 MR** |

> **面试这么答**："SonarQube 是**客户端采集、服务端判定**的架构，scanner 只上报不判定。所以判断一个团队的 SonarQube 是不是真门禁，只看一件事：**MR 检查里 scanner 有没有等 Server 的 Quality Gate 结论，并据此返回非 0 退出码。** 绝大多数团队接了 SonarQube 但没配这个，于是 Quality Gate 永远只是块面板上的红绿。"

### 2.4 Quality Gate 的判定逻辑

**门禁不是"一个分数"，是"一组条件的合取"。** SonarQube 的 Quality Gate 里可以配多类条件：

| 条件类型 | 例子 | 作用 |
|---|---|---|
| **度量条件** | New Code 覆盖率 ≥ 80%、重复行占比 ≤ 3%、复杂度 ≤ 15 | 控"结构性"指标 |
| **问题数条件** | New Issues = 0、New Vulnerabilities = 0、New Code Smells = 0 | 控"增量"缺陷 |
| **热点评审条件** | New Security Hotspots Reviewed = 100% | 强制人去看存疑的安全点 |
| **既有代码条件** | Overall 覆盖率、Overall 漏洞数 | 控"历史债"，**慎用** |

**判定规则很简单**：**所有条件全过 → OK；任意一条不过 → ERROR。**

#### New Code 与 Overall Code 必须分开设条件

这是本节的核心。两种范围：

| 范围 | 定义 | 适合卡什么 | 卡它的风险 |
|---|---|---|---|
| **New Code** | 本次变更涉及的代码。**怎么界定由服务端配置**（按上一版本 / 按最近 N 天 / 按特定分析 / 按参考分支） | **增量质量**：新写的代码必须达标 | 低——存量不影响它 |
| **Overall Code** | 项目全部代码（含历史） | 整体健康度趋势 | **高——历史债永远还不完，门禁必红** |

**为什么 New Code 门禁是防技术债的关键**：

```
时间 ──────────────────────────────────────────────►

Overall 门禁：   ████████████████████████  ← 一条线，永远达不到
                 （历史债 5000 个 issue，只增不减）

New Code 门禁：  ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
                 ██                     ██  ← 锯齿，但基线能守住
                 新代码质量被守住，历史债单独立项慢慢还
```

**算一笔账**。假设一个老项目有 **2000 个历史 issue**（用 SonarQube 的 issue 量级举例，具体数值因项目而异）：

| 门禁口径 | 第一次提 MR 会发生什么 | 团队的理性反应 |
|---|---|---|
| 卡 Overall | 门禁 ERROR，因为 2000 个存量问题永远不会自己消失 | **要求 Leader 关掉门禁** → 门禁彻底失效 |
| 卡 New Code | 门禁只看这次改的那几行，改好了就过 | 继续用，门禁活下来 |

> **这是本文最重要的一条工程结论**：
> **门禁的第一个版本一定要"只卡新代码"。**
> 老代码的债**单独开一个技术债清理项目**，按优先级排期偿还，不要试图让门禁顺便把它还了。
>
> 现实里最常见的失败路径是：老项目接 SonarQube → 门禁全红 → 没人能合并 → Leader 关掉门禁 → 半年后再接 → 又全红 → 又关掉。**门禁不是被技术难死的，是被"全量卡死"这种配置杀死的。**

#### New Code 范围怎么界定

服务端为项目配置 **New Code Period**，常见定义方式（官方提供多选，具体可选项随版本变动，⚠️ 以你所用版本的 Web UI 为准）：

| 定义方式 | 含义 | 适用 |
|---|---|---|
| 按上一版本 | 与上一个版本比较 | 有明确发布节奏 |
| 按最近 N 天 | 时间窗 | 持续交付、每天合并多次 |
| 按特定分析 | 指定某次分析作为基线 | 复杂基线管理 |
| 按参考分支 | 以某分支为基线 | monorepo / 多分支并行 |

**实践建议**：优先用**"上一版本"或"最近 N 天"**，并确保这个定义与团队的合并节奏匹配。**如果定义是"最近 30 天"而团队一天合并 20 次，那 New Code 就几乎等于 Overall Code，门禁又会变红。**

### 2.5 质量维度：六个维度各查什么

| 维度 | 查什么 | 典型规则 | 门禁怎么用 |
|---|---|---|---|
| **漏洞（Vulnerability）** | 有真实安全影响 | SQL 注入、命令注入、路径穿越、XSS、硬编码凭据 | **必卡，New Code 必须为 0** |
| **缺陷（Bug）** | 逻辑上一定会出错 | 空指针、可能的 NPE、资源未关闭、错误的条件判断 | **必卡，New Code 必须为 0** |
| **代码异味（Smell）** | 现在不错，以后会出事 | 重复代码、超长函数、深层嵌套、魔法数字 | **可卡可宽**，多数团队先只告警 |
| **覆盖率** | 测试覆盖了多 | 行覆盖 / 分支覆盖 | **卡 New Code**，阈值按团队现状定 |
| **重复率** | 有多少是复制粘贴 | 重复行占比 | 卡 New Code，阈值不宜高 |
| **复杂度** | 有多难懂、难改 | 圈复杂度、认知复杂度 | **先只告警**，直接卡会引发大量重构噪声 |

**六个维度的优先级（这是策略，不是事实）**：

> **安全类（漏洞）→ 正确性类（缺陷）→ 覆盖率 → 重复率 → 复杂度。**
>
> 前两类是**对错问题**，卡了没人有意见。后三类是**风格与工程效率问题**，卡严了立刻会被绕过。
> **先把前两类做硬，后三类慢慢调。**

### 2.6 规则集与自定义规则

**三层概念必须分清**：

| 概念 | 管什么 | 在哪配 | 谁改 |
|---|---|---|---|
| **Quality Profile（质量配置）** | **哪些规则被启用/禁用** | Web UI | 架构师 / 技术负责人 |
| **规则集（Rule Set）** | 一批规则的集合（如各语言默认规则集） | 随版本分发 | 官方维护 |
| **Quality Gate（质量门禁）** | **达标条件**（阈值） | Web UI | 架构师 / 技术负责人 |

**顺序很重要**：规则决定"报什么问题"，门禁决定"报了就一定挂"。**关掉一条规则 = 从源头减少误报**，比调门禁阈值更精准。

**自定义规则的三条现实路径**：

| 路径 | 怎么实现 | 适合什么 | 代价 |
|---|---|---|---|
| **改 Quality Profile** | 在 Web UI 里把某条规则设为不适用（`Won't Fix` / `Not a Bug`） | 误报规则、框架特有的噪音 | 最低，**优先用这个** |
| **写自定义规则**（Java） | 实现 SonarQube Plugin API，打成 jar 装进 Server | 公司特有的编码规范 | 中，要写 Java + 装插件 + 升级兼容性 |
| **外部规则接入** | 别的工具产出 SARIF，用 Server 的 External Issues 导入 | 已有 SCA / 自研检查 | 低，但**结果不在同一个 Quality Gate 里算**（⚠️ 具体行为随版本变动） |

> **务实建议**：**90% 的"规则太严"问题，用"改 Quality Profile"就能解决，不要一上来就写插件。**
> 写插件意味着：每次升级 SonarQube 都要验证插件、团队里得有人懂 Java 和 SonarQube 插件 API。**这个维护成本远超收益。**
>
> **能讲清"误报应该在哪里解决"，比会写 SonarQube 插件更能体现落地经验。**

### 2.7 Trivy 的两种扫描（两种扫描查的不是一回事）

Trivy 常被当成"镜像漏洞扫描器"，但它至少有两种主用法，**很多人只用了一种，就以为覆盖了安全检查**：

| 维度 | **① 镜像漏洞扫描** | **② 配置合规扫描（misconfiguration）** |
|---|---|---|
| **查什么** | 镜像里**装了哪些包**、这些包有哪些已知 CVE | 编排与镜像的**配置写法**对不对 |
| **扫什么对象** | 镜像 / 文件系统里的 OS 包（rpm/deb/apk）与语言依赖（jar/go/npm…） | K8s YAML、Dockerfile、Terraform、CloudFormation |
| **判断依据** | **漏洞库**（CVE 数据） | **规则库**（策略，如 CIS Benchmark、容器安全最佳实践） |
| **典型发现** | `CVE-2024-xxxxx`，`HIGH/CRITICAL` | 容器以 root 运行、开了 `privileged`、用了 `latest` 镜像标签、缺少资源限制 |
| **官方子命令** | `trivy image` / `trivy fs` / `trivy repo` | `trivy config` / `trivy k8s` |
| **门禁价值** | 挡住**已知漏洞**进生产 | 挡住**危险配置**进生产 |

**这两类必须都做，理由很直白**：

> **漏洞扫描查的是"包里有没有洞"，配置扫描查的是"你会不会被打"。**
>
> 一个 `nginx:latest` 镜像可能**零 CVE**（因为它是刚发布的），但它依然危险——`latest` 意味着**今天和明天是两个不同的东西**，回滚不可复现、行为不可预期。**这类问题只有配置扫描能发现。**
>
> 反过来，一个配置完美但装了 3 年没更新的 `openjdk:8` 的镜像，配置扫描**一条问题都不会报**，但它满是 CVE。**这就是为什么两类扫描是互补的，不是一条。**

**镜像扫描的粒度（跟 L2 的镜像分层直接挂钩）**：

| 层面 | 说明 | 与本套资料的关系 |
|---|---|---|
| **扫的是最终镜像的文件系统** | Trivy 读镜像各层，把所有层的文件合起来看包清单 | 多阶段构建里**被丢弃的 builder 阶段不进最终镜像**，所以**构建期依赖的漏洞不会出现在运行镜像扫描结果里**——这是好事（builder 不上生产），但**别误以为扫描漏了** |
| **层越多 = 扫描面越大** | 层里有包，才有包的 CVE | **A 的 Java 镜像 vs B 的 Go 镜像**：后者基础镜像层几乎没有 OS 包 → **CVE 数量天然低一个量级、扫描也更快**。**镜像瘦身同时是安全收益**，这是 L2 那条结论的延伸 |
| **`scratch` / `distroless` 的特殊性** | 里面几乎没有包 | 扫描结果会很"干净"，但**这不等于安全**——你的应用代码引入的问题 Trivy 不管。**distroless 的安全靠的是"里面没东西可被攻击"，不是"扫描通过"** |

### 2.8 Trivy 漏洞库的更新机制与"库过期 = 结果失真"

**Trivy 不自带漏洞数据**，它从外部拉一个漏洞库（trivy DB）下来再比对。这个设计有好处（库和工具解耦、可离线），也带来一个**必须理解的后果**：

```
Trivy 扫描镜像
   │
   ├─ 读本地缓存的漏洞库（~/.cache/trivy/db/ 之类）
   │    ↑ 这个库是"某一天"的快照
   │
   └─ 比对：镜像里有 libssl 1.1.1k
              │
              ├─ 库里说它有 CVE-2024-XXXX → 报出来（**真阳性**）
              ├─ 库里说它安全        → 不报
              └─ **库里根本没有这条信息** → **也不报** ← ⚠️ 这就是漏报
```

**核心结论**：

> **Trivy 报"没问题"≠"没有问题"。**
> **它只说"我手上的这张库里没有记录"。**
> **库过期 = 扫描结果失去意义**，尤其是"镜像里有个昨天刚披露的 0day"这种情况——库里没有，就查不出来。

**更新机制（官方标称行为）**：

| 机制 | 说明 |
|---|---|
| **按需更新** | Trivy 运行时检查本地库是否需要更新，需要就从远端仓库拉取 |
| **缓存到本地目录** | 拉下来的库存到缓存目录，供后续扫描复用（**这既是性能优化，也是"库会过期"的根源**） |
| **两个库** | ① 通用漏洞库（OS 包 + 部分语言依赖）；② **Java 专用库**（分析 jar 内部依赖，需要单独的 DB）。**只更新通用库会导致 Java 依赖扫不全** |
| **可配置远端仓库** | 通过环境变量把库仓库指到内网镜像（**国内 CI 必做**，否则拉库会超时） |
| **离线模式** | 完全不联网，只用本地库（内网/涉密场景） |

**更新频率的取舍**：

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **每次扫都更新** | 每次跑 Trivy 前拉最新库 | 最准 | **慢**（拉库是大头）、网络不稳就失败 |
| **CI 里缓存库 + 定时更新** | 缓存目录持久化，每天/每次流水线刷新一次 | 平衡 | 库有"最长一天"的滞后 |
| **完全离线** | 预置库文件 | 可控、稳 | **滞后更大**，必须自己保证更新节奏 |

> **务实的做法**：CI 里用**持久化缓存目录** + **在流水线开始时更新一次**（或每天第一个 job 更新），**不要每个扫描 job 各更新一次**——那是同一份数据拉 N 遍。
>
> **另外：库更新失败时必须让扫描"失败"而不是"跳过"**。很多配置里 `skip-db-update` 一开就忘了配更新任务，结果 CI 半年都用同一份库，扫描结果早就没有参考价值了，而且**没有任何报错**——因为"扫完了，没问题"。**这是最隐蔽的假安全。**

### 2.9 SBOM：把制品内容变成可留档的证据

**SBOM（Software Bill of Materials，软件物料清单）= 一份机器可读的"这个制品里到底有什么"的清单。**

| 关注点 | 没有 SBOM | 有 SBOM |
|---|---|---|
| 出了 CVE，问"我们受影响吗" | **挨个仓库翻** | **对着 SBOM 查** |
| 监管方要证据 | **说不清** | **直接交清单** |
| 两个版本的差异 | 靠人肉 diff | **机器 diff** |
| 供应链审计 | 靠信任 | 有据可查 |

**在 Trivy 里怎么生成**：

| 方式 | 命令 | 产物 |
|---|---|---|
| **按 SBOM 格式导出** | `trivy image --format cyclonedx --output sbom.cdx.json <image>` | CycloneDX 格式 SBOM |
| **SBOM 子命令** | `trivy sbom <image>`（⚠️ 官方文档标称的子命令，具体形态随版本变动，**以你版本 `--help` 为准**） | SBOM |
| **用已有 SBOM 再扫** | `trivy sbom sbom.cdx.json`（⚠️ 参数形态随版本变动，以 `--help` 为准） | 以 SBOM 为输入的扫描结果 |

**SBOM 格式（官方支持的两种主流）**：

| 格式 | 特点 |
|---|---|
| **CycloneDX** | 轻量、工具链友好，Trivy 默认导出这个 |
| **SPDX** | 更早的 License 治理标准，合规场景常见 |

> **必须点破的一个区分：SBOM 不是"扫描报告"，是"资产清单"。**
>
> | | 扫描报告 | **SBOM** |
> |---|---|---|
> | 回答什么 | **现在有什么问题** | **里面有什么** |
> | 会不会过期 | **会**（漏洞被修复、版本升级，报告就旧了） | **不会**（清单描述的是"这个制品由哪些东西组成"，是**事实**） |
> | 用途 | 一次性的风险判断 | **持续检测的输入** |
>
> **所以「SBOM + 漏洞库 = 持续检测能力」**：
> **有了 SBOM，新披露一个 CVE，拿它一查就知道自己受不受影响**——**不用重新扫一遍全世界的镜像**。
> **而这个能力的前提是 SBOM 一直在维护**：出了新版本就出新 SBOM，**只生成一次就扔掉的 SBOM 很快就过期了**，和扫描报告一样没用。
>
> **D5 日课里的等保场景，SBOM 就是"证据链"**：
> **"发现 → 整改 → 复测"** 三段里，第一段的证据是扫描报告，第三段的证据是复测记录，**中间那段"这个制品里到底有什么"就是 SBOM**。
> 测评师问"你怎么证明这个上线镜像里只有你审过的那 300 个包"，答案不是"我们扫过了"，而是"**这是随制品一起归档的 SBOM，版本号、哈希、时间戳都在**"。

### 2.10 报告输出格式

| 格式 | 用途 | 谁消费 |
|---|---|---|
| **`table`（默认）** | **人看**。CI 日志里直接可读 | 开发者 |
| **`json`** | **机器消费**。接内部平台、看板、归档 | 脚本 / 平台 |
| **`sarif`** | **代码平台原生支持**（GitHub Code Scanning、GitLab SAST 报告）。结果直接显示在代码 diff 上 | 平台 |
| **`template`** | **自定义模板**（Go template 语法），可以做成固定格式的通知 | 告警脚本 |
| **`cyclonedx` / `spdx-json`** | **SBOM 输出** | 合规归档 |

**选型的实操口径**：

> **CI 日志给人看用 `table`（默认，别改）；要归档和接平台用 `json`；要塞进代码评审界面用 `sarif`。**
> `template` 是**做告警消息**时用的——把格式定死，脚本直接 POST 到钉钉/企微，不用再写一遍解析。

**报告必须作为 artifact 留存**：

| 只在日志里 | 归档成 artifact |
|---|---|
| 日志会滚动、会过期、会被新一次运行覆盖 | 按保留期保存（**常见做法：90 天**，具体按合规要求定） |
| 出了事想查"上个月那次扫描发现了什么" → **查不到** | 可查、可导出 |
| 测评师要看证据 → 现场手忙脚乱 | 直接导出 |

> **但要说清 artifact 的边界：它只用来传"报告类"的东西——扫描报告、测试报告、覆盖率、SBOM、诊断日志。**
>
> **镜像本身不要走 artifact，要走镜像仓库。** 原因有三：
> ① **artifact 有保留期，会过期**——而镜像仓库里的版本要长期可回溯；
> ② **artifact 是一份打包文件，没有 digest 这种不可变引用**——你没法用"内容哈希"精确指认"就是这一版"；
> ③ **只有镜像仓库里的产物才能被 Trivy 扫、能被签名验签、能按 label 追溯来源**。
>
> **顺带分清一对最容易混的东西：artifact ≠ cache。** 这是两类完全不同的故障：
>
> | | **cache（缓存）** | **artifact（制品）** |
> |---|---|---|
> | 干什么 | **加速下次运行**（依赖、构建产物、工具链） | **把结果传出去**（报告、覆盖率、SBOM） |
> | 丢了会怎样 | **慢**，但结果正确 | **东西没了**——报告丢了 = 证据没了 |
> | 有保留期吗 | 按缓存策略，通常较短 | **有明确的 `expire_in`，且默认会过期** |
> | 跨 job 共享 | ✅ 通常共享 | ✅ 共享，但**受保留期限制** |
> | 谁负责 | CI 的**缓存助手**（只管缓存，不管制品） | CI 的**制品机制**（只管传输，不管加速） |
>
> **一句话**：**"缓存不命中"是慢的问题，"制品拿不到"是丢的问题——排障方向完全不同。**
> **扫描报告属于 artifact 不属于 cache**：它不是"加速用的"，它是"要留证的"，**按 cache 存就一定会过期消失**。
>
> **一句话**：**artifact 传"这次运行的观测结果"，镜像仓库存"这次运行的交付物"。** 门禁扫的是交付物，所以交付物必须在仓库里——**这正是 `push` 必须排在 `scan` 之后、且扫描对象是构建产物的另一个理由。**

### 2.11 阻断是怎么发生的：退出码 → job 失败 → stage 不执行

**这是"有门禁"和"没门禁"的物理分界线。** 完整链路：

```
① 扫描工具发现问题
       │
       ▼
② 工具以**非 0 退出码**结束
   （Trivy: --exit-code 1；SonarQube: 门禁 ERROR 时 scanner 等待后返回非 0）
       │
       ▼
③ CI 看到 job 退出码非 0 → **job 标记为 failed**
       │
       ▼
④ 流水线按"后续 stage 默认依赖前面全部成功"的规则
   → **后续 stage 不执行**（deploy 不跑）
       │
       ▼
⑤ 合并请求被标记为"检查未通过"（如果 CI 集成在 MR 上）
```

**第 ④ 步是 GitLab CI 的默认语义**（GitLab CI 默认 `when: on_success`）——**但这个默认值非常容易被无意改掉**：

| 写法 | 效果 | 门禁是否成立 |
|---|---|---|
| 默认（无 `when`） | 前面 stage 失败 → 后面不跑 | ✅ 成立 |
| `when: always` | 失败也跑 | ❌ **门禁被穿透** |
| `when: on_failure` | 只在失败时跑 | ❌ 不作为门禁用（是通知用） |
| `needs: [xxx]` + `optional: true` | 即使 xxx 失败也继续 | ❌ **门禁被穿透** |
| **`allow_failure: true`** | **job 失败但 pipeline 仍算成功** | ❌ **最隐蔽的穿透** |

> **`allow_failure: true` 是门禁最常见的死法。**
> 它的语义是"**这个 job 失败不算这条流水线的失败**"——团队当初加它多半是为了"扫描失败别卡住发布"（比如扫描器自己挂了），但**结果就是：工具挂了 = 门禁失效 = 漏洞畅通无阻**，而且**没人会收到通知**（因为 pipeline 是绿的）。
>
> **正确做法**：让扫描工具**本身**决定要不要失败（用退出码），**不要用 `allow_failure` 去"宽容"工具故障**。如果确实要区分"扫描发现问题"和"扫描器自己崩了"，就分成两个 job：真正扫出问题的 job 不许 `allow_failure`；扫描器崩的 job 用 `allow_failure: true` **但必须告警**。

**告警层与阻断层的关系**：

```
阻断层（必须）：job 失败 → 后续 stage 不执行
                    ↓ 顺带触发
通知层（补充）：when: on_failure → 推钉钉/企微
```

**通知层永远在阻断层之后**，而且**只推真正需要人处理的事**：

| 该推 | 不该推 |
|---|---|
| **main 分支**的门禁失败 | 每个 MR 的每次失败 |
| **生产发布**被门禁拦住 | dev 环境构建失败 |
| 扫描器自身故障（DB 拉不下来、Server 连不上） | 已被人工豁免的失败 |
| 汇总日报（每日一次） | 实时逐条 |

> **告警刷屏的后果是"静音"，而静音 = 门禁失效。**
> D5 日课里"钉钉告警刷屏最后被全员静音"那个事故，本质是**把通知层当成了主要机制**。**主要机制必须是阻断，通知只是让人知道"为什么被挡了"。**

## 3. 动手

> **本章命令为示意与设计说明**，用于讲清"每一步看到什么算对"。本文编写期间**未执行任何 docker / kubectl / helm / sonar / trivy 命令**，也未拉取任何镜像——遵循本套资料"不新建环境、不拉新镜像"的纪律（见 [`../00-写作规范.md`](../00-写作规范.md) 第四节）。命令的官方语义以你所用版本的 `--help` 与官方文档为准。

### 3.1 三道拦截点落在流水线的哪里

```
GitLab CI 的 stage 划分（对应本套资料的 D4/D5 日课结构）
│
├─ stage: build          ← 产出镜像（提交前那道由本地 pre-commit 承担）
│    └─ job: build_image
│
├─ stage: test           ← 单元测试        ┐ 这两个 stage **并行**（用 needs 表达）
│    └─ job: unit_test                   │ 二者都通过才继续
├─ stage: scan           ← ★ 两道门禁都在这里 ┘
│    ├─ job: sonar_quality_gate     ← 拦截点②：合并前
│    └─ job: trivy_image_scan       ← 拦截点③：发布前
│
├─ stage: push           ← 镜像入库（**必须在 scan 之后**）
│
└─ stage: deploy_prod    ← 流程层：tag 触发 + manual 审批
```

**三个必须确认的事**：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | `scan` stage 与 `push` stage 之间**不能有 `allow_failure`、不能有 `when: always`、不能有 `optional: true`** | 这不是风格问题，**是门禁是否成立的问题** |
| 2 | **`push` 必须排在 `scan` 之后** | 顺序反了 = **高危镜像先进了仓库**，再被扫出来——**仓库里已经躺着一个带 CRITICAL 漏洞的镜像**了，谁拉谁中招。**扫描的对象是构建产物（本地镜像），不需要先推上去** |
| 3 | **`test` 与 `scan` 应并行**（用 `needs` 表达），不要串成两个 stage | 二者互不依赖，串行会**白等一倍时间**；门禁反馈越快，研发越愿意用 |

**失败归属（排障时先看这个，能省很多时间）**：

| 失败的 job | 归属 | 去哪查 |
|---|---|---|
| `build` / `test` / `scan` | **研发的锅**（代码、依赖、配置、规则） | 翻代码、改流水线、找规则豁免 |
| `push` / `deploy` | **运维的锅**（凭据过期、网络、仓库权限、集群权限） | **别去翻代码**——源码没问题 |

> **"push 失败去翻代码"是纯浪费时间。** 凭据过期、仓库权限不够、镜像名打错——**这三个跟你的代码一行关系都没有**，但报错信息长得都很像。

### 3.2 sonar-project.properties 最小可用集

放在仓库根目录，**随代码提交**（这是"配置即代码"的一部分）：

```properties
# ── 项目标识 ──────────────────────────────────────
sonar.projectKey=day1-demo
sonar.projectName=Day1 Demo
sonar.projectVersion=1.0.0

# ── 扫描范围 ──────────────────────────────────────
sonar.sources=src
sonar.tests=test
sonar.sourceEncoding=UTF-8
sonar.exclusions=**/*.test.ts,**/node_modules/**,**/dist/**

# ── 质量门禁等待（★ 决定这是不是真门禁）────────────
sonar.host.url=$SONAR_HOST_URL
sonar.token=$SONAR_TOKEN
sonar.qualitygate.wait=true
sonar.qualitygate.timeout=300

# ── CI 环境常见问题：容器里没有 .git ─────────────────
sonar.scm.disabled=true
```

**逐项说明"为什么这么写"**：

| 配置 | 为什么必须有 | 少了会怎样 |
|---|---|---|
| `sonar.projectKey` | **项目唯一标识**。Server 按它归集历史 | **每次扫描被当成新项目** → 历史趋势全断、门禁的 New Code 基线算不出来 |
| `sonar.sources` | 告诉 scanner 去哪找代码 | 扫不到东西 → **0 个问题 → 门禁永远绿**（假门禁的另一种形态） |
| `sonar.tests` | 覆盖率要靠测试代码 | 覆盖率算不出 → 覆盖率条件永远不满足 |
| `sonar.exclusions` | 排除生成代码、第三方代码 | 规则在噪声上疯狂报错 → 团队直接关门禁 |
| **`sonar.qualitygate.wait=true`** | **让 scanner 等 Server 判定并据此返回退出码** | **scanner 上传完就退出 0 → 门禁只是块面板**（本文 2.3 的核心结论） |
| `sonar.token` | 认证 | **401/403** → 典型报错见第 6 节 |
| `sonar.scm.disabled=true` | CI 容器里常没有完整 `.git` | SCM 相关分析报错或噪声 |

**CI 侧的调用（两种写法都要知道）**：

```bash
# 推荐：token 走环境变量，不进命令行（避免出现在 ps 输出与 CI 变量展开日志里）
export SONAR_HOST_URL="<你的 SonarQube Server 地址>"
export SONAR_TOKEN="<从 CI 的 Masked 变量注入>"
sonar-scanner -Dsonar.projectKey=day1-demo

# 官方示例与社区里也常见的简写形式（属性名可省略 sonar. 前缀）
sonar-scanner -DprojectKey=day1-demo -Dsonar.host.url=$SONAR_HOST_URL -Dsonar.token=$SONAR_TOKEN
```

> **两种写法的属性名映射（`projectKey` ↔ `sonar.projectKey`）在官方示例中都会出现**，具体以你所用 scanner 版本的官方文档为准（⚠️ 待验证：不同版本对无前缀属性名的兼容范围）。**稳妥做法：用 `sonar.` 全名**，与 `sonar-project.properties` 里的写法保持一致。
>
> **另外**：**`sonar.token` 一定要走 CI 的 Masked 变量**，不要写进 `.gitlab-ci.yml` 或 `sonar-project.properties`。后者是**提交进 Git 的文件**，token 一旦提交，历史记录里就永远抹不掉了。

### 3.3 Trivy 的三种典型用法 + 阻断验证

**用法①：镜像漏洞扫描（门禁主力）**

```bash
# 只阻断 CRITICAL：存量 HIGH 出报告不阻断（见第 5 节对比）
trivy image \
  --severity CRITICAL \
  --exit-code 1 \
  --no-progress \
  --format table \
  $IMAGE
```

**用法②：配置合规扫描（补上 Trivy 的另一半能力）**

```bash
# 扫 K8s 清单的合规问题（容器 root、privileged、latest 标签…）
trivy config --severity HIGH,CRITICAL --exit-code 1 ./k8s/

# 或直接扫集群里的活资源（⚠️ 需集群读权限，且扫的是"当前实际状态"而非"将要部署的内容"）
trivy k8s --severity HIGH,CRITICAL --exit-code 1 .
```

**用法③：SBOM 生成（合规证据）**

```bash
trivy image --format cyclonedx --output sbom.cdx.json $IMAGE
```

**"看到什么算对"——必须自己验证门禁真的生效**：

| # | 动作 | 期望看到 | 不符合说明 |
|---|---|---|---|
| 1 | 拿一个**故意带 CRITICAL 漏洞**的镜像跑用法① | 工具**退出码非 0** | 退出码是 0 → **门禁没生效**（检查 `--exit-code`） |
| 2 | 在 CI 里让该 job 失败 | **后续 stage 不执行**（publish/deploy 跳过） | 后续照跑 → 检查 `allow_failure` / `when: always` |
| 3 | 换成**干净镜像**再跑 | 退出码 0，stage 正常往下走 | 仍失败 → 检查是不是把告警当成了错误 |
| 4 | 故意改坏 `sonar.qualitygate.wait`（改成 false） | scanner 上传完立刻退出 0，**门禁形同虚设** | 这就是"假门禁"长什么样 |
| 5 | 检查漏洞库时间戳 | 库是**近期的** | 库很旧 → 结果无意义（2.8 节） |

> **第 4 步是本篇最重要的实验**：**亲手把 `sonar.qualitygate.wait` 从 true 改成 false，你会看到 MR 变绿——即使代码质量是不及格的。** 这就是"接了 SonarQube 但没有门禁"的现场。**做过的破坏实验比看过的文档记得牢。**

## 3.4 常用运维命令面板（按场景）

> **本节能做什么**：3.3 是"Trivy 三种用法"，本节是**每天值班 / 面试都会敲的质量门禁运维命令**——SonarQube 扫描与门禁验证、Trivy 扫描与漏洞库维护都在这。**门禁侧的肌肉记忆就来自这一张表。**

### ① SonarQube 扫描与门禁验证

```bash
# 本地/CI 里跑扫描（token 走变量，别写进 properties）
sonar-scanner \
  -Dsonar.host.url=https://sonar.example.com \
  -Dsonar.token=$SONAR_TOKEN \
  -Dsonar.projectKey=my-app
# 等扫描完看 Quality Gate 结果：
sonar-scanner -Dsonar.qualitygate.wait=true    # 门禁不过则扫描器退出码非 0（阻断关键）
# 用 API 查某次任务的门禁状态：
curl -u $SONAR_TOKEN: "https://sonar.example.com/api/qualitygates/project_status?projectKey=my-app"
```

> **实战价值**：**`sonar.qualitygate.wait=true` 是门禁真正生效的开关**——设成 false，扫描器传完就退出 0，MR 照样绿，等于"假门禁"（3.3 第 4 步实验）。CI 里必须设 true，并用 `project_status` API 复核，而不是只看网页。

### ② Trivy 扫描（镜像 / 配置 / SBOM）

```bash
trivy image --severity CRITICAL --exit-code 1 --no-progress $IMAGE   # 只拦 CRITICAL，阻断
trivy config --severity HIGH,CRITICAL --exit-code 1 ./k8s/           # 扫 K8s 清单合规
trivy k8s --severity HIGH,CRITICAL --exit-code 1 .                   # 扫集群活资源（需读权限）
trivy image --format cyclonedx --output sbom.cdx.json $IMAGE         # 生成 SBOM（合规证据）
trivy image --scanners secret $IMAGE                                 # 只扫硬编码密钥
```

> **实战价值**：`trivy image` 查依赖漏洞、`trivy config` 查清单合规（root/privileged/latest），**两者查的不是一回事，门禁要两道都上**。`--exit-code 1` 是阻断的硬开关——没有它，扫出 CRITICAL 流水线也绿。

### ③ 漏洞库维护（库过期 = 结果失真）

```bash
trivy image --download-db-only                  # 手动更新漏洞库（离线/CI 缓存复用）
trivy image --db-repository mirror.example.com/trivy-db  # 用内网镜像源（无外网环境）
trivy --version                                 # 看 trivy 自身版本
# 看库的采集时间，判断是否过期：
trivy image --list-all-pkgs $IMAGE              # 列出所有包，间接确认 DB 是否最新
```

> **实战价值**：Trivy 的漏洞结论**完全依赖本地漏洞库**。库过期 → 扫不出新 CVE，等于门禁形同虚设（2.8 节）。**生产要把 `download-db-only` 接进定时任务或 CI 缓存**，并用内网镜像源保证无外网环境也能更新。

### ④ 排障：门禁假绿 / scanner 卡住 / 结果失真

```bash
curl -u $SONAR_TOKEN: ".../api/qualitygates/project_status?projectKey=my-app"  # 复核门禁真状态
grep sonar.qualitygate.wait sonar-project.properties                            # 是不是被设成 false
trivy image --download-db-only                                                  # DB 过期先更新
sonar-scanner -X                                                                 # 开 debug，看扫描卡在哪一步
```

> **实战价值**：**"网页红 but 流水线绿"或反过来，通常是 `qualitygate.wait` 设错或 API 没接**。先 `project_status` 用 API 拿到真值，再回头查配置；scanner 卡住用 `-X` 看卡在哪（多半是连不上 SonarQube 或 token 权限不够）。

## 3.5 质量门禁排障实战（3 个场景串命令）

> **把 3.4 的命令用起来**：三个最典型的门禁故障，按"现象 → 敲的命令 → 怎么读"走一遍。**在测试项目上练，别动生产 SonarQube。**

### 场景 A：流水线绿了，但代码明明质量不过

```bash
grep sonar.qualitygate.wait sonar-project.properties   # 现象：MR 绿但质量差
curl -u $SONAR_TOKEN: ".../api/qualitygates/project_status?projectKey=my-app"  # 看真值
# 若 API 返回 ERROR 但流水线绿 → wait 被设成 false
```

> **读法**：这是"假门禁"现场。根因几乎都是 `sonar.qualitygate.wait=false`——扫描器传完立刻退出 0。**CI 里必须设 true**，并用 `project_status` API 复核，不能只看网页绿不绿。

### 场景 B：Trivy 扫不出新漏洞（结果失真）

```bash
trivy image --download-db-only                # 先更新漏洞库
trivy image --list-all-pkgs $IMAGE            # 确认库是否含最新 CVE 数据
trivy image --severity CRITICAL --exit-code 1 $IMAGE   # 再扫，确认能拦住
```

> **读法**：扫不出新 CVE = 漏洞库过期。`--download-db-only` 更新后重扫；无外网环境要配 `--db-repository` 内网源，否则库永远停在第一次拉的版本。

### 场景 C：scanner 卡住 / 连不上 SonarQube

```bash
sonar-scanner -X                              # 开 debug，看卡在哪一步
curl -I https://sonar.example.com             # SonarQube 服务活不活
echo $SONAR_TOKEN                             # token 有没有注入（别 echo 明文，只看有没有值）
```

> **读法**：`-X` 会打印每一步网络/解析；卡在连接 → 服务或网络问题；卡在认证 → token 没注入或权限不够（project 没授权该 token）。**token 必须走 Masked 变量，别写进 `sonar-project.properties`**（那是提交进 Git 的文件）。

> **三个场景的共同心法**：**先 `project_status`/重扫拿到真值 → 再区分"是配置错（wait=false）还是库过期还是连不上" → 最后才是改配置或更新库。门禁最怕"假绿"，一切以 API 真值为准。**

### 4.2 Trivy 常用命令与参数

| 命令 / 参数 | 类型 | 必填 | 含义 | 写错的后果 |
|---|---|---|---|---|
| `trivy image <image>` | 子命令 | ✅（扫描镜像） | 扫镜像里的 OS 包与语言依赖 | — |
| `trivy fs <dir>` | 子命令 | | 扫文件系统（依赖清单等） | 漏掉"源码依赖"这一层 |
| `trivy config <dir>` | 子命令 | | **配置合规扫描**（misconfiguration） | 只做漏洞扫描 → **危险配置全漏** |
| `trivy k8s <dir/cluster>` | 子命令 | | 扫 K8s 清单或集群活资源 | 需要集群读权限 |
| `trivy sbom <file>` | 子命令 | | 用 SBOM 作输入扫描 / 生成 SBOM（⚠️ 形态随版本变动） | 参数形态不对 → 直接报错 |
| `--severity` | 逗号分隔枚举 | | 过滤严重级别（`UNKNOWN,LOW,MEDIUM,HIGH,CRITICAL`） | 写错值 → **参数解析失败**；不写 → 全级别都算 |
| **`--exit-code <n>`** | int | ✅（门禁必填） | **发现问题时返回的退出码** | **不写 = 永远返回 0 → 门禁形同虚设**（本文 2.11） |
| `--ignore-unfixed` | bool | | 只报**有修复版本**的漏洞 | 加了它 → **无补丁的漏洞全隐藏**，看着干净实则有洞 |
| `--format` | 枚举 | | `table`/`json`/`sarif`/`template`/`cyclonedx`… | 选 `sarif` 但下游只认 `json` → 平台接不到 |
| `--output` | 路径 | | 报告输出文件 | 忘写 → 结果只在 stdout → **CI 日志滚动后就没了，无法留证** |
| `--template` | 路径 | | 自定义模板文件（配合 `--format template`） | 模板语法错 → 渲染失败 |
| `--ignorefile` | 路径 | | 豁免文件（默认读 `.trivyignore`） | 豁免无过期时间 → **永久豁免，等于没扫** |
| `--scanners` | 逗号分隔 | | `vuln,misconfig,secret,license` | 写错枚举 → 参数错误 |
| `--vuln-type` | 逗号分隔 | | `os,library` | 只扫 `os` → **应用依赖的漏洞全漏** |
| `--skip-db-update` | bool | | 跳过拉取最新漏洞库 | 库过期 → **结果失真且无报错**（本文 2.8） |
| `--offline-scan` | bool | | 完全离线，只用本地库 | 库多久没更新，扫描结果就多久没意义 |
| `--cache-dir` | 路径 | | 指定缓存目录 | CI 不配缓存 → **每次都重拉库**，慢且易失败 |
| `--timeout` | 时长 | | 单次扫描超时（默认官方标称 `5m`，⚠️ 以版本为准） | 复杂镜像超时 → 扫描被判失败 |
| `--no-progress` | bool | | 关闭进度条 | CI 日志里一堆 `█` 噪声 |
| `--insecure` | bool | | 跳过 TLS 校验 | **私库自签证书时用**；滥用 → 供应链风险 |
| `--list-all-pkgs` | bool | | 列出全部包（含未命中漏洞的） | 日志爆炸 |
| `--trivy-config` | 路径 | | 指定配置文件 | 配置文件里的默认值与你以为的不一致 |
| `TRIVY_DB_REPOSITORY`（环境变量） | string | | **漏洞库仓库地址** | **国内 CI 不配 → 拉库超时 → 扫描失败或跳过** |
| `TRIVY_CACHE_DIR`（环境变量） | 路径 | | 缓存目录 | 不配 → CI 实例间不共享缓存 |

## 5. 横向对比

### 5.1 SonarQube vs Trivy vs SCA 工具（各自查什么）

| 维度 | **SonarQube** | **Trivy** | **SCA 工具**（Dependency-Check / OSV 类） |
|---|---|---|---|
| **扫什么** | **源码** | **镜像/文件系统/配置** | **第三方依赖声明文件**（pom.xml / package-lock.json / go.sum） |
| **查什么** | 漏洞 / 缺陷 / 异味 / 覆盖率 / 重复率 / 复杂度 | **① 包的 CVE ② 配置不合规 ③ SBOM** | **依赖版本的已知 CVE**（含传递依赖） |
| **看不看源码** | ✅ 逐行分析 | ❌ 只看包清单和配置 | ❌ 只看依赖声明 |
| **看不看镜像** | ❌ | ✅ | ❌（除非专门支持容器扫描） |
| **门禁维度** | **代码层** | **制品层** | 依赖层 |
| **长处** | 能发现"逻辑写法不对"，能卡覆盖率与重复率 | **能覆盖基础镜像的系统包**（这是 SCA 覆盖不到的） | 依赖解析深、误报低、**能给出修复版本建议** |
| **短板** | **不查基础镜像的系统包漏洞** | 不做代码逻辑分析、覆盖率算不了 | **不查镜像里实际装了什么**（声明 ≠ 实际） |
| **误报来源** | 规则误判、框架特有写法 | **库过期导致漏报**（不是误报，是漏报） | 依赖解析不准确、CVE 数据不全 |
| **典型工具** | SonarQube Server + Scanner | Trivy CLI | Dependency-Check、OSV-Scanner、各云的 SCA |

**三者的正确关系（不是三选一）**：

```
        ┌─────────────────────────────────────────┐
        │  源码层：SonarQube                        │
        │  → 写法、逻辑、覆盖率、重复                │
        └─────────────────────────────────────────┘
        ┌─────────────────────────────────────────┐
        │  依赖层：SCA                              │
        │  → 声明了什么依赖、哪些依赖有 CVE          │
        └─────────────────────────────────────────┘
        ┌─────────────────────────────────────────┐
        │  制品层：Trivy                            │
        │  → **镜像里实际装了什么** + 配置对不对     │
        └─────────────────────────────────────────┘
              ↓ 三层结果汇到同一个结论
        ┌─────────────────────────────────────────┐
        │  门禁：达标才放行                          │
        └─────────────────────────────────────────┘
```

> **最容易漏掉的是制品层。**
> 源码再干净，基础镜像里那个三年没更新的 `openjdk:8` 依然满是 CVE。**"我们的代码很干净"和"我们的镜像很安全"是两件事**，而 D5 日课里那个"Trivy 扫出 300 个 HIGH"的场景，**根因就在制品层，不在源码层**。

### 5.2 门禁 vs 告警

| 维度 | **门禁（阻断）** | **告警（通知）** |
|---|---|---|
| **结论的作用对象** | **流水线** | **人** |
| **不通过时会发生什么** | **后续 stage 不执行、MR 不能合、发布被拦** | 消息发出去，**事情照做** |
| **依赖人的响应** | ❌ 不依赖 | ✅ **完全依赖** |
| **留痕** | ✅ **天然的**（流水线记录里有失败记录、有审批记录） | ⚠️ 靠你自己存（发出去的消息很快被刷走） |
| **能不能被绕过** | 难（要改 CI 配置，要过 code review） | **容易**（静音、忽略、划走） |
| **适用** | **必须 100% 拦住的东西**：漏洞、严重缺陷 | 需要人判断的事：性能波动、体验类问题、待确认的热点 |
| **本地民企的实际形态** | 制品层漏洞阻断 + 生产发布审批 | 钉钉/企微推质量报告、推扫描报告 |

**为什么必须有"阻断"这一层，不能只靠告警**：

| 场景 | 只有告警 | 有阻断 |
|---|---|---|
| 开发提交了带 SQL 注入的代码 | 群里出现一条消息，**没人看** | **MR 合不了** |
| 镜像带 CRITICAL 漏洞 | 上线了，**事后才知道**（永远不知道） | **发布被拦下** |
| 合规检查 | 说不清"拦过什么" | **流水线记录就是证据** |

> **一句能直接用的话**："**告警是给人看的，门禁是给机器执行的。** 我们把'一定会造成安全问题'的东西做成门禁——因为这类事一次都不能漏；把'需要人判断'的事做成告警——因为机器判断不了。"
>
> **反过来做（什么都做成门禁）也是错的**：团队会被卡到开始绕过门禁，那比只有告警更糟。**判断标准是"这件事能不能被容忍一次"。能容忍的 → 告警；不能容忍的 → 门禁。**

### 5.3 Quality Gate on New Code vs Overall

| 维度 | **New Code 门禁** | **Overall Code 门禁** |
|---|---|---|
| **卡谁** | 本次变更涉及的代码 | 项目所有代码（含历史债） |
| **实现** | 在 Quality Gate 里把条件指向 New Code 范围 | 条件指向 Overall 范围 |
| **对存量债的态度** | **不卡**（单独排期治理） | **全卡** |
| **新 MR 的结果** | 改好了就过 | **可能永远红** |
| **团队的第一反应** | 继续用 | **要求关掉门禁** |
| **技术债趋势** | 债务总量缓慢下降（增量被守住） | 不下降（因为增量被卡，**但如果关掉门禁就完全失控**） |
| **什么时候用 Overall** | **几乎不用**；或仅在"从零开始的项目"上 | 只有一种例外：**存量已经是零的新项目**，此时 Overall 等于 New Code |

**正确的组合方式**：

```
Quality Gate:
  ├─ New Code 覆盖率 ≥ 团队当前水平（起步阶段可以定低，先守住）
  ├─ New Issues = 0            ← 硬条件
  ├─ New Vulnerabilities = 0   ← 硬条件
  ├─ New Code Smells ≤ 小额度   ← 软条件，可以给缓冲
  └─ Overall 覆盖率             ← **不配**（或者只配一个"不低于历史基线"的下限）
```

**"Overall 覆盖率不低于基线"是个巧妙的折中**：它**不要求还债，只要求不继续欠**。存量覆盖率 30% 就保持 30%，不许降到 25%。**这比"卡 New Code"更严、比"卡 Overall 目标值"更可行。**

> **面试这么答**："SonarQube 的 Quality Gate 可以对 New Code 和 Overall Code 分别设条件。**我们只卡 New Code**，因为卡 Overall 意味着卡历史债，老项目永远过不了，团队第一天就会要求关掉门禁——**门禁一旦被关就等于不存在**。整体覆盖率我们只设一个'不低于历史基线'的下限，**既不要求还债，也不许继续欠**。技术债单独开项目按优先级还，不指望门禁顺带还完。"

## 6. 踩坑与排障

| 你看到的（症状） | 状态 | 真实原因 | 怎么修 | 下次怎么防 |
|---|---|---|---|---|
| **`sonar-scanner` 连不上 Server**：`Connection refused` / `Unable to connect` / 认证失败 | CI job 失败 | ① **网络**：CI runner 在容器网络里，`localhost:9000` 指向的是 runner 自己，不是 SonarQube → 换成服务名或内网域名；② **版本**：Scanner 与 Server 版本不兼容（官方要求 Scanner 版本需被目标 Server 支持）；③ **token**：没配、过期、权限不足 | 依次查：DNS 能不能解析 → 端口通不通 → token 有效吗 → 版本兼容矩阵 | 在 CI 里固定 Scanner 镜像 tag（**不用 `latest`**）；把 `sonar.host.url` 做成变量而不是硬编码 |
| **日志里出现明文 token**，或 token 被提交进 Git | — | 把 token 写进了 `-Dsonar.token=` 命令行、`.gitlab-ci.yml` 或 `sonar-project.properties`（后者是提交进 Git 的文件） | **立即吊销并重新生成 token**；从 Git 历史里彻底清除（`git filter-repo` 或 BFG）；把历史文件里的凭据全部视为已泄漏 | token 走 **CI 的 Masked 变量**并注入环境变量；`sonar-project.properties` 里**永远不写 token**；加 pre-commit 密钥扫描（gitleaks / trufflehog 类） |
| **流水线是绿的，但报告里明明有 CRITICAL** | pipeline 成功 | **`allow_failure: true`** —— job 失败被标记成"允许失败"，**pipeline 不算失败**，后续 stage 照跑 | 去掉 `allow_failure`；用工具退出码表达阻断；把"扫描器自身故障"拆成独立 job 且**必须告警** | 门禁 job 的 `allow_failure` 视为**禁止项**，写进 CI 模板的硬约束；code review 时专门查这一行 |
| **SonarQube 面板上 Quality Gate 是红的，MR 却能合** | pipeline 成功 | scanner **上传完就退出**，没等 Server 判定（`sonar.qualitygate.wait` 没配或为 false） | 配 `sonar.qualitygate.wait=true`；配 `sonar.qualitygate.timeout` | CI 模板里**默认带上**这两个参数；定期做"故意制造不合规代码，验证 MR 真的被挡"的演练 |
| **Trivy 报 "没有问题"，但确实存在已知漏洞** | 退出码 0 | **漏洞库过期**（`skip-db-update` + 缓存不更新）→ 库里没有这条记录 → **漏报** | 更新库；`trivy clean --vuln-db` 后重扫；确认库仓库地址可达 | CI 里持久化缓存目录 + **在流水线开始时统一更新一次库**；**库更新失败必须让 job 失败**，不能静默跳过 |
| **Trivy 在 CI 里超时 / 拉库失败** | job 失败或跳过 | 漏洞库仓库在境外，默认地址拉不动（网络问题） | 配 `TRIVY_DB_REPOSITORY` 指向内网镜像/代理；或预置离线 DB 包 | 内网镜像同步 DB；把库地址做成 CI 变量；**准备离线兜底方案** |
| **Trivy 扫出来"0 个问题"，但镜像明显很旧** | 退出码 0 | ① 扫的是**最终镜像**，`scratch`/`distroless` 里几乎没有 OS 包 → 确实没东西可报；② `--vuln-type` 只配了 `os` 漏了 `library`；③ **`--ignore-unfixed` + `.trivyignore`** 把东西全豁免了；④ **扫描的是缓存里的旧镜像**（同名 tag 被覆盖，节点上还是旧的） | 逐项排除：用 `--list-all-pkgs` 看实际扫到了哪些包；检查豁免文件内容与过期时间；确认扫描的是**本次构建产出的镜像 digest**而不是 tag | 门禁扫描**用 digest 不用 tag**（tag 可变、digest 不可变）；`.trivyignore` 每条**必须写原因和过期日期**，到期自动失效重新暴露 |
| **Trivy 只报了漏洞，没报"容器跑 root"这类问题** | — | 只用了 `trivy image`（漏洞扫描），**没跑配置合规扫描** | 补 `trivy config ./k8s/` | CI 里配**两类扫描**：`trivy image`（制品）+ `trivy config`（配置），缺一不可 |
| **Trivy 拉私有镜像报 401 / 认证失败** | job 失败 | **没登录，或用了 `docker login -p $PASS`**（密码进进程表，且可能被 CI 日志记录）；或凭据过期 | 改成 **`docker login --password-stdin`**（密码从 stdin 读，不进参数、不进 `ps`）；**凭据用 masked + protected 变量** | **CI 里永远不用 `-p`/`--password` 传密码**；**记住 `~/.docker/config.json` 里的 `auth` 只是 base64 编码，不是加密**——它能被一条 `base64 -d` 还原，所以**必须是 masked 变量 + 最小权限凭据** |
| **门禁上线一周后被要求关掉** | pipeline 恢复全绿（无门禁） | **规则太严导致误报太多 → 团队开始绕过 → 门禁名存实亡**。根因：① 卡了 Overall（老债卡死）；② 阈值定得远高于团队当前水平；③ 豁免流程太重，研发宁愿改 CI 配置 | ① 门禁改成**只卡 New Code**；② 存量漏洞先单独立项治理（尤其是**基础镜像升级**，收益最大）；③ 阻断级别先定 CRITICAL；④ 豁免走**带过期时间的白名单流程** | **监控两个指标：门禁豁免率、平均修复时长**。豁免率飙升 = 门禁正在失效；**把"降低误报"当成门禁的日常运营，而不是一次性配置** |
| **SonarQube 扫出来一堆看不懂的问题，全在生成代码里** | — | `sonar.exclusions` 没配 / 配错；或语言分析器把前端产物当源码扫了 | 补 `sonar.exclusions`（`**/dist/**`、`**/node_modules/**`、生成代码目录） | 骨架项目里就把 `exclusions` 定好；新增目录时同步更新 |
| **Java 覆盖率条件永远不满足 / 覆盖率显示 0** | 门禁恒红 | 没生成 JaCoCo 报告，或路径没配 `sonar.coverage.jacoco.xmlReportPaths`；或测试没跑 | 先确认 CI 里真的产出了 XML 报告，再配路径 | 覆盖率条件**先设成"当前真实水平"**，别一步到位定 80%；测试报告作为 artifact 留存 |
| **MR 门禁忽好忽坏 / 结论不稳定** | 间歇性失败 | ① 多个 SonarQube 实例负载均衡但**会话/缓存不一致**；② CI runner 复用了旧的工作目录（缓存了 `.scannerwork`） | 清理 `.scannerwork`；确认 SonarQube 集群配置一致 | CI 里显式清理 scanner 工作目录；runner 不用跨 job 复用工作区 |
| **告警发出去没人看 / 群里被刷屏后静音** | pipeline 正常 | **把通知当成了主要机制**，每个 MR 每次失败都推 | 只推 **main 分支失败** + **生产发布被拦** + **扫描器自身故障**；其余进日报 | 告警分级（紧急 / 每日汇总）；**通知永远在阻断之后**，不替代阻断 |
| **钉钉/企微机器人偶发发不出去** | — | 机器人**接口限流**（平台对群机器人有频率上限，官方标称具体数值随平台策略调整，⚠️ 以平台当前文档为准）；**网络瞬断**；**消息体超长** | 指数退避重试（带上限次数）；**同一类消息做聚合与去重**；失败进重试队列而非直接丢弃 | 告警发送包一层：重试 + 限流 + 降级（日志兜底）；**webhook URL 当密钥管**，不进 Git |

## 8. 自测三问

1. **能说清输入输出吗？** —— **输入**：源码（+ 测试报告 + 依赖清单）+ 漏洞库 + 事先配置的 Quality Gate 条件；**输出**：两个独立结论——① **质量结论**（Quality Gate = OK/ERROR，由 Server 判定）；② **安全结论**（漏洞清单 + 退出码）。**中间**：Scanner 采集并上报 → Server 存储并计算 → scanner 按门禁结论决定退出码 → CI 按退出码决定后续 stage 是否执行。**"扫描器跑完没报错"与"门禁通过"是两件事。**
2. **能故意改坏再倒推吗？** —— 四个具体实验：① 把 `sonar.qualitygate.wait` 改成 `false` → **MR 立刻变绿，即使质量不及格**（假门禁现场）；② 把门禁 job 加上 `allow_failure: true` → **Trivy 报 CRITICAL，流水线仍然绿**；③ 在 `.gitlab-ci.yml` 里手抄一次 SonarQube token → 跑一次流水线 → **在 runner 的 job 日志里搜这个 token 就能搜到**；④ 用一个**故意带 CRITICAL 漏洞的镜像**跑 `trivy image` 但**不加 `--exit-code 1`** → **退出码是 0**，门禁不触发。
3. **能画上下游吗？** —— 画出「开发者提交 → pre-commit（拦截点①）→ MR 触发 CI → SonarQube Scanner 上传（拦截点②）→ SonarQube Server 判定 Quality Gate → scanner 按结论返回退出码 → Trivy image/config 扫描（拦截点③）→ SBOM 归档 → publish → deploy_prod（tag + 人工审批）→ **钉钉/企微通知（阻断之后）**」这条链，并在每两个环节之间标出"**这一步失败会看到什么**"。**特别标出两个物理阻断点**：scanner 的退出码、CI 的 stage 依赖。**
