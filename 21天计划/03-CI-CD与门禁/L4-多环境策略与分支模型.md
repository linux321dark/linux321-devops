## 1. 概念

### 1.1 环境的定义：四个环境各自回答什么问题

**"环境"这个词被用得很滥。先把它拆成一个可回答的问题：**

> **每一个环境，必须回答一个"别的环境回答不了"的问题。回答不了的问题，就不该单独设一个环境。**

| 环境 | 它回答的问题 | 形态特征 | 谁在上面改东西 | 挂了会怎样 |
|---|---|---|---|---|
| **dev（开发）** | **"能不能跑起来？"** | 资源最小、可以随时重建、**数据可以是假的** | 开发者自己，改完就生效 | **没人关心**——它是耗材 |
| **test（测试）** | **"功能对不对？"** | 有测试数据、跑自动化测试、**数据可以是假的** | 研发 + 测试 | 阻塞测试，**不阻塞线上** |
| **staging（预发）** | **"用接近生产的形态，能跑通吗？"** | **配置与拓扑尽量像生产**、数据可以是脱敏的 | 运维/平台（**改动需要走流程**） | 阻塞发布，**但不直接影响用户** |
| **prod（生产）** | **"能给真实用户用吗？"** | 真实数据、真实流量、**改动必须审批** | 运维/平台，**必须审批 + 留痕** | **直接影响用户** |

**这张表是本篇的骨架。** 它的用法是：

> **当有人提议"再加一个环境"的时候（常见诉求：加个 pre-prod、qa-env、sit-env），用这张表问一句：**
> **"这个新环境回答的是哪个'别的环境回答不了'的问题？"**
> 答不出来 → 这个环境就是"多一份要维护的配置、多一套会漂移的东西"，**不要加。**

**为什么"环境"容易失控**：

| 现象 | 根因 |
|---|---|
| 环境越加越多（dev/test/qa/sit/uat/pre/prod 七八个） | 每个环境都是"上次某个问题需要单独环境"堆出来的，**没人回头合并** |
| 每个环境配置都不一样，且**说不清为什么不一样** | 配置不是从同一套基线派生的，是**各写各的** |
| 测试环境和生产的配置差异没人知道 | **没有配置矩阵，也没有 diff** |

**"环境个数 × 差异项数 = 配置管理复杂度"**。这条乘法关系是本篇所有权衡的来源：**你要么砍环境数，要么砍差异项，要么引入工具把复杂度收进系统里。**

### 1.2 staging 存在的意义：为什么"接近生产的形态"值钱

**staging（预发）最容易被做成一个"没用的 test"**——最后变成 dev 的另一个名字。**那它就该被删掉。**

**staging 的唯一不可替代价值**：它是**唯一能验证"生产形态"的环境**。什么叫"生产形态"？至少包含这四样：

| 维度 | dev/test 常见形态 | staging 应该是什么样 | 为什么不一样会出事 |
|---|---|---|---|
| **配置来源** | 写死在 YAML 里 | **从配置中心 / 外部 Secret 注入** | 生产走注入路径，dev 走硬编码 → **注入路径从来没被测过** |
| **依赖拓扑** | 只有一个数据库 | **完整依赖链**（下游服务、缓存、消息队列、第三方 API） | 依赖链没验证过 → **上线才发现下游接口超时** |
| **流量与证书** | HTTP、内部访问 | **HTTPS、真实域名、外部可达** | 证书/域名/SNI 问题**只在这里能暴露** |
| **伸缩行为** | 固定 1 副本 | **HPA 开启、多副本** | 单副本测不出 HPA 与会话保持的问题；**HPA 扩容要拉镜像，镜像大就慢**（见 [`../01-基础篇/L2-Dockerfile与多阶段构建.md`](../01-基础篇/L2-Dockerfile与多阶段构建.md)） |

**staging 形同虚设的四种典型形态（对照检查用）**：

| # | 形同虚设的表现 | 真实原因 | 后果 |
|---|---|---|---|
| 1 | staging 的配置**是 dev 那套复制来的** | 建环境时图省事 | **它验证的还是 dev 的形态**，生产形态没被验证过 |
| 2 | staging **跑的是同一个分支、同一个 tag** | 没人管 | staging 只是个装饰性的 URL |
| 3 | staging **没有接入生产依赖链** | 接第三方要花钱/要审批 | 依赖问题只能上线才暴露 |
| 4 | staging **从不被真正访问**（只在流水线里跑完就没了） | 没有真实访问 | 证书、域名、性能问题一个都测不出来 |

> **一句判断标准**：
> **"如果 staging 上发现了一个问题，这个问题在生产上也一定会出现（且更严重）"——满足这条，staging 有价值；不满足，它就是个昂贵的 dev。**
>
> **反过来说：staging 上什么都没发现，也不能证明生产没问题**——它只是**排除了**这一类问题。**staging 的价值是排除风险，不是保证正确。**

### 1.3 配置与代码分离：为什么同一份镜像要跑遍所有环境

**核心原则（可以背）**：

> **一份代码 + 一个镜像，跑遍所有环境。环境差异全部由"配置"注入，不进镜像。**

**为什么镜像不能带环境标记**：

| 做法 | 问题 |
|---|---|
| **镜像 tag 带环境**（`app:dev` / `app:prod`） | ① **镜像内容不同** → 每个环境一个产物 → **要构建 N 次**，N 次都可能构建出不同结果；② **"prod 镜像"不可复现**（三个月后重建一次，tag 还在但内容可能不同）；③ **测试过的产物 ≠ 生产部署的产物**——测试的是 dev 镜像，上线的是 prod 镜像，**门禁全部白做** |
| **配置烘进镜像**（`ENV DB_HOST=prod-db`） | 同上。更糟：**密钥会进镜像层**，`docker history` 一看就露（见 [`../01-基础篇/L2-Dockerfile与多阶段构建.md`](../01-基础篇/L2-Dockerfile与多阶段构建.md) 的 ENV/ARG 对照表） |

**正确的形态**：

```
        ┌──────────────────────────────────┐
        │  同一份源码 → 构建一次 → 一个镜像   │
        │  引用 = digest（tag 给人读）      │
        │  内容 = 与环境完全无关            │
        └───────────────┬──────────────────┘
                        │
        ┌───────────────┼───────────────┬───────────────┐
        ▼               ▼               ▼               ▼
   ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
   │   dev   │    │  test   │    │ staging │    │   prod  │
   │ +注入A   │    │ +注入B   │    │ +注入C   │    │ +注入D   │
   └─────────┘    └─────────┘    └─────────┘    └─────────┘
                       ↑
              配置从哪来：ConfigMap/Secret/配置中心/环境变量
              （由环境决定，与镜像无关）
```

**"配置注入"的四种常见载体**：

| 载体 | 内容 | 谁提供 | 适合 |
|---|---|---|---|
| **ConfigMap** | 非敏感配置（端口、开关、日志级别、第三方地址） | 集群内 | 静态配置 |
| **Secret** | 敏感配置（密码、token、AK/SK） | 集群内 / 外部密钥系统 | 敏感配置（**但见 2.7 的限制**） |
| **环境变量** | 单个值，容器内 `process.env` | 容器编排 | 应用支持读环境变量时最省事 |
| **配置中心 / Apollo / Nacos** | 运行时可动态改 | 独立服务 | 需要**不重启改配置**的场合 |

**配置注入带来的三个直接收益**：

| 收益 | 为什么 |
|---|---|
| **同一产物过所有门禁** | Trivy 扫的是这一个镜像；SonarQube 扫的是这一份代码 → **门禁结果对所有环境有效** |
| **回滚 = 换配置引用** | 不需要重新构建，回滚速度以秒计 |
| **配置可审计** | 配置变更走 Git / 配置中心的变更记录，**能被 diff、能被审批** |

### 1.4 术语表（中英对照）

| 英文 | 中文 | 一句话 |
|---|---|---|
| Environment | 环境 | 一套独立的配置 + 资源 + 数据组合 |
| Configuration | 配置 | 决定应用"怎么跑"的外部参数，与代码分离 |
| Trunk-based Development | 主干开发 | **所有人直接在 main 上开发**，用小批次 + 特性开关控制风险 |
| GitHub Flow | GitHub 流 | 基于分支的 PR 流程：开分支 → PR → 评审 → 合并 → 部署 |
| GitFlow | GitFlow | 多分支模型：develop / release / feature / hotfix 长期并存 |
| Feature Flag | 特性开关 | 用运行时开关控制功能是否生效，**让代码合并与功能上线解耦** |
| Pull Request / Merge Request | 合并请求 | 代码变更进入主干的唯一入口，**门禁挂在这里** |
| Release Branch | 发布分支 | 从主干拉出、专门用于发布的分支 |
| Hotfix Branch | 紧急修复分支 | 从生产版本拉出、修完合回主干 |
| Config Drift | 配置漂移 | **实际配置**与**声明的配置**不一致，或**各环境配置逐渐分叉** |
| Drift Detection | 漂移检测 | 定期比对实际状态与期望状态并告警 |
| Canary | 金丝雀 | 先放少量流量给新版本，观察指标后再全量 |
| Blue/Green | 蓝绿 | 两套环境切换流量，**回滚 = 切回去** |
| Immutable Artifact | 不可变制品 | 发布后内容不再变化；**版本标识不可覆盖** |
| Rollback | 回滚 | 回到上一个已知可用版本 |
| GitOps | — | **以 Git 中的声明为唯一事实源**，由控制器持续把集群拉向期望态 |
| Commit-based Delivery | 提交物驱动 | **由"提交物"（artifact）而非"分支"触发部署** |

## 2. 机制

### 2.1 分支模型三选一

先看清三个模型的**真实形状**，而不是名字：

```
① 主干开发（Trunk-based）
   main ──●──●──●──●──●──●──►
          短分支                ← 每个人开一个短命分支，小时~几天内合回 main
   风险控制：特性开关 + 自动化测试 + 小批次

② GitHub Flow（基于分支的 PR 流）
   main ──────────●───────────●──►
          └feature-a┘         └feature-b┘
   风险控制：评审 + CI 检查 + 合并即部署

③ GitFlow（多分支长期并存）
   main         ─●─────────────●─────►
   release/1.0  ─●─────●───●──┘
   develop ──●──●──●──●──┬──●──●───►
   feature/x      └─●──●┘
   hotfix/1 ────────●──┘
   特点：**同一个版本要合并到多个分支，合并冲突是日常**
```

### 2.2 为什么小团队更适合主干开发（成本账）

**先说结论**：**GitFlow 是为大团队、多版本并行、且有专职发布管理者的组织设计的。** 一个 10 几人的企业常用 GitFlow，**管理成本会超过它带来的收益**。

**成本对比（按"一个版本从开发到上线"计）**：

| 维度 | **主干开发** | **GitHub Flow** | **GitFlow** |
|---|---|---|---|
| **分支数量** | 1 长期 + N 个短命分支 | 1 长期 + N 个分支 | **4 类长期分支并存**（main/develop/release/hotfix） |
| **一次发布要合并几次** | 0~1 次 | 1 次 | **≥ 2 次**（feature→develop→release→main，hotfix 还要合回 develop） |
| **合并冲突的次数** | 少（分支活得短） | 中 | **多**（release 分支活得久，与 develop/main 越分越开） |
| **"线上跑的是哪个提交"怎么查** | **直接看 main 的 SHA** | 看 main 的 SHA | **要问 release 分支 / tag，可能有多个候选** |
| **回滚** | 切回上一个 SHA | 切回上一个 SHA | **要判断该切 main 还是 release 分支的哪个版本** |
| **谁做合并** | 所有人直接推 main / 或一个 gate | 评审人 | **需要专人协调版本号与合并顺序** |
| **新人上手** | 一条命令 | 一条命令 | **要理解 4 类分支的语义** |
| **并行版本支持** | 弱 | 弱 | **强（这是它唯一不可替代的能力）** |

**GitFlow 唯一真正不可替代的能力**：**同时维护多个并行版本**（比如线上 1.0 还在维护、1.1 在开发、1.2 在规划，需要 hotfix 同时落到 1.0 和 1.1）。

**那什么时候才需要？** 三个条件**同时**成立：

| 条件 | 本地 10 几人民企的实际情况 |
|---|---|
| ① 有多个版本需要**同时维护** | ❌ 通常只有一个线上版本 |
| ② 有**专职**的发布/版本管理者 | ❌ 研发自己发版 |
| ③ 团队规模大到**合并冲突成为主要损耗** | ❌ 12 个人，冲突成本可控 |

**三个都不成立 → GitFlow 纯属负担。**

**那主干开发为什么不是无脑选它？它的代价要认**：

| 主干开发的代价 | 缓解手段 |
|---|---|
| **主干随时可能是坏的** | 靠**自动化测试 + CI 门禁**兜底（门禁不严 = 主干开发不可用） |
| **半成品代码进了主干** | 靠**特性开关**（Feature Flag）——功能没开关就不能合 |
| **一次合入的东西多、不好 review** | 靠**小批次 + 频繁合并**控制单次 diff 大小 |

> **关键因果链（面试要讲出来）**：
> **主干开发把"分支合并的风险"转嫁给了"CI 门禁 + 特性开关"。**
> **所以门禁严不严，直接决定你能不能用主干开发。**
> 这就把 [`L3-质量门禁-SonarQube与Trivy.md`](L3-质量门禁-SonarQube与Trivy.md) 和本篇连起来了：**L3 讲的是"怎么建门禁"，本篇讲的是"有了门禁之后，分支可以少到什么程度"。**

**三种模型的选择依据（一句话版）**：

| 团队形态 | 选谁 | 理由 |
|---|---|---|
| **小团队、无专职发布管理、单线维护** | **主干开发** | 分支模型的价值 = 版本并行能力，用不上就纯是成本 |
| 中等团队、要评审、要 CI | **GitHub Flow** | 便宜、够用，评审天然挂在 PR 上 |
| 多版本并行、有专职发布 | **GitFlow** | 只有它能同时维护多个版本 |

### 2.3 环境与分支的映射：三种做法的取舍

**"环境要对应哪个分支？"这是多环境策略里最容易纠结、也最容易做错的一个决定。** 三种做法：

| 做法 | 机制 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **A. 一环境一分支**（`dev` / `test` / `prod` 各一条常驻分支） | 提 MR 到 dev → 合并到 test → 合并到 prod | 直观，"环境当前是什么代码"一眼能查 | **多两次合并**；**修 bug 要在多条分支上重复修**（最致命）；分支长期分叉，冲突累积 | **几乎不推荐**。它把"环境"和"代码版本"绑死了，与 1.3 的"配置与代码分离"直接冲突 |
| **B. 一条 release 分支多环境推进** | 从 main 拉 `release/x.y`，依次部署到 staging → prod | 版本明确；**发布内容冻结**；回滚目标清晰 | 每次发版要拉分支、跑一遍合并；hotfix 要同时合回 main 和 release；**分支活得越久冲突越多** | 有明确发布节奏、需要在发布前冻结内容的团队 |
| **C. 代码只有一条线，环境靠配置区分**（提交物驱动） | **所有环境跑同一个 artifact**，只换配置 | **回滚最快**（换引用，不重建）；**没有分支间合并**；**门禁结果对所有环境一致** | **没有"冻结发布内容"的天然边界**（用 tag / 版本号 + 制品库来补）；要求有制品库与配置管理能力 | **小团队首选**；也是 **ArgoCD 时代的标准做法** |

**取舍的判断逻辑**：

| 你有没有这些需求 | 说明 |
|---|---|
| 需要"发布前冻结内容" | → 选 B（release 分支）**或** C + 制品库（用 tag 冻结，**更干净**） |
| 需要同时维护多个线上版本 | → 选 B，且必须有专职版本管理者 |
| 只是想"每个环境跑不同代码" | → **这个需求本身就该被质疑**——那叫"发布频繁"，不叫"多环境" |

> **对本地民企（10 几人、无专职 DevOps）的现实答案**：
> **选 C**。理由不是"先进"，而是：
> ① **分支少 = 合并少 = 冲突少**，12 个人的团队最怕日常损耗；
> ② **回滚快且可靠**（切引用，不重建、不依赖 Git 状态）；
> ③ **省掉"release 分支谁合谁"这个协调成本**——**没有专人，就不要引入需要专人协调的流程。**
>
> **C 的前置条件是"有制品库 + 配置管理"**，这是硬门槛：
> - **制品库**（ACR / Harbor）存**不可变**的镜像，用 **digest 或不可覆盖的 tag** 标识；
> - **配置**（values 文件 / 配置中心 / K8s 里的 ConfigMap+Secret）按环境分开管；
> - **部署清单进 Git**（`04-交付与GitOps/L1-Helm-模板化封装.md` 的 Chart + ArgoCD Application 就是这个）。
>
> **三条都做不到的话，退回"一条 release 分支推进"（B）**，比 A 好。

### 2.4 配置分层的三种实现

**"分层"的意思是：同一个应用的配置，按"变化频率"和"环境差异"拆成几层，每层单独管。**

| 层 | 内容 | 变化频率 | 归属 |
|---|---|---|---|
| **结构层** | Deployment/Service/Ingress 的**结构**（有几个副本、什么端口、有没有 HPA） | 低 | 模板/Chart |
| **环境差异层** | 各环境不同的值（副本数、镜像 tag、资源规格、域名） | 中 | **values 文件** |
| **敏感层** | 密码、AK/SK、token | 低但**必须可轮换** | Secret / 外部密钥系统 |
| **运行期层** | 开关、灰度比例、临时调参 | 高 | 配置中心 / 特性开关 |

**三种落地实现**：

| 实现 | 机制 | 适合 | 代价 |
|---|---|---|---|
| **① Helm values 分环境覆盖** | 一个 Chart + `values-dev.yaml` / `values-prod.yaml`，`helm install -f` 指定 | **自研应用、多环境、需要 release 历史** | 要学 Helm 模板语法；**值覆盖优先级容易搞错**（见 Helm 篇 4.2） |
| **② Kustomize overlays** | `base/` + `overlays/prod/`，用 `patches` 打补丁 | **改第三方 Chart / 只补丁不改结构**；**不想要模板语言** | **不产生 release 历史**；overlay 多了会看不懂；**值是"补丁"不是"声明"，容易叠出畸形结果** |
| **③ ConfigMap 模板** | 一份 ConfigMap 模板 + 部署时替换占位符 | 应用只吃配置文件（不读环境变量）；**环境少** | **没有版本历史、没有类型检查**；模板替换容易出错；**扩环境要复制文件** |

**三者的选择**：

```
自研应用 + 多环境 + 要回滚历史  →  ① Helm
别人给的 Chart / 只想打几个补丁  →  ② Kustomize
只有两三个环境 + 应用只读配置文件  →  ③（能用但要知道它在还债）
```

**为什么"配置中心（Apollo/Nacos）"是另一条路**：

| 维度 | 文件式配置（Helm/Kustomize/ConfigMap 模板） | 配置中心 |
|---|---|---|
| 改配置 | **改文件 → 走 Git 审批 → 同步 → 重启/热加载** | **平台上点一下 → 秒级生效** |
| 审计 | ✅ **Git 天然有** | ⚠️ 要靠平台自己的审计日志 |
| 变更成本 | 高（要走流水线） | 低 |
| 适合 | **变更低频、要求可审计** | **变更高频、要求快速**（灰度开关、活动配置） |

> **务实结论**：**两者不是二选一，是分工。**
> **"这个配置该谁改、谁审批"决定了它该放在哪**：
> - **研发能改、但要留痕** → 文件式（Git 审批）
> - **运维能改、不需要研发参与、且经常改** → 配置中心
> - **谁都不该直接改** → **应该被移除，而不是搬个地方**

### 2.5 同一环境多个集群：蓝绿 / 金丝雀 / 多可用区

**一个环境（prod）对应多个集群/多套 Pod，是常态**，来源有三个：

| 形态 | 结构 | 配置管理的额外复杂度 |
|---|---|---|
| **蓝绿** | 两套完整环境（blue 跑旧版、green 跑新版），**切 Ingress 流量切换** | **两套配置必须对称**（域名、证书、DB 连接、监控都要有两份）；切换后"两套谁在跑"的记录要清楚 |
| **金丝雀** | 一套环境，内部按**流量比例**分给新旧版本 | **同一套配置，但版本/流量比例是额外的、且要动态改的输入**；**新旧版本必须行为兼容**（DB schema、接口） |
| **多可用区 / 多集群** | 同一版本跑在多个集群/可用区 | **同一份配置要下发到 N 个集群，且要保证它们一致**；**Secret 要在每个集群里都有** |

**这三种形态带来的配置管理复杂度，本质是同一个问题**：

> **"同一份逻辑配置"要落到"多个不同的物理目标"上，而每个目标的实际状态可能已经和声明不一致了。**

**关键问题（也是配置漂移的高发区）**：

| 问题 | 后果 |
|---|---|
| 蓝绿两套的**配置对称性**靠人记 | 切过去才发现 green 少配了一个开关 → **故障发生在切流量的那一刻** |
| 金丝雀的**权重/比例**是运行时状态，不是 Git 里的声明 | 声明与实际不一致 → **"现在到底多少流量在新版本"**没人说得清 |
| 多集群的 Secret 是**各自独立的副本** | 在 A 集群轮换了 AK/SK，**B 集群还是旧的** → 一半流量用旧凭据 → 诡异故障 |

**应对手段**：

| 手段 | 解决什么 |
|---|---|
| **同一套 Chart + 同一套 values 模板，只换少量参数** | 蓝绿/多集群的"对称性"变成**结构性保证**，而不是靠人记 |
| **GitOps 同步器持续比对并纠正**（见 5.3） | 漂移**被自动发现并纠正**，而不是等人发现 |
| **Secret 用外部密钥系统**（不是各集群各存一份） | 轮换一次全局生效；**不存在"某个集群漏轮换"** |
| **把"切流量比例"也纳入声明**（Argo Rollouts 类） | 比例不再是运行时手工状态，而是**可审计的声明** |

> **本篇与 [`../04-交付与GitOps/L1-Helm-模板化封装.md`](../04-交付与GitOps/L1-Helm-模板化封装.md) 的关系**：
> **Helm 解决"怎么把一套资源参数化"，GitOps 解决"怎么保证多个集群上的实际状态都等于声明"。**
> **只有一个集群时，Helm 就够了；多个集群 + 多环境时，必须补上同步器这一层。**

### 2.6 配置漂移：定义、成因、检测

**先区分两个不同的"漂移"**（很多团队混为一谈，导致用错工具）：

| 类型 | 定义 | 谁造成 | 怎么发现 |
|---|---|---|---|
| **① 状态漂移（State Drift）** | **同一个环境的实际状态** ≠ **声明的期望状态**（有人 `kubectl edit` 改了线上、有人手工改了 HPA 阈值） | **人**（应急操作后忘了改回声明） | **GitOps 同步器的差异检测**（compare desired vs live） |
| **② 配置分叉（Config Divergence）** | **各环境之间的配置**逐渐分叉，且**分叉的理由没有被记录**（dev 改了 A，prod 没改 A，两个月后没人知道该不该同步） | **流程缺失**（改了没同步、没记录原因） | **配置矩阵 + 环境间 diff**（把各环境 values 拉出来逐项比对） |

**成因为主的四个来源**：

| # | 来源 | 表现 | 对策 |
|---|---|---|---|
| 1 | **应急改了线上，没改声明** | 线上多了一个手工加的环境变量、副本数被临时调高 | 应急走**受控通道**（GitOps 自动纠正 / 或者明确记录到变更单）；**别让"改线上"成为常规手段** |
| 2 | **改了 dev 没同步到 prod** | 两边配置项不一致，且没有理由记录 | **配置矩阵显式列出每个环境每个配置项**（4.1 的表就是产物） |
| 3 | **每个环境各写各的 YAML** | 差异藏在"整份文件"里，看不出来 | **改成"一份模板 + 差异值"**（Helm/Kustomize） |
| 4 | **默认值在代码里**（不配就用代码里的默认） | **同一份配置在不同环境跑出不同行为**，而且"没配"这件事看不出来 | **关键配置项改成 `required`**（Helm 的 `required` 函数）——**没配就报错，而不是默默用默认值** |

**检测手段（按成本排序）**：

| 手段 | 成本 | 能发现什么 | 发现不了什么 |
|---|---|---|---|
| **人工拉各环境配置做 diff** | 低（一小时） | **配置分叉** | 状态漂移 |
| **流水线里自动 diff**（各环境 values 对比，PR 时跑） | 中 | **配置分叉**，且能在合并前发现 | 状态漂移 |
| **GitOps 同步器的 OutOfSync 状态** | 中（要装同步器） | **状态漂移**（能自动纠正）+ 部分分叉 | 跨环境的语义差异 |
| **运行时配置快照对比**（应用把生效配置打到日志/端点） | 中高 | **"实际生效的"配置**，包括默认值带来的意外 | — |

> **最实用的一条**：**把"某环境的关键配置项"做成一张人工维护也能看懂的表**（4.1 的矩阵），**每次改动顺手更新它**。
> **理由**：12 个人的团队装一套 GitOps 的成本可能高于收益，**但一张表几乎零成本**。**先有可见性，再谈自动化。**
>
> **面试这么答**："配置漂移有两个层面：**状态漂移**（线上被手工改了，与声明不一致）和**配置分叉**（各环境配置逐渐不一样且没有理由记录）。前者用 GitOps 同步器的 OutOfSync 检测并自动纠正；后者靠**配置矩阵**——一张'环境 × 配置项 × 来源'的表，每次改配置顺手更新。我们团队 10 几人，一上来装 ArgoCD 不现实，但**这张表当天就能建**，而且它顺便解决了'新同学不知道该配什么'的问题。"

### 2.7 密钥管理

**第一句结论**：

> **密钥不能放在普通 ConfigMap 里。**
> **不是"不太安全"，是"安全边界错了"。**

**为什么 ConfigMap 不行**：

| 理由 | 说明 |
|---|---|
| **ConfigMap 不是加密存储** | 默认以**明文**存在 etcd 里。**任何人有读 ConfigMap 的权限就能读到** |
| **权限模型没有区分** | 开发、测试、运维读 ConfigMap 的权限通常是一样的 → **能读普通配置的人顺手就读到了密钥** |
| **会被渲染进日志/诊断输出** | `kubectl describe`、`kubectl get cm -o yaml`、应用的配置打印，都会明文打出来 |
| **会被带进制品** | 如果是模板渲染进 Deployment 的 `env`，它就**进了一次 Git 历史**（值在 values 里）**或进了镜像层**（值在 Dockerfile ENV 里） |
| **Secret 也是 base64，不是加密** | K8s Secret 默认只是 base64 编码。**必须配 etcd 静态加密 + RBAC 最小化才算真正安全**（官方文档明确说明这一点） |

**正确做法（按安全性排序）**：

| 层级 | 做法 | 适合 | 代价 |
|---|---|---|---|
| **① 外部密钥系统**（云厂商 KMS / Vault / External Secrets Operator） | 密钥**只存在密钥系统里**，K8s 里只存"引用"；同步器把值拉进来 | **生产环境的正确解法**；**天然支持轮换** | 要多部署一个组件；**要解决"同步器自己怎么认证"的引导问题** |
| **② 外部密钥 + 密封（Sealed Secrets）** | 密钥在 Git 里，但是**加密后的密文**，只有集群能解开 | 密钥也要走 Git 审批流 | 要装控制器 |
| **③ K8s Secret + etcd 静态加密 + RBAC 最小化** | 原生 Secret，但把存储和权限做对 | 规模小、能管好 RBAC 的团队 | **轮换要手工做**（改完还要重启 Pod） |
| **④ 降级方案**：应用启动时从云厂商 SDK 拿凭据 | 代码里不带密钥，靠实例角色/工作负载身份取 | 云上、用了云厂商 IAM 的场景 | 迁移到别的云要改代码 |
| **❌ 不要** | 写进 values.yaml / ConfigMap / Dockerfile ENV / Git 明文 | — | **等于公开** |

**多环境密钥怎么隔离**：

| 隔离维度 | 做法 | 为什么 |
|---|---|---|
| **不同集群** | 每个环境一个集群 + 各自的 Secret（最好由同一个外部密钥系统按环境分区管理） | **dev 的密钥泄露不该影响 prod** |
| **同一集群不同 namespace** | 每个环境一个 namespace，Secret 也在各自 namespace；**RBAC 按 namespace 隔离** | namespace 是**逻辑隔离不是安全边界**——**RBAC 才是安全边界**（官方文档明确） |
| **不同密钥值** | **dev/prod 的 AK/SK 必须是不同的凭据** | 用同一套 AK/SK，"测试环境泄露"= "生产泄露" |
| **不同权限主体** | prod 的 AK/SK 只授予生产资源权限 | **凭据泄露的影响面被权限模型限制住** |

**AK/SK 轮换（这是最实际的部分）**：

| 步骤 | 做法 | 要点 |
|---|---|---|
| **1. 定期轮换** | 定期（如按月/按季）换一批 | **周期由合规要求定，不是由"记起来了"定** |
| **2. 双凭据过渡** | 旧 AK + 新 AK **同时有效**一段窗口 | **关键**：直接换会立刻打断在跑的请求 |
| **3. 灰度切换** | 先让部分环境/部分实例用新 AK，确认无异常再全量 | 复用"金丝雀"思路 |
| **4. 停用旧 AK** | 确认全量切换后**禁用旧 AK** | **最容易被忘的一步**——旧 AK 一直有效 = 轮换等于没做 |
| **5. 留痕** | 轮换记录（谁、何时、为什么）进变更单 | **等保/审计会查** |

> **一条容易被忽略但很值钱的话**：
> **"轮换"不等于"换密钥"，"换密钥"不等于"旧密钥失效"。**
> **只有旧密钥真的被禁用，轮换才完成。** 面试能主动说出这一点，说明你真做过。

### 2.8 发布策略与回滚：不可变镜像 + 版本递增

**先建立一条因果链（整篇最实用的一段）**：

```
不可变镜像（发布后内容永不变）
   +
**固定 digest 引用**（不是浮动 tag）
   +
配置与镜像分离（换配置不用重建）
        ↓
回滚 = 把"当前引用的 digest"换回上一个
        ↓
回滚成本 = 一次声明变更 + 一次同步
        ↓
回滚时间 ≈ 秒级到分钟级（取决于同步器与拉镜像速度）
```

**为什么"不可变"是回滚可靠的前提**：

| 情况 | 能不能回滚 | 为什么 |
|---|---|---|
| **固定 digest + 版本递增** | ✅ 能，而且**确定** | 上一个 digest 还在制品库里，**内容一模一样**，拉下来就是那个东西 |
| **浮动 tag（同名可被覆盖）** | ❌ **不能确定** | tag 还是 `v1.2`，但**内容已经变了** → "回滚"拉回来的是**另一个东西**。**回滚动作本身变成了不确定行为** |
| **配置也变** | ⚠️ **能退代码，退不了配置** | 回滚了镜像，但新配置还在 → **接口对不上，二次故障** |

**最后一条是真实事故的高频形态**，D6 日课里也提到过：

> **回滚只退了一半。** 代码回到 v1，配置（新增的必填字段、数据库 schema）还是 v2 的 → 服务起不来或者数据错乱 → **回滚引发二次故障**。
>
> **对策**：**回滚必须包含"配置回滚"**，而且**数据库变更要走"先兼容、后切换、再清理"**（向前兼容的 schema），不能指望回滚能退数据。

**版本标识的三种形态**：

| 形态 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| **语义版本 tag** | `v1.2.3` | 人好读 | **是可变指针**（同名再 push 即改写指针，registry 官方不校验）→ 不可变性靠纪律保证 |
| **提交 SHA tag** | `a1b2c3d` | **唯一、追溯到代码** | **仍然是 tag = 仍是可变指针**——只是"实践中很少有人覆盖同一个 SHA"，**不是机制保证的不可变** |
| **digest** | `sha256:...` | **manifest 内容哈希，机制层面绝对不可变** | 完全不可读，要靠工具关联到业务版本 |

> **这一条是本篇最容易被讲错的地方，务必说准**：
> **tag 与 digest 的差别不是"哪个更规范"，是"哪个由机制保证不可变"。**
> **tag 是可变指针**（registry 存的是 `manifests/<tag>` 的映射，同名再 push 就改写了指针，官方不校验）；
> **digest 是 manifest 的内容哈希，改内容就变 digest**。
> **所以"用 commit SHA 当 tag 就不可变了"是错的**——SHA 只是让人不太会去覆盖它，**机制上它依然可变**。

**务实的组合**（推荐，也是最常见的）：

> **tag 用 commit SHA 兼做"人读的版本号"，digest 才是"部署时真正钉住的那一版"。**
> **生产部署固定 `image: <repo>@sha256:<64位>`**（K8s 支持这种写法）。
> **绝不覆盖已发布的 tag**，但**真正的保险是 digest**——**tag 只是给人看的，digest 才是给机器执行的。**

**为什么"固定 digest"是回滚可靠的前提**：

| 只固定 tag | 固定 digest |
|---|---|
| tag 被覆盖 → 线上"同一版本"内容已变 | **内容与 digest 一一对应，永不变** |
| 回滚"回到 v1.2"→ 拉回来的是**另一个东西** | 回滚 = 换回**确定的那个 digest** |
| 依赖"没人覆盖它"这条**纪律** | 依赖 **registry 的内容寻址机制** |

> **纪律能撑到出事那天的概率不为零。** **digest 能。**

**发布策略的三个层次**：

| 层次 | 做什么 | 收益 | 代价 |
|---|---|---|---|
| **① 滚动更新** | K8s 逐批替换 Pod（`maxSurge`/`maxUnavailable` 控制节奏） | 零额外成本，K8s 原生 | 滚动过程中**新旧版本同时在跑**，接口必须兼容 |
| **② 蓝绿** | 两套完整环境，切流量 | **回滚最快**（切回去） | 双倍资源；切流量的那一刻才暴露配置差异 |
| **③ 金丝雀** | 先给一小部分流量 | **用真实流量验证，风险最小** | 需要按流量比例路由的能力；**新旧必须行为兼容** |

**共同的硬约束（不管选哪种）**：

| 约束 | 原因 |
|---|---|
| **新旧版本必须能共存** | 滚动/金丝雀期间两个版本同时在跑；**数据库 schema 变更必须向前兼容** |
| **一次只改一个变量** | 改了镜像又改了配置，出问题分不清是谁的锅 |
| **回滚路径必须提前验证** | **没演练过的回滚路径 = 没有回滚路径** |

### 2.9 谁该改配置：职责边界决定流程

**这不是"谁更闲"的问题，而是"改错了谁承担后果"的问题。**

| 配置类型 | 该谁改 | 为什么 | 变更频率 | 流程 |
|---|---|---|---|---|
| **业务功能开关** | **研发** | 属于产品行为定义 | 高 | PR + 评审（走 Git） |
| **副本数 / 资源规格 / HPA 阈值** | **研发提单、平台执行** | 改错了影响成本与稳定性，但**需要了解负载** | 中 | 工单/变更单 |
| **域名 / 证书 / 负载均衡** | **平台/运维** | 属于基础设施 | 低 | 变更单 + 审批 |
| **第三方凭据（AK/SK）** | **平台/运维** | **不经过研发**（研发拿到就等于扩大暴露面） | 定期 | **轮换流程 + 留痕** |
| **数据库连接串 / 中间件地址** | **平台维护、研发申请** | 平台知道拓扑 | 低 | 变更单 |
| **生产发布时机** | **业务负责人决策、平台执行** | 商业决策不是技术决策 | — | **审批 + 留痕** |

**三条设计原则**：

| 原则 | 说明 |
|---|---|
| **① 改配置的权限要和"改错了谁背锅"匹配** | 研发的代码写错研发背锅 → 研发自己改；生产的证书配错运维背锅 → 运维自己改。**权限错配 = 流程必然被绕过** |
| **② 改配置必须留痕** | 文件式 → Git 天然有；配置中心 → 平台审计日志。**没有留痕 = 等保扣分** |
| **③ 不该存在的配置项应该被删掉** | 每多一个配置项，就多一份"各环境不一致"的可能。**配置项是负债，不是资产** |

> **面试这么答**："我们的划分是：**研发改业务相关的，平台改基础设施相关的**。关键不是谁改，而是**改的权限和改错的代价要匹配**——所以 AK/SK 平台自己管，研发不接触；副本数研发提单、平台执行，因为改副本数需要了解负载。**流程被绕过通常不是人的态度问题，是流程设计和代价不匹配**：让研发去改证书，研发就会找运维代改，流程就断了。"

### 2.10 本地民企的真实约束与最现实做法

**先把约束摊开（这些是决策的输入，不是借口）**：

| 约束 | 后果 |
|---|---|
| **团队 10 几人** | 一个人请假就卡住流程；**任何需要"专人维护"的机制都活不长** |
| **无专职 DevOps** | 没人全职做 CI/CD、没人盯同步器状态、**没人做版本管理** |
| **交付节奏快**（业务压力） | 流程每加一步，开发者就多一分想绕过的冲动 |
| **多应用 × 多环境** | 配置量随"应用数 × 环境数"增长，**手工维护一定崩** |
| **要过等保 / 要应付客户审计** | **必须有留痕**，不能"口头说好" |

**在这个约束下，什么是真可行的**：

| 做法 | 可行性 | 理由 |
|---|---|---|
| **一个 Chart + 每环境一份 values** | ✅ **最推荐** | 零额外组件、零额外运维；差异显式、可 diff；新人看 values 就知道该配什么 |
| **同一镜像跑遍所有环境** | ✅ **强烈推荐** | 门禁结果对所有环境有效；回滚快 |
| **保护分支 + CI 门禁 + 生产手动审批** | ✅ **推荐** | 一次配置，长期生效；**审批天然产生留痕** |
| **一张配置矩阵表**（环境 × 配置项 × 来源） | ✅ **推荐** | **零成本**，解决可见性；也是新人手册 |
| **Kustomize**（用于改第三方 Chart） | ✅ 可用 | `kubectl diff -k` 给审计留痕，很划算 |
| **GitOps（ArgoCD）** | ⚠️ **可以做，但要有人管** | 有价值（自动纠正漂移、多集群一致），**但需要有人持续看状态**。**没人管 = 没人看 = 白装** |
| **配置中心（Apollo/Nacos）** | ⚠️ **看变更频率** | 配置变更高频、且已有 Apollo 经验 → 用；否则多一个组件就多一份运维 |
| **GitFlow** | ❌ **不推荐** | 需要专人协调版本，**没有专人** |
| **一环境一分支** | ❌ **不要** | 修 bug 要在多分支重复修 |

> **本篇最重要的一条判断**：
> **小团队不要为"先进"引入需要专人维护的机制。**
> **引入一个没人维护的 ArgoCD，比不做 GitOps 更糟**——因为它会产生"我们有 GitOps"的错觉，同时**漂移依然存在**（没人纠正）。
> **正确的顺序是：先有可见性（配置矩阵 + 保护分支 + 门禁），再谈自动化（同步器 + 密钥系统）。**

## 3. 动手

> **本章是设计说明与配置样例**，用于讲清"每一步看到什么算对"。**本文编写期间未执行任何 docker / kubectl / helm 命令，未创建或修改任何容器、集群资源**——遵循 [`../00-写作规范.md`](../00-写作规范.md) 第四节的纪律。命令语义以你所用版本的官方文档为准。

### 3.1 把"一份镜像 + 四份配置"落到具体文件

**目录结构（配置进 Git，镜像进制品库）**：

```
repo/
├─ chart/                      ← 唯一的模板
│  ├─ Chart.yaml
│  ├─ values.yaml              ← 默认值（= dev 的基线）
│  ├─ templates/
│  │  ├─ deployment.yaml
│  │  ├─ service.yaml
│  │  └─ configmap.yaml
│  └─ ...
├─ envs/                       ← 只放差异，每份 10~30 行
│  ├─ dev.yaml
│  ├─ test.yaml
│  ├─ staging.yaml
│  └─ prod.yaml
├─ .gitlab-ci.yml              ← 流水线：同一镜像逐环境推进
└─ sonar-project.properties
```

**四个环境的差异文件（长这样，才叫"分层"）**：

```yaml
# envs/dev.yaml
replicaCount: 1
image:
  tag: ""                      # ← 由流水线注入 commit SHA（给人读的版本号）
  digest: ""                   # ← 生产固定 digest；这里留空表示开发环境用 tag
resources:
  requests: { cpu: 100m, memory: 128Mi }
config:
  logLevel: debug
  featureFlags:
    newCheckout: false
```

```yaml
# envs/prod.yaml
replicaCount: 3
image:
  tag: ""                      # ← 同样注入，绝不写死 prod tag
  digest: "sha256:<64位>"      # ← ★ 生产钉死这一版内容（tag 只是给人看的）
resources:
  requests: { cpu: 500m, memory: 512Mi }
config:
  logLevel: info
  featureFlags:
    newCheckout: true
```

**"看到什么算对"**：

| # | 检查 | 期望 | 不符合说明 |
|---|---|---|---|
| 1 | 对比 `dev.yaml` 与 `prod.yaml` | **只有 10~30 行差异**，结构完全一样 | 差异很大 → **配置分层没做对**，在复制粘贴 YAML |
| 2 | 搜四个环境文件里的 `tag:` | **全是空/占位**，没有硬编码的版本号 | 有硬编码 → **镜像带环境了**，回滚会出问题 |
| 3 | 搜四个文件里的密钥字段 | **一个都没有** | 有 → **密钥进 Git 了**（红线） |
| 4 | 流水线里镜像引用的来源 | **同一个 commit SHA / 同一个 digest 贯穿四个环境** | 各环境不同 → **门禁结果对生产无效** |
| 5 | 改 `prod.yaml` 的 `replicaCount` | **只影响一个文件，且能被 diff 出来** | 要改多处 → 分层失败 |

### 3.2 流水线上的环境推进

```
build (一次)  →  test ∥ scan (Trivy + SonarQube 门禁)  →  push 镜像（digest 固定）
                    │                                          │
                    │                                          └→ 同一个 digest 贯穿四个环境
                    ├─→ deploy dev     （自动）
                    ├─→ deploy test    （自动）
                    ├─→ deploy staging （自动，但**用 prod 形态的 values**）
                    └─→ deploy prod    （**tag 触发 + 手动审批**）
```

> **`push` 必须在 `scan` 之后**——顺序反了就变成"先让高危镜像进仓库，再把它扫出来"，**仓库里已经躺着一个带 CRITICAL 漏洞的镜像**，谁拉谁中招。扫描的对象是**构建产物（本地镜像）**，不需要先推上去。
> **`test` 与 `scan` 并行**（用 `needs` 表达），二者互不依赖，串行会白等一倍时间。

**关键检查点**：

| 检查 | 为什么重要 |
|---|---|
| **四个环境引用的是同一个镜像 digest** | 保证"测过的就是发的" |
| **staging 用的 values 里有 prod 的形态配置**（HTTPS、依赖地址、拓扑），只是数据不同 | **staging 形同虚设的根因就在这里** |
| **prod 阶段是 `when: manual` 且只认 tag** | 流程层门禁；**产生审批留痕** |
| **prod 的部署用的是 `helm upgrade` 而不是 `apply`** | **保留 release 历史 → 回滚有目标** |

### 3.3 回滚演练（**必须真的演练过一次**）

| 步骤 | 动作 | 期望 |
|---|---|---|
| 1 | `helm history <release> -n prod` | 看到每一版 revision + **用的镜像 tag/digest + 更新时间** |
| 2 | 故意在 prod 部署一个**行为错误**的版本（不改镜像，只改配置） | 应用出错，告警出现 |
| 3 | `helm rollback <release> <明确 revision>`（**必须写明确 revision 号**） | 应用恢复正常 |
| 4 | 确认 Pod 用的镜像是**上一次的 digest**（不是"看起来差不多"的 tag） | digest 一致才算回滚成功 |
| 5 | **再试一次只回滚镜像、不回滚配置** | **观察是否二次故障**——这一步才是重点 |

> **第 5 步是本篇最有价值的一次实验**：**回滚只退一半的故障，比不回滚更难查。**
> 只有亲手造出一次"代码退回来了但配置还是新的"，你才会真的相信"**回滚必须包含配置回滚**"这句话。

## 4. 逐字段表

### 4.1 多环境配置矩阵（环境 × 配置项 × 来源）

**这张表本身就是产物**——**零成本，解决可见性，是新人上手手册，也是等保审计的证据之一。**

| 配置项 | dev | test | staging | prod | **来源** | **谁改** | **不进 Git 的部分** | **写错的后果** |
|---|---|---|---|---|---|---|---|---|
| **镜像 tag / digest** | commit SHA | 同一个 SHA | 同一个 SHA | **同一个 SHA + 固定 digest** | **流水线注入** | 流水线 | — | **prod 填了可变 tag → 线上跑的是谁构建的说不清，回滚定位不到版本**（tag 会被同名覆盖）；**正确做法是锁 digest** |
| **副本数** | 1 | 1~2 | 2 | 3 | values | 研发提单 | — | **prod 副本数大于节点可调度容量 → 多出来的副本一直 Pending，服务容量比预期少**，且 Pending 的 Pod 还会占着调度记录；上限超过 HPA `maxReplicas` 则扩容永远不生效 |
| **CPU requests** | 100m | 100m | 500m | 500m | values | 研发提单 | — | **填大了 → HPA 分母偏大、利用率永远偏低、流量高峰不扩容**（`HPA` 算的是 `当前利用率 = 实际用量 ÷ requests`，分母一大比值就小）；**填小了 → 节点超卖、Pod 的驱逐优先级上升**，节点内存/CPU 紧张时**你的 Pod 会被先杀掉**；**各环境的 limit 与 request 比例不一致 → 节流行为不同、HPA 行为在测试环境验证不出来**（被节流时利用率算得偏低） |
| **内存 requests** | 128Mi | 256Mi | 512Mi | 512Mi | values | 研发提单 | — | **填小了 → 容器被 OOMKill，且重启后仍然 OOM**（这是配置问题不是偶发，**重启解决不了**）；**填大了 → 节点内存紧张、驱逐优先级上升**；**内存 limit 填小了同样致命 → 明明还有余量却被 cgroup 杀掉，表现为"莫名重启"，最难查** |
| **HPA** | 关闭 | 关闭 | **开启**（min=2） | **开启**（min=3, max=20） | values | 研发提单 | — | **prod 忘了开 → 流量上来只能靠人工扩容，等于放弃了弹性**；**`minReplicas` 大于 `maxReplicas` → 控制器行为异常**；**各环境 min/max 差异过大 → 扩容行为在测试环境完全验证不出来**（测试环境 min=1 永远不触发扩容） |
| **探针阈值** | 宽松 | 宽松 | **接近生产** | **生产值** | values | 研发 | — | **阈值比生产宽松 → 测试全绿、上线即失败**（生产的负载更高、更容易超时）；**探针阈值写错 → 容器被反复重启**，表现为 `CrashLoopBackOff`；**liveness 失败会重启、readiness 失败只摘端点不重启**，两者配反了排查方向全错 |
| **日志级别** | debug | debug | info | info | values / ConfigMap | 研发 | — | **prod 设成 debug → 日志量暴增、可能含敏感字段（参数、令牌、手机号）、磁盘与采集成本直线上升**；**生产开 debug 常常是在排查问题，忘了改回去 → 成本问题会持续到没人注意** |
| **特性开关** | 全关 | 部分开 | 全开 | 全开 | values / 配置中心 | **研发** | — | **prod 误开未完成的功能 → 半成品功能直接对真实用户开放**；**prod 误关已上线功能 → 功能"凭空消失"，客服工单立刻进来**；**开关只在配置中心改、没同步回 Git → 别人按声明重建环境，功能静默消失** |
| **CronJob 定时任务** | 关闭 | 关闭 | **开启** | **开启** | values | 研发 | — | **prod 忘关 staging 的定时任务 → 同一份数据被处理两次**（跑两次对账、跑两次结算、跑两次清理，**且不可逆**）；**cron 表达式按本地时区解释 → 服务器时区不同，任务在半夜而不是白天跑**；**没设并发策略 → 上一次没跑完下一次又起一份** |
| **数据库地址** | 本地/共享测试库 | 测试库 | **接近生产** | 生产 | **Secret / 配置中心** | 平台 | ✅ | **staging 指向 prod 库 → 测试数据直接写进生产库，这是不可逆事故**（测试用例造的数据、外键级联、批量清表都会打真数据）；**prod 指向测试库 → 线上数据写错地方，且发现时已经晚了** |
| **数据库账号密码** | 测试凭据 | 测试凭据 | 预发凭据 | **生产凭据** | **Secret（外部密钥系统）** | **平台** | ✅ | **staging 用 prod 凭据 → 测试环境泄密即生产泄密**（测试环境的日志、报错页、调试工具都更"不设防"）；**prod 用了权限过大的账号 → 一旦泄漏，影响面是整个数据库而不是一个表** |
| **第三方 AK/SK** | **独立测试凭据** | **独立测试凭据** | 预发凭据 | **生产凭据** | **Secret（外部密钥系统）** | **平台** | ✅ | **staging 用 prod AK/SK → 真实计费、真实生产操作被测试脚本触发**（发短信、扣款、推消息）；**prod 凭据泄漏 → 影响面是那个云账号下的所有资源**；**凭据轮换只轮了一半 → 一半流量用旧凭据，表现为"时好时坏"最难定位** |
| **内部服务地址** | 测试命名空间 | 测试命名空间 | 预发命名空间 | 生产命名空间 | values | 平台 | — | **指向错误命名空间 → dev 的请求打到 prod 服务**（跨环境串流量，dev 的脏数据写进生产）；**指向已下线的实例 → 连接被拒**，且**重试逻辑会把它放大成雪崩** |
| **域名 / 证书** | 内部域名 | 内部域名 | **正式域名（灰度）** | **正式域名** | **Ingress / 平台** | 平台 | ✅（证书私钥） | **prod 用测试证书 → 浏览器告警、客户端连接失败**（自签证书不信任，部分客户端直接拒绝）；**证书没覆盖 prod 域名 → SNI 不匹配，握手失败**；**证书私钥进了 Git → 私钥泄漏，必须吊销重签** |
| **访问控制** | 无限制 | 无限制 | 账号白名单 | **账号 + IP 白名单** | 平台 | 平台 | — | **prod 白名单配松 → 应用直接裸奔在公网**，任何人可调用；**配得过严 → 内部服务也调不通**；**只有账号没有 IP 白名单 → 凭据泄漏即可从任意来源访问** |
| **数据** | 假数据 | 假数据 | **脱敏数据** | **真实数据** | 平台 | 平台 | ✅ | **staging 用真实数据 → 测试操作直接污染生产数据**（不可逆，且往往在生产业务已经用到时才被发现）；**脱敏做得不彻底 → 脱敏数据里留着真实手机号/身份证，**本身就是一起数据合规事故**；**prod 用了假数据 → 真实用户看到假数据** |
| **备份策略** | 无 | 无 | 每日 | **按合规要求** | 平台 | 平台 | — | **prod 没配备份 → 数据损坏后无法恢复**，且**故障时才发现没备份**；**配了备份但没做过恢复验证 → 备份文件本身是空的或坏的**，**有备份不等于能恢复**；**保留期短于合规要求 → 等保测评直接扣分** |
| **发布方式** | 自动 | 自动 | 自动 | **tag + 手动审批** | 流水线规则 | 业务负责人 | — | **prod 没设手动审批 → 谁都能直接发版**（改错一行就上线，**没有拦点**）；**tag 触发条件写错 → 该发的不发、不该发的乱发**；**审批人白名单没配 → 审批形同虚设，等保要的"变更可追溯"拿不出来** |

**这张表怎么用（三条纪律）**：

| 纪律 | 说明 |
|---|---|
| **① 每一行都要有"来源"** | 来源不明的配置项 = **没人知道它为什么是这个值** |
| **② 每一行都要有"谁改"** | 没有负责人的配置项 = **它会漂移，且没人管** |
| **③ "不进 Git 的部分"一列必须填** | 填不出来 = **这一行有密钥进 Git 的风险** |

### 4.2 分支模型对照表

| 维度 | **主干开发**（Trunk-based） | **GitHub Flow** | **GitFlow** |
|---|---|---|---|
| **长期分支数** | 1（main） | 1（main） | **2~4**（main / develop / release / hotfix） |
| **短分支生命周期** | **小时~1 天** | 1~3 天 | **功能分支可存在数周** |
| **合并次数（一次发布）** | 0~1 | 1 | **≥2**（可能 4，含 hotfix 回补） |
| **特性开关依赖** | **强依赖**（没有开关就别用主干开发） | 可选 | 不需要 |
| **CI 门禁依赖** | **强依赖**（门禁不严 = 主干随时坏） | 依赖（PR 检查） | 依赖（合并前检查） |
| **并行版本支持** | ❌ | ❌ | ✅ **唯一不可替代处** |
| **"线上是哪个提交"** | **看 main 的 SHA** | 看 main 的 SHA | **看 tag / release 分支** |
| **回滚目标** | 上一个 SHA | 上一个 SHA | **要判断切哪条分支** |
| **冲突频率** | 低 | 中 | **高**（release 分支越老冲突越多） |
| **对专职角色的要求** | 无 | 无 | **需要发布/版本管理者** |
| **适合团队规模** | **小（≤ 15 人）** | 中 | **大 + 多版本并行** |
| **不适合的原因** | 没门禁/没开关 → 主干随时坏 | — | **无专人 → 协调成本压死团队** |
| **本套资料的采用** | **✅ 推荐**（配合 L3 门禁 + 特性开关） | 可用 | **不推荐** |

## 5. 横向对比

### 5.1 GitFlow vs GitHub Flow vs 主干开发

| 问题 | GitFlow | GitHub Flow | 主干开发 |
|---|---|---|---|
| **谁合并代码** | feature → develop → release → main | feature → main | **直接 main**（或极短分支 → main） |
| **一次功能上线要几次合并** | 2~4 | 1 | **0~1** |
| **出紧急 bug 怎么修** | hotfix 分支 → 合回 main **和 develop**（**两处**） | hotfix 分支 → main | **直接改 main**（小改动） |
| **回滚怎么做** | 切 release/main 的某个版本 | 切回上一个 SHA | **切回上一个 SHA** |
| **最大的隐性成本** | **版本号管理 + 多分支合并冲突** | 评审排队 | **主干质量要求高**（没有兜底网） |
| **失败的典型表现** | "这个改动该合到哪个分支" 争论半天 | PR 挂久了冲突一堆 | **主干频繁被打断、大家不敢在 main 上工作** |
| **什么时候必须选它** | 多版本并行 + 有专人 | 需要评审但没多版本需求 | **小团队、有门禁、想减少日常损耗** |

**一条选择口诀（面试可直接用）**：

> **"版本并行能力用不上，就是纯成本；用上了，缺了就是灾难。"**
> **先问"要不要同时维护多个线上版本"：不需要 → 主干开发或 GitHub Flow，选人少的那个；需要 → GitFlow，且必须配专职角色。**

### 5.2 Helm values vs Kustomize vs 环境变量

| 维度 | **Helm values** | **Kustomize** | **环境变量** |
|---|---|---|---|
| **核心机制** | **模板化**：同一份模板 + 不同值渲染出不同结果 | **变体叠加**：base + overlay 补丁 | 运行时注入单个值 |
| **值怎么表达** | 嵌套 map，**有覆盖优先级** | **patch 操作**（JSON Patch / 战略合并） | 平铺的 key=value |
| **适合"结构性差异"** | ✅ **强**（副本数变了、Service 类型变了、要不要开 HPA） | ⚠️ 弱（改结构要写 patch） | ❌ |
| **适合"打几个补丁"** | ⚠️ 要改 values | ✅ **强**（改副本、加注解、换镜像） | — |
| **类型检查** | ✅ 有 `values.schema.json`（可选） | ❌ | ❌ |
| **版本历史 / 回滚** | ✅ **有 release / revision**（`helm history` / `helm rollback`） | ❌ **没有**（要靠 Git revert + `kubectl apply`） | ❌（靠重新部署） |
| **渲染需要集群吗** | ❌ `helm template` 本地渲染 | ❌ `kubectl kustomize` 本地渲染 | — |
| **CI 里最好用的命令** | `helm template` / `helm diff` | `kubectl diff -k` | `kubectl diff` |
| **最大的坑** | **值覆盖优先级写反**（`--set` > 后面的 `-f` > 前面的 `-f`） | **overlay 叠多了看不懂**，patch 叠出畸形结果 | **散落各处**，难审计；**密钥用 env 容易进镜像层** |
| **本套资料的采用** | ✅ **自研应用首选** | ✅ **改第三方 Chart 时用** | ✅ **应用只读 env 时用（但别放密钥）** |

**三者常常是叠加的，不是互斥的**：

```
Helm template（渲染出结构）
      ↓
Kustomize（对渲染结果打环境补丁）
      ↓
kubectl apply / ArgoCD 同步
```
> **判断用哪个的一句话**：**"我要改的是'值'还是'结构'？"** 改值 → Helm；打补丁（尤其改别人给的） → Kustomize；只是传一个开关/地址 → 环境变量。

### 5.3 分支驱动发布 vs 提交物驱动发布

**这是 GitOps 时代最重要的一个范式转变。**

| 维度 | **分支驱动发布**（Branch-based） | **提交物驱动发布**（Commit-based / Artifact-based） |
|---|---|---|
| **什么触发部署** | **某条分支的 HEAD** | **某个不可变的提交物**（镜像 digest / 版本化 Chart） |
| **部署的是什么** | **分支上的代码状态**（浮动） | **一个确定的内容**（不可变） |
| **"线上跑的是哪版"** | **要查**（分支在动，可能是新提交） | **一眼可见**（引用了哪个 digest） |
| **同一环境能否同时跑两个版本** | 难（要开分支、要合并） | ✅ **天然可以**（两个 digest 指向两套 Deployment）→ **蓝绿/金丝雀的基础** |
| **回滚** | 切分支 / revert 提交 | **换引用回上一个 digest**（更直接） |
| **Git 的角色** | **Git 是发布的事实源**（分支状态即发布状态） | **Git 是声明的事实源**（提交物清单即发布声明） |
| **谁把状态同步到集群** | **人 / CI 脚本**（`kubectl apply`） | **同步器**（ArgoCD 等）：持续比对并纠正 |
| **漂移会怎样** | **没人发现**（实际状态与分支不一致了，也只有人知道） | **同步器发现 OutOfSync → 纠正或告警** |
| **审计** | 靠 Git 历史 + CI 日志 | **Git 里的声明变更记录 + 同步历史** |
| **对人的要求** | 有人执行发布 | **有人维护同步器与告警** |

**同步器的两个关键策略（官方文档标称的语义）**：

| 策略 | 含义 | 关掉的后果 |
|---|---|---|
| **Prune（剪枝）** | 声明里删掉的资源，**同步时一并从集群删除** | 关掉 → **删了不删，集群里堆满僵尸资源**；开着 → **改错声明 = 直接删生产资源**（这是最需要 review 的一道） |
| **SelfHeal（自愈）** | 实际状态与声明不一致时，**自动纠正回声明** | 关掉 → **漂移只会被发现，不会被修正**（要靠人处理） |

> **必须配着看的一件事**：
> **SelfHeal 是"自动纠正"**，意味着**任何人对线上的临时改动都会被改回去**。
> **所以：应急改动必须走"改声明"的正规通道**，否则人改完发现"过一会儿又变回去了"——这不是 bug，是 SelfHeal 在正常工作，但**人会不理解、会试图关掉它**。
>
> **Prune 更危险**：它让"**从 Git 里删一行**"变成"**从生产里删一个服务**"。**这一道必须有强 review 保护。**

> **对本地民企的现实取舍**：
> **提交物驱动的理念（不可变镜像 + 声明式清单 + 引用而非浮动标签）今天就该用**，这部分**零成本**。
> **而"装一个同步器持续纠正"这一层，需要有人管才有意义**——**没人管的同步器会把"我们有 GitOps"变成一个说法**。
> **正确的推进顺序**：先把"不可变 + 引用 digest + 清单进 Git + 保护分支"做实，**同步器作为第二步**。

## 6. 踩坑与排障

| 你看到的（症状） | 状态 | 真实原因 | 怎么修 | 下次怎么防 |
|---|---|---|---|---|
| **各环境配置逐渐分叉，且没人说得清为什么** | 环境行为不一致、线上问题复现不了 | **配置分叉**：改了 dev 没同步 prod，**且分叉理由没被记录**；或每个环境各写各的 YAML | 建**配置矩阵表**（4.1），把差异显式化；把"从文件复制"改成"模板 + 差异值" | 每次改配置**同步更新矩阵**；PR 里加一步"是否需要同步其他环境"的检查项；**CI 里做环境间 diff** |
| **线上实际状态与 Git 里的声明不一致** | 有人 `kubectl edit` 改过，或应急改动没留痕 | **状态漂移**。线上手工改了，但声明没改 | 有同步器 → 会自动纠正（**注意 Prune 的删除风险**）；没同步器 → 手工改回声明并**补一条变更记录** | 应急走受控通道；**禁止把"直接改线上"当常规手段**；开启漂移检测 |
| **密钥出现在 Git 仓库里**（或 values.yaml 里） | 密钥泄漏 | 为了"方便"把 AK/SK 写进 values；或写进 Deployment 的 `env` 后 values 提交进 Git | **立即吊销并轮换该凭据**（**旧凭据必须真的禁用**）；从 Git 历史彻底清除；**所有历史版本里出现过的凭据一律视为已泄漏** | 密钥只进 **Secret / 外部密钥系统**；values 里只放**引用**；加 pre-commit 密钥扫描；**Code review 时把 values 文件当敏感文件对待** |
| **staging 一切正常，上生产就出问题** | 生产故障 | **staging 形同虚设**：① staging 的配置是 dev 复制的；② staging 没接生产依赖链；③ staging 用的是 dev 的 HTTP 而非生产的 HTTPS/真实域名；④ staging 从没被真实访问过 | 逐项对照 1.2 的四维表补齐 staging 的形态；**staging 必须用接近 prod 的 values（只是数据不同）** | **staging 的 values 与 prod 的差异应该被限制在一张白名单里**（只允许数据与副本数不同）；**每次 prod 故障后问一句"为什么 staging 没发现"** |
| **测试环境全过，生产还是失败** | 生产故障 | 差异不在代码，在**环境本身**：配置、数据规模、依赖版本、网络可达性、证书、时区/字符集、并发量 | 列出"测试通过"依赖的**隐含前提**（数据量小、依赖是 mock、并发=1、时区=UTC），逐条在 staging 复现 | **在测试用例里显式声明环境前提**；staging 用**接近生产的并发与数据量**做一轮压测 |
| **想回滚，但不知道该回哪个版本** | 回滚受阻 | ① 用了**浮动 tag**（同一个 tag 覆盖过），**回滚拉回来的不是原来那个东西**；② release 分支上有多条候选；③ 没做过 release 历史管理 | 立刻改成**固定 digest 引用**（生产部署用 `<repo>@sha256:<64位>`）；用 `helm history` / 制品库版本列表**确定目标**再回滚 | **发布产物不可覆盖 + 生产固定 digest**；每次发布记录"版本 → digest → 配置版本"的对应关系；**定期演练回滚** |
| **高危镜像已经躺在仓库里了** | 仓库里存在带 CRITICAL 漏洞的镜像 | **`push` 排在了 `scan` 之前**：先推后扫，扫出来时**镜像已经入库**，任何人拉取即中招 | 把 `push` 移到 `scan` 之后；**清理已入库的不合格镜像**（删 tag 或覆盖为修复版）；排查是否有人已拉取 | **流水线顺序固定为 build → test ∥ scan → push → deploy**；`scan` 与 `push` 之间**禁止** `allow_failure` / `when: always` / `optional: true` |
| **回滚代码后仍然起不来（二次故障）** | 回滚后服务异常 | **只回滚了镜像，没回滚配置**；或 DB schema 已经变了 | 回滚**必须包含配置**；DB 变更走"先兼容后切换"；必要时按预案做数据修复 | **把"配置回滚"写进回滚 runbook**；**发布前确认新旧版本对配置与 schema 的兼容矩阵** |
| **同一个服务在 A 集群正常、B 集群异常** | 部分流量异常 | **多集群配置不一致**：两个集群的 values / Secret 不是同一份；B 集群的 Secret 忘了轮换 | 比对两集群的**实际生效配置**（values + Secret 内容）；统一从**同一份声明**下发 | **一个 Chart + 同一套 values 模板**；**Secret 用外部密钥系统统一管理**（轮换一次全局生效） |
| **蓝绿切换后才发现 green 少配了一个开关** | 切流量瞬间故障 | **两套配置的"对称性"靠人记**，没有结构性保证 | 切流量的**前置检查**：两套配置的 diff 必须只剩"版本相关"的部分 | **蓝绿两套用同一套模板 + 同一套 values，只换版本参数**；**把 diff 检查做成流水线一步** |
| **新同学不知道该配哪些值** | 配置漏配、默认值意外生效 | **配置项没有文档**，或者**默认值在代码里**（不配就默默生效） | values 里写**注释**说明每个键的含义与影响；**关键项用 `required`**（Helm）——**不配直接报错，而不是默默用默认值** | `values.yaml` 注释齐全；**配套 schema 校验**；把 values 当**配置说明书**维护 |
| **多环境流水线里，某环境的镜像和别的环境不是同一个** | 环境行为不一致、门禁结果失效 | ① 各环境构建了各自镜像（**镜像带环境**）；② tag 写死在 values 里被覆盖 | 改为**构建一次 + 同一个 digest 贯穿**；values 里 tag 留空由流水线注入 | CI 里**断言各环境引用的 digest 相同**；**禁止在 values 里写死 tag** |
| **配置在文件里，但改完不生效** | 改了没反应 | ① ConfigMap 变了但 **Pod template 没变 → Pod 不重启**；② 应用不热加载配置；③ 同步器没同步（Prune/SelfHeal 状态不对） | 用 **checksum 注解**触发滚动；或让应用支持热加载；查同步器状态 | **配置变更必须确认"生效路径"**（重启还是热加载）；把"改配置 → 验证生效"做成一条固定动作 |
| **分支合并冲突天天有，发布天天延期** | 日常损耗 | 分支活得太久（GitFlow / 长命 feature 分支）；**主干开发没有配套的门禁** | 缩短分支寿命；**主干开发必须配齐门禁 + 特性开关** | 特性开关 + 门禁齐了，**分支可以短到几小时**；把"分支存活时长"当指标看 |
| **装了 ArgoCD 但漂移依然存在** | 漂移没被纠正 | **没人维护同步器**：OutOfSync 状态没人看；告警没人收；**Prune 关着又没人删僵尸资源** | **先确认有没有人看同步器状态**；没有就先做可见性（矩阵表 + CI diff），同步器放第二步 | **任何需要专人持续维护的机制，引入前先确认那个人存在**；否则它只是一个说法 |

## 8. 自测三问

1. **能说清输入输出吗？** —— **输入**：一份源码 + 一次构建产出的**不可变镜像** + 每个环境的一份**配置**（values + Secret）；**输出**：四个环境上跑着**同一产物**的四个实例集合。**中间**：构建（一次）→ 门禁（[`L3`](L3-质量门禁-SonarQube与Trivy.md)）→ 制品库（不可变引用）→ 按环境注入配置 → 逐环境推进（prod 需审批）→ 持续漂移检测。**"环境差异只允许出现在配置里"是整条链的纪律。**
2. **能故意改坏再倒推吗？** —— 四个具体实验：① 在 `envs/prod.yaml` 里写死一个 `image.tag: prod-v1` → 观察**测试环境测的产物和生产部署的产物不是同一个** → 这就是"门禁全白做"；② **只回滚镜像、不回滚配置** → 观察服务起不来 → 这就是"回滚引发二次故障"；③ 把 staging 的 values 换成 dev 的 → 观察 staging **再也发现不了生产形态的问题**；④ 在生产环境 `kubectl edit` 改一个副本数 → 观察它与 Git 里的声明不一致（**这就是配置漂移的现场**）。
3. **能画上下游吗？** —— 画出「源码 → 构建一次 → **不可变镜像（同一 digest）** → 制品库 → 分环境注入（values / Secret）→ dev → test → staging（**prod 形态**）→ prod（审批）→ 运行时漂移检测 → 回滚路径（**含配置回滚**）」这条链，并标出三处关键分叉：**① digest 是否全环境一致 ② staging 与 prod 的差异白名单 ③ 回滚是否包含配置**。
