# 第 08 天 · Terraform 阿里云起步（P0 卡门槛）

## 一、今日目标（结论先行）
用 Terraform + alicloud provider 把 **VPC + OSS** 代码化，配 OSS 远程 state——这是行业A 硬卡"IaC 精通至少一项"的破局第一天，也是你唯一"零基础却卡门槛"的技能。

## 二、企业真实需求背景
- **行业A（行业A）JD 实锤**："IaC 工程化：精通至少一项 IaC 工具，具备'环境即代码'工程素养"——**硬卡项**。
- **行业B**："多公有云（阿里云/火山/移动）资源运维"——IaC 是多云一致性的唯一解。
- 本地民企现状：Terraform（alicloud provider）是跨云首选；阿里云自有 ROS 会厂商锁定，面试少提。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜为什么民企突然都要 IaC（不是跟风，是被事故逼的）
真实起因通常是这三件事之一：

| 触发事件 | 具体表现 | 老板的结论 |
|---|---|---|
| **环境重建** | 要新建一套预发环境，三个人点控制台点了两天，还漏了安全组规则，联调炸了 | "环境要能一键复制" |
| **配置漂移** | 线上问题排查发现某台 ECS 的安全组被人手改过，谁改的、什么时候改的查不到 | "变更必须可追溯" |
| **多云/多region** | 行业B这类要同时对接阿里云/火山/移动，各家控制台操作逻辑不同 | "用一套代码管多云" |

**面试里的正确切入方式**：不说"我会 Terraform"，说"**我用 IaC 解决了环境重建和配置漂移**"，然后给数字——比如"新环境从 2 天 3 个人降到 12 分钟 1 条命令"。

### 场景 B｜真实事故现场（IaC 的坑比 K8s 更阴，因为它直接动生产资源）
1. **state 文件泄露 = 云端家底泄露**：state 里含资源 ID、部分敏感属性，提交到 Git 或放在本地共享盘，等于把架构图公开。正确：OSS 远程后端 + 加密 + 访问控制，本地 `.tfstate` 加进 `.gitignore`。
2. **两个人同时 apply，资源互相覆盖**：本地 state 没有锁。正确：OSS 后端自动带锁（Terraform ≥0.13 用 OSS 的 lock 机制），团队协作必须用远程后端。
3. **`terraform destroy` 打穿生产**：没区分环境目录，在 prod 目录下敲了 destroy。正确：目录按环境隔离、生产 workspace 加保护（`prevent_destroy`）、CI 里 destroy 需人工二次确认。
4. **provider 版本漂移导致 plan 出现大量莫名变更**：没钉版本，某人 `init -upgrade` 后 provider 从 1.230 跳到新版，属性语义变了。正确：`required_providers` 里钉死版本 + `.terraform.lock.hcl` 提交进 Git。
5. **AK 写进 `.tf` 或 `.tfvars` 提交**：这是等保红线，且等于把云账号交出去。正确：环境变量 / RAM 角色 / CI 的 Masked 变量，代码里一个字都不能有。

### 场景 C｜面试官的真实痛点
- **行业A"精通至少一项 IaC"是硬卡**：面试官会直接问"你写过 state 后端吗？团队怎么避免冲突？"——答不上来就是没真用过。
- 面试官还会追问 **"你有没有误删过生产资源"**。这题的正确答法不是"没有"，而是"我做了什么防护让这件事不可能发生"（目录隔离 + prevent_destroy + 审批）。
- 另一层：他们想知道你是**把 IaC 当脚本用**（`apply` 一把梭），还是**当工程用**（模块、环境隔离、state 管理、CI 流水线）。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| state | 本地 state / 提交 Git | OSS 远程后端 + 加密 + 锁 |
| 鉴权 | AK 写进 .tf | 环境变量 / RAM 角色 / CI 变量 |
| 环境隔离 | 一个目录切 workspace 硬扛 | 目录按 env 分离，变量分文件 |
| 删除保护 | 直接 destroy | `prevent_destroy` + CI 二次确认 |
| 版本 | 不钉 provider 版本 | 钉版本 + 提交 lock 文件 |

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 安装（国内优先）
```bash
# Mac（managed 环境用系统 brew 或官方二进制）
brew tap hashicorp/tap && brew install hashicorp/tfenv && tfenv install 1.9.8
terraform version
# 若 brew 不可达，走官方（坑2：只用官方源，禁第三方镜像假包）
# curl -fsSL https://releases.hashicorp.com/terraform/1.9.8/terraform_1.9.8_darwin_arm64.zip -o tf.zip && unzip tf.zip && mv terraform /usr/local/bin/
```

### 5.2 鉴权（AK 用环境变量，禁写进 .tf）
```bash
export ALICLOUD_ACCESS_KEY="<你的AK>"
export ALICLOUD_SECRET_KEY="<你的SK>"
export ALICLOUD_REGION="cn-hangzhou"
```

### 5.3 写 VPC + OSS（含 OSS 远程 state 后端）
`versions.tf`：
```hcl
terraform {
  required_providers {
    alicloud = { source = "aliyun/alicloud", version = "1.230.0" }
  }
  backend "oss" {
    bucket     = "tf-state-<你的桶>"
    key        = "day8/vpc.tfstate"
    region     = "cn-hangzhou"
    encrypt    = true
  }
}
```
`vpc.tf`：
```hcl
resource "alicloud_vpc" "main" {
  vpc_name   = "devops-vpc"
  cidr_block = "10.0.0.0/16"
}
resource "alicloud_oss_bucket" "logs" {
  bucket = "devops-logs-<唯一后缀>"
}
```
`provider.tf`：
```hcl
provider "alicloud" { region = "cn-hangzhou" }
```

### 5.4 初始化 + 计划 + 应用 + 验证
```bash
terraform init          # 下载 provider + 配置 OSS 后端
terraform plan          # 看变更图（应显示 +2 资源）
terraform apply -auto-approve
# 验证
aliyun vpc DescribeVpcs --RegionId cn-hangzhou --output cols=VpcName,Status
aliyun oss ls oss://devops-logs-<唯一后缀>
```

### 5.5 回滚演练（幂等验证）
```bash
terraform destroy -auto-approve   # 释放资源（练习用，真环境谨慎）
terraform apply -auto-approve     # 再次 apply 应无差异（幂等）
```

## 六、成果验证方式
1. `terraform plan` 输出 `+2` 资源；`terraform apply` 成功，阿里云控制台出现 VPC + OSS 桶。
2. OSS 桶内生成 `day8/vpc.tfstate`（远程 state 生效）。
3. `terraform destroy` 后资源消失；`apply` 幂等无差异。
4. 全程 AK 不出现在任何 `.tf` 文件（用 `grep -r ALICLOUD_SECRET_KEY *.tf` 校验为空）。

## 七、常见坑与排错
- 坑1/2：brew 无公式→`brew tap hashicorp/tap`；国内假包→只用 `releases.hashicorp.com`。
- 坑10：State 泄露/冲突→OSS 远程后端 + 锁，AK 用环境变量不写 `.tf`。
- 坑3/12：终端连 GitHub 超时→`export https_proxy=127.0.0.1:7897`。
- `provider 版本 pinning`：生产须钉死 `version` 避免破坏性升级。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：你 IaC 到什么程度？（坦诚 + 有实证，别吹）
> "Terraform 是我这轮系统性补的，现在能独立做到这个程度：用 alicloud provider 把 VPC、交换机、安全组、OSS、ACK 节点池代码化，state 放 OSS 远程后端并开加密，provider 版本钉死、lock 文件进 Git，AK 走环境变量不进代码。`plan` 出来先看变更再 `apply`，练习环境跑完就 `destroy` 控成本。
> 我在上一个项目用的是 Ansible 做配置管理和批量变更，那是'配置即代码'；Terraform 是'资源即代码'，两者我分得清——Ansible 管机器里的状态，Terraform 管云上有什么资源。现在我把资源层这块补上了。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| state 是干什么的？为什么不能提交 Git？ | "state 是 Terraform 记录'代码里的资源'和'云上真实资源 ID'的映射表，没有它下次 plan 就不知道谁是谁。它里面有资源 ID 和部分属性，提交到 Git 等于公开架构，而且多人本地 state 会互相覆盖，所以必须放远程后端加锁。" |
| 团队多人怎么避免冲突？ | "远程后端自带锁，一个人 apply 时另一个人会被 block。再配合目录按环境分离、CI 里统一执行（不让人在本地 apply 生产），基本不会冲突。" |
| 怎么防止误删生产？ | "三层：目录按 env 分开，prod 的 state 和 dev 完全隔离；关键资源加 `prevent_destroy`；CI 里 destroy 属于高危任务，要人工二次确认才放行。" |
| Terraform 和 Ansible 什么区别？ | "Terraform 管'资源存在不存在'，声明式、有 state、幂等；Ansible 管'机器里面配成什么样'，过程式、无 state。生产上我一般是 Terraform 建机器，Ansible 配机器内容，中间用动态 inventory 接起来。" |
| 为什么不用阿里云 ROS？ | "ROS 是阿里云原生的，跟阿里云绑得深，但跨云就废了。行业B这种多云场景必须用 Terraform，一套 HCL 配不同 provider。ROS 我会用，但不作为首选。" |
| IaC 和 GitOps 什么关系？ | "IaC 是'基础设施用代码描述'，GitOps 是'用 Git 作为唯一事实源、由控制器自动同步'。Terraform 是 IaC，ArgoCD 是 GitOps；Terraform 管集群外资源，ArgoCD 管集群内工作负载，两者配合才是完整闭环。" |

### 数字锚点
`plan → apply → destroy 全流程`｜`OSS 远程 state + 加密`｜`provider 钉版 1.230`｜`AK 零进入代码`
