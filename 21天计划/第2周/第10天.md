# 第 10 天 · ArgoCD 安装与同步（P1）

## 一、今日目标（结论先行）
在 kind 部署 ArgoCD，对接 Git 仓库，把 D6 的 Helm Chart 用 **GitOps 声明式同步** 部署——中高端 岗区分"传统运维"的关键词，企业常用 ArgoCD + 钉钉通知。

## 二、企业真实需求背景
- **行业B**："配置一致性、一键回滚"——传统 Jenkins 命令式易漂移。
- **行业A**："熟练掌握 ArgoCD" 明确写在任职要求。
- 本地民企现实：ArgoCD（Pull 模型、K8s 原生）是 GitOps 主流；变更走 Git PR Review，集群自动同步，钉钉发同步结果。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜Push 和 Pull 的差别，决定了半夜三点谁被叫醒
| 维度 | Jenkins/Kubectl push（命令式） | ArgoCD pull（GitOps） |
|---|---|---|
| 谁有集群凭证 | CI 服务器持有 kubeconfig，权限大 | 集群内的 ArgoCD 拉取，CI 不需要集群权限 |
| 集群被手改后 | 没人知道，漂移长期存在 | 控制器持续对比，SelfHeal 自动还原 |
| 回滚怎么做 | 重跑旧流水线，可能重建错版本 | `git revert` 或选历史 revision，一键同步 |
| 谁改了什么 | CI 日志（易丢） | Git commit 历史（永久、可审计） |
| 生产发布审计 | 靠日志拼凑 | Git PR + 审批记录，等保直接可用 |

**这就是行业A 把 ArgoCD 写进任职要求的原因**：不是因为它新，是因为**合规审计要"变更有记录"**，Git 天然满足。

### 场景 B｜真实事故现场
1. **同步一直 `OutOfSync` 但不知道差在哪**：repo URL/分支/path 写错，或 `targetRevision` 指的分支没这个目录。排查：`argocd app diff myapp` 直接看差异，比猜快十倍。
2. **开了 SelfHeal，运维半夜改的东西被还原，故障扩大**：SelfHeal 是"以 Git 为准"，手改必然被覆盖。正确：紧急热修也要走 Git（哪怕是快速 PR），或临时关 SelfHeal 并在事后补提交——**关之前必须记录，否则事后没人知道集群被手改过**。
3. **开了 Prune，Git 里删了个资源，集群里连带删了数据库**：Prune 会删掉 Git 中不存在的资源。正确：对关键资源加 `argocd.argoproj.io/sync-options: Prune=false` 注解，或按 App 粒度控制。
4. **ArgoCD 拉不到私有 Git 仓库**：没配 repo 凭证。正确：`argocd repo add ... --username --password`，或用 Deploy Key。
5. **同步成功但 Pod 没起来**：ArgoCD 只看 K8s 资源是否 apply 成功，`Synced` 不等于业务健康，要看 `Healthy`。正确：配 readinessProbe，看 `argocd app get` 的 HEALTH 状态。

### 场景 C｜面试官的真实痛点
面试官关心：**① 你是真跑过 GitOps，还是只知道概念；② 出了事故（手改被还原 / Prune 误删）你怎么处置；③ CI 和 CD 的边界你怎么划**。第三问最见水平——正确答案是"CI 负责构建制品并更新 Git 里的镜像 tag，CD 由 ArgoCD 拉取，CI 不碰集群"。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 集群凭证 | 放在 CI 里 | 只给 ArgoCD，CI 无集群权限 |
| 变更入口 | 有人 `kubectl edit` 热修 | 一律走 Git PR，热修事后必须补提交 |
| 危险操作 | Prune/SelfHeal 全局开 | 按 App 控制，关键资源加 `Prune=false` |
| 发布判定 | `Synced` 就算成功 | 看 `Healthy` + 就绪探针 |
| 回滚 | 重跑流水线 | `git revert` 或 `argocd app rollback` |

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 安装 ArgoCD（kind 本地）
```bash
# 镜像若拉不动先 export https_proxy=127.0.0.1:7897 或 kind load quay.io 镜像
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl rollout status deployment/argocd-server -n argocd --timeout=180s

# 暴露端口（本地访问 UI）
kubectl port-forward svc/argocd-server -n argocd 8080:443 &
# 取初始密码
argocd admin initial-password -n argocd
```

### 5.2 CLI 登录 + 建 Application（对接 Git + Helm）
```bash
argocd login localhost:8080 --username admin --password <上一步密码>
argocd cluster add kind-day2           # 把 kind 集群注册进 ArgoCD（先 kind create cluster --name day2）
argocd app create myapp \
  --repo https://jihulab.com/<你>/devops-journey.git \
  --path week1/myapp \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace demo \
  --helm-set image.tag=go-v1 \
  --sync-policy automated
argocd app get myapp
argocd app sync myapp
```

### 5.3 验证自动同步
```bash
# 改 Git 里的 values（如 replicaCount: 3）→ push
git commit -am "bump replicas" && git push
# 观察 ArgoCD 自动检测并同步
argocd app wait myapp --health
kubectl get pods -n demo        # 副本数应随 Git 变化
```

### 5.4 钉钉通知（可选）
ArgoCD 通过 `argocd-notifications` 配置钉钉 webhook；或在 Application 上挂 webhook 触发 CI 通知。

## 六、成果验证方式
1. `kubectl get pods -n argocd` 全部 Running；`argocd login` 成功。
2. `argocd app get myapp` 显示 `HEALTHY/SYNCED`。
3. 改 Git 值 push 后，`argocd app wait myapp` 自动同步，集群副本数变化。
4. `argocd app history myapp` 显示同步版本。

## 七、常见坑与排错
- 同步卡 OutOfSync→查 repo URL/分支/path/RBAC。
- ArgoCD 镜像来自 quay.io/ghcr，kind 本地需 proxy 或 kind load。
- SelfHeal 会还原手动改；热修须走 Git。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：GitOps 你怎么理解？CI 和 CD 的边界在哪？（区分水平的核心题）
> "GitOps 我的理解是一句话：**Git 是集群状态的唯一事实源，任何变更都必须先在 Git 里体现**。四个要素：声明式描述、版本控制、控制器自动拉取、持续对比纠偏。
> 举个具体分工：CI 负责构建镜像、扫描、把新 tag 写回 Git 的 values 文件，**它不需要集群凭证**；ArgoCD 在集群内监听 Git，检测到变更就同步，同时持续对比实际状态和期望状态，发现漂移就 SelfHeal 拉回来。
> 这样最大的好处是两件事：一是权限收敛，CI 拿不到集群凭证，被攻破也炸不了生产；二是审计天然合规，谁在什么时候改了什么，Git 历史清清楚楚，等保查变更直接导 commit 记录，不用拼日志。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| Auto-sync、SelfHeal、Prune 分别是什么？ | "Auto-sync 是 Git 变了自动同步；SelfHeal 是集群被手改后自动改回 Git 的样子；Prune 是 Git 里删掉的资源在集群里也删掉。前两个基本必开，Prune 要谨慎——它真的会删东西，关键资源我会加 `Prune=false` 注解。" |
| 开了 SelfHeal，运维紧急热修怎么办？ | "两条路：正规做法是走快速 PR，几分钟也能合；实在紧急就先 `argocd app set --sync-policy none` 暂停自动同步，手工改，**同时立刻记录并补 PR**，改完恢复。绝对不能悄悄改完不管，那样下次同步会覆盖，故障二次发生。" |
| 同步一直 OutOfSync 怎么查？ | "先 `argocd app diff` 看差异，再看 repo/分支/path 是否对得上，最后看 RBAC 有没有权限。90% 是 path 指错目录或者 targetRevision 分支不对。" |
| ArgoCD 和 FluxCD 怎么选？ | "ArgoCD 有 UI、多集群管理成熟、社区大，民企用得多；Flux 更轻、更贴近 GitOps 原教旨，资源占用小。我选 ArgoCD 主要是因为运维和研发都能看 UI，推广成本低。" |
| ArgoCD 挂了会不会影响业务？ | "不会。它是控制器，挂了只是停止同步，运行中的 Pod 不受影响，恢复后自动追上。真正要防的是它误操作，所以 Prune 和 SelfHeal 的策略要按应用分级。" |
| 和 Helm 什么关系？ | "互补。Helm 负责把 values 渲染成清单，ArgoCD 负责把清单同步到集群并持续纠偏。Helm 管'长什么样'，ArgoCD 管'保不保持这个样子'。" |

### 数字锚点
`Git = 唯一事实源`｜`CI 无集群凭证`｜`Synced ≠ Healthy`｜`Prune 需分级`

### 禁忌
- ✗ "GitOps 就是 CI 里 kubectl apply" —— 那是 push 模式，恰好是 GitOps 的反面。
- ✗ 说不清 SelfHeal 与 Prune 区别 —— 说明没真开过这两个开关。
- ✗ 说"回滚就是重跑流水线" —— GitOps 下回滚是 Git revert。
