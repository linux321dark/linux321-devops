# 第 12 天 · Prometheus + PromQL（P1）

## 一、今日目标（结论先行）
部署 Prometheus + Node Exporter，用 **PromQL 查 CPU/内存/QPS**，配 Alertmanager 钉钉告警——对应行业B"Prometheus、夜莺"和行业A"Prometheus+Grafana+ELK/Loki"。

## 二、企业真实需求背景
- **行业B JD 实锤**："熟练使用 Prometheus、**夜莺(Nightingale)** 等监控告警平台"——夜莺是本地/国内民企常用，常与 Prom 并存。
- **行业A**："熟悉 Prometheus + Grafana + ELK/Loki"。
- 你已有 Zabbix+Prom 基础，今日补 PromQL 深度与告警治理。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜为什么容器化之后必须换监控（这是你不换就会被淘汰的点）
| 维度 | Zabbix（你熟的） | Prometheus（云原生） |
|---|---|---|
| 采集模式 | 服务端推/主动拉固定 IP 列表 | 目标发现（K8s SD）自动发现新 Pod |
| 实例会变吗 | 主机固定，IP 不变 | Pod 随时重建、IP 天天变 |
| 指标类型 | 数值型为主 | 支持 histogram/summary，能做 P99 分位 |
| 适合对象 | 主机、网络设备、中间件 | 容器、K8s 对象、微服务、业务指标 |
| 告警治理 | 触发器 + 依赖 | Alertmanager 分组/抑制/静默 |

**结论**：Zabbix 不是被淘汰，是**边界收缩到主机与硬件层**。企业的真实形态是"Zabbix 看主机 + Prometheus 看容器 + 夜莺统一告警治理"三件套并存。你如果只会 Zabbix，面试官会认为你只懂传统运维。

### 场景 B｜真实事故现场（监控的坑一半在指标，一半在告警）
1. **TSDB 爆盘**：给每个请求打上 `user_id` 标签，指标基数爆炸，一天写 200GB。正确：**label 只能是低基数维度**（service、endpoint、status、method），用户 ID、订单号、URL 全路径绝对不能进标签。
2. **告警风暴，手机一晚上 300 条**：一个交换机故障触发 200 个实例告警。正确：Alertmanager 的 `group_by` 收敛同类、`inhibit_rules` 抑制衍生告警（主机 down 时抑制其上所有服务告警）、`repeat_interval` 拉长重复间隔。
3. **告警没人看，因为全是误报**：阈值拍脑袋（CPU>80% 就告警），而业务高峰常年 85%。正确：阈值来自历史分位数（P95/P99 的 1.2 倍），且区分"业务时段/非业务时段"。
4. **告警了但不知道影响谁**：告警只写"CPU 高"，没写服务名、没写影响面。正确：告警注解里必须有 `summary`（是什么）+ `description`（影响谁、怎么办）+ `runbook_url`（怎么处理）。
5. **P99 算出来是错的**：直接对 histogram 的 bucket 求平均。正确：必须用 `histogram_quantile(0.99, rate(..._bucket[5m]))`，且 bucket 的边界要覆盖真实延迟范围。

### 场景 C｜面试官的真实痛点
面试官问三句：**① 你们的 SLI 是什么（不是"CPU 高不高"，是"用户感不感觉得到慢"）；② 告警风暴怎么治理；③ 指标基数怎么控**。第三问是资深与初级的硬分界线——只有真管过 Prometheus 的人，才知道 cardinality 会杀人。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 指标设计 | 高基数 label（user_id/order_id） | 低基数：service/status/method |
| 告警阈值 | 拍脑袋 80% | 历史 P95 × 1.2，分时段 |
| 告警内容 | 只写"CPU 高" | summary + description + runbook |
| 告警治理 | 全推一个群 | 按 severity 分级路由 + 抑制规则 |
| 延迟指标 | 平均响应时间 | P95/P99（平均值掩盖长尾） |

- **原理**：拉模型定时 scrape `/metrics`；TSDB 存储；Recording/Alerting Rule。
- **理论**：RED（Rate/Errors/Duration）/USE（Util/Sat/Err）；SLO/SLI。

- **横向对比**：Prometheus（云原生标准，拉）vs Zabbix（推/主机向，你熟）vs 夜莺（告警治理+可视化，本地常用）vs VictoriaMetrics（高性能）。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 部署 kube-prometheus-stack（kind）
```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
# 镜像若拉不动，先 export https_proxy 或预拉镜像；用 aliyun 镜像覆盖：
helm install prom prometheus-community/kube-prometheus-stack -n monitoring --create-namespace \
  --set prometheus.prometheusSpec.image.registry=registry.cn-hangzhou.aliyuncs.com \
  --set prometheus.prometheusSpec.image.repository=google_containers/prometheus
kubectl rollout status deployment/prom-kube-prometheus-stack-prometheus -n monitoring --timeout=180s
```

### 5.2 端口转发 + 写 PromQL
```bash
kubectl port-forward svc/prom-kube-prometheus-stack-prometheus -n monitoring 9090:9090 &
```
在 `http://localhost:9090` 执行：
```promql
# 节点 CPU 使用率
100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
# Pod 内存使用
sum by(pod)(container_memory_working_set_bytes{namespace="demo"})
# 请求率（若有 http 指标）
rate(http_requests_total[5m])
# P99 延迟
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
```

### 5.3 Alertmanager 钉钉告警
`alertmanager-config.yaml`：
```yaml
route:
  receiver: dingtalk
  group_by: [alertname]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 1h
receivers:
- name: dingtalk
  webhook_configs:
  - url: https://oapi.dingtalk.com/robot/send?access_token=<token>
```
在 PrometheusRule 里加告警：
```yaml
- alert: HighCpuUsage
  expr: 100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]))*100) > 80
  for: 5m
  labels: { severity: warning }
  annotations: { summary: "节点 CPU > 80%" }
```

## 六、成果验证方式
1. `kubectl get pods -n monitoring` 全 Running；`localhost:9090` 能查到 `up` 指标。
2. 三条 PromQL 均返回数据（CPU/内存/请求率）。
3. 手动触发 HighCpuUsage（造 CPU 负载）→ Alertmanager 经钉钉机器人推送告警。
4. 告警风暴测试：同时触发多个→验证 group/抑制生效（不刷屏）。

## 七、常见坑与排错
- label 爆炸致 TSDB 爆盘→合理 cardinality。
- 告警风暴须分组抑制；镜像源用阿里云 registry。
- kube-prometheus Operator CRD 多，卸载用 `helm uninstall` + 清 CRD。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：说一下你的监控体系怎么设计的（50–70 秒逐字稿）
> "我按三层设计。
> **第一层是指标来源**：主机和硬件继续用 Zabbix，因为主机是固定的；容器和微服务用 Prometheus，靠 K8s 服务发现自动跟上 Pod 的变化，node-exporter、cadvisor、kube-state-metrics 三个 exporter 分别看主机、容器、K8s 对象状态。
> **第二层是告警口径**：我不看 CPU 高不高，我看 SLI——请求成功率、P99 延迟、错误率。这些才是用户能感知的。指标用 RED 和 USE 两套框架定，告警阈值从历史 P95 的 1.2 倍来，不拍脑袋。
> **第三层是告警治理**：Alertmanager 做分组和抑制，主机 down 的时候抑制它上面所有服务的衍生告警，同一类告警 5 分钟内只推一次；告警内容必须带 summary、影响面和处理手册链接，否则运维看到也不知道干什么。
> 这样做的结果是告警量从每天几百条降到十几条，而且每条都能对应到用户影响。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 拉模型会不会漏采？ | "拉模型靠服务发现，目标消失就不采了，符合容器场景；如果目标存在但 scrape 失败会有 `up=0` 指标，本身就是一个告警项。相比推模型，拉模型天然能反映'服务死了'这件事。" |
| 指标基数怎么控？ | "核心原则：label 必须是低基数枚举。service、status、method、endpoint 可以，user_id、order_id、完整 URL 绝对不能。高基数我一般用日志或 trace 去查，不放进指标。曾见过有人把 URL 全路径当 label，一天写了 200G。" |
| 告警风暴怎么处理？ | "三个手段：`group_by` 把同类合成一条；`inhibit_rules` 做抑制，上游故障时抑制下游衍生告警；`repeat_interval` 控制重复推送。再配 severity 分级路由——P0 打电话、P1 钉钉群、P2 进日报。" |
| P99 怎么算？ | "`histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))`，注意 bucket 边界要覆盖真实区间，不然分位数插值不准。summary 类型的可以直接 `quantile`，但跨实例没法聚合。" |
| 为什么还要夜莺？ | "Prometheus 自带告警能力弱，Alertmanager 配置分散、多集群不好统一管。夜莺在告警治理上更强——统一告警规则、统一分派、有 UI 和值班表，还能做告警聚合和升级。所以国内很多公司是 Prometheus 采集 + 夜莺告警，行业B JD 里两个都写就是这个原因。" |
| 监控和日志怎么分工？ | "指标回答'有没有问题'（低成本、长期存储），日志回答'为什么有问题'（高成本、短期存储），trace 回答'问题在哪一环'。我的顺序是先看指标发现异常，再用 trace 定位链路，最后查日志找根因。" |

### 数字锚点
`三层监控`｜`RED + USE`｜`阈值 = P95×1.2`｜`告警 每天几百 → 十几条`｜`P99 用 histogram_quantile`

### 禁忌
- ✗ "CPU 超过 80% 就告警" —— 没有 SLI 思维，停留在主机监控。
- ✗ "指标越多越好" —— 暴露不懂 cardinality。
- ✗ 说平均值当延迟指标 —— 掩盖长尾，资深面试官会立刻反问 P99。
