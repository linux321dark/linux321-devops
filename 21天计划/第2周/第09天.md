# 第 09 天 · Terraform 模块化（P0）

## 一、今日目标（结论先行）
把昨日 `.tf` 封装成 **Module + 多环境 variables/outputs**，并短跑验证 ACK（练完立即释放，控成本）——对标行业A"模块化、环境即代码"。

## 二、企业真实需求背景
- **行业A**："环境即代码工程素养"——模块化复用是工程化核心，不是写死一份 `.tf`。
- 本地民企成本现实：ACK 按量贵，短跑练完释放；阿里云按量门槛"余额+代金券≥100元"（坑15），建议充 100 元现金不花。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜模块化到底解决了什么（一张表说清）
一家公司 3 套环境 × 5 个可用区 × 2 朵云，如果不模块化：

| 维度 | 复制粘贴式 `.tf` | 模块化之后 |
|---|---|---|
| 文件数量 | 3 环境 × 每套 200 行 ≈ 600 行高度重复 | 模块 200 行 + 每环境 20 行参数 |
| 加一条安全组规则 | 改 3 处，漏一处就是环境不一致 | 改模块 1 处，全环境生效 |
| 新人搭环境 | 照文档点 2 天，还容易漏 | `terraform apply` 12 分钟，一条命令 |
| 环境一致性 | 靠人自觉 | 靠代码保证，`plan` 可 diff |
| 审计 | "谁改的？"查不到 | Git 提交记录即变更记录 |

**行业A JD 写"环境即代码工程素养"，翻译过来就是这张表**——他要的是"新人能复刻环境"和"改一处全生效"，不是"会写 `.tf`"。

### 场景 B｜真实事故现场
1. **模块 `source` 指向 Git 分支，某天全环境同时变**：有人改了 master 上的模块，所有人下次 `init` 都拉最新，dev/prod 一起漂。正确：`source` 钉 **tag 或 commit SHA**，升级是显式动作。
2. **dev 和 prod 共用一个 state**：`apply` dev 的变更把 prod 的资源也纳管了，或者 `destroy` 连带删掉。正确：每环境独立后端路径（`key = "env/dev/terraform.tfstate"`）。
3. **模块输出没定义，上游拿不到值**：子模块建了 vswitch 但没 `output`，根模块里 `module.vpc.vswitch_id` 报错。正确：模块的三件套是"输入变量 + 资源 + 输出值"，缺一不可。
4. **变量没写 `type`，传错类型静默通过**：`cidr = 10.0.0.0/16`（没引号）被当成别的类型。正确：所有变量必须声明 `type` 和 `description`，关键变量加 `validation`。
5. **ACK 短跑忘了 destroy，账单突然多几百**：ACK 管理费 + 节点 ECS + SLB + NAT 都在计费。正确：练完立即 `destroy`，并在 `terraform plan` 后先看一遍资源清单预估费用。

### 场景 C｜面试官的真实痛点
面试官会问三句：**① 你的模块怎么划分的？（按网络/计算/存储，还是按业务）② 环境差异怎么处理？（变量 vs 目录 vs workspace）③ 模块升级怎么不炸？** 第三问最能筛人——因为模块升级炸过一次的人，一定会说"钉版本"。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 模块划分 | 一个模块包所有资源 | 按网络/计算/存储/中间件分层，单模块职责单一 |
| 环境差异 | 复制目录改值 | 同模块 + 每环境独立变量文件与 state |
| 模块引用 | `source = "git::...?ref=main"` | 钉 `ref=v1.2.0` 或 commit SHA |
| 变量 | 不写 type | `type` + `description` + 关键项 `validation` |
| 输出 | 不定义 output | 每个模块导出被上游引用的值 |

- **原理**：Module = 输入(variables)→资源→输出(outputs)；`module "xxx" { source=... }` 引用。
- **理论**：DRY；环境参数化；状态隔离（每环境独立 state）。
- **核心易忘点**：`variable "xxx" { type=... default=... }`；`output` 导出；`terraform workspace` 或目录分环境。
- **横向对比**：单文件 `.tf`（你昨天）vs Module（工程化，今日）vs Terragrunt（多层编排）。
- **常见问题**：state 冲突→每环境独立后端；module 版本→`source` 钉 git tag；ACK 费用→短跑释放（坑15）。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 抽 Module（vpc / oss）
```bash
mkdir -p modules/vpc modules/oss
cat > modules/vpc/main.tf <<'EOF'
variable "cidr" { type = string }
variable "name" { type = string }
resource "alicloud_vpc" "this" {
  vpc_name   = var.name
  cidr_block = var.cidr
}
output "vpc_id" { value = alicloud_vpc.this.id }
EOF
cat > modules/oss/main.tf <<'EOF'
variable "bucket" { type = string }
resource "alicloud_oss_bucket" "this" { bucket = var.bucket }
output "bucket" { value = alicloud_oss_bucket.this.bucket }
EOF
```

### 5.2 多环境组合（dev / prod）
`dev.tf`：
```hcl
module "vpc"  { source = "./modules/vpc"  cidr = "10.0.0.0/16"  name = "dev-vpc" }
module "oss"  { source = "./modules/oss"  bucket = "devops-logs-dev" }
```
`prod.tf`：
```hcl
module "vpc"  { source = "./modules/vpc"  cidr = "10.1.0.0/16"  name = "prod-vpc" }
module "oss"  { source = "./modules/oss"  bucket = "devops-logs-prod" }
```

### 5.3 短跑 ACK（验证 K8s 集群可被 IaC 拉起，练完释放）
`ack.tf`：
```hcl
resource "alicloud_cs_managed_kubernetes" "demo" {
  name_prefix = "devops-"
  cluster_spec = "ack.pro.small"
  worker_vswitch_ids = [alicloud_vswitch.this.id]   # 需先有 vswitch
  worker_number = 2
  worker_instance_types = ["ecs.g6.large"]
}
```
```bash
terraform init && terraform plan -out dev.tfplan
terraform apply dev.tfplan
# 验证集群
aliyun cs DescribeClustersV1 --output cols=name,state
```

### 5.4 立即释放（控成本）
```bash
terraform destroy -auto-approve        # 释放 ACK + VPC + OSS，避免按量扣费
```
> 坑15：ACK 按量余额门槛，短跑练完必 `destroy`；**工行代金券严禁用于个人 ACK**。

## 六、成果验证方式
1. `terraform apply dev.tfplan` 成功创建 VPC + OSS；`terraform output` 打印 vpc_id/bucket。
2. ACK 集群 `DescribeClustersV1` 返回 `running`（短跑验证）。
3. `terraform destroy` 后资源全部消失，控制台无残留（成本可控）。
4. `prod.tf` 用不同 cidr/name 能独立 apply（环境参数化）。

## 七、常见坑与排错
- 坑15：ACK 按量余额门槛，短跑练完必 `destroy`；工行代金券禁用于个人 ACK。
- state 每环境独立后端，避免互相覆盖。
- module `source` 钉 git tag 而非 branch，避免漂移。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：你的 Terraform 模块怎么设计和管理的？
> "我按资源层次拆，一个模块只管一类东西：网络模块管 VPC/交换机/安全组，存储模块管 OSS 和 NAS，计算模块管 ECS 或 ACK 节点池。
> 每个模块是三件套：输入变量、资源、输出。变量必须声明 `type` 和 `description`，关键项加校验，比如 CIDR 格式不对在 plan 阶段就报错，而不是等到 apply 失败。
> 环境差异不复制模块，用同一模块加不同变量文件，dev 和 prod 各用独立 state 后端路径，互不干扰。模块引用钉 tag 不钉分支——这点我特别较真，因为分支一改，全公司环境同时漂移。新人拿这套东西，改变量就能拉起一套完整环境。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 模块怎么划分才合理？ | "按生命周期和变更频率分。网络几乎不变、计算经常变、中间件单独管，混在一起会导致改一个小东西 plan 出一堆变更。我用过最糟的一个模块是 800 行包了 VPC 到 RDS 全部，谁都不敢动。" |
| 环境差异用 workspace 还是目录？ | "我选目录分环境。workspace 共享同一份 backend 配置，容易误操作切错 workspace 把生产改了；目录隔离更蠢但更安全，配合不同后端路径，物理上就切不过去。" |
| 模块升级怎么保证不炸？ | "两件事：模块引用钉 tag/commit，升级走 MR 评审；升级前先在 dev apply 一次，看 plan 有没有 unexpected change。重大版本升级我会先在一个非核心环境跑一两周。" |
| 有没有用过 Terragrunt？ | "看过没在主流程用。Terragrunt 解决的是多环境多模块的编排和 backend 生成，规模很大时会省事；但小团队用纯 Terraform 加目录结构就够了，多引入一层反而增加学习成本。" |
| 你怎么控成本？ | "练习环境 apply 完立刻 destroy；生产资源打标签（env/project/owner），每月按标签看账单；ACK 这类按量的东西练完必须释放，管理费加节点费一天就不少。" |

### 数字锚点
`模块三件套（变量/资源/output）`｜`每环境独立 state`｜`source 钉 tag`｜`环境重建 2天→12分钟`

### 禁忌
- ✗ "我用 workspace 切环境" —— 会被追问误操作风险，答不上就是没踩过坑。
- ✗ 模块 `source` 指向 main 分支 —— 资深面试官一眼看出没做过多人协作。
- ✗ 说不出模块划分依据 —— 说明只是照着教程抄过。
