# 第 13 天 · Grafana 大屏 + Loki 日志管道（可观测三支柱收口）

## 一、今日目标（结论先行）
导入集群 Dashboard + 自定义 **QPS/Error 业务面板** + **Promtail→Loki 日志管道打通（LogQL 能从告警直跳日志）**——形成"金融级稳定性"人设的完整可观测闭环。**指标 + 日志两条腿必须同时立住**：12 个 中高端 岗位 JD 里，4 个把"ELK/Loki 日志统一采集"写成硬要求，只做指标会被判"半套可观测"。

## 二、企业真实需求背景
- **行业B**："可观测性能力建设"。**行业AJD 原文**："可观测性：熟悉 Prometheus + Grafana + **ELK/Loki** 等主流可观测性技术栈，具备生产环境排障经验"。
- **DevOps 开发运维岗 JD 原文（原话更硬）**："**必须**熟悉 Elasticsearch/Elastic Stack（ELK/EFK），具备**日志采集、索引生命周期管理及性能调优**能力"——这条是硬门槛，不是加分。
- **某工控企业**："日志统一采集（ELK/Loki）"、"日志统一收集（ELK 或 Loki）"。
- 本地民企现实：Grafana 大屏上墙是运维团队标配；日志侧多用 Loki/ELK，链路用 SkyWalking（Java 微服务）。**今天两条腿都补齐**。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜大屏到底是给谁看的（搞错对象就白做）
同一套数据要做三种视图，**面向对象不同，指标和刷新率完全不同**：

| 看板 | 受众 | 核心内容 | 刷新频率 | 设计要点 |
|---|---|---|---|---|
| 值班大屏（NOC） | 值班运维 | 告警列表、核心服务红绿、当前事件 | 10–30 秒 | 红黄绿三色，5 米外能看清；不追求信息密度 |
| 业务健康看板 | 技术负责人 / 产品 | QPS、错误率、P99 延迟、订单量 | 1 分钟 | 与业务节奏对齐（下单高峰、发版时间打标记） |
| 容量与成本看板 | 运维 / 财务 / FinOps | 节点利用率、请求/核、存储增长、预估月费 | 1 小时 | 趋势线为主，配合资源申请量对比 |
| 发版观察看板 | 研发 / SRE | 发布后 30 分钟内错误率/延迟对比、Pod 重启数 | 10 秒 | 与上一次发布基线对比，判断要不要回滚 |

**面试要说的关键一句**：大屏不是"炫"，是**缩短 MTTR**——值班看到红色 → 点进去直接看到是哪个服务、哪个实例、什么时间开始的 → 拿着链接去找研发。做不做得到这一点，是"做过大屏"和"贴过 JSON"的区别。

### 场景 B｜真实事故现场
1. **面板全空**：PromQL 对但数据源 URL/命名空间填错，或者社区 Dashboard 版本和你的指标名不匹配（kube-state-metrics 大版本改过指标名）。正确：先在 Explore 里跑单条 PromQL 验证，再往面板上贴。
2. **大屏卡死/浏览器崩**：30 个 Panel × 24 小时 × 15 秒采样。正确：长周期用降采样（`rate(...[5m])` 换成 `[1h]`）、限制 Panel 数、关闭自动刷新。
3. **Grafana 成了第二个事故源**：Dashboard 被人在 UI 上改乱，没人知道改了什么。正确：Dashboard JSON 进 Git，用 provisioning 或 Terraform 管，禁止 UI 直接改生产看板。
4. **告警挂在 Panel 上但 Grafana 挂了就没人告警**：Grafana 的告警是"看板内"的，Grafana 自身故障时静默。正确：**生产告警必须走 Prometheus Rule + Alertmanager**，Grafana 只做可视化。这条是硬规矩。
5. **密码/API Key 泄露**：Dashboard JSON 里带了数据源内网地址和 token。正确：导出时脱敏，token 走 secret 管理。

### 场景 C｜面试官的真实痛点
面试官想知道：**① 你做的看板有没有人真的用（还是上线即荒废）；② 你懂不懂可观测三支柱的分工；③ 你的告警入口在哪（Grafana 还是 Alertmanager）**。第三问一问就知道深浅。

### 场景 D｜为什么日志不能靠 `kubectl logs`（这条最容易被面试官抓住）
指标告诉你"错了 3.2%"，日志才告诉你"错在哪一行"。但生产环境用 `kubectl logs` 捞日志，有四个绕不过去的硬问题：

| 问题 | 真实后果 | 正确做法 |
|---|---|---|
| Pod 重建即丢 | Deployment 滚动后旧 Pod 删除，日志一起没了 | 日志必须**落外部存储**（Loki/ES），集群只是生产端 |
| 多副本查不全 | 3 副本，你 `kubectl logs` 只连上 1 个 | 按 label 聚合查询（LogQL `{app="x"}` 天然跨 Pod） |
| 权限过宽 | 给研发 `pods/log` 权限 = 能看所有服务日志，等保不过 | 日志平台按命名空间/租户做权限隔离 |
| 无法回溯时间窗 | 只能看当前容器，`--previous` 只到上一次崩溃 | 集中存储设保留期（7–30 天），支持任意时间窗查询 |

**这就是"日志管道"存在的意义**：不是"方便看日志"，是**在没有 Pod 的时候还能查到日志**。等保三级"安全审计"那条要求"调三个月前的操作记录"，只有集中存储能给出证据。

**Loki 与 ELK 的真实取舍**（面试高频对比题）：

| 维度 | Loki（PLG 栈） | ELK / EFK |
|---|---|---|
| 索引方式 | **只索引 label**，日志正文不建索引 | 全文倒排索引 |
| 存储成本 | 低（约为 ES 的 1/5–1/10） | 高（索引膨胀） |
| 查询能力 | LogQL，按 label 收敛后 grep，**不支持复杂全文检索** | 强全文检索 + 聚合分析 |
| 上手成本 | 低（配置少，和 Grafana 天然一体） | 高（分片/副本/ILM 调优） |
| 适用场景 | K8s 云原生日志、排障为主 | 需要全文检索、合规审计、业务分析 |

**结论口径（可直接背）**：**K8s 集群日志用 Loki 省成本，合规审计与全文检索场景用 ELK**。两边都上时，Loki 承接运维排障，ELK 承接审计留痕——这也正是很多金融客户的实际架构。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 看板来源 | UI 手搭，无版本 | JSON 进 Git，provisioning 部署 |
| 告警入口 | 挂 Grafana Panel 告警 | Prometheus Rule + Alertmanager |
| 面板数量 | 一个看板 30 个 Panel | 按受众拆 3–4 个看板 |
| 数据精度 | 全量高精度 | 长周期降采样，短周期高精度 |
| 日志落地 | `kubectl logs` 现捞 | Promtail/Fluent Bit 采集 → Loki/ES 集中存 |
| 日志 label | 把 traceId、用户 ID 打成 label | label 只放低基数维度（app/pod/ns），高基数进正文 |

- **原理**：Grafana 查 Prometheus 数据源；Panel 用 PromQL；Dashboard JSON 可版本化。Loki 只索引 label，日志正文压缩分块存对象存储/本地盘，查询时按 label 定位分块再 grep。
- **理论**：可观测三支柱（指标 / 日志 / 链路）；SLO 看板；**label 基数（cardinality）控制**——这是 Loki 与 ES 共同的性能命门。
- **核心易忘点**：导入社区 Dashboard ID；自定义 Panel（条形/热力/表格）；变量 `$datasource`/`$namespace`；告警规则挂 Panel。Loki 侧：Promtail 的 `scrape_configs` + `relabel_configs`、LogQL 的 `{label=~"re"}` 筛选与 `|= "关键字"` 过滤、`| json` 解析、`rate()` 日志速率告警。
- **横向对比**：Grafana（开源主流）vs 夜莺（国内一体化）vs 云监控（阿里云原生）；日志侧 Loki（低成本）vs ELK/EFK（强检索）vs ClickHouse 方案（超大规模）。
- **常见问题**：数据源连不上→Prometheus URL/鉴权；面板空→PromQL 时间范围/label；大屏卡→降采样；Loki 查不出→先确认 label 名与实际一致（`{app="x"}` 还是 `{app_kubernetes_io_name="x"}`），再确认时间窗内是否有数据。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 部署 Grafana + 接数据源
```bash
helm install grafana grafana/grafana -n monitoring \
  --set adminPassword=admin --set service.type=ClusterIP
kubectl port-forward svc/grafana -n monitoring 3000:80 &
# 浏览器 http://localhost:3000，加 Prometheus 数据源：http://prom-kube-prometheus-stack-prometheus:9090
```

### 5.2 导入集群 Dashboard
- 在 Grafana → Import，输入社区 ID `3119`（Kubernetes cluster monitoring）或 `6417`（K8s/Spring Boot)，选 Prometheus 数据源。
- 验证 node/pod 级 CPU/内存面板出图。

### 5.3 自定义业务面板
新建 Dashboard，加 Panel：
```promql
# QPS
sum(rate(http_requests_total[1m]))
# 错误率
sum(rate(http_requests_total{status=~"5.."}[1m])) / sum(rate(http_requests_total[1m]))
# P99 延迟
histogram_quantile(0.99, sum by(le)(rate(http_request_duration_seconds_bucket[5m])))
```
加变量：`$namespace` 用 `label_values(kube_namespace_created, namespace)` 实现下拉筛选。

### 5.4 面板挂告警 + 导 JSON
```bash
# 导出 Dashboard JSON 存仓库（版本化）
curl -s -H "Authorization: Bearer <grafana-apikey>" \
  http://localhost:3000/api/dashboards/uid/<uid> > dashboards/business.json
```

### 5.5 日志管道：Loki + Promtail（JD 硬要求项，30 分钟跑通）
```bash
helm repo add grafana https://grafana.github.io/helm-charts && helm repo update
helm install loki grafana/loki-stack -n monitoring \
  --set loki.persistence.enabled=true \
  --set loki.persistence.size=10Gi \
  --set promtail.enabled=true \
  --set grafana.enabled=false          # 复用 5.1 的 Grafana
kubectl get pods -n monitoring -l app=loki
kubectl port-forward svc/loki -n monitoring 3100:3100 &
```
在 Grafana 加 Loki 数据源：`http://loki:3100`，然后 Explore 里跑 LogQL：
```logql
# 1. 按 app 聚合查某服务日志（天然跨所有副本）
{app="myapp"}

# 2. 过滤 + 关键字（|= 包含，|~ 正则，!= 排除）
{namespace="prod"} |= "ERROR" != "healthcheck"

# 3. JSON 日志解析后按字段过滤（应用打 JSON 日志时的标准姿势）
{app="myapp"} | json | level="error" | duration_ms > 1000

# 4. 错误日志速率（可做成告警规则，这才是"日志告警"）
sum by (app) (rate({namespace="prod"} |= "ERROR" [5m]))

# 5. 把 traceId 从日志里提出来，和链路追踪对上
{app="myapp"} | json | line_format "{{.trace_id}} {{.msg}}"
```
**Promtail 采集的关键配置**（确认它抓的是 stdout，不是文件）：
```yaml
scrapeConfigs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs: [{ role: pod }]
    pipeline_stages:
      - docker: {}          # 解析 containerd/docker 的 JSON 日志行
      - json:               # 若应用打 JSON，解析出低基数字段当 label
          expressions:
            level: level
      - labels: [level]     # 只把 level 提成 label，traceId 绝不进 label（基数爆炸）
```
**必须实测的一件事**：删掉一个 Pod 再查它的日志——**还能查到 = 管道通了；查不到 = 还在依赖容器本地日志**。这是"做过日志管道"和"装过 Loki"的分界线。

## 六、成果验证方式
1. `localhost:3000` 能导入集群 Dashboard 并出图。
2. 自定义 QPS/错误率/P99 三个业务 Panel 实时刷新。
3. `$namespace` 变量下拉切换生效。
4. `business.json` 导出并 commit 仓库（可复现）。
5. **Loki 管道验证（硬指标）**：`kubectl delete pod` 删掉一个应用 Pod，等新 Pod 起来后，LogQL `{app="myapp"}` 仍能查到**已删除那个 Pod** 的历史日志（label 里能看到旧 pod 名）——证明日志已脱离容器生命周期。
6. Grafana 里完成一次"指标 → 日志"跳转：业务面板错误率告警里挂上 Loki 查询链接，点进去直接是该时间窗的错误日志。

## 七、常见坑与排错
- 数据源鉴权；PromQL 时间范围；社区 Dashboard 版本错配导致空白。
- Grafana admin 密码默认 `admin/admin` 须改；API key 权限够用。
- **Loki 查不出数据**：① `kubectl logs -n monitoring -l app=promtail` 看采集是否报错；② `curl localhost:3100/loki/api/v1/labels` 看 label 到底叫什么（Helm 版常是 `app_kubernetes_io_name` 而非 `app`）；③ 确认 Pod 日志确实打到 stdout 而不是文件。
- **label 基数爆炸导致 Loki OOM**：把 traceId、requestId、userId、完整 URL 打成 label 是头号杀手。规则：label 只放**取值有限**的维度（app / namespace / pod / level），高基数字段留在正文用 `| json` 现场解析。
- **日志盘写满节点**：Loki 默认存本地，必须设 persistence + retention（`limits_config.retention_period`），否则节点磁盘会被日志吃掉，反过来导致集群故障。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：你的可视化体系怎么做的？（50 秒）
> "我不做一个大而全的看板，我按受众拆四类：值班看的是告警和红绿灯，要 5 米外看清、30 秒刷新；技术负责人看业务健康，QPS、错误率、P99，还要在时间轴上标出发布点和营销活动；运维和财务看容量成本，节点利用率、每核承载请求数、存储增长趋势；研发看发版观察，发布后 30 分钟内和上次基线对比，决定要不要回滚。
> 底层数据全来自 Prometheus，Dashboard 的 JSON 进 Git 用 provisioning 部署，不允许在 UI 上直接改生产看板。
> 一个硬规矩：**Grafana 只做可视化，告警一律走 Prometheus Rule + Alertmanager**。因为 Grafana 自己挂了的时候，挂在它上面的告警是静默的——这是最危险的单点。"

### 主问 2：日志是怎么收集和查询的？为什么不用 ELK？（JD 出现率最高的可观测题）
> "日志走的是 **Promtail 采集 → Loki 存储 → Grafana 查询**这条链。采集端用 DaemonSet 常驻每个节点，抓容器的 stdout，集群里不需要任何 SDK 改造，应用只负责把日志打到标准输出。存储端 Loki **只索引 label、不索引正文**，所以存储成本大概是 ES 的五分之一到十分之一——同样 30 天保留期，ES 要几十 T，Loki 几 T 就够。
> 查询用 LogQL，先按 label 收敛（app、namespace、level），再用 `|=` 做关键字过滤。排障路径是：指标告警告诉我哪个服务错了 → 点进来直接是该时间窗该服务的日志 → 需要链路再跳到 traceId。
> **为什么不用 ELK**：不是不用，是分场景。Loki 适合 K8s 排障，成本低、和 Grafana 一体；但**合规审计和全文检索必须 ELK**——等保三级要调三个月前的操作记录、要做全文审计检索，那个场景 Loki 顶不住。所以我在金融项目里是 ELK 承接审计留痕、Loki 承接运维排障，两边各管一段。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| 为什么告警不挂 Grafana？ | "Grafana 的告警依赖 Grafana 服务本身活着，它挂了告警就没了，等于监控把自己变成了单点。Alertmanager 独立部署、独立告警通道，Grafana 只负责看。" |
| 面板数据为空怎么排查？ | "三步：Explore 里单独跑 PromQL 看有没有数据；确认时间范围和 step；再确认 Dashboard 变量和实际 label 对得上。社区 Dashboard 最常见的问题是 kube-state-metrics 大版本改了指标名。" |
| 大屏卡怎么优化？ | "降采样、减 Panel 数量、关自动刷新、长周期用 Recording Rule 预计算。Recording Rule 是最有效的——把复杂 PromQL 提前算好存成新指标，查的时候直接读。" |
| 可观测三支柱你怎么分工？ | "指标看'有没有问题'，成本低能长期存；日志看'为什么'，成本高留 7–30 天；链路看'哪一环'，采样存储。排障顺序是异常指标 → 链路定位 → 日志找根因。" |
| 怎么让大屏真的有人用？ | "两个动作：一是把大屏链接放进告警通知里，收到告警点进去就是现场，养成习惯；二是每月清理没人看的面板。上线没人用的大屏，基本是因为它回答不了值班当下最想问的那个问题。" |
| 日志量大怎么控成本？ | "三刀：① label 严格控基数，高基数字段绝不进 label；② 分级保留——ERROR 留 30 天、INFO 留 7 天、DEBUG 默认不打；③ 采样，高频重复日志（比如每请求一条的 access log）改用指标聚合，不进日志。" |
| Pod 删了日志还能查到吗？ | "能，这是日志管道的验收标准。日志在采集端就写进 Loki 了，和容器生命周期无关。我验收时固定做一步：删 Pod 再查历史日志，查得到才算通。" |
| ELK 的索引生命周期管理是什么？ | "ILM 是按时间把索引分成 hot/warm/cold/delete 四个阶段，自动滚动、降副本、迁冷存储、到期删除。不做 ILM，ES 的索引会无限膨胀直到集群撑爆——这就是 JD 里写'索引生命周期管理'的原因。" |

### 数字锚点
`四类看板`｜`告警走 Alertmanager`｜`Dashboard JSON 进 Git`｜`发版观察 30 分钟对比`｜`Loki 存储约为 ES 的 1/5–1/10`｜`日志保留 ERROR 30 天 / INFO 7 天`｜`label 只放 app/ns/pod/level`
