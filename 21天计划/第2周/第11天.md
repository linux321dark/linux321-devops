# 第 11 天 · ArgoCD 策略（漂移 / SelfHeal / Prune）

## 一、今日目标（结论先行）
演示 **漂移检测 + SelfHeal 自动还原 + Prune 清理孤儿资源**，并把策略固化成面试可讲的标准——对应行业B"稳定性体系"和行业A"多环境一致性"。

## 二、企业真实需求背景
- **行业B**："故障治理、告警治理"——漂移就是隐性故障源。
- **行业A**："多环境一致性"——SelfHeal 保证集群==Git。
- 本地民企合规：等保要求"变更可追溯"，GitOps 的 PR 留痕天然满足。

## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜漂移不是理论问题，它每天都在发生
本地民企一个百级应用的集群，漂移来源几乎全部是这五类：

| 漂移来源 | 典型动作 | 造成的后果 | GitOps 之后 |
|---|---|---|---|
| 排障热修 | 半夜 `kubectl edit` 改副本/镜像 | 修完忘了改回，配置长期偏离 | 下次同步自动还原，**热修必须进 Git 才留得住** |
| 扩容应急 | 手工 `kubectl scale` 加副本 | 与 HPA/Helm 的期望值打架 | ArgoCD 会拉回，需改 Git 或交给 HPA |
| 配置手改 | 改 ConfigMap 里的超时参数 | 环境间不一致，复现困难 | 覆盖回 Git 值 |
| 资源残留 | 改了资源名，旧对象没人删 | 孤儿资源占资源、留安全隐患 | Prune 自动清理 |
| 权限失控 | 谁都能 `kubectl apply` | 无法追责 | 只留 ArgoCD 一个写入口 |

**这是行业B"故障治理"最实在的一层**：漂移是隐性故障源——今天手改的参数，三个月后没人记得，出问题时所有人都以为"配置是 Git 里那份"。

### 场景 B｜真实事故现场（SelfHeal 和 Prune 是双刃剑，两面都要会讲）
1. **SelfHeal 把排障热修还原了，故障二次发生**：半夜改大内存 limit 临时扛住，第二天同步还原，又 OOM。正确：热修必须落 Git（哪怕是先提交再优化），或临时 `--sync-policy none` 并记录。
2. **Prune 删掉了 Git 里"暂时注释掉"的资源**：有人为了临时停某个服务注释了 manifest，Prune 直接删了 Deployment 和 Service。正确：停机用副本数置 0 或 `suspend`，不要靠删 manifest。
3. **Prune 把 CRD 连带的 CR 全删了**：删了 CRD manifest，集群里所有该类型的自定义资源一起消失。正确：CRD 单独管、加保护、`PruneLast=true`。
4. **`ApplyOutOfSyncOnly=true` 之后，改了但没生效**：这个选项只同步差异资源，某些需要"重新 apply 才生效"的变更（如 webhook）会漏。正确：知道它的语义，关键环境关掉。
5. **多环境共用一个 App**：dev 和 prod 被同一个 Application 管，一次同步同时改两个环境。正确：一环境一 App、一 AppProject 做隔离。

### 场景 C｜面试官的真实痛点
面试官想知道：**① 你敢不敢在生产开 SelfHeal（很多人不敢，因为怕出事）；② 你开了之后怎么处理紧急变更；③ Prune 你开不开，为什么。** 三问本质在问"你有没有为自动化设计过逃生通道"——只会说"全开很爽"的人，没在生产跑过。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 生产开 SelfHeal | 不敢开，或开了不给逃生通道 | 开，同时约定热修流程（PR 加急/临时关+补提交） |
| Prune | 全局一刀切开 | 按 App 分级，关键资源 `Prune=false`，开 `PruneLast` |
| 停机 | 删 manifest | 副本置 0 / suspend |
| 隔离 | 一个 App 管所有环境 | 一环境一 App + AppProject 限定 repo 与 namespace |

- **原理**：ArgoCD 周期性 diff Git 期望态 vs 集群实际态；差异即漂移。
- **理论**：声明式系统的"期望态收敛"；不可变发布。
- **核心易忘点**：`selfHeal`/`prune`/`pruneLast` 开关；`argocd app sync --force`；`argocd app rollback`。
- **横向对比**：SelfHeal（自动还原）vs 手动 sync（需审批）；Prune 开（自动清孤儿）vs 关（保留）。
- **常见问题**：SelfHeal 误删手动热修→热修须走 Git；Prune 误删→`prune=false` 临时保护。

## 五、可操作实战任务（含具体命令/步骤）

### 5.1 触发漂移 + 观察 SelfHeal
```bash
# 手动改集群（模拟手滑）
kubectl scale deployment myapp -n demo --replicas=5
argocd app get myapp        # 状态变 OutOfSync
argocd app sync myapp       # SelfHeal 把副本数还原回 Git 里的值
kubectl get deployment myapp -n demo   # 副本数回到 Git 定义值
```

### 5.2 删除 Git 资源 → 验证 Prune
```bash
# 从 Git 删除某个 manifest 并 push
git rm week1/myapp/templates/ingress.yaml && git commit -m "remove ingress" && git push
argocd app sync myapp       # Prune 自动删除集群中对应的 Ingress
kubectl get ingress -n demo  # 应为空
```

### 5.3 固化策略 YAML
`myapp-appproject.yaml`：
```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata: { name: default, namespace: argocd }
spec:
  sourceRepos: ["https://jihulab.com/<你>/*"]
  destinations: [{ server: "*", namespace: "*" }]
  clusterResourceWhitelist: [{ group: "*", kind: "*" }]
```
`myapp-app.yaml` 关键段：
```yaml
spec:
  syncPolicy:
    automated:
      selfHeal: true
      prune: true
    syncOptions: ["PruneLast=true", "ApplyOutOfSyncOnly=true"]
```

### 5.4 画闭环图 + 钉钉联动
用 Excalidraw 画 `Git → ArgoCD → 集群`，标注 SelfHeal/Prune 两个回环；钉钉通知接 `argocd-notifications`。

## 六、成果验证方式
1. 手动 `kubectl scale` 后 `argocd app sync` 副本数还原（SelfHeal 生效）。
2. 删 Git manifest push 后 `argocd app sync` 集群孤儿资源被 Prune。
3. `myapp-app.yaml` 含 `selfHeal: true / prune: true` 策略固化。
4. 闭环图完成并存入仓库。

## 七、常见坑与排错
- 热修须走 Git 而非 `kubectl edit`；Prune 误删用 `prune=false` 临时保护。
- 镜像来源 quay.io/ghcr 本地需 proxy 或 kind load。

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：生产上你敢开 SelfHeal 吗？开了紧急变更怎么做？（最有区分度的一题）
> "敢开，但必须同时准备逃生通道，否则就是给自己埋雷。
> 我的策略是**分级**：无状态业务应用、dev/test 环境全开 Auto-sync + SelfHeal + Prune；生产核心应用开 Auto-sync 和 SelfHeal，但 Prune 要么只对无状态资源开，要么给关键资源加 `Prune=false` 注解，并且开 `PruneLast` 让它最后执行。
> 紧急变更的流程我定死了三条：第一，**热修也必须进 Git**，走一个加急 PR，改完 3 分钟内能合；第二，真来不及就先 `argocd app set --sync-policy none` 暂停自动同步，手工修，**同时必须在群里登记**，修完立刻补 PR 并恢复同步；第三，事后复盘要能回答'为什么当时必须手改'，如果答不出来说明流水线有瓶颈，要改流水线。
> 核心一句话：**SelfHeal 防的是遗忘，不是防人。人要知道自己在绕什么，绕完必须补回去。**"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| Prune 你开不开？ | "开，但分级。无状态资源开，数据库、CRD、PV 这类关掉，用 `Prune=false` 注解保护。另外一定开 `PruneLast`，让它在同步完成后最后执行，避免资源被提前删掉导致同步过程中断。" |
| 怎么判断集群有漂移？ | "`argocd app list` 看 OutOfSync 状态，或者用 `argocd app diff` 看具体差在哪。生产我会把 OutOfSync 超过 10 分钟的事件接进钉钉告警，因为长期 OutOfSync 要么是同步失败，要么是有人在手改。" |
| 漂移是怎么产生的？ | "九成是人：排障热修、应急扩容、改配置。剩下一成是外部控制器改了对象，比如 HPA 改 replicas、Operator 改 status。所以 HPA 管的字段要在 Helm 里留空，否则也会显示漂移——这是两个控制器抢所有权的问题。" |
| SelfHeal 和 HPA 打架吗？ | "会。HPA 改 replicas，ArgoCD 认为偏离 Git 就拉回，来回抖。解决办法是 Helm 里不设 replicas，让 HPA 独占，或者给 Deployment 加 `ignoreDifferences` 忽略 spec.replicas。" |
| 多环境怎么隔离？ | "一个环境一个 Application，一个 AppProject 限定 repo 和 namespace，权限也在这个层面切。绝不让一个 App 同时管 dev 和 prod，那等于把炸一个环境变成炸两个。" |

### 数字锚点
`分级开策略`｜`Prune=false 保护关键资源`｜`PruneLast=true`｜`OutOfSync >10min 告警`

### 禁忌
- ✗ "全开，很爽" —— 没在生产跑过的人才会这么说。
- ✗ "紧急就直接改，回头再说" —— 直接违背 GitOps 前提。
- ✗ 不知道 HPA 与 SelfHeal 冲突 —— 一开就抖，属于没见过真环境。
