## 三、业务场景（真实工作现场，学到即用）

### 场景 A｜这一周串起来的，是一家公司"平台化"的完整骨架
把 D8–D13 的六件东西按职责摆好，就是运维团队交付给研发的"平台"：

| 层 | 工具 | 一句话职责 | 谁用 |
|---|---|---|---|
| 资源层 | Terraform | 集群、网络、存储"存在不存在" | 运维 |
| 构建层 | GitLab CI | 代码变镜像，带门禁 | 研发（自助） |
| 制品层 | ACR / Harbor | 存镜像和 Chart，不可变 | 流水线 |
| 部署层 | ArgoCD + Helm | 集群状态向 Git 收敛 | 运维 + 研发 |
| 观测层 | Prometheus + Grafana | 知道"有没有事" | 全员 |
| 告警层 | Alertmanager + 钉钉 | 有事找对人 | 值班 |

**平台化的判断标准只有一条**：研发能不能**自助完成从提交到上线**，而不需要找运维开权限、改配置、点部署。你这一周做的六件事，全部是朝这个目标。

### 场景 B｜串起来才会暴露的四个跨层问题（这才是整合的价值）
1. **Terraform 建的集群和 ArgoCD 的 dest-server 对不上**：集群重建后 kubeconfig 变了，ArgoCD 里还指着旧集群。正确：集群注册用可复现方式（`argocd cluster add` 落到 Git 或脚本），集群重建后重新注册。
2. **CI 构建的 tag、Helm values 的 tag、GitOps 仓库的 tag 三处不一致**：这是最隐蔽的问题——流水线明明成功，部署的还是旧版本。正确：**单一真相**，CI 只把 tag 写回 GitOps 仓库的 values，ArgoCD 只读那个仓库。
3. **监控没跟着新命名空间走**：ArgoCD 在 `demo` 部署，Prometheus 的 ServiceMonitor 只监听了 `default`。正确：ServiceMonitor 按 namespace 或 label 选择器配置，新环境部署时一起创建。
4. **告警发出去了但没人认领**：钉钉群是技术大群，告警没人接。正确：按服务归属分群 + 值班表 + 告警升级规则（15 分钟未响应升级到负责人）。

### 场景 C｜面试官的真实痛点
面试官看你能否"贯通"，会问：**"这套东西是六件独立的工具，还是它们之间真的接上了？"** 判据就是上面四个跨层问题——能说出这些坑的人，是真串过；只会分别介绍六个工具的人，是拼装的。

### 标准动作 vs 反例
| 环节 | 反例 | 标准动作 |
|---|---|---|
| 镜像 tag | 三处各自维护 | GitOps 仓库为唯一真相，CI 写入 |
| 集群注册 | 手工 kubeconfig | 脚本/声明式注册，可重建 |
| 监控接入 | 默认只盯一个 ns | ServiceMonitor 按 label 选择器覆盖全环境 |
| 告警归属 | 全推一个大群 | 按服务分群 + 值班表 + 升级规则 |

## 八、技术复盘沉淀（可直接背诵，含追问应对）

### 主问 1：你搭过完整的平台链路吗？从资源到告警怎么串？（90 秒）
> "串过一条完整的，六层。
> **资源层用 Terraform**，把 VPC、交换机、安全组、OSS、ACK 节点池代码化，state 放 OSS 远程后端加锁，多环境独立 state。
> **构建层用 GitLab CI**，五段：检查、单测、多阶段构建镜像、Trivy 扫漏洞、推 ACR。门禁卡新增代码，CRITICAL 阻断，不让高危进仓库。
> **部署层用 ArgoCD + Helm**，Git 是唯一事实源，CI 只负责把镜像 tag 写回 GitOps 仓库，ArgoCD 在集群内拉取同步，开 SelfHeal 防漂移。
> **观测层用 Prometheus**，exporter 覆盖主机、容器和 K8s 对象；Grafana 按受众拆看板；告警走 Alertmanager 分组抑制后推钉钉。
> 串这一条最容易出的不是单点问题，是**跨层对齐**：比如镜像 tag 在 CI、values、Git 仓库三处不一致，流水线全绿但部署的还是旧版本；比如 ArgoCD 部署到新 namespace，Prometheus 的 ServiceMonitor 没覆盖过去，上线了但没监控。这些坑只有真串过才会遇到。"

### 追问应对
| 追问 | 你的回答 |
|---|---|
| Terraform 和 ArgoCD 职责怎么分？ | "Terraform 管集群外——网络、集群本身、云资源；ArgoCD 管集群内——工作负载。中间的分界线是 kubeconfig：集群建好注册进 ArgoCD，之后集群内的东西一律走 Git，不再用 Terraform 管。" |
| 镜像 tag 怎么保证一致？ | "单一真相原则：CI 构建完把 tag 写回 GitOps 仓库的 values 文件，ArgoCD 只认那个仓库。CI 不直接 kubectl set image，否则两套机制打架。" |
| 新环境接监控要做什么？ | "ServiceMonitor 按 namespace 或 label 选，新环境部署时一起创建；Grafana 变量按 namespace 聚合，自动出现新环境；告警路由按 namespace 或 service 打标签分派。" |
| 这套东西挂了先查哪？ | "从交付链路上游往下：Git 仓库有没有新 commit → ArgoCD 有没有 Synced → Pod 是否 Healthy → Prometheus 有没有 up=0 → 告警有没有发出去。这五步能覆盖 90% 的问题。" |
| 成本和这套架构怎么平衡？ | "练习环境全部用 kind + 短跑 ACK，用完 destroy；生产上把资源打标签做成本归集，看每核承载请求数，利用率低的合并。FinOps 不是省小钱，是知道钱花在哪。" |

### 数字锚点
`六层链路`｜`tag 单一真相`｜`Terraform 管外 / ArgoCD 管内`｜`排障五步`
