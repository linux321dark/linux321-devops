# 授渔篇 · 怎么自己搞懂一个陌生的命令和中间件

> **为什么有这一篇**：21 篇日课单页给的是"这一枪怎么打"——命令是别人验证过的**结果**，不是你**推出来的**。面试官换个问法、生产换个报错，照抄的命令立刻失效。本篇给的是"遇到没见过的东西时，怎么把它拆开"的固定动作，**21 天每天用同一套**。
> 读法：第一次通读一遍（15 分钟），之后每天动手前扫一眼第一节的三态模型。日课单页里出现"见授渔篇"的地方，回来对照。

---

## 一、K8s 只有三个状态，所有命令都归三类

这是整套方法的地基。理解这一条，90% 的命令不用背就知道该用哪个。

任何 K8s 对象都活在三个东西之间：

| 状态              | 存在哪       | 谁写的         | 你怎么看                                   |
| --------------- | --------- | ----------- | -------------------------------------- |
| **期望态**（spec）   | etcd      | 你，用 `apply` | `kubectl get <资源> -o yaml` 的 `spec:` 段 |
| **实际态**（status） | etcd      | 控制器回写       | 同一个 yaml 的 `status:` 段                 |
| **真实运行态**       | 节点上的进程/容器 | kubelet 拉起  | `get pods`、`logs`、`exec`、`top`         |

**控制器（controller）是一个死循环**：读期望态 → 读实际态 → 两者不一样就动手改 → 改完再读。这个循环永不停止，叫 reconciliation。

由此推出三类命令：

| 你想要的      | 命令                                                         | 本质              |
| --------- | ---------------------------------------------------------- | --------------- |
| 改期望态      | `apply` / `create` / `patch` / `scale` / `edit` / `delete` | 改 spec          |
| 看现在什么样    | `get` / `describe` / `logs` / `top` / `exec`               | 看 status 或真实运行态 |
| 看它为什么没变过来 | `describe` 的 **Events** 段、`get events`                     | 看协调失败在哪一步       |

**排障就按这个顺序走，不要乱试**：

```
① yaml 本身写错了吗？        → get <资源> -o yaml 看 spec 是不是你要的
② spec 对，但没达到？        → describe 看 Events，协调卡在哪一步
③ Pod 起来了，但业务不对？    → logs / exec 进去看，这是应用层的事
```

> **今天你遇到的就是第 ②类**：`deployment "day1-go" exceeded its progress deadline` —— spec 没错（镜像地址是对的），但 kubelet 拉不到镜像，协调卡在"拉镜像"这一步。所以 `rollout status` 只会告诉你"超时了"，真正的原因只有 `describe pod` 的 Events 里有。**报错分三层：症状（rollout 超时）→ 状态（ImagePullBackOff）→ 原因（Events 里的 401）。永远查到第三层再动手。**

## 二、五个"自己查"的动作（替代问人、替代搜博客）

这五个动作能回答 90% 的"这个是什么/怎么填/为什么不行"。

| 想知道 | 动作 | 说明 |
|---|---|---|
| 这集群支持哪些对象 | `kubectl api-resources` | 别背资源名，查。看 `SHORTNAMES` 列省事（deploy/pod/svc 都是缩写） |
| **某个字段是什么意思、怎么填** | `kubectl explain <资源>.<字段路径>` | **最高杠杆的一个，K8s 自带的字段字典，版本永远匹配，不用联网** |
| 真实对象完整长什么样 | `kubectl get <资源> <名字> -o yaml` | 会包含 `status`，这是你写的 yaml 里没有的 |
| 为什么没达到期望 | `kubectl describe <资源> <名字>` → 拉到最底 **Events** | 唯一的真凶来源，Events 里的 `Message` 才是原始错误 |
| 刚才集群发生了什么 | `kubectl get events --sort-by=.lastTimestamp` | 跨对象的时间线，排查"突然全挂了"时用 |

**`kubectl explain` 用法**（这是本篇最该记住的一条）：

```bash
kubectl explain deployment                              # 顶层有哪些字段
kubectl explain deployment.spec.template.spec.containers # 容器段能写什么
kubectl explain hpa.spec.metrics --recursive            # 递归展开所有子字段
kubectl explain deployment.spec.template.spec.containers.resources.requests
```

输出里有两列值得看：`Type`（类型，决定你写字符串还是数字）和 `Description`（官方解释）。**遇到任何不认识的字段，先 explain，不要先搜。**

**为什么 `describe` 比 `get` 重要**：`get` 只给你状态摘要（`Running`、`0/1`、`ImagePullBackOff`），`describe` 给你**推导过程**——调度到哪个节点、拉了几次镜像、探针失败几次、每次失败的原文和时间。**摘要告诉你"病了"，describe 告诉你"什么病"。**

## 三、拿到一段陌生 yaml：四问拆解

日课单页里有大段的 yaml（比如 D2 的 metrics-server 那一整段），看着像天书。用四个问题拆，每个 yaml 都一样：

| 问 | 看哪 | 目的 |
|---|---|---|
| ① 它是什么？ | `apiVersion` + `kind` | 确定对象类型，然后 `api-resources` 查缩写 |
| ② 它要什么？ | `spec:` 段 | 这是**期望态**，你要理解的核心 |
| ③ 它现在怎样？ | `get -o yaml` 的 `status:` 段 | 现状，yaml 文件里看不到 |
| ④ 谁在管它？ | 看有没有 controller / operator | 决定谁负责把它变成期望态 |

### 实例：D2 的 metrics-server 那段 yaml，四问拆完就不难了

这段 yaml 有 6 个对象（ServiceAccount / Service / Deployment / ClusterRole / ClusterRoleBinding / APIService），初学者最容易懵的是**为什么要这么多**。用"输入从哪来、输出给谁用"这条线串：

```
kubelet（每个节点上的 cAdvisor）
   ↓ 暴露 /stats 接口，里面有容器 CPU/内存用量
metrics-server（一个普通 Deployment，跑在集群里）
   ↓ 通过 Summary API 拉这些数据，聚合成 K8s 的资源格式
APIService（v1beta1.metrics.k8s.io）
   ↓ 把 metrics-server 注册进 kube-apiserver 的 API 目录
   ↓ 于是 kubectl top 和 HPA 能像查内置资源一样查它
```

现在对着看，每个对象的存在理由就清楚了：

| 对象 | 为什么必须有 |
|---|---|
| **ServiceAccount + ClusterRole + ClusterRoleBinding** | 读 `nodes/stats` 和 `nodes/metrics` 需要权限。**少了这个就是 403**，metrics-server 能起来但拿不到数据 |
| **Deployment** | metrics-server 本身也是个容器，得有人跑它 |
| **Service** | APIService 要用 `service.name/namespace` 找到它，没有 Service 就注册不上 |
| **APIService** | 这一步是"接进 K8s"的关键。不加它，metrics-server 就是个内部服务，`kubectl top` 和 HPA 根本不知道它存在 |
| **`--kubelet-insecure-tls`** | kind 的 kubelet 用自签证书，metrics-server 默认要校验，校验不过就连不上。**这是 kind/Minikube 环境特有的，生产 ACK 上不需要** |
| **`--metric-resolution=15s`** | 采集间隔。这个数字直接决定 HPA 的反应速度，D2 话术里"扩容延迟 1-2 分钟"的第一段就是它 |

> **这就是授渔**：不是记住 metrics-server 要装哪些对象，而是知道"**一个外部组件要接进 K8s，必须走 APIService 注册**"这条规律。以后遇到 Prometheus Adapter、KEDA、各种 custom metrics 组件，都是同一个套路。

**通用推论（可以套到任何组件上）**：一个东西要变成"K8s 的资源"，必须做三件事——① 有个 Pod 跑着 ② 有 Service 让 apiserver 找得到 ③ 有 APIService 注册成 API 组。缺一个都不通。

## 四、命令忘了：三层兜底；文档查哪：三类来源分工

### 4.1 命令记不住：三层兜底

| 层级 | 动作 | 适用 |
|---|---|---|
| 1 | `kubectl --help`、`kubectl <子命令> --help` | 忘了参数名 |
| 2 | `kubectl explain <字段路径>` | 忘了字段怎么填 |
| 3 | 官方文档 **只查这一个**：`kubernetes.io/docs/reference/kubectl/` | 忘了有哪个命令 |

**为什么不直接搜博客**：博客的 K8s 版本、发行版、云厂商都和你不一样，抄来的 yaml 字段经常已废弃（比如 `extensions/v1beta1` 早就没了）。**官方文档和 `kubectl explain` 跟你当前的集群版本一致，这是它们唯一但决定性的优势。**

同理，中间件的用法优先看**官方文档 + 官方 examples 目录**（metrics-server 仓库里的 `manifests/` 就是各版本的官方 yaml）。日课单页里的 yaml 是从官方 manifests 改出来的——**知道它从哪来，你就知道以后该去哪拿最新的**。

### 4.2 概念不懂：三类来源各管一件事

> 完整来源矩阵见 [`09-参考索引/README.md`](09-参考索引/README.md)，全部链接实测过。

| 类型 | 界定 | **用它做什么** | **禁止用它做什么** |
|---|---|---|---|
| **A 官方文档**（英文优先） | 项目自己的 docs 站、API 参考 | 查字段语义、默认值、版本差异、API 契约 | — |
| **B 中文官方 / 社区** | 官方站中文版、社区翻译、掘金 / CSDN / 博客园 / 阿里云开发者社区 | 建概念直觉、查中文术语、找国内特有议题 | **不得作为"字段怎么写"的唯一依据** |
| **C 云厂商中文文档** | 阿里云 ACK/ACR/云效、腾讯云 TKE、华为云 CCE | 看**托管版与自建版的差异**、厂商特有注解、**面试落点** | 不能替代 A 类理解原理 |

**冲突时以 A 为准**，并在正文写一行：「中文来源说 X，官方为 Y，以官方为准」。**这行标注本身就是加分项——它证明你查过一手。**

### 4.3 硬规矩：每个知识点至少两个来源

1. **一个知识点 = A（官方）+ B 或 C（中文）之一**。做不到的标 `⚠️ 单源待补`，不许蒙混过关。
2. **版本敏感的内容必须标版本**（K8s 字段行为、Helm 3 vs 2、Terraform 1.x、GitLab CI 的 `rules` vs `only/except`）。
3. **链接必须实测可访问**，并记下实测日期。抄别人博客里的链接 = 继承别人的错误。

> **实测踩过的坑**（都写进 `09-参考索引` 了）：
> - Docker 官方文档**已无中文站**——`/zh-cn/` 8 条路径全 404，只能走云厂商 + 社区
> - Terraform 变量文档搬过家——`/language/variables` 404，正确是 `/language/values/variables`
> - Helm 的 `/docs/charts/` 404，正确是 `/docs/topics/charts/`
> - **批量校验时返回 000 是网络抖动不是失效**——必须重试，否则来源表里全是假的"已失效"

### 4.4 一条通用判断：这份来源配不配得上这个知识点

问自己三个问题：

1. **它是这个组件的第一方吗？** 不是 → 只能当 B 类用
2. **它跟我的版本对得上吗？** 对不上 → 字段行为已变
3. **它是转抄的吗？** 转抄百科/互相抄 → 溯源到第一方再用

> 答不上第一条的，**别拿来定"字段怎么写"**；答不上第二条的，**别拿来定"默认值是多少"**。

## 五、自测：三问判断"我是真懂了还是只会敲"

每天收工前花 2 分钟过这三问。**三个都过才算懂，否则只是复现了别人的操作。**

1. **能不能说出它的输入和输出？** —— 不看文档：数据从哪来、给谁用、中间经过谁。
   （例：metrics-server 的输入是 kubelet 的 /stats，输出是 metrics.k8s.io 这个 API 组，消费者是 `kubectl top` 和 HPA。）

2. **能不能故意改坏一个字段，再从现象倒推原因？** —— **这是最有效的检验**。把 `requests.cpu` 删掉，看 HPA 变成 `<unknown>/50%`；把 `imagePullPolicy` 改成 `Always`，看它开始重复拉镜像。**你造过的错，比你看过的文档记得牢。**
   （今天的 ImagePullBackOff 就是活教材：症状是 rollout 超时，状态是 ImagePullBackOff，原因是 Events 里的 `401 insufficient_scope`，根因是 kind 节点没有仓库凭据。）

3. **能不能画出它和上下游的关系图？** —— 画不出来说明你只知道它"能跑"，不知道它"为什么能跑"。

> **面试的差别就在这三问上**：只会敲命令的人答"我配过 HPA"；过了三问的人答"HPA 的分母是 requests，漏写就 `<unknown>`，而且它只改 Pod 数不管节点，节点没余量就全 Pending"。**前者是操作员，后者是运维。**

## 附：本方法的三个反面清单

- ✗ **照抄日课单页的命令跑通就过** —— 跑通只证明环境对，不证明你懂。下次环境变一个变量就崩。
- ✗ **搜到一段能跑的 yaml 直接用** —— 字段版本对不上是小事，权限和网络策略对不上会直接出生产事故。
- ✗ **报错只看第一行** —— `rollout status` 的超时、`kubectl apply` 的 `created`、`get pods` 的 `Running`，这三个都是最表层的信息。**永远往下挖到 Events 的 Message。**
