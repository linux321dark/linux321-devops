## 1. 概念

### 1.1 一句话定义

> **排障的本质是"把现象翻译成链路上的位置"——你不需要理解整个 K8s，你只需要知道它卡在哪一步。**

L2 的 9 步链路给了这张地图 [S1]：

| # | 步骤 | 失败时的状态 |
|---|---|---|
| 1 | kubectl → apiserver | 连接被拒 |
| 2 | apiserver 认证 → 授权 → 准入 | 401 / 403 |
| 3 | apiserver → etcd | `etcdserver: request timed out` |
| 4 | deployment-controller 建 ReplicaSet | 看不到 RS |
| 5 | replicaset-controller 建 Pod | `get pods` 空、Event `FailedCreate` |
| 6 | kube-scheduler 选节点 | `Pending` + `FailedScheduling` |
| 7 | kubelet 拉镜像 | `ImagePullBackOff` / `ErrImagePull` |
| 8 | kubelet 建容器、配网络、跑探针 | `CrashLoopBackOff` / `Running 0/1` |
| 9 | controller 聚合 status | 进度停滞、`progress deadline exceeded` |

**本篇的所有方法，都是"怎么用最少的命令确定它卡在第几步"。**

### 1.2 为什么 K8s 排障特别难

| 难点 | 具体表现 | 本篇的对策 |
|---|---|---|
| **状态是"合成的"** | `STATUS` 列不是单一字段，是 kubectl 把多个 container state **渲染**出来的字符串 | 2.3 速查表 + 用 `-o yaml` 看真实字段 |
| **同一个 STATUS 背后原因不同** | 都叫 `Pending`，可能是资源不够 / 亲和性不匹配 / 污点 / PVC 没绑 | 2.1 三层模型 + 读 Events 原文 |
| **Events 有历史残留** | 三小时前失败过一次，现在 Events 里还挂着 → 误导判断 | 2.4 看 `LastTimestamp` 与 `Count` |
| **组件是分布式的** | 一个 Deployment 要经过 4 个控制器 + 调度器 + kubelet 才跑起来 | 1.1 的 9 步地图 |
| **错误信息层层包装** | 用户看到的可能是 `503 Service Unavailable`，根因在 etcd | 往上游查（2.9） |
| **"改了没生效"** | 改了 yaml 但 Pod 用的是旧配置 | 2.5 的 `env` 方式陷阱 + 声明式管理的语义 |
| **没有 shell** | distroless 镜像里 `kubectl exec` 进不去 | 2.6 `kubectl debug` |

### 1.3 术语表（中英对照）

| 英文 | 中文 | 一句话 |
|---|---|---|
| symptom | 症状 | 用户/监控看到的**现象**（"服务挂了"） |
| status | 状态 | 对象 `status` 里的**结构化字段**（`phase`、`reason`、`exitCode`） |
| `Events` | 事件 | 对象生命周期里发生的**一次性/可聚合的事实**记录 |
| `reason` | 原因 | Event 的机器可读短串（`FailedScheduling`） |
| `message` | 消息 | Event 的**人类可读原文**——**排障的真正证据** |
| `count` | 计数 | 同一条 Event 发生了多少次 |
| `lastTimestamp` | 最后时间戳 | 最近一次发生的时间 |
| `firstTimestamp` | 首次时间戳 | 第一次发生的时间 |
| `involvedObject` | 关联对象 | 这条 Event 是关于哪个对象的 |
| `phase` | 阶段 | Pod 的**五档**高层状态（`Pending`/`Running`/`Succeeded`/`Failed`/`Unknown`） |
| `reason`（容器级） | 容器状态原因 | 如 `CrashLoopBackOff`、`ImagePullBackOff`、`OOMKilled` |
| `exitCode` | 退出码 | 容器退出时的返回码（**137 = 128+9 = SIGKILL**） |
| `previous` | 上一次 | `kubectl logs --previous` 取**上一个容器实例**的日志 |
| `--previous` | — | **崩溃重启后看上一次崩因的唯一办法** |
| `initContainer` | 初始化容器 | 主容器启动前按顺序跑完的一次性容器 |
| `ephemeral container` | 临时容器 | **调试用**，加进运行中的 Pod，不能重启 |
| `rollout status` | 发布状态 | **只等 `progressDeadlineSeconds`，不诊断** |
| `progressDeadlineSeconds` | 进度截止时间 | 默认 **600 秒**，超了报 `exceeded its progress deadline` |
| `readyReplicas` | 就绪副本数 | Deployment 里真正 Ready 的 Pod 数 |
| `desiredReplicas` | 期望副本数 | Deployment 想要的副本数（**HPA 改的就是它**） |
| `disruption` | 中断 | Pod 被主动删除（`drain`、缩容、PDB 管的就是它） |
| `NotReady` | 未就绪 | 节点条件 `Ready` 不为 `True` |

## 2. 机制

### 2.1 三层追查模型：症状 → 状态 → Events.Message

**这是本篇的核心。** 授渔篇的三态模型（期望态 / 实际态 / 真实运行态）是它的基础 [S2]。

```
   第 1 层：症状（Symptom）                ← 你/用户/监控看到的
   "服务 503"、"Pod 起不来"、"发布卡住"
        │  这层信息量几乎为零
        │  "Pod 起不来"可能是 8 种完全不同的原因
        ▼
   第 2 层：状态（Status）                  ← kubectl get 渲染出来的 STATUS 列
   Pending / ImagePullBackOff / CrashLoopBackOff / Running 0/1 / OOMKilled / Evicted
        │  这层能定位到"9 步链路的大致区间"
        │  但仍然可能歧义（Pending 有 4 种原因）
        ▼
   第 3 层：原因（Events 里的 Message）      ← kubectl describe 的 Events 段
   "0/3 nodes are available: 3 Insufficient cpu."
   "Failed to pull image ...: 401 Unauthorized"
   "Back-off restarting failed container"
        │  这层是**原始错误**，直接对应根因
        │  绝大多数排障在这一层就结束了
        ▼
   第 4 层（可选）：实际运行态              ← logs / exec / debug / top
   应用自己的日志、进程、网络连接、CPU 曲线
```

**官方原文对 Pod phase 的严谨警告（L2 之外的补充）** [S3]：

> The phase of a Pod is a simple, high-level summary of where the Pod is in its lifecycle. **The phase is not intended to be a comprehensive rollup of observations of container or Pod state, nor is it intended to be a comprehensive state machine.**

> **The number and meanings of Pod phase values are tightly guarded. Other than what is documented here, nothing should be assumed about Pods that are given a `phase` value.**

> **Make sure not to confuse `Status`, a kubectl display field for user intuition, with the pod's `phase`.** Pod phase is an explicit part of the Kubernetes data model and of the `Pod API`.

> **这三条是本节的方法论依据**：
> 1. **`phase` 只有五档**（`Pending`/`Running`/`Succeeded`/`Failed`/`Unknown`），**不要以为每个 STATUS 都是 phase**——`ImagePullBackOff`、`CrashLoopBackOff` 都是 **kubectl 渲染的显示状态**，不是 phase。
> 2. **phase 不是完整的状态汇总**——一个 `Running` 的 Pod 可能有容器在崩溃循环。
> 3. **`Status` ≠ `phase`**——`Status` 是给人看的，`phase` 是数据模型里的。

**三层模型落到具体动作**：

| 层 | 你该跑的命令 | 你该问的问题 |
|---|---|---|
| **① 症状** | `kubectl get pods` | 哪些 Pod 不对？**状态是什么？** |
| **② 状态** | `kubectl get pod <p> -o yaml`（看 `status.conditions` 和 `containerStatuses`） | 哪个容器、什么 `state`、什么 `reason`、`exitCode` 多少？ |
| **③ 原因** | `kubectl describe pod <p>` → **拉到最底 Events** | **Message 原文说了什么？** |
| **④ 运行态** | `kubectl logs` / `logs --previous` / `exec` / `debug` / `top` | 应用自己在说什么？ |

### 2.2 为什么 `rollout status` 的超时零信息量

**官方原文（Deployment 的滚动更新）** [S4]：`progressDeadlineSeconds` 默认 **600 秒**（L2 实测口径）。

**`kubectl rollout status deploy/<name>` 的行为**：

```
$ kubectl rollout status deploy/web
Waiting for deployment "web" rollout to finish: 3 of 3 updated replicas are available...
error: deployment "web" exceeded its progress deadline
```

**这条报错的信息量是零。** 原因是：

| 它告诉你了 | 它没告诉你 |
|---|---|
| "等了 600 秒还没完成" | **卡在哪一步** |
| "发布超时了" | **为什么超时**（镜像拉不下来？探针不过？调度不上？） |
| — | **哪些 Pod 有问题** |

**为什么它必然零信息量（设计原因）**：

| 原因 | 说明 |
|---|---|
| **它只是一个计时器** | 它每几秒查一次 Deployment 的 `status`，看 `updatedReplicas`、`readyReplicas`、`availableReplicas` 是否都达到目标 |
| **超时判定是纯计数** | 官方：`progressDeadlineSeconds` 是"多久算这次发布失败"。**它不分析任何原因** |
| **真正的原因在别处** | Deployment 的 `status.conditions` 里有一条 `Progressing=False / Reason=ProgressDeadlineExceeded`，**但那条也不说原因** |
| **根因在 Pod 层** | 你必须去看那些**没 Ready 的 Pod** 的 Events |

**正确的用法（把 rollout status 降级为"计时器"）**：

```bash
# ① rollout status 只是告诉你"还没完"
kubectl rollout status deploy/web --timeout=30s

# ② 真正该看的是：谁没 Ready？
kubectl get pods -l app=web

# ③ 这些 Pod 的 Events 里才是根因
kubectl describe pod <那个没 Ready 的 pod>

# ④ 或者直接看 Deployment 的 status
kubectl get deploy web -o jsonpath='{.status}' | jq
```

> **面试能这么答**："`rollout status` 报错只说明**等了 600 秒还没达到期望态**，它不包含任何诊断信息。正确做法是把它当计时器——它告诉你超时了，然后立刻去看**没 Ready 的那些 Pod** 的 Events，根因在那里。"
>
> **这也解释了 L2 里"报错分三层"的由来**：症状（rollout 超时）→ 状态（ImagePullBackOff）→ 原因（Events 里的 401）。

### 2.3 Pod 状态完整速查表

**先分清两套东西（官方明确）** [S3]：

| 类别 | 是什么 | 值 |
|---|---|---|
| **`phase`**（数据模型里的） | **5 档**，受官方严格保护 | `Pending` / `Running` / `Succeeded` / `Failed` / `Unknown` |
| **`Status` 列**（kubectl 渲染的） | 给人看的**综合显示**，**可以是 phase 之外的字符串** | `ContainerCreating`、`CrashLoopBackOff`、`ImagePullBackOff`、`Init:0/1`、`Terminating`、`Evicted`… |

**官方对五个 phase 的定义（逐字）** [S3]：

| phase | 官方原文 |
|---|---|
| `Pending` | *"The Pod has been accepted by the Kubernetes cluster, but one or more of the containers has not been set up and made ready to run. **This includes time a Pod spends waiting to be scheduled as well as the time spent downloading container images over the network.**"* |
| `Running` | *"The Pod has been bound to a node, and **all of the containers have been created**. At least one container is still running, or is in the process of starting or restarting."* |
| `Succeeded` | *"**All containers in the Pod have terminated in success**, and will not be restarted."* |
| `Failed` | *"**All containers in the Pod have terminated, and at least one container has terminated in failure.** That is, the container either exited with non-zero status or was terminated by the system, and is not set for automatic restarting."* |
| `Unknown` | *"For some reason the state of the Pod could not be obtained. This phase typically occurs **due to an error in communicating with the node** where the Pod should be running."* |

**完整速查表（本篇最实用的一张表）**：

| 你在 `kubectl get pods` 看到的 STATUS | 真实含义 | 卡在 9 步链路的第几步 | 根因在哪 | 第一条该跑的命令 |
|---|---|---|---|---|
| **`Pending`**（且 `READY` 是 `0/N`） | Pod 对象存在，但没被调度 **或** 镜像在下载 | **6（调度）** 或 **7（拉镜像）** | Events 的 `FailedScheduling`（资源/亲和性/污点/PVC） | `kubectl describe pod <p>` |
| **`Pending`** + Events 有 `FailedScheduling` + `Insufficient cpu` | 节点资源装不下 requests | **6** | 调度器 | 调小 requests 或加节点 |
| **`Pending`** + Events 有 `untolerated taint` | 节点有污点，Pod 没容忍 | **6** | 调度器 | 加 `tolerations` |
| **`Pending`** + Events 有 `didn't match Pod's node affinity` | 亲和性写错 | **6** | 调度器 | 核对节点标签 |
| **`Pending`** + Events 有 `pod has unbound immediate PersistentVolumeClaims` | **PVC 没绑上**（不是调度问题！） | **5/6 之间** | StorageClass / PVC | `kubectl get pvc` |
| **`ContainerCreating`** | 容器还没建起来（通常在拉镜像或等卷） | **7** | Events 里通常是 `Pulling` / `MountVolume` | `kubectl describe pod <p>` |
| **`ImagePullBackOff`** | 镜像拉取失败，**在退避重试** | **7** | Events: `Failed` + `Failed to pull image` | 查 401 / 404 / 网络 |
| **`ErrImagePull`** | 镜像拉取失败（**第一次**，还没进退避） | **7** | 同上 | 同上 |
| **`Init:0/1` / `Init:CrashLoopBackOff`** | **初始化容器**没跑完 | **8（init 阶段）** | `kubectl logs <p> -c <initContainer名>` | 看 init 容器日志 |
| **`Running 0/1`** | 容器起来了但**没 Ready** | **8（探针）** | Events: `Unhealthy` + 探针失败次数 | `kubectl describe pod <p>` 看探针配置 |
| **`CrashLoopBackOff`** | 容器反复起反复挂，**在退避等待** | **8** | 容器退出原因 | `kubectl logs <p> --previous` |
| **`Running 1/1`** 但**访问不通** | Pod 本身健康，**Service 或网络的问题** | **Service/网络层** | `kubectl get endpoints` | 检查 endpoints 是否为空 |
| **`Terminating`** | 正在删除（还在等优雅停机） | — | `terminationGracePeriodSeconds`（默认 30s） | `preStop` 钩子可能卡住 |
| **`Completed`** | 正常结束（Job） | — | 正常 | 无需处理 |
| **`OOMKilled`**（`describe` 里的 `lastState.terminated.reason`） | **容器内存超了自己的 limit，被内核杀** | **8（运行时）** | 内存 limit 太小 / 内存泄漏 | 调大 `limits.memory` |
| **`Evicted`** | **被驱逐**（节点压力或资源不足） | **节点层** | 节点内存/磁盘压力；**或 Pod 超出节点资源上限** | `kubectl describe pod <p>` 看 `Reason` |
| **`Failed`** + `Reason: Evicted` | 节点压力驱逐 | 节点层 | 内存/磁盘压力 | `kubectl describe node` |
| **`Failed`** + `Reason: NodeAffinity` | 节点亲和性/污点不满足被**直接拒绝**（不是 Pending） | **6** | 调度器 | 核对亲和性 |
| **`Unknown`** | **和节点通信不上** | 节点层 | 节点宕机 / kubelet 挂了 | `kubectl get nodes` |

**"崩溃重启"与"Pod 重建"的区别（官方原文）** [S3]：

> **While a Pod is running, the kubelet is able to restart containers to handle some kind of faults.**

> - **Initial crash**: Kubernetes attempts an immediate restart based on the Pod `restartPolicy`.
> - **Repeated crashes**: After the initial crash Kubernetes applies an **exponential backoff delay** for subsequent restarts... This prevents rapid, repeated restart attempts from overloading the system.
> - **CrashLoopBackOff state**: This indicates that the backoff delay mechanism is currently in effect for a given container that is in a crash loop, failing and restarting repeatedly.
> - **Backoff reset**: If a container runs successfully for a certain duration (e.g., 10 minutes), Kubernetes resets the backoff delay, treating any new crash as the first one.

> **A given Pod (as defined by a UID) is never "rescheduled" to a different node;** instead, that Pod can be replaced by a new, near-identical Pod... **Kubernetes does not guarantee that a replacement for an existing Pod would be scheduled to the same node as the old Pod that was being replaced.**

> **这个区别决定了两条完全不同的排查路径**：
> - **容器重启**（`RESTARTS` 递增，Pod 名不变）→ **同一个 Pod 里容器反复挂** → 看 `logs --previous`
> - **Pod 重建**（Pod 名变了，新 UID）→ **控制器删了旧的建了新的** → 看**控制器**和**新 Pod 的 Events**

### 2.4 Events 的读法：`LastTimestamp` 与 `Count`

**官方原文（Event API 参考）** [S5]：

> Event is a report of an event somewhere in the cluster. **Events have a limited retention time and triggers and messages may evolve with time.** Event consumers **should not rely on the timing of an event with a given Reason reflecting a consistent underlying trigger, or the continued existence of events with that Reason.** **Events should be treated as informative, best-effort, supplemental data.**

**Event 的关键字段（官方原文）** [S5]：

| 字段 | 官方原文 | 排障用途 |
|---|---|---|
| `involvedObject` | *"The object that this event is about."* | 确认这条 Event 是关于哪个对象的（**跨对象串起来的关键**） |
| `reason` | *"This should be a **short, machine understandable string** that gives the reason for the transition into the object's current status."* | **快速筛选**（`FailedScheduling`、`Failed`、`Pulled`） |
| `message` | *"A **human-readable description** of the status of this operation."* | **真正的证据** |
| `firstTimestamp` | *"The time at which the event was **first** recorded."* | **这个原因从什么时候开始** |
| `lastTimestamp` | *"The time at which the **most recent occurrence** of this event was recorded."* | **现在还在发生吗** |
| `count` | *"**The number of times this event has occurred.**"* | **发生了几次** |
| `type` | *"Type of this event (Normal, Warning), new types could be added in the future"* | **Warning 优先看** |
| `series` | *"Data about the Event series this event represents or nil if it's a singleton Event."* | 连续事件序列 |

**读 Events 的三个动作**：

```bash
# ① 看某个对象的全部 Events（按时间倒序）
kubectl describe pod <p>

# ② 看跨对象的时间线（"刚才集群发生了什么"）
kubectl get events --sort-by=.lastTimestamp

# ③ 只看 Warning
kubectl get events --field-selector type=Warning --sort-by=.lastTimestamp

# ④ 只看某个对象相关的
kubectl get events --field-selector involvedObject.name=<pod名>
```

**`count` 与 `lastTimestamp` 的组合判读表（本节题眼）**：

| `count` | `lastTimestamp` | 判读 | 该做什么 |
|---|---|---|---|
| **1** | **很旧**（比如 2 小时前） | **历史残留**——一次性事件，已经过去了 | **别在这条上浪费时间**，去看 `lastTimestamp` 最新的那条 |
| **1** | **很新**（几秒内） | 刚刚发生的一次性失败 | 看 Message |
| **N（>1）** | **很新** | **持续失败**——同一原因反复发生 | 这就是当前根因，**优先处理** |
| **N（>1）** | **很旧** | 曾经反复失败，现在停了 | 历史问题，已自愈或已绕过 |
| **—** | **很旧但只有 Warning** | 可能是**启动时的正常告警**（如 `FailedMount` 后重试成功） | 看后面有没有 `Mounted` / `Pulled` / `Created` 这类 Normal 事件**抵消了它** |

> **"历史残留"是最常见的误判来源。** 官方自己都说 Events 是 *"informative, best-effort, supplemental data"* [S5]，**不能假设某个 Reason 持续存在就代表问题还在**。
>
> **实操判据**：
> 1. **按 `lastTimestamp` 排序，最新的在最上面**——**先看最新那条**。
> 2. **看 `count`**：`count` 很大 + 时间很新 = **持续失败**，这是根因。
> 3. **看有没有被"抵消"**：如果 `FailedScheduling` 之后有 `Scheduled`（Normal），说明已经解决了。
> 4. **别看 `count` 大就慌**——`count` 大也可能只是"历史上重试了很多次，最后成功了"。

**一个必须注意的现象**：`kubectl describe pod` 里的 Events 是**倒序**（最新在上）。**很多人从上往下读，读到最老的一条就下了结论**——而那恰恰是最不相关的。

### 2.5 kubectl 排障命令集

**按"能回答什么问题"分组，而不是按字母序**：

| 你想知道 | 命令 | 关键点 |
|---|---|---|
| **谁有问题** | `kubectl get pods -o wide` | `STATUS` + `NODE` + `RESTARTS` 三列最有用 |
| **谁有问题（按标签筛）** | `kubectl get pods -l app=web` | selector 匹配不上 → 什么都不会显示（见 2.7） |
| **标签是什么** | `kubectl get pods --show-labels` | 用来核对 selector |
| **它到底怎么了（结构化）** | `kubectl get pod <p> -o yaml` | 看 `status.conditions`、`containerStatuses[].state`、`lastState` |
| **它到底怎么了（人话）** | `kubectl describe pod <p>` | **Events 段是核心** |
| **刚才发生了什么（全局）** | `kubectl get events --sort-by=.lastTimestamp` | 跨对象时间线 |
| **只看待办** | `kubectl get events --field-selector type=Warning` | 过滤噪音 |
| **应用说了什么** | `kubectl logs <p>` | 当前容器实例的日志 |
| **上一次崩在哪** | `kubectl logs <p> --previous` | **崩溃重启后看上一次的唯一办法** |
| **多容器指定** | `kubectl logs <p> -c <container名>` | sidecar 场景必用 |
| **跟 init 容器要日志** | `kubectl logs <p> -c <initName>` | init 容器名要单独给 |
| **实时跟日志** | `kubectl logs -f <p>` | 配合 `--since` / `--tail` |
| **进容器** | `kubectl exec -it <p> -- sh` | **distroless 会失败**（见 2.6） |
| **进不了 shell 时的替代** | `kubectl debug -it <p> --image=busybox --target=<容器名>` | 临时容器 |
| **本机访问 Pod 端口** | `kubectl port-forward pod/<p> 8080:8080` | 绕开 Service，直连 Pod |
| **本机访问 Service** | `kubectl port-forward svc/<svc> 8080:80` | 验证 Service 转发 |
| **资源用量** | `kubectl top pods` / `kubectl top nodes` | 需要 metrics-server |
| **发布状态** | `kubectl rollout status deploy/<d>` | **只计时，不诊断**（见 2.2） |
| **发布历史** | `kubectl rollout history deploy/<d>` | 找上一个可用版本 |
| **回滚** | `kubectl rollout undo deploy/<d>` | 回到上一版 |
| **暂停发布** | `kubectl rollout pause deploy/<d>` | 排查时冻结变更 |
| **改副本数** | `kubectl scale deploy/<d> --replicas=3` | 直接改 `spec.replicas` |
| **临时改配置** | `kubectl set env deploy/<d> KEY=VALUE` | **只改 env，不重启已有 Pod 的其他字段**（见 2.10 陷阱） |
| **改镜像** | `kubectl set image deploy/<d> app=img:tag` | 触发滚动更新 |
| **看字段是谁管的** | `kubectl get deploy <d> -o yaml --show-managed-fields` | server-side apply 的字段归属 |
| **看 API 定义** | `kubectl explain pod.spec.containers.resources` | **本集群版本的字段字典**，不用联网 |
| **看原始 API** | `kubectl get --raw /apis/metrics.k8s.io/v1beta1/pods` | 绕过客户端 |
| **看集群健康** | `kubectl get --raw='/readyz?verbose'` | apiserver 逐项健康（见 2.9） |

**`kubectl explain` 的四种典型用法（官方字段字典，本地版本永远匹配）**：

```bash
kubectl explain deployment                              # 顶层有哪些字段
kubectl explain deployment.spec.template.spec.containers # 容器段能写什么
kubectl explain hpa.spec.metrics --recursive            # 递归展开所有子字段
kubectl explain deployment.spec.template.spec.containers.resources.requests
```

**`-o yaml` 时最该看的四段**：

```bash
kubectl get pod <p> -o yaml
```

| 段 | 看什么 |
|---|---|
| `status.conditions` | `PodScheduled` / `Initialized` / `ContainersReady` / `Ready` 四个条件的状态与 `reason` |
| `status.containerStatuses[].state` | 当前状态：`waiting` / `running` / `terminated` |
| `status.containerStatuses[].lastState.terminated` | **上一次退出的 `reason` 和 `exitCode`**（OOMKilled 的证据在这里） |
| `status.containerStatuses[].restartCount` | 重启了几次 |
| `status.containerStatuses[].state.waiting.reason` | **`CrashLoopBackOff` / `ImagePullBackOff` / `ContainerCreating` 的原文出处** |

### 2.6 `kubectl debug` 临时容器（distroless 无 shell 的解法）

**官方原文** [S6]：

> You can use the `kubectl debug` command to add **ephemeral containers** to a running Pod.

> **Ephemeral containers are useful for interactive troubleshooting when `kubectl exec` is insufficient because a container has crashed or a container image doesn't include debugging utilities, such as with distroless images.**

> Sometimes Pod configuration options make it difficult to troubleshoot in certain situations. For example, **you can't run `kubectl exec` to troubleshoot your container if your container image does not include a shell or if your application crashes on startup.** In these situations you can use `kubectl debug` to create a copy of the Pod with configuration values changed to aid debugging.

**没有 shell 时的官方报错原文** [S6]：

```
OCI runtime exec failed: exec failed: container_linux.go:346: starting container process caused "exec: \"sh\": executable file not found in $PATH": unknown
```

**`kubectl debug` 的三种用法（官方示例）**：

```bash
# ① 给运行中的 Pod 加一个临时容器（官方示例）
kubectl debug -it ephemeral-demo --image=busybox:1.28 --target=ephemeral-demo
# 官方说明：This command adds a new busybox container and attaches to it.
#           The --target parameter targets the process namespace of another container.

# ② 复制一份 Pod 再加调试容器（官方示例）
kubectl debug myapp -it --image=ubuntu --share-processes --copy-to=myapp-debug
# 官方说明：The --share-processes allows the containers in this Pod to see processes
#           from the other containers in the Pod.

# ③ 清理
kubectl delete pod ephemeral-demo
```

**`--target` 的限制（官方原文，必须知道）** [S6]：

> **Note: The `--target` parameter must be supported by the Container Runtime. When not supported, the Ephemeral Container may not be started, or it may be started with an isolated process namespace so that `ps` does not reveal processes in other containers.**

> **这是 `--target` 唯一的坑**：**不是所有 CRI 都支持进程命名空间共享**。不支持时，临时容器起不来，或者起来了但 `ps` 看不到目标容器的进程（**看起来像"debug 进去了但看不到东西"**）。

**`kubectl debug` 与 `kubectl exec` 的选择**：

| 场景 | 用哪个 | 原因 |
|---|---|---|
| 容器正常，有 shell | **`kubectl exec`** | 更快，不改动 Pod |
| 容器没有 shell（distroless / scratch） | **`kubectl debug --image=busybox`** | 用一个带工具的镜像借工具 |
| 容器崩溃了（起不来） | **`kubectl debug`** | **exec 进不去**（官方明确：*"a container has crashed"* [S6]） |
| 需要看目标容器的进程 | `kubectl debug --target=<容器名>` | 共享进程命名空间 |
| 想改配置再试 | `kubectl debug --copy-to=<新名字>` | 复制一份改配置，**不动生产 Pod** |

> **"distroless 的代价是没有 shell，排障要靠 `kubectl debug`"** —— 这句话在面试里很好用，它说明你**知道镜像瘦身的代价，也知道代价的解法**。

### 2.7 selector 匹配：`--show-labels` 与 `labelSelector`

**官方原文（kubectl 速查）** [S7]：

```bash
# Show labels for all pods (or any other Kubernetes object that supports labelling)
kubectl get pods --show-labels
```

> **`--show-labels` 是排障时验证 selector 的标准动作。**

**selector 的匹配规则（L2 已述，此处补排障视角）**：

| 规则 | 排障含义 |
|---|---|
| **集合相等**（不是"包含"） | Service 的 `selector: {app: web}` **只匹配 `app=web`**，不匹配 `app=web,team=a` |
| **selector 与 template 标签必须一致** | Deployment 的 `spec.selector.matchLabels` 与 `spec.template.metadata.labels` 不一致 → **apply 直接报错** |
| **`-l` 筛不出来 ≠ 不存在** | 也可能是标签打错了、或者 Pod 根本还没创建 |

**排障时的三条标准命令**：

```bash
# ① 我以为的标签 vs 实际的标签
kubectl get pods --show-labels

# ② Service 的 selector 到底选谁？（看 Service 的 selector，再去比）
kubectl get svc <svc> -o jsonpath='{.spec.selector}{"\n"}'

# ③ 端点到底有没有？（Service 挂了最常见的原因）
kubectl get endpoints <svc>
# 官方（L2）口径：空的就是没匹配上
```

**`kubectl get endpoints` 为空但 Pod 都 Running —— 这是"应用正常但服务不通"的第一大原因**（L2 已强调）。

### 2.8 节点层排障

**官方原文（集群排障）** [S8]：

> **The first thing to debug in your cluster is if your nodes are all registered correctly.** Run `kubectl get nodes` and verify that all the nodes you expect to see are present and that they are all in the `Ready` state.

> To get detailed information about the overall health of your cluster, you can run `kubectl cluster-info dump`.

> As with Pods, you can use `kubectl describe node` and `kubectl get node -o yaml` to retrieve detailed information about nodes.

**节点的五个 Conditions（官方 `describe node` 示例原文）** [S8]：

| Condition | 官方示例 Reason | 官方示例 Message | 含义 | 排障动作 |
|---|---|---|---|---|
| `Ready` | `KubeletReady` | *"kubelet is posting ready status"* | 节点能接活 | **`False`** → 节点有问题 |
| `Ready` | `NodeStatusUnknown` | *"Kubelet stopped posting node status."* | **kubelet 不上报了**（节点宕机或 kubelet 挂了） | 上机看 kubelet |
| `MemoryPressure` | `KubeletHasSufficientMemory` | *"kubelet has sufficient memory available"* | 内存压力 | **`True`** → 节点在驱逐 Pod |
| `DiskPressure` | `KubeletHasNoDiskPressure` | *"kubelet has no disk pressure"* | 磁盘压力 | **`True`** → 清磁盘 / 扩盘 |
| `PIDPressure` | `KubeletHasSufficientPID` | *"kubelet has sufficient PID available"* | 进程数压力 | **`True`** → 查进程泄漏 |
| `NetworkUnavailable` | `WeaveIsUp` | *"Weave pod has set this"* | CNI 未就绪 | **`True`** → 查 CNI |

> **官方原文**：`status: "False"` 表示**压力不存在**（"has sufficient memory available"）。**所以 `MemoryPressure: True` 才是有压力。**

**NotReady 节点上会发生什么（官方原文）** [S8]：

> Notice the events that show the node is NotReady, and also notice that the pods are no longer running (**they are evicted after five minutes of NotReady status**).

> ```
> Taints:             node.kubernetes.io/unreachable:NoExecute
>                     node.kubernetes.io/unreachable:NoSchedule
> ```

**节点压力驱逐的阈值（来自 L7 的官方来源）** [S9]：

| 硬驱逐阈值 | 触发后 |
|---|---|
| `memory.available<100Mi`（Linux） | 触发 `MemoryPressure`，kubelet 开始驱逐 |
| `nodefs.available<10%` | 触发 `DiskPressure` |
| `imagefs.available<15%` | 触发 `DiskPressure` |
| `nodefs.inodesFree<5%` | 触发 `DiskPressure` |
| `imagefs.inodesFree<5%` | 触发 `DiskPressure` |

**节点层排障的标准动作序列**：

```bash
# ① 节点在不在、Ready 吗
kubectl get nodes

# ② 五个条件分别是什么状态
kubectl describe node <n> | sed -n '/Conditions/,/Addresses/p'

# ③ 节点上还剩多少资源、已被分配多少
kubectl describe node <n> | sed -n '/Allocated resources/,/Events/p'

# ④ 这个节点上的 Pod 都怎么了
kubectl get pods --field-selector spec.nodeName=<n>

# ⑤ 节点级事件（硬件故障、网络、驱逐）
kubectl get events --field-selector involvedObject.kind=Node
```

**节点层故障的三个典型现象 → 根因**：

| 现象 | 根因 | 依据 |
|---|---|---|
| 节点 `NotReady` 且 `Ready` 的 Reason 是 `NodeStatusUnknown` | **kubelet 停止上报** | 官方 Message 原文 [S8] |
| 节点 `NotReady` 后 5 分钟，节点上的 Pod 全没了 | **被驱逐**（`node.kubernetes.io/unreachable:NoExecute` 生效） | 官方原文 [S8] |
| 节点 `MemoryPressure: True`，别的 Pod 被 `Evicted` | **节点内存到阈值**，kubelet 按 QoS 顺序驱逐 | [S9] + L7 |

### 2.9 集群层排障

**官方原文（健康检查端点）** [S10]：

> The Kubernetes API server provides **3 API endpoints** (`healthz`, `livez` and `readyz`) to indicate the current status of the API server. **The `healthz` endpoint is deprecated (since Kubernetes v1.16), and you should use the more specific `livez` and `readyz` endpoints instead.**

> - **livez**: Use this to determine if the API server should be restarted. If `/livez` returns a failure status code (such as 500), the API server is likely in a non-recoverable state, such as a deadlock, and requires a restart.
> - **readyz**: Use this to determine if the API server is ready to accept traffic. If `/readyz` returns a failure status code, it indicates the server is **still initializing or temporarily unable to serve requests (for example, waiting for etcd to be available or waiting for every registered watch cache to complete initial synchronization from etcd)**, and traffic should be routed away from it.

> Machines that check the `healthz`/`livez`/`readyz` of the API server **should rely on the HTTP status code**. A status code `200` indicates the API server is `healthy`/`live`/`ready`, depending on the called endpoint.

**排查 apiserver 的官方命令** [S10]：

```bash
# 逐项健康检查（官方示例）
kubectl get --raw='/readyz?verbose'
```

官方输出示例（逐字）：

```
[+]ping ok
[+]log ok
[+]etcd ok
[+]poststarthook/watch-cache-initialization ok
[+]poststarthook/start-kube-apiserver-admission-initializer ok
...
healthz check passed
```

> **`[+]xxx ok` 是通过，`[-]xxx failed` 是失败**。**这一行输出直接告诉你 apiserver 哪一项坏了**（etcd 挂了会看到 `[+]etcd failed`）。
> 官方还给了排除某项的用法：`curl -k 'https://localhost:6443/readyz?verbose&exclude=etcd'`。

**`componentstatus` 的现状（官方 API 参考）** [S11]：

> ComponentStatus (and ComponentStatusList) holds the cluster validation info. **Deprecated: This API is deprecated in v1.19+**

> **所以 `kubectl get cs` 会报 `Warning: v1 ComponentStatus is deprecated in v1.19+`。**
> **正确做法：用 `/readyz?verbose` 代替 `kubectl get cs`。**

**集群层故障的分层定位**：

| 层 | 检查命令 | 官方依据 |
|---|---|---|
| **apiserver 活着吗** | `kubectl get --raw='/readyz?verbose'` | [S10] |
| **apiserver 各项健康** | 看输出里 `[+]xxx ok` 的逐项结果 | [S10] |
| **etcd 正常吗** | `/readyz?verbose` 里的 `[+]etcd ok` | [S10] |
| **控制面组件日志** | `/var/log/kube-apiserver.log`、`/var/log/kube-scheduler.log`、`/var/log/kube-controller-manager.log` | [S8] |
| **节点侧日志** | `/var/log/kubelet.log`、`/var/log/kube-proxy.log` | [S8] |
| **系统化排障** | `kubectl cluster-info dump` | [S8] |

**官方原文（日志位置）** [S8]：

> For now, digging deeper into the cluster requires logging into the relevant machines. Here are the locations of the relevant log files. **On systemd-based systems, you may need to use `journalctl` instead of examining log files.**

> **Control Plane nodes**:
> - `/var/log/kube-apiserver.log` - API Server, responsible for serving the API
> - `/var/log/kube-scheduler.log` - Scheduler, responsible for making scheduling decisions
> - `/var/log/kube-controller-manager.log` - a component that runs most Kubernetes built-in controllers, with the notable exception of scheduling (the kube-scheduler handles scheduling).

> **Worker Nodes**:
> - `/var/log/kubelet.log` - logs from the kubelet, responsible for running containers on the node
> - `/var/log/kube-proxy.log` - logs from `kube-proxy`, which is responsible for directing traffic to Service endpoints

> **注意**：`journalctl` 的用法（systemd 环境）：
> ```bash
> journalctl -u kubelet -n 100 --no-pager
> journalctl -u kube-apiserver -n 100 --no-pager
> ```

**集群层故障的典型现象 → 根因**：

| 现象 | 根因 | 第一条命令 |
|---|---|---|
| 所有 `kubectl` 命令都超时 | apiserver 无响应 / etcd 卡住 | `kubectl get --raw='/readyz?verbose'` |
| `kubectl` 报 `etcdserver: request timed out` | **etcd 问题**（L2 第 3 步） | `/readyz?verbose` 看 `[+]etcd` |
| **所有 Pod 突然都 `Unknown`** | **节点与 apiserver 通信断了** | `kubectl get nodes` |
| **所有 Pod 突然 `Pending`，且调度器不工作** | kube-scheduler 挂了 | `kubectl get pods -n kube-system` |
| `kubectl get cs` 报 deprecation 警告 | 正常（**v1.19+ 已废弃**） | 改用 `/readyz?verbose` |

### 2.10 排障纪律：四条铁律

**这一节是本篇给面试的"方法论答案"。**

| # | 铁律 | 理由 | 具体动作 |
|---|---|---|---|
| **①** | **先定性，再动手** | **症状层的猜测 90% 是错的** | 先跑 `kubectl get pods` 确定状态，**再**决定查哪个方向 |
| **②** | **按依赖顺序查** | 上游没通，查下游全是噪音 | **API → 控制器 → 调度器 → kubelet → 容器**（9 步链路顺序） |
| **③** | **每步只改一个变量** | 一次改三处，**不知道是哪一处生效的** | 改一个 → 观察 → 再改下一个 |
| **④** | **改动前先记录现状** | 现场是**唯一的证据** | 先 `kubectl get -o yaml > snapshot.yaml`，再动手 |

**补充两条容易被忽略的**：

| # | 纪律 | 理由 |
|---|---|---|
| **⑤** | **区分"症状消失了"和"问题解决了"** | Pod 变 Running **不等于**业务正常（可能探针太松） |
| **⑥** | **不要在生产上"试试看"** | 改配置是变更，**要走正常发布流程**；生产上的临时改动要**记录并回滚** |

**"先定性再动手"的具体含义（对照表）**：

| 错误做法 | 正确做法 |
|---|---|
| 看到 Pod 不起来 → 立刻改镜像 tag | 先 `get` → 看状态 → 看 Events → 定位到"拉镜像"还是"调度" |
| 看到 503 → 改 Service selector | 先 `kubectl get endpoints` → 空的话再看 selector 匹配 |
| 看到 rollout 超时 → 加长 `progressDeadlineSeconds` | **超时只是计时器**；去看没 Ready 的 Pod |
| 看到内存高 → 调大 limits | 先看是谁在用（`kubectl top pods`），**是不是有泄漏** |

**"按依赖顺序"的示意图**：

```
  kubectl 命令能通吗？              → 不能：API/etcd 层（集群层排障）
        │ 能
        ▼
  对象创建成功了吗？                → 不能：认证/授权/准入（看 403 原文）
        │ 能
        ▼
  Pod 对象存在吗？                  → 不能：控制器层（看 RS/Event）
        │ 能
        ▼
  Pod 调度上去了吗？                → 不能：调度层（FailedScheduling）
        │ 能
        ▼
  容器起来了吗？                    → 不能：镜像/卷（ImagePullBackOff）
        │ 能
        ▼
  容器 Ready 了吗？                 → 不能：探针层（Unhealthy）
        │ 能
        ▼
  流量到了吗？                      → 不能：Service/网络层（endpoints）
```

### 2.11 关键参数与默认值

| 参数 | 默认 | 含义 | 出处 |
|---|---|---|---|
| `Deployment.progressDeadlineSeconds` | **600 秒** | 多久算这次发布失败 | L2 实测口径 |
| `terminationGracePeriodSeconds` | **30 秒** | 收到删除信号后等多久再强杀 | 官方原文：*"A Pod is granted a term to terminate gracefully, which defaults to 30 seconds."* [S3] |
| kubelet 探针默认 | period **10s** / failureThreshold **3** | 失败 3 次才判死 | L2 实测口径 |
| Pod `phase` 的取值 | **只有 5 档**：`Pending`/`Running`/`Succeeded`/`Failed`/`Unknown` | 官方明确 *"tightly guarded"* | [S3] |
| `Unknown` phase 的典型原因 | **与节点通信出错** | 官方原文 | [S3] |
| 容器重启退避 | **指数退避**（exponential backoff） | 防止反复重启压垮系统 | [S3] |
| 退避重置 | 容器成功运行一段时间后**重置**（官方举例 10 分钟） | 把新崩溃当第一次 | [S3] |
| NotReady 节点驱逐 Pod 的时间 | **5 分钟** | 官方原文 | [S8] |
| NotReady 节点自动打的污点 | `node.kubernetes.io/unreachable:NoExecute` + `:NoSchedule` | 官方示例 | [S8] |
| 硬驱逐阈值（Linux） | `memory.available<100Mi`、`nodefs.available<10%`、`imagefs.available<15%`、`nodefs.inodesFree<5%`、`imagefs.inodesFree<5%` | 官方默认 | [S9] |
| apiserver 健康端点 | `healthz` / `livez` / `readyz` **三个** | `healthz` **自 v1.16 起废弃** | [S10] |
| `/readyz?verbose` 输出格式 | `[+]xxx ok` / `[-]xxx failed` | 逐项健康 | [S10] |
| `componentstatus` API | **v1.19+ 已废弃** | 改用 `/readyz?verbose` | [S11] |
| 控制面日志路径 | `/var/log/kube-apiserver.log` 等 | systemd 环境用 `journalctl` | [S8] |
| 节点日志路径 | `/var/log/kubelet.log`、`/var/log/kube-proxy.log` | 同上 | [S8] |
| `kubectl apply` 写入的注解 | `kubectl.kubernetes.io/last-applied-configuration` | 记录上次 apply 的内容 | [S12] |

## 3. 动手

> **前置提醒**：本节的演练在**你自己的测试命名空间**里做。**本篇不代为执行**，所有命令都可自行验证。

### 3.1 制造一个故障

用一个**必然拉不到**的镜像来制造"拉镜像失败"（比制造调度失败更可控，且不会影响别人）：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-pull-fail
  namespace: default
spec:
  containers:
  - name: app
    image: registry.example.com/does-not-exist/app:v1
```

```bash
kubectl apply -f demo-pull-fail.yaml
```

**看到什么算对**：Pod 一直 `Pending`/`ContainerCreating`，`describe` 的 Events 里出现 `Failed` + `ErrImagePull` 或 `ImagePullBackOff`。

### 3.2 五步走完

```bash
# ── 第 1 步：定性（症状层）────────────────────────────────
kubectl get pods
# 期望：看到 demo-pull-fail，STATUS 不是 Running

# ── 第 2 步：状态层（结构化）────────────────────────────────
kubectl get pod demo-pull-fail -o yaml
# 期望：status.conditions 里 PodScheduled=True（说明调度成功了！）
#       containerStatuses[0].state.waiting.reason = ImagePullBackOff 或 ErrImagePull
#       state.waiting.message 里有具体的拉取失败原因

# ── 第 3 步：原因层（Events 原文）──────────────────────────
kubectl describe pod demo-pull-fail
# 期望：Events 段最上面（最新）的是：
#       Normal  Scheduled     → 调度成功（说明不是调度问题！）
#       Warning Failed       → ErrImagePull / Failed to pull image ...
#       Warning Failed       → ImagePullBackOff（退避重试中）
# 注意：要按 lastTimestamp 从新到旧读

# ── 第 4 步：运行态（这一层用不上，因为容器根本没起来）──────
kubectl logs demo-pull-fail
# 期望：报容器还在等镜像的错误（因为压根没启动）

# ── 第 5 步：验证修复 ──────────────────────────────────────
# 换成真实存在的镜像
kubectl set image pod/demo-pull-fail app=registry.k8s.io/pause:3.10
# 期望：Pod 变成 Running
```

**这个演练的三个教学点**：

| 教学点 | 体现在哪 |
|---|---|
| **调度和拉镜像是两步** | 第 2 步看到 `PodScheduled=True` 就排除了调度问题 |
| **Events 要从新到旧读** | `Scheduled`（Normal）在 `Failed`（Warning）**下面**——**如果从上往下读会先看到 Scheduled，误以为没问题** |
| **"没日志"不等于"没问题"** | 第 4 步 `logs` 报错本身就是信息 |

### 3.3 验证清单

| 检查 | 命令 | 期望 |
|---|---|---|
| 定性 | `kubectl get pods -o wide` | 状态 + 节点 + 重启次数 |
| 结构化状态 | `kubectl get pod <p> -o yaml` | `status.conditions` + `containerStatuses` |
| 原因 | `kubectl describe pod <p>` | Events 段最新一条 Warning |
| 持续失败还是历史残留 | 看 `count` 与 `lastTimestamp` | count 大 + 时间新 = 持续失败 |
| 上一次崩因 | `kubectl logs <p> --previous` | 崩溃场景必用 |
| 服务端点 | `kubectl get endpoints <svc>` | 非空 |
| 标签匹配 | `kubectl get pods --show-labels` | 与 selector 逐字核对 |
| 集群健康 | `kubectl get --raw='/readyz?verbose'` | 全部 `[+]xxx ok` |

## 4. 速查表

### 4.1 排障症状速查表

| 症状（你看到的） | 最可能的层 | 第二可能的层 | **第一步该跑的命令** | **决定性证据在哪** |
|---|---|---|---|---|
| Pod 一直 `Pending` | 调度层 | 存储层（PVC） | `kubectl describe pod <p>` | Events：`FailedScheduling` + `Insufficient cpu` / `untolerated taint` / `didn't match Pod's node affinity` / `unbound immediate PersistentVolumeClaims` |
| `ImagePullBackOff` / `ErrImagePull` | 镜像层 | 网络层 | `kubectl describe pod <p>` | Events：`Failed to pull image ...` 后的**具体错误**（401 / 404 / timeout） |
| `CrashLoopBackOff` | 应用层 | 配置/依赖层 | `kubectl logs <p> --previous` | 上一个容器实例的日志尾部 |
| `Running 0/1` | 探针层 | 应用启动慢 | `kubectl describe pod <p>` | Events：`Unhealthy` + 探针失败次数 |
| `Init:0/1` 卡住 | init 容器 | 依赖服务没起 | `kubectl logs <p> -c <initName>` | init 容器日志 |
| `OOMKilled` | 运行时（内存） | 应用内存泄漏 | `kubectl get pod <p> -o yaml` | `lastState.terminated.reason = OOMKilled` + `exitCode 137` |
| `Evicted` | 节点层 | 资源层 | `kubectl describe pod <p>` | Pod 的 `Reason` + `kubectl describe node` 的压力条件 |
| `Terminating` 很久 | 删除流程 | `preStop` 卡住 | `kubectl describe pod <p>` | Events + 容器日志 |
| 访问 503 / 连接超时 | Service 层 | 应用层 | `kubectl get endpoints <svc>` | **endpoints 为空 = selector 没匹配上** |
| rollout 超时 | **无信息量** | — | `kubectl get pods -l <selector>` | **没 Ready 的那些 Pod 的 Events** |
| HPA 不扩容 | 指标链路 | 分母/容差 | `kubectl top pods` | top 有输出 → 查 HPA 的 `ScalingActive`；top 报错 → 查 metrics-server |
| 节点 `NotReady` | 节点层 | 主机层 | `kubectl describe node <n>` | `Ready` 的 Reason：`NodeStatusUnknown` = kubelet 停止上报 |
| 别的 Pod 莫名被驱逐 | 节点层（压力） | — | `kubectl describe node <n>` | `MemoryPressure` / `DiskPressure` 为 `True` |
| 所有 Pod 变 `Unknown` | 集群层 | 节点层 | `kubectl get nodes` | 节点与 apiserver 通信断了 |
| 所有 kubectl 命令超时 | 集群层 | etcd | `kubectl get --raw='/readyz?verbose'` | `[+]etcd failed` |
| apply 报 `Forbidden` | 授权层 | 准入层 | 看报错原文 | `User "xxx" cannot ...` = 授权；`exceeded quota` / `violates PodSecurity` = 准入 |
| 改了 yaml 没生效 | 配置层 | 发布流程 | `kubectl get <obj> -o yaml` | 改的是**哪个字段**？env 改了要重启 Pod；镜像改了走滚动更新 |

### 4.2 kubectl 排障命令表

| 命令 | 用途 | 典型输出解读 |
|---|---|---|
| `kubectl get pods -o wide` | 定性：谁有问题 | `STATUS` 是合成状态；`NODE` 空 = 没调度上；`RESTARTS` 递增 = 容器反复重启 |
| `kubectl get pods -l app=web` | 按标签筛 | **什么都没输出** = selector 没匹配上（不是"没有 Pod"） |
| `kubectl get pods --show-labels` | 看真实标签 | 用来核对 selector / NetworkPolicy 的 `podSelector` |
| `kubectl get pod <p> -o yaml` | 结构化状态 | `status.conditions`（`PodScheduled`/`Ready`）、`containerStatuses[].state.waiting.reason`、`lastState.terminated.reason`、`exitCode` |
| `kubectl describe pod <p>` | **原因层**（核心） | Events 段**从新到旧**读；Warning 优先；`count` 大 + 时间新 = 持续失败 |
| `kubectl get events --sort-by=.lastTimestamp` | 跨对象时间线 | 回答"刚才集群发生了什么" |
| `kubectl get events --field-selector type=Warning` | 过滤噪音 | 只看 Warning |
| `kubectl get events --field-selector involvedObject.kind=Node` | 节点级事件 | 硬件、网络、驱逐相关 |
| `kubectl logs <p>` | 当前容器日志 | **空/报错不代表没问题**（可能容器根本没起来） |
| `kubectl logs <p> --previous` | **上一个容器实例的日志** | **崩溃重启后定位根因的唯一办法** |
| `kubectl logs <p> -c <name>` | 指定容器 | sidecar / init 容器场景 |
| `kubectl logs -f <p> --tail=100` | 实时跟 | `--since=5m` 看最近 5 分钟 |
| `kubectl exec -it <p> -- sh` | 进容器 | **distroless 报 `executable file not found in $PATH`** |
| `kubectl debug -it <p> --image=busybox --target=<c>` | 临时容器（无 shell 时） | 官方明确支持 distroless 场景；`--target` 需 CRI 支持 |

| `kubectl rollout status deploy/<d>` | 发布计时器 | **超时零信息量**，只说明"等够了" |

| `kubectl rollout undo deploy/<d>` | 回滚 | 回到上一版 |
| `kubectl rollout pause deploy/<d>` | 冻结发布 | 排查时防止变更继续 |
| `kubectl scale deploy/<d> --replicas=3` | 直接改副本数 | 绕过 HPA 也会被 HPA 改回 |
| `kubectl set image deploy/<d> app=img:tag` | 换镜像 | 触发滚动更新 |
| `kubectl set env deploy/<d> K=V` | 改 env | **只改 env**；改其他字段（resources 等）**不会**自动生效 |
| `kubectl diff -f <file>` | 预演 apply | 官方：走 server-side dry-run |
| `kubectl apply -f <file>` | 声明式更新 | 会写 `last-applied-configuration` 注解 |
| `kubectl explain <res>.<path>` | **本集群版本的字段字典** | **不用联网，版本永远匹配** |
| `kubectl get --raw='/readyz?verbose'` | apiserver 逐项健康 | `[+]xxx ok` / `[-]xxx failed`；`[+]etcd failed` → etcd 问题 |

## 5. 横向对比

### 5.1 Pod 层 vs 节点层 vs 集群层

| 维度 | **Pod 层** | **节点层** | **集群层** |
|---|---|---|---|
| **典型症状** | 某个/某几个 Pod 不正常 | **一批** Pod 同时异常；节点 `NotReady` | **所有** Pod、所有命令都异常 |
| **影响范围** | 局部（一个服务） | 一台机器上的所有 Pod | 整个集群 |
| **第一条命令** | `kubectl get pods` | `kubectl get nodes` | `kubectl get --raw='/readyz?verbose'` |
| **核心命令** | `describe pod` → Events | `describe node` → Conditions | `/readyz?verbose` + 控制面日志 |
| **典型根因** | 镜像 / 配置 / 探针 / 调度约束 | kubelet 挂了 / 内存磁盘压力 / CNI 故障 | apiserver / etcd / 调度器 / 控制器 |
| **时间尺度** | 分钟 | 小时（压力累积） | 秒级（**大面积同时挂 → 优先怀疑集群层**） |
| **谁负责** | 应用团队 | 平台/SRE | 平台/SRE |
| **典型处置** | 改镜像、改配置、回滚 | 清理磁盘、重启 kubelet、驱逐负载 | 恢复 etcd、重启 apiserver、扩容控制面 |

**"从大到小"的排查顺序（为什么）**：

| 顺序 | 理由 |
|---|---|
| **① 集群层** | **如果 apiserver 挂了，你连 `kubectl get pods` 都跑不了**——先确认工具能用 |
| **② 节点层** | **如果节点挂了，它上面的所有 Pod 都会异常**——局部异常先排除是不是节点的问题 |
| **③ Pod 层** | 确认了集群和节点都正常，才轮到单个 Pod |

> **实操判据**：**一个 Pod 异常 → Pod 层；同一节点上一批 Pod 异常 → 节点层；不同节点上的一批 Pod 同时异常 → 集群层。**

### 5.2 `describe` vs `get -o yaml` vs `logs`

| 维度 | `kubectl describe` | `kubectl get -o yaml` | `kubectl logs` |
|---|---|---|---|
| **给谁看** | **人**（排障时） | **机器**（脚本 / 二次加工） | **应用**（运行时） |
| **核心内容** | **Events（原因）** + 人工整理过的字段摘要 | **原始对象**（spec + status 全量） | 容器标准输出/错误 |
| **能回答"为什么"** | ✅ **能**（Events 的 Message） | ⚠️ **间接**（`status` 里的 reason/exitCode） | ⚠️ **只说应用自己看到的** |
| **能回答"是什么"** | ⚠️ 部分 | ✅ **最全** | ❌ |
| **时间维度** | **历史 + 当前**（Events 有时间戳） | **当前快照** | **当前容器实例**（`--previous` 才到上一次） |
| **输出量** | **大**（可能几百行） | **大**（可能上千行） | 小 |
| **适合脚本处理** | ❌ 格式不稳定 | ✅ **稳定（结构化）** | ✅ |
| **典型用途** | **排障第一步** | 查字段、取证、给脚本 | 定位应用层问题 |

**三者的正确配合顺序**：

```
kubectl get pods -o wide      →  定性（哪些 Pod、什么状态）
        ↓
kubectl describe pod <p>      →  找原因（Events 的 Message）★ 最关键
        ↓
kubectl get pod <p> -o yaml   →  取精确证据（exitCode、lastState、conditions）
        ↓
kubectl logs <p> [--previous] →  应用自己在说什么
        ↓
kubectl exec / debug          →  进去看实时状态
```

> **一条实用技巧**：`describe` 的输出太长时，**用 `-o yaml` 精确取字段**比在 `describe` 里翻更快：
> ```bash
> kubectl get pod <p> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}'
> ```
> **这能一眼确认是不是 `OOMKilled`。**

### 5.3 排障动作 vs 变更动作

**这两类动作的纪律完全不同，混在一起是生产事故的常见来源。**

| 维度 | **排障动作（诊断）** | **变更动作（修复）** |
|---|---|---|
| **目的** | **获取信息** | **改变系统状态** |
| **代表性命令** | `get`、`describe`、`logs`、`events`、`top`、`explain`、`auth can-i`、`--raw` | `apply`、`set`、`scale`、`patch`、`edit`、`rollout`、`delete`、`label`、`annotate` |
| **风险** | **低**（只读） | **高**（改变集群状态） |
| **要不要走审批** | 通常不用 | **要** |
| **要不要留痕** | 记录输出（取证） | **记录变更单**（谁改的、为什么、怎么回滚） |
| **能不能在生产直接做** | **能** | **不能**（除非是明确的止损操作） |
| **回滚** | 不需要 | **必须预先想好** |

**四条纪律（把两者分开）**：

| # | 纪律 |
|---|---|
| **①** | **诊断阶段只用只读命令**。`get`/`describe`/`logs`/`events` 随便跑；`apply`/`edit`/`patch` **先别碰** |
| **②** | **先记录现状再改**：`kubectl get <obj> -o yaml > before.yaml` |
| **③** | **每步只改一个变量**，改完立刻观察，**不要攒着改** |
| **④** | **止损操作（删 Pod、扩副本、改流量）要立刻执行并记录**；**结构性修复走正常变更流程** |

> **第 ④ 条的边界怎么判**：
> - **止损**：Pod 卡住影响线上 → 删掉它让控制器重建、改 `maxSurge` 缓解、临时提副本数。**这些先做，再复盘。**
> - **非止损**：改镜像 tag、升级依赖、改架构。**这些不能"试试看"，要走发布流程。**
>
> **判据**：*"这个改动会不会让正在恢复的线上更糟？"* 会 → 止损；不会 → 走流程。

## 6. 踩坑与排障（症状 → 状态 → 真实原因）

**排障铁律：永远往下挖到第三层（Events 里的 Message 原文）。**

| 你看到的（症状） | 状态 | 真实原因 | 怎么修 | 下次怎么防 |
|---|---|---|---|---|
| **`kubectl get pods` 一切正常，但用户说服务挂了** | 正常 | **Service 的 selector 没匹配上** → endpoints 为空 → 访问 503 | `kubectl get endpoints <svc>`，空就是它；核对 Service 的 `spec.selector` 与 Pod 标签 | 部署后必查 endpoints；Service 与 Deployment 的标签用同一份模板 |
| **只看 `get pods` 就下结论"没问题"** | 正常 | **`Running` 不等于业务正常**（探针太松、应用内部 500） | 加业务探针；看应用日志与流量指标 | 健康检查要探**业务接口**不是探进程 |
| **Events 里有一条 `FailedScheduling`，就认定是调度问题** | `Pending` | **可能是历史残留**（几小时前的失败，条件早就变了） | 看 `lastTimestamp` 与 `count`；**从最新一条往下读** | 排查时先 `kubectl get events --sort-by=.lastTimestamp` 看全局时间线 |
| **`kubectl logs <pod>` 显示为空，以为没问题** | 正常 | 容器**根本没起来**（在等镜像/等卷）；或**这是重启后的新实例**（日志被清空） | `kubectl describe pod` 看容器 `state`；崩溃场景用 **`--previous`** | 崩溃排查**永远先试 `--previous`** |
| **`kubectl exec` 报 `executable file not found in $PATH` 就放弃** | 正常 | **镜像没有 shell**（distroless/scratch） | **`kubectl debug -it <pod> --image=busybox --target=<容器名>`** | 镜像瘦身是好事，排障用 debug 借工具 |
| **`kubectl debug` 进去了但 `ps` 看不到别的容器的进程** | 正常 | **CRI 不支持进程命名空间共享**（官方明确说明） | 去掉 `--target`，或换支持 CRI 的运行时 | 知道这个限制；不纠结 |
| **改了 Deployment 的 yaml，`get` 出来没变** | 正常 | ① **改的不是 `spec.template` 里的字段**（比如 env 之外的）；② **Pod 模板没变就不会滚动更新**；③ **env 改了不重启现有 Pod** | `kubectl rollout restart deploy/<d>` 触发重建；核对 `spec.template` 的 diff | 记住"改 env 要重启，改 image 自动滚" |
| **改了 `resources.requests`，Pod 没变化** | 正常 | **requests 变更需要重建 Pod**；且**原地调整可能改变 QoS 等级 → 准入被拒** | `kubectl rollout restart`；改 requests 前想清楚 QoS 影响 | requests/limits 变更走发布流程 |
| **改了 ConfigMap，应用的配置没变** | 正常 | **ConfigMap 挂载到文件后不会自动刷新**（除非应用自己 watch） | 重启应用或改用能热加载的配置方式 | 配置变更清单里写明"要不要重启" |
| **Pod 显示 `OOMKilled`，以为是内存 limit 太小** | `Failed`/`OOMKilled` | **可能是内存泄漏**（limit 只是最后一道防线）；也可能**根本没有 limit** | `kubectl get pod -o yaml` 看 `lastState.terminated.reason` 确认；对比 limit 与实际用量曲线 | 监控内存使用趋势；给 JVM 配合理的堆上限 |
| **把 `OOMKilled` 当成"节点内存压力驱逐"** | `OOMKilled` | **两者完全不同**：OOMKilled = **容器自己的**内存超 limit（内核杀的）；驱逐 = **节点整体**压力（kubelet 杀的） | OOMKilled → 查这个容器的 limit；Evicted → 查节点的 `MemoryPressure` | 记住 L7 的那张对照表 |
| **节点 `NotReady`，以为是节点挂了** | `NotReady` | 可能是 **kubelet 停止上报**（网络问题、kubelet 进程挂了） | `kubectl describe node` 看 `Ready` 的 Reason：`NodeStatusUnknown` = kubelet 停止上报 | 监控节点的心跳与 `Ready` 条件 |
| **节点 `NotReady` 后 Pod 全没了，以为是 Pod 自己退出的** | Pod 消失 | **5 分钟后被驱逐**（官方原文），节点被打了 `unreachable:NoExecute` 污点 | 修节点；`kubectl get events --field-selector involvedObject.kind=Node` 看原因 | 节点维护前先 `drain`（走 Eviction API，遵守 PDB） |
| **`kubectl get cs` 报 deprecation 警告，以为集群有问题** | 正常 | **`componentstatus` API 自 v1.19+ 已废弃**（官方明确） | 改用 `kubectl get --raw='/readyz?verbose'` | 用 `/readyz?verbose` 做集群健康检查 |
| **集群大面积同时异常，先怀疑业务代码** | 各种异常 | **集群层问题**（apiserver / etcd / 网络） | `kubectl get --raw='/readyz?verbose'`；看 `[+]etcd ok` | 建集群级监控（apiserver 可用性、etcd 延迟） |
| **Pod 重建了但名字变了，以为是 bug** | 正常 | **Pod 被删后控制器重建，新 UID**（官方明确：*"A given Pod ... is never 'rescheduled' to a different node"*） | 正常；`kubectl get pods --sort-by=.metadata.creationTimestamp` 看时间线 | 理解 Pod 是"可抛弃的"（L2 的核心认知） |
| **`kubectl logs` 有输出但日志里没有业务内容** | 正常 | 日志写到了**别的容器**（sidecar 收集器）；或应用写的是**文件**不是 stdout | `kubectl logs <p> -c <真实容器名>`；检查应用的日志配置 | 日志规范：统一输出到 stdout |
| **`kubectl get pods -l app=web` 什么都没有** | — | **selector 没匹配上**（标签拼错 / Pod 还没建 / 标签在 template 里但没生效） | `kubectl get pods --show-labels` 逐字核对 | 标签用模板变量生成，不手抄 |
| **HPA 不扩容，去改 Deployment 的 replicas** | 正常 | **HPA 会把它改回去**（HPA 管的就是这个字段） | 先查 `kubectl top pods`（指标链路）与 HPA 的 `ScalingActive` | 扩容问题查 HPA，不手动改 replicas |
| **重装了 Pod 还是不行，开始怀疑 etcd** | 各种 | **跳过了中间层**：Events 都没读就怀疑底层 | 回到三层模型：症状 → 状态 → Events | 固化"先 Events 后底层"的纪律 |
| **`kubectl describe` 输出太长找不到重点** | — | **没按"最新在上"读** | 用 `-o jsonpath` 精确取字段；用 `kubectl get events --sort-by` | 熟练用 jsonpath 取单个字段 |

## 8. 自测三问

1. **能说清输入输出吗？** —— 输入是一个**异常现象**（"Pod 起不来"/"服务 503"/"发布卡住"）；输出是"**它卡在 9 步链路的第几步，根因的原始报错是什么**"。中间靠三层模型：**症状（kubectl get 的 STATUS）→ 状态（`-o yaml` 的 conditions 与 containerStatuses）→ 原因（describe 的 Events.Message）**。**`rollout status` 的超时只是第一层，它不参与定位。**
2. **能故意改坏再倒推吗？** —— 五个实验：① 用一个不存在的镜像 → 看到 `ErrImagePull`/`ImagePullBackOff`，并**从 Events 里区分出"调度成功了（Scheduled）但拉镜像失败"**；② 把 `requests.cpu` 改成天文数字 → 看到 `FailedScheduling` + `Insufficient cpu`；③ 删掉 Pod 的 `command` 让它立刻退出 → 看到 `CrashLoopBackOff`，并用 **`logs --previous`** 拿到崩因（**这是 `--previous` 的核心价值**）；④ 给一个标签写错的 `nodeSelector` → 看到 `didn't match Pod's node affinity`；⑤ **在 Events 里故意留一条旧的 Warning，然后制造一个新事件** → 体会"历史残留"的误判（**这一条是本篇最容易被忽略、也最容易在面试里体现经验**）。
3. **能画上下游吗？** —— 画出 `用户/监控 → 症状 → kubectl get（状态）→ kubectl describe（Events.Message）→ 根因`，并画出**平行的一条链**：`kubectl get -o yaml → status.conditions / containerStatuses / lastState.terminated → exitCode / reason`。然后在**旁边**画出三层排查顺序：**集群层（/readyz?verbose）→ 节点层（describe node 的五个 Conditions）→ Pod 层（Events）**，并标出"**大面积同时异常 → 优先查上层**"这条判据。
