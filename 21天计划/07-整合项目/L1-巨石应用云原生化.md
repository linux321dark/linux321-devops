## 1. 概念

### 1.1 什么是"巨石应用"（本篇的项目设定）

> **一句话**：巨石应用不是"代码写得好不好"的问题，是**一个进程里塞了所有业务、所有部署方式只有一种、所有变更都要停机**的问题。

本篇设定一个**真实形态**的应用（不是 Hello World，是一个能拿来讨论的中小型系统）：

| 组件 | 技术栈 | 形态 | 现在的痛点 |
|---|---|---|---|
| `order-api` | Spring Boot 单体（Java 17 + Maven） | 一个进程包揽下单、查询、对账入口 | 镜像 A 起步（教学口径）；改一行配置要重新打整个包 |
| `settle-job` | 同 `order-api` 镜像里的定时任务（`@Scheduled`） | 跟 API 跑在同一个进程 | 定时任务跟在线服务互相抢资源；扩容 API 会把定时任务也扩一份 |
| `report-tool` | Go 工具服务（内部报表导出） | 一个 Go 二进制 | 裸机跑，依赖人工传文件 |

**这三个组件决定了本篇的三个技术选型点**：

1. `order-api`（Java）→ 必须讲**多阶段构建 + 镜像瘦身 + 非 root**，因为它决定**扩容速度**（D1 的核心收益）
2. `settle-job`（同镜像不同形态）→ 必须讲**同一个镜像两种工作负载**（Deployment + CronJob），这是很多人不知道的"一次构建两处用"
3. `report-tool`（Go）→ 必须讲**scratch 静态编译**（`CGO_ENABLED=0` + `-ldflags="-s -w"`），它是**镜像能跑但 HTTPS 全挂**的经典坑

> **为什么选这三类而不是"三个 Java 服务"**：Java 单体 + 定时任务 + Go 工具服务，**刚好覆盖了三种不同的失败模式**（大镜像慢启动、进程内资源争抢、静态链接缺证书）。选样例要有区分度，否则整篇就退化成"照抄 D1"。

### 1.2 为什么不能一次做完（分阶段的三个理由）

这是本篇的方法论内核。**"一次做完"在真实项目里几乎必翻车**，三个理由：

| 理由 | 具体表现 | 分阶段怎么解 |
|---|---|---|
| **① 收益不可见 → 拿不到资源** | 一次性改造三个月的活，领导看不到中间成果，第三个月被砍预算 | 每个阶段独立出成果，**阶段 1 就能拿出"镜像 A / B"这个可汇报的数字** |
| **② 变量太多 → 出问题归因不了** | 容器化 + K8s + CI + GitOps 同时上，出故障不知道是探针、是 HPA、还是同步竞态 | 每个阶段只引入**一个新变量**，故障归因范围被压到最小 |
| **③ 回滚成本随进度非线性上升** | 第 8 周时配置已搬进 K8s、数据已迁到 Operator，回退要同时撤三处 | 早期回滚 = 改一行 yaml；后期回滚 = 数据双写、流量切回、配置源迁回 |

> **第三点最重要，也最容易被忽略。** 很多"云原生化"项目死在同一个地方：**改造顺序让回滚成本指数上升**。本篇的阶段顺序不是按技术难度排的，是按**回滚成本从低到高**排的。

## 2. 机制

### 2.1 改造的三条主线

整个改造看起来有八个阶段，但拆开只有**三条主线**。看懂这三条，阶段顺序就不会排错。

```
主线 A · 制品线（把"每次都不一样"变成"每次都一样"）
  源码 ──多阶段构建──▶ 不可变镜像 ──扫描──▶ 镜像仓库
  收益：镜像体积↓ → 拉取快 → 扩容快；漏洞可拦截；版本可回溯
  阶段：1（容器化） → 4（CI/CD 与门禁）

主线 B · 交付线（把"人去点"变成"声明去拉"）
  Git（唯一事实源）◀──PR 评审── 研发提交
        │
        └─▶ ArgoCD（拉模型）──▶ K8s 集群实际态
  收益：变更可审计（Git 历史）、集群不漂移（SelfHeal）、回滚 = revert
  阶段：2（上 K8s） → 5（交付与 GitOps）

主线 C · 运行线（把"坏了才知道"变成"坏了马上知道、坏了自己好"）
  指标 / 日志 / 发布事件 ──▶ 判定 ──▶ 自动动作
  收益：MTTR↓、扩容及时、发布可控
  阶段：3（弹性） → 6（可观测与告警） → 7（渐进发布）
```

**三条线的依赖关系是单向的**：

| 依赖 | 为什么是这个方向 |
|---|---|
| A → B | **镜像必须先不可变**，GitOps 才有意义。否则同步的是"每次渲染结果都不同"的清单，SelfHeal 会把你自己覆盖自己 |
| B → C | **必须先能声明式部署**，才有"版本"这个概念。有版本才能给指标打版本标签，才能做渐进发布 |
| A → C | **指标要关联到版本**，前提是版本可识别。tag 覆盖（用 `latest`）的话，指标永远对不上是哪次发布 |

> **一句话记住顺序**：**先让制品可识别（A），再让交付可声明（B），最后让运行可判定（C）**。跳过 A 直接做 GitOps，是 90% 的团队踩过的第一个坑——同步出一堆 `OutOfSync`，但说不清哪个是对的。

### 2.2 基线量化：量什么、怎么量、量不出来怎么办

**这是阶段 0 的全部内容，也是整篇项目方法论的支点。** 没有基线，后面所有"提效 XX%"都是编的。

| 要量的指标 | 怎么量（可执行） | 记录形式 | 用途 |
|---|---|---|---|
| 镜像体积 | `docker images <repo>:<tag> --format "{{.Size}}"`；分层归因用 `docker history` | MB 数字 + 层明细 | 决定拉取时间 → 扩容时间 |
| 构建耗时 | CI 里看单个 job 的 duration（不是整条流水线） | 秒 | 归因到"哪一层慢" |
| 流水线总耗时 | 从 push 到镜像可拉的总时长 | 分钟 | 对外汇报的主指标 |
| 发布一次耗时 | 从"决定发布"到"新版本对外可用" | 分钟 | 交付效率 |
| 发布频率 | 一个月发布次数 × 每次耗时 | 小时/月 | 算年度节省 |
| 故障恢复耗时 | 从"故障发生"到"业务恢复"（要人确认） | 分钟 | 算 MTTR 收益 |
| 峰值资源占用 | 业务高峰时的 CPU / 内存 / 实例数 | 核 / GB | 算弹性收益的分子 |
| 缩容是否优雅 | 缩容时是否有 5xx / 连接被断 | 是/否 | 决定能不能上弹性 |
| 故障类型分布 | 近 3 个月事故单分类 | 各类占比 | 决定先做哪条主线 |

**量不出来怎么办**（真实项目里一半的指标都量不出来）：

| 量不出来 | 替代做法 | 口径声明 |
|---|---|---|
| 故障恢复耗时没人记录 | 从最近 3 次事故的复盘单里倒推 | **标"回溯估算，非精确统计"** |
| 流量曲线没有 | 用负载均衡的请求日志按小时聚合 | 标"近 7 天口径" |
| 没有 CI 历史 | **现在就开始记**——加一个最简流水线，只记录时间戳 | 标"从 X 月起开始采集，之前无数据" |
| 副本资源说不清 | 先按"平均使用量 × 1.5"估，后面用监控校准 | 标"估算值，阶段 6 有数据后回填" |

> **数据纪律**：**宁可写"量不出来 + 打算怎么量"，也不要填一个看起来合理的数字。** 面试官追问"这个 62% 怎么来的"，答"我按 7 天流量曲线积分算的"和答"我估的"是两种完全不同档次的回答。前者能深聊，后者当场掉价。

### 2.3 阶段依赖图：谁解锁谁

```
阶段 0 基线量化
   │  （产出：基线表，后面每一阶段都要回填一列）
   ▼
阶段 1 容器化 ──────────────────┐
   │  解锁：拉取快 → 扩容快     │
   ▼                            │
阶段 2 上 K8s ──────────────┐   │  解锁：可声明、可版本化
   │  解锁：HPA 有对象可管    │   │
   ▼                         │   │
阶段 3 弹性 ◀────────────────┘   │  解锁：指标可关联版本
   │  解锁：节点可自动伸缩       │   │
   ▼                             │
阶段 4 CI/CD 与门禁              │  解锁：制品可追溯
   │  解锁：版本可识别            │   │
   ▼                             ▼
阶段 5 交付与 GitOps ─────────────────────────┐
   │  解锁：变更可审计、漂移可见              │  解锁：可安全灰度
   ▼                                        ▼
阶段 6 可观测与告警 ───────────────────▶ 阶段 7 渐进发布
   │  解锁：判定"这次发布好不好"
   ▼
（阶段 8 · 中间件 Operator —— 独立支线，不阻塞主线）
```

**"阶段 3 弹性"为什么排在"阶段 4 CI/CD"前面**（这是个常见纠结点）：

- 弹性对**制品**的敏感度低于对**资源声明**的敏感度。HPA 能不能工作，取决于 `requests.cpu` 有没有写，**跟镜像是不是 CI 产出的没关系**
- 而反过来，CI 流水线接进 K8s 之后，如果集群已经有 HPA，**"Helm 管 replicas 还是 HPA 管 replicas"这个冲突会立刻出现**（见 [`../第1周/第07天.md`](../第1周/第07天.md) 场景 B 第 4 条）
- **先上弹性，等 CI 接进来的时候冲突已经暴露过一次了**，不至于在流水线里第一次遇到

### 2.4 关键参数与默认值（跨篇一致口径）

本篇所有阶段都用这张表，**口径与本资料库其他篇目完全一致**：

| 参数 | 默认 / 口径 | 出处 | 写错的后果 |
|---|---|---|---|
| `Deployment.progressDeadlineSeconds` | **600** | [`../02-K8s核心/L2-K8s架构与对象模型.md`](../02-K8s核心/L2-K8s架构与对象模型.md) | `rollout status` 超时——**这个报错零信息量**，要去 Pod Events 找真因 |

| `scaleDown.stabilizationWindowSeconds` | **300s** | 同上 | 缩容抖动 1→3→1→3 |
| 扩容稳定窗口 | **0s**（故意不对称：扩要快、缩要慢） | 同上 | — |
| HPA 生效延迟 | 采集 15s + 同步周期 + 调度拉镜像 + 就绪探针，**1–2 分钟量级** | 同上 | 指望 HPA 救秒级尖峰 → 必须 `minReplicas` 预留 + 限流兜底 |

| 探针默认 | `period 10s` / `failureThreshold 3` | 同上 | — |
| 探针语义 | **liveness 失败 → 重启；readiness 失败 → 只摘端点、不重启** | 同上 | 混淆两者 → 要么假成功上线，要么误杀正常 Pod |
| QoS 三档 | BestEffort → Burstable → Guaranteed（**驱逐顺序**） | 同上 | 没配 requests → BestEffort → 节点紧张时**第一个被驱逐** |
| Prometheus 采集模型 | **拉模型**（Prometheus 主动 scrape `/metrics`） | [`../第2周/第12天.md`](../第2周/第12天.md) | 与 Zabbix 的推模型混淆 → 讲不清"服务死了怎么发现" |
| ArgoCD 同步模型 | **拉模型**（集群内的 ArgoCD 拉 Git） | [`../第2周/第10天.md`](../第2周/第10天.md) | CI 里 `kubectl apply` = push 模式，**恰好是 GitOps 的反面** |

### 3.1 阶段 0 · 现状盘点与基线量化

**目标**：在动任何一行代码之前，把"现在到底什么样"变成一张有数字的表。

**具体产物**：

```
baseline/
├── baseline.md          # 基线表（下面这张）
├── app-inventory.md     # 应用清单：组件 / 负责人 / 依赖 / 部署方式
```

[`baseline.md`](baseline/baseline.md) 模板：

| 指标 | 改造前 | 测量方法 | 数据来源 | 采集起始 |
|---|---|---|---|---|
| `order-api` 镜像体积 | （填） | `docker images` | 本机 / ACR 控制台 | 即日 |
| `report-tool` 镜像体积 | （填） | 同上 | 同上 | 即日 |

| 发布频率 | （填） | 发布单计数 | 发布单 | 近 3 个月 |

**验证方法**：

```bash
# ① 镜像体积（只读已有镜像，不拉新镜像）
docker images --format "{{.Repository}}:{{.Tag}}  {{.Size}}" | grep -E 'order-api|report-tool'

# ② 分层归因：这 A 花在哪
docker history <order-api 镜像> --format "{{.Size}}\t{{.CreatedBy}}" | head -20

# ③ 峰值资源（宿主机上，只读）
top -bn1 | head -5
free -m

# ④ 查不到时先建"计时器"——从今天起记
#    （这是最低成本、也最容易被忽略的一步）
```

**看到什么算成功**：
- [`baseline.md`](baseline/baseline.md) 八行**全部有值或明确标注"暂无/估算/回溯"**
- 每一行都写清了**测量方法**和**数据来源**（没有方法的数字不算基线）
- [`traffic-profile.md`](baseline/traffic-profile.md) 里有一条 **7 天峰谷曲线**（哪怕是手画的折线）

**常见失败点**：

| 失败点 | 表现 | 怎么破 |
|---|---|---|
| 没人配合填表 | 表格空着，改造做到一半没有基线可比 | **先只填 3 项**：镜像体积、构建耗时、发布耗时。这三项自己就能测 |
| 把"行业数据"当"本项目数据" | 表格里出现 D2 场景 A 的"峰谷 3–5 倍" | **明确标注来源列**。行业口径只能当假设，不能当基线 |
| 基线数字记成区间又说不出分布 | 汇报时"大约 60%"但追问怎么算的答不出 | 记**区间 + 样本量**（如"近 3 个月 11 次发布，5–40 分钟"） |
| 基线表做完没人回填 | 阶段 8 汇报时改造后一栏全是空的 | **基线表和阶段表放在同一个文件里**，改一个必须改另一个 |

**这一步解决了基线里的哪条**：**全部**。阶段 0 不解决任何运行时问题，它解决的是"**能不能证明改造有效**"这个元问题。

> **这是整篇最重要的一段。** 面试里被问"这个改造带来了什么收益"，答案的第一句不该是数字，**第一句该是"我先量了基线，量的是这八项"**——这才是工程师的思维顺序。

### 3.2 阶段 1 · 容器化

**目标**：让 `order-api` 和 `report-tool` 变成**不可变、可拉取、可复现**的制品。

**具体产物**：

```
app/
├── order-api/
│   ├── Dockerfile
│   ├── .dockerignore
│   └── pom.xml
└── report-tool/
    ├── Dockerfile
    ├── .dockerignore
    └── go.mod
```

`order-api/Dockerfile`（关键行与理由）：

```dockerfile
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
RUN mkdir -p /root/.m2 && printf '%s' \
  '<settings><mirrors><mirror><id>aliyun</id><mirrorOf>central</mirrorOf><name>aliyun maven</name><url>https://maven.aliyun.com/repository/public</url></mirror></mirrors></settings>' \
  > /root/.m2/settings.xml
COPY pom.xml .
RUN mvn dependency:go-offline -q
COPY src ./src
RUN mvn package -DskipTests -q
FROM eclipse-temurin:17-jre-alpine AS runtime
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
USER 1000
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app.jar"]
```

| 行 | 为什么 | 写错的后果 |
|---|---|---|
| `COPY pom.xml .` → `go-offline` → `COPY src` | **依赖层在前**，改代码只重跑最后两层 | 顺序颠倒 → 每次改代码重下全部依赖 |
| `FROM ...jre-alpine AS runtime` | **JRE 不是 JDK** | 用 JDK 当运行时 → 白带一套编译器 |
| `USER 1000` | 非 root，容器逃逸第一道防线 | 默认 root → 容器被攻破即宿主 root |
| `ENTRYPOINT ["java","-jar",...]` | **exec 形式**，java 是 PID 1，能收到 SIGTERM | shell 形式 → sh 是 PID 1 不转发 SIGTERM → **优雅停机完全失效，每次缩容等满 30 秒grace period 被强杀，用户看到 502** |

`report-tool/Dockerfile`（Go → scratch）：

```dockerfile
FROM golang:1.26.0 AS build
ENV GOPROXY=https://mirrors.aliyun.com/goproxy/,https://goproxy.cn,direct
ENV GOSUMDB=sum.golang.google.cn
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /bin/app .
FROM scratch
COPY --from=build /bin/app /bin/app
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
USER 65532:65532
EXPOSE 8080
CMD ["/bin/app"]
```

| 行 | 为什么 | 写错的后果 |
|---|---|---|
| `ENV GOSUMDB=sum.golang.google.cn` | **校验和库也要走国内** | 只改 `GOPROXY` 不改它 → 校验仍连 `sum.golang.org` → 一样卡死（最隐蔽的一个坑） |
| `CGO_ENABLED=0` | 纯静态编译 | 动态链接 → `FROM scratch` 跑不起来（缺 glibc） |
| `COPY ca-certificates.crt` | **scratch 连 `/etc/ssl/certs` 都没有** | 不拷 → **所有 HTTPS 请求报 `x509: certificate signed by unknown authority`**（典型报错），镜像能跑但接口全挂 |
| `USER 65532:65532` | 非 root | root → 安全风险 |

`.dockerignore`（两个项目都要有）：

```
.git
target/
node_modules/
*.log
.env
```

**验证方法**：

```bash
# ① 构建（本地）
docker build -t order-api:phase1 app/order-api
docker build -t report-tool:phase1 app/report-tool

# ② 体积（关键判据）
docker images order-api:phase1 report-tool:phase1 --format "{{.Repository}} {{.Size}}"
# 期望：Java 在 300MB 量级（实测基准 A），Go 在 V 量级（实测基准 B）

# ③ 非 root 生效
docker run --rm order-api:phase1 id -u     # 输出非 0
docker run --rm report-tool:phase1 id -u   # 输出 65532

# ④ 最终阶段不含工具链
docker history order-api:phase1 | grep -iE 'maven|javac|jdk'   # 期望无输出

# ⑤ 优雅停机信号可达（exec 形式验证）
docker run --rm -d --name t1 order-api:phase1
docker stop t1        # 期望：应用自己处理 SIGTERM 后退出，不是等满 grace period 被 SIGKILL
```

**看到什么算成功**：
- `docker images` 显示 Java **A 量级**、Go **B 量级**（与本机实测基准对齐）
- `id -u` 返回非 0
- `docker history` 的 runtime 阶段**无 JDK / 编译器 / 工具链**
- `docker stop` 后应用日志里能看到**优雅退出记录**，而不是被强杀的痕迹

**常见失败点**：

| 失败点 | 典型报错 | 怎么修 | 下次怎么防 |
|---|---|---|---|
| 依赖层顺序颠倒 | 构建从 40 秒变成 5 分钟 | `COPY pom.xml` → `go-offline` → `COPY src` | 写进 Dockerfile 模板，评审时看层顺序 |
| Go 缺 CA | `x509: certificate signed by unknown authority` | `COPY --from=build /etc/ssl/certs/ca-certificates.crt` | Go 项目模板里固定这一行 |
| 动态链接 | `fork/exec: no such file or directory` | `CGO_ENABLED=0` | CI 里加"镜像启动探针" |
| `COPY . .` 把 `target/` 也拷进去 | 镜像 1GB+ | 加 `.dockerignore` | 模板内置 |
| 端口特权 | 容器起不来 | 容器内监听 8080，Service 映射 80 → 8080 | 不用 `NET_BIND_SERVICE` |
| 架构不符 | `exec format error` | `docker buildx build --platform linux/amd64` | **CI 里统一构建，禁止本地 build 的镜像当制品** |

**这一步解决了基线里的哪条**：**镜像体积、构建耗时**（依赖分层缓存直接砍构建时间）。

> **两个必须说清的代价**：
> 1. **scratch / distroless 没有 shell**，出问题时进不去容器，只能 `kubectl debug` 起临时容器挂进去。这是"最小攻击面 vs 可排障性"的权衡。
> 2. **`settle-job` 与 `order-api` 共用同一个镜像**——所以定时任务和在线服务**必须配置外置**（阶段 2 做），否则改一个定时参数要重新构建整个 API 镜像。**这是"配置与镜像耦合"这个坑的第一现场。**

### 3.3 阶段 2 · 上 K8s

**目标**：把运行态从"人登机器改文件"变成"声明式声明"。

**具体产物**：

```
deploy/k8s/
├── order-api-deployment.yaml     # Deployment + Service
├── order-api-ingress.yaml        # Ingress
├── configmap.yaml                # 非敏感配置
├── secret.yaml                   # 敏感配置（演示用，生产走 External Secrets）
├── pdb.yaml                      # PodDisruptionBudget
├── settle-job-cronjob.yaml       # 同一镜像的 CronJob 形态
└── report-tool-deployment.yaml
```

`order-api-deployment.yaml` 的关键字段与写错后果：

| 字段 | 类型 | 必填 | 含义 | 写错的后果 |
|---|---|---|---|---|
| `spec.selector.matchLabels` | map | ✅ | 选哪些 Pod 归我管 | 与 template 标签不一致 → **apply 直接报错** `selector does not match template labels` |
| `spec.template.metadata.labels` | map | ✅ | 打给 Pod 的标签 | 与 selector **必须完全一致**（等值匹配，不是包含） |
| `spec.template.spec.containers[].resources.requests.cpu` | Quantity | ✅ | **调度依据 + HPA 分母** | 漏写 → HPA 永远 `<unknown>/50%`，一个不扩，**且不报错不告警** |
| `resources.limits.cpu` | Quantity | | 上限，超了被 cgroup 节流（**不杀容器**） | 太低 → 采集值顶到 limit → **HPA 会扩但每个新 Pod 同样被限死，扩了没用** |
| `readinessProbe` | Probe | ✅ | 能接流量吗 | 缺失 → **发布假成功**（Pod 一 Running 就进端点，实际还没准备好） |
| `livenessProbe` | Probe | ✅ | 还活着吗 | 过严 → 正常 Pod 被反复重启 |
| `startupProbe` | Probe | | 启动慢的应用用它，成功后才启用其他探针 | 不用 → 慢启动应用被 liveness 误杀 |
| `securityContext.runAsNonRoot` | bool | ✅ | 非 root | 不配 → 与阶段 1 的 `USER 1000` 脱节，安全上下文形同虚设 |
| `lifecycle.preStop` | Handler | ✅ | 终止前先做什么（排空连接） | 缺失 → 缩容把长连接硬切 |
| `terminationGracePeriodSeconds` | int | ✅ | 停止后等多久（默认 30） | 太短 → 优雅停机没跑完就被 SIGKILL |
| `imagePullPolicy` | enum | | `IfNotPresent` / `Always` | `Always` + 私有仓库无凭据 → `ImagePullBackOff` |

`settle-job-cronjob.yaml`（**同一镜像，第二种形态**）：

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: settle-job
spec:
  schedule: "0 30 2 * * *"        # 每天 02:30
  concurrencyPolicy: Forbid        # 上一次没跑完就不启新的
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: settle-job
            image: <同一 order-api 镜像>
            command: ["java","-jar","/app.jar","--job=settle"]
            envFrom:
            - configMapRef: { name: order-api-config }
```

| 字段 | 含义 | 写错的后果 |
|---|---|---|
| `concurrencyPolicy: Forbid` | 上一次没跑完就不启新的 | 设成 `Allow` → 定时任务堆积，**和在线服务抢数据库连接** |
| `restartPolicy: OnFailure` | 失败重启（不是 Always） | CronJob 里用 `Always` → **Job 永不结束** |
| `command` 覆盖启动参数 | 同一镜像跑不同角色 | 不覆盖 → API 容器里跑起了定时任务 |

> **这就是"同一个镜像两种形态"的价值**：`order-api` 和 `settle-job` 共用一个镜像、一次构建、一份漏洞扫描结果，**但跑成 Deployment 和 CronJob 两个工作负载**。既避免了"为定时任务单独维护一个仓库"，又避免了"定时任务随 API 一起扩容"。

**验证方法**：

```bash
# ① 语法自检（不碰集群）
kubectl apply -f deploy/k8s/ --dry-run=client

# ② 实际部署
kubectl apply -f deploy/k8s/

# ③ 等就绪（用 rollout status，不要只看 apply 返回 0）
kubectl rollout status deployment/order-api --timeout=300s

# ④ 关键判据：端点挂上了吗
kubectl get endpoints order-api-svc
# 期望：有 IP:PORT 列表；**空的就说明 selector 没匹配上**

# ⑤ 探针生效了吗
kubectl describe pod -l app=order-api | sed -n '/Events/,$p'

# ⑥ QoS 档位确认（阶段 3 要靠它）
kubectl get pod -l app=order-api -o jsonpath='{range .items[*]}{.status.qosClass}{"\n"}{end}'
```

**看到什么算成功**：
- `rollout status` 返回成功（**不是 `apply` 返回 0**）
- `kubectl get endpoints` **非空**
- Pod 的 `qosClass` 是 `Burstable` 或 `Guaranteed`（**不是 BestEffort**——否则节点紧张时第一个被驱逐）
- CronJob 手动触发一次成功：`kubectl create job --from=cronjob/settle-job settle-manual-001`

**常见失败点**：

| 失败点 | 症状 | 真实原因 | 怎么修 |
|---|---|---|---|
| 发布假成功 | `apply` 成功，访问 502/504 | **没配 readinessProbe**，Pod 一 Running 就进端点 | 补 readinessProbe，探到业务就绪接口而不是只探端口 |
| Service 503 | Pod 都 Running 但访问不通 | **Service selector 与 Pod label 对不上** | `kubectl get endpoints` 一看就清楚 |
| Ingress 404 | — | 没装 Ingress Controller / `ingressClassName` 写错 / `pathType` 用 `Exact` | 查 Controller Pod 是否 Running → `kubectl get ingress` 有无 ADDRESS → Events |
| 定时任务拖累在线服务 | 凌晨 2:30 API 延迟飙升 | 定时任务和 API 同副本、共资源 | `concurrencyPolicy: Forbid` + 独立 requests + 错峰 |
| 密钥进了 Git | 审计命中 | `kubectl create secret` 导出 YAML 提交 | 生产走 External Secrets 接 KMS；Git 里只留声明 |
| 配置打进镜像 | 改配置要重新构建 | `application.yml` 打进 jar | 配置全部外置为 ConfigMap（**阶段 1 遗留的问题在这里收口**） |

**这一步解决了基线里的哪条**：**发布一次耗时（部分）、故障恢复耗时（部分，靠自愈重建）、缩容是否优雅（补上 preStop 后变"是"）**。

### 3.4 阶段 3 · 弹性

**目标**：让副本数随负载自动伸缩——**前提是资源声明已经就位**。

**具体产物**：

```
deploy/k8s/
├── hpa.yaml          # HPA（order-api）
└── resources-patch.yaml   # 补 requests/limits（如果阶段 2 漏了）
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 2                # ← 谷时下限，也决定了弹性收益的上限
  maxReplicas: 8
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 默认值，写出来是为了让人看到
```

**前置条件（必须逐条确认，缺一条 HPA 就是空转）**：

| # | 前置条件 | 不满足的症状 |
|---|---|---|
| 1 | `resources.requests.cpu` 已写 | `TARGETS` 显示 `<unknown>/50%` |
| 2 | `metrics-server` 装好且 `kubectl top` 有数 | `kubectl top` 报错 / HPA `<unknown>` |
| 3 | `limits.cpu` 不低于常态用量 | CPU 打满但**扩了也没用**（被 cgroup 节流，每个新 Pod 同样被限死） |
| 4 | 节点有余量或配了 cluster-autoscaler / ACK 弹性伸缩组 | **HPA 扩了但 Pod 全 `Pending`** |
| 5 | `minReplicas` ≥ 2（生产） | 单副本时 surge=1、unavailable=0，滚动更新期间容量翻倍 |

> **第 4 条是 HPA 最常见的"以为扩了其实没扩"**：HPA 只管 Pod 数量，**不管节点**。Pod 数上去了但没节点放 → 全 Pending。

**验证方法**：

```bash
# ① HPA 状态
kubectl get hpa order-api
# 期望：TARGETS 是真实百分比（如 43%/50%），**不是 <unknown>/50%**

# ② 制造负载（Pod 内造 CPU；有 shell 用 exec，无 shell 用 ephemeral container）
POD=$(kubectl get pods -l app=order-api -o jsonpath='{.items[0].metadata.name}')
kubectl exec -it $POD -- sh -c 'yes > /dev/null & sleep 180'

# ③ 观察副本变化
kubectl get hpa order-api -w
kubectl get pods -l app=order-api -w

# ④ 缩容回落（注意默认 300s 窗口，别急着判失败）
kubectl describe hpa order-api | sed -n '/Events/,$p'
# 期望看到 SuccessfulRescale 记录
```

**看到什么算成功**：
- `TARGETS` 是**真实百分比**，不是 `<unknown>`
- 压测中 `REPLICAS` 从 2 涨到 8；停止负载后**约 300 秒**（缩容窗口）回落到 2
- `kubectl describe hpa` 的 Events 里有 `SuccessfulRescale` 记录

**常见失败点**：

| 失败点 | 症状 | 真实原因 | 怎么修 |
|---|---|---|---|
| HPA 永远 `<unknown>/50%` | 一个都不扩 | **漏写 `requests.cpu`**（分母不存在） | 补 `requests.cpu`；CI 里加 policy 校验必填字段 |
| HPA 有值但不扩 | TARGETS 一直低于阈值 | **分母被撑大**（只写 limits 而 limits ≫ 实际用量）／命中 10% 容差／已达 maxReplicas | 显式写 requests.cpu；或改用 QPS 这类业务指标（Prometheus Adapter） |
| 扩了但全 Pending | Pod 数上去了不起来 | **节点没余量** | 配 cluster-autoscaler / ACK 弹性伸缩组；`requests` 要真实 |
| 副本数来回抖 | 1→3→1→3 | 阈值卡在业务均值上 | `scaleDown.stabilizationWindowSeconds: 300` + 阈值放在"日常峰值 × 1.2" |
| 缩容打断长连接 | 用户看到 502 | 没有 `preStop` + 优雅停机 | 补 `preStop: sleep 15` + `terminationGracePeriodSeconds` + PDB |
| 和 Helm 打架 | 来回抖 | Helm upgrade 把 replicas 重置回 values，HPA 又改回去 | **HPA 管的 Deployment，Helm 里不设 replicas**（或设 null） |
| 扩容慢半拍 | 高峰过去了才扩 | 四段延迟：采集 15s + 同步 + 调度拉镜像 + 就绪探针 | 缩镜像（阶段 1 的收益在这里兑现）+ `minReplicas` 预留 |

**这一步解决了基线里的哪条**：**峰值资源占用**（弹性直接压低常态资源）、**扩容耗时**。

### 3.5 阶段 4 · CI/CD 与门禁

**目标**：让每次构建**可复现、可追溯、可拦截**。

**具体产物**：

```
ci/
├── .gitlab-ci.yml
└── templates/
    ├── build.yml
    ├── scan.yml
    └── deploy-gitops.yml
```

`build.yml` 的骨架（阶段划分与时间预算）：

| 阶段 | 干什么 | 失败率最高的原因 | 产物 |
|---|---|---|---|
| 触发 | `rules` 分流：MR 跑检查+单测+构建；main 跑全量；tag 才允许生产 | rules 写宽了，每个分支都跑全量 | — |
| 静态检查 | lint + 规范 + 敏感信息扫描 | 工具版本不固定 | — |
| 单测 | 并行分片 | 没有依赖缓存，每次重装依赖 | 覆盖率报告 |
| 构建镜像 | 多阶段 + `buildx --platform linux/amd64` | 无 layer 缓存、镜像源不通 | **镜像（tag = commit SHA）** |
| 安全扫描 | Trivy（CRITICAL 阻断）+ SonarQube（只卡新增代码） | 阈值定太严，全红后没人能合并 | 扫描报告（artifact 留 90 天） |
| 推制品 | 推 ACR，**tag 用 commit SHA，不用 latest** | 推 latest → 回滚找不到版本 | 镜像 digest |
| 交付 | **只写回 Git 的 values**，不碰集群 | 推了集群就变成 push 模式 | Git commit |

**核心设计（本项目的关键决策）**：

```yaml
variables:
  IMAGE: registry.cn-hangzhou.aliyuncs.com/linux321-devops/order-api:$CI_COMMIT_SHORT_SHA
  BUILDX_PROVENANCE: "false"      # ACR 个人版不认 provenance 附件

build:
  stage: build
  image: docker:25-cli
  services: [docker:25-dind]
  variables: { DOCKER_TLS_CERTDIR: "/certs" }
  cache:
    key: $CI_COMMIT_REF_SLUG       # 依赖缓存
    paths: [~/.m2/repository/]
  script:
    - docker buildx build --platform linux/amd64 --provenance=false --sbom=false -t $IMAGE --push .
  rules:
    - if: '$CI_PIPESTAGE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'

scan:
  stage: scan
  image: aquasec/trivy:latest
  variables:
    TRIVY_DB_REPOSITORY: "ghcr.io/aquasecurity/trivy-db:2"   # 国内源
  script:
    - trivy image --severity CRITICAL --exit-code 1 --no-progress $IMAGE

deploy_gitops:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    # 只改 Git 里的 values —— 集群交给 ArgoCD 拉
    - kubectl -n gitops set image ...   # 或直接改仓库文件后提交
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  when: manual                        # 生产手动审批
```

| 设计点 | 为什么 | 写错的后果 |
|---|---|---|
| `BUILDX_PROVENANCE=false` | Docker 23+ 默认附 provenance/SBOM，ACR 个人版拒收 | 典型报错：`oci.empty` / `manifest invalid` |
| `buildx --platform linux/amd64` | 研发用 Mac(arm64)，生产是 amd64 | `exec format error`，Pod `CrashLoopBackOff` |
| tag = commit SHA | 不可变、可精确回滚 | 用 `latest` → 回滚时找不到版本，且**覆盖了旧版本** |
| Trivy 只卡 CRITICAL | 全量 HIGH 阻断 → 没人能发版 → 门禁被关掉 | 门禁设计失败的头号原因不是工具，是阈值 |
| SonarQube 只卡新增代码 | 老项目几千个历史 bug，卡全量永远红 | 门禁被绕过 |
| 缓存 key 含 lockfile 哈希 | 只写分支名会跨分支命中脏缓存 | "本地能跑 CI 不能跑" |
| 生产 `when: manual` | MR 合并即部署生产 = 误发布 | 审计无留痕 |

**验证方法**：

```bash
# ① 流水线结构
#    GitLab → Pipelines 页看三段（build / scan / deploy_gitops）是否都绿

# ② 门禁真的能挡住吗（必须实测，别信配置）
#    故意引入一个 CRITICAL 漏洞镜像，scan 段应标红、流水线失败

# ③ 制品可追溯
docker pull $IMAGE && docker inspect $IMAGE --format '{{index .RepoDigests 0}}'
# 期望：digest 与流水线记录一致

# ④ 架构正确
docker manifest inspect $IMAGE | grep -E '"architecture"'
# 期望：amd64

# ⑤ AK 不进代码
grep -rE 'ALICLOUD_SECRET_KEY|ACCESS_KEY' .gitlab-ci.yml ci/ || echo "干净"
```

**看到什么算成功**：
- 流水线三段全绿，**且故意造漏洞时 scan 段确实变红**
- 镜像 tag 是 commit SHA，**仓库里没有 `latest` 这个 tag**
- `docker manifest inspect` 显示 amd64

**常见失败点**：

| 失败点 | 症状 | 怎么修 |
|---|---|---|
| DinD 起不来 | 容器 Running 但构建失败 | 集群策略禁 `privileged` → 换 Kaniko（无需 daemon） |
| 缓存投毒 | A 分支的依赖被 B 分支复用 | key 绑 lockfile 哈希 |
| CI 变量泄露 | AK 出现在日志 | Masked + Protected 变量；**严禁 echo** |
| 生产误发布 | 未审批就上了 | 保护分支 + `when: manual` + tag 触发 |
| Trivy DB 拉不下来 | 扫描超时 | 配 `TRIVY_DB_REPOSITORY` 国内源 + 进 CI cache |

**这一步解决了基线里的哪条**：**构建耗时**（缓存 + DAG 并行 + 依赖分层）、**发布一次耗时**（交付从"人推"变成"流水线推 Git"）。

### 3.6 阶段 5 · 交付与 GitOps

**目标**：让集群状态**只从 Git 来**。

**具体产物**：

```
charts/
└── order-api/
    ├── Chart.yaml
    ├── values.yaml
    ├── values-dev.yaml
    ├── values-prod.yaml
    └── templates/
        ├── deployment.yaml
        ├── service.yaml
        ├── ingress.yaml
        ├── configmap.yaml
        ├── hpa.yaml
        └── _helpers.tpl

gitops/
├── appproject.yaml
└── application.yaml
```

**Chart 的关键设计**：

| 设计点 | 规则 | 为什么 |
|---|---|---|
| 副本数 | **不设 `replicas`**（或设 null） | **HPA 独占副本数**。设了就打架 |
| 镜像 tag | `values.yaml` 里只放默认值，部署时注入 | 避免"CI 打的 tag 和 values 里的 tag 对不上" |
| 版本标签 | `podTemplate.labels` 里带 `app` / `version` / `env` 三个 | **阶段 6 的指标要靠它关联版本**（这是本项目最关键的一处埋点） |
| 敏感信息 | values 只放**引用**，值走 External Secrets | 密钥进 Git = 等保红线 |
| 通用性 | 名字用 `_helpers.tpl` 生成，环境差异全部收敛在 values | Chart 要能被别人复用 |
| Chart `version` / `appVersion` | 分开管理，每次发布必升 `version` | 同版本号覆盖 → 说不清发的是哪版 |

`application.yaml`：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: order-api-prod
  namespace: argocd
spec:
  project: prod
  source:
    repoURL: https://git.example.com/<org>/gitops.git
    targetRevision: main
    path: charts/order-api
    helm:
      valueFiles: [values-prod.yaml]
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      selfHeal: true
      prune: true
    syncOptions: ["PruneLast=true"]
    retry:
      limit: 5
      backoff: { duration: 10s, factor: 2, maxDuration: 3m }
```

| 字段 | 含义 | 写错的后果 |
|---|---|---|
| `automated.selfHeal` | 集群被手改 → 自动拉回 Git 的样子 | 不开 → 漂移长期存在，且没人知道 |
| `automated.prune` | Git 里删掉的资源，集群里也删 | **开在关键资源上 = 删库**（给关键资源加 `Prune=false` 注解） |
| `syncOptions: PruneLast=true` | 剪枝放最后执行 | 资源被提前删掉 → 同步过程中断 |
| `retry` | 同步失败自动重试 | 不配 → 一次网络抖动就停在 OutOfSync |
| `targetRevision` | 同步哪个分支/版本 | 指错分支 → 同步出完全不同的东西 |
| `path` + `valueFiles` | Chart 路径与环境 values | 指错目录 → `OutOfSync` 且 diff 看着莫名其妙 |

**验证方法**：

```bash
# ① ArgoCD 状态
argocd app get order-api-prod
# 期望：SYNCED + HEALTHY（**Synced ≠ Healthy**，见下）

# ② 改 Git 看自动同步
#    改 values-prod.yaml 的某个字段 → push
argocd app wait order-api-prod --health
kubectl get pods -n prod

# ③ 制造漂移，看 SelfHeal
kubectl scale deployment/order-api -n prod --replicas=6
argocd app get order-api-prod        # 应变 OutOfSync
argocd app sync order-api-prod       # SelfHeal 拉回
kubectl get deployment/order-api -n prod   # 副本数回到 Git 里的值

# ④ 差异定位
argocd app diff order-api-prod
```

**看到什么算成功**：
- `SYNCED` 且 `HEALTHY`（**只 Synced 不够**——ArgoCD 只看资源 apply 成功，不看业务健康）
- 手工 `kubectl scale` 后副本数被自动拉回
- `argocd app diff` 能给出具体差异行

**常见失败点**：

| 失败点 | 症状 | 真实原因 | 怎么修 |
|---|---|---|---|
| 一直 `OutOfSync` | 同步不动 | repo URL / 分支 / path 写错 | `argocd app diff` 直接看差异，别猜 |
| `Synced` 但业务不通 | — | **Synced ≠ Healthy** | 看 `HEALTH` 状态 + 就绪探针 |
| SelfHeal 把热修还原了 | 故障二次发生 | 紧急改动没进 Git | 热修也走 PR；实在不行先 `argocd app set --sync-policy none` 并**立刻登记** |
| Prune 删掉了数据库 | 数据没了 | Prune 无差别清理 | 关键资源加 `Prune=false`；**停机用副本置 0，不要删 manifest** |
| CI 和 ArgoCD 双写 | 互相覆盖 | CI 里 `kubectl set image` + ArgoCD 同步 | **CI 只写 Git，集群写入权只给 ArgoCD** |
| HPA 与 ArgoCD 打架 | 副本来回抖 | Helm 里设了 `replicas` | replicas 归 HPA 独占；或给 Deployment 加 `ignoreDifferences` |
| 一个 App 管两个环境 | 炸一个炸两个 | 多环境共用 Application | **一环境一 Application + AppProject 限定 repo 与 namespace** |

**这一步解决了基线里的哪条**：**发布一次耗时**（从"人执行脚本"变成"合并即同步"）、**故障恢复**（SelfHeal 自动拉平）、以及**变更可追溯**（Git 历史 = 审计证据，等保直接可用）。

### 3.7 阶段 6 · 可观测与告警

**具体产物**：

**版本标签埋点（本项目最关键的一处设计）**：

| 标签 | 值 | 埋在哪 | 用来干什么 |
|---|---|---|---|
| `app` | `order-api` | `podTemplate.labels`（Chart 模板） | 选服务 |
| `version` | commit SHA 或语义化版本 | **同上，同一处** | **把指标劣化对上"刚发布的那次变更"** |

```yaml
# templates/deployment.yaml

  labels:
    {{- include "order-api.labels" . | nindent 4 }}
```

**为什么 `version` 标签是关键**（这是本项目"可观测"和"监控"的区别）：

| 场景 | 有 `version` 标签 | 没有 `version` 标签 |
|---|---|---|
| 发布后错误率涨了 | `sum by(version)(rate(http_requests_total{status=~"5.."}[5m]))` → **一眼看出是新版本还是老版本的问题** | 只能看到总错误率涨了，**不知道是不是这次发布引起的** |
| 对比两个版本 | `sum by(version)(...)` 并列对比 | 做不了 |
| 回滚判断 | 新版本错误率高 → 有依据回滚 | 靠猜 |
| 灰度 | 按 version 切流量、看每个版本指标 | 灰度是瞎的 |

> **这是整篇最值钱的一句话**：**没有版本标签的监控，只能告诉你"出事了"；有版本标签的监控，才能告诉你"是不是这次发布出的事"。** 后者才是能做决策的信息。

**告警规则（三个层次，不要只有一条 CPU 告警）**：

| 层次 | 指标类型 | 例子 | 阈值怎么定 | 严重级 |
|---|---|---|---|---|
| 用户可感知（SLI） | RED | 错误率 > 1%（持续 5m） | **历史 P95 × 1.2**，不拍脑袋 | P0 |
| 用户可感知（SLI） | RED | P99 延迟 > 阈值 | 同上 | P1 |
| 资源饱和（USE） | USE | CPU 持续 > 85% | 与常态峰值比 | P2 |
| 容量 | — | HPA 一直贴着 maxReplicas | — | P2 |
| 交付健康 | — | ArgoCD 长时间 `OutOfSync` | > 10 分钟 | P1 |

```yaml
# observability/prometheus/rules/order-api.yaml
groups:
- name: order-api-slo
  rules:
  - alert: OrderApiHighErrorRate
    expr: |
      sum by(version) (rate(http_requests_total{app="order-api",status=~"5.."}[5m]))
        / sum by(version) (rate(http_requests_total{app="order-api"}[5m])) > 0.01
    for: 5m
    labels: { severity: critical, app: order-api, env: prod }
    annotations:
      summary: "order-api 错误率超过 1%"
      description: "版本 {{ $labels.version }} 错误率超阈值，影响下单主链路"
      runbook_url: "https://wiki.example.com/runbook/order-api-error-rate"
```

| 字段 | 含义 | 写错的后果 |
|---|---|---|
| `labels.app` / `labels.env` | **告警能回溯到具体应用** | 不带 → 告警进一个大群，**没人认领** |
| `labels.version` | 关联到具体发布 | 不带 → 不知道是不是这次发布引起的 |
| `annotations.summary` | 是什么 | 只有 summary → 收到告警不知道影响谁 |
| `annotations.description` | 影响谁、怎么办 | — |
| `annotations.runbook_url` | 处理手册 | 没有 → 每次告警都要现查，**MTTR 拉长** |
| `for: 5m` | 持续多久才触发 | 不写 `for` → 抖动即告警，**告警风暴** |

**日志管道**（Loki）：**label 只放低基数字段**（app / namespace / pod / level），**traceId 绝不进 label**。

```yaml
scrape_configs:
- job_name: kubernetes-pods
  kubernetes_sd_configs: [{ role: pod }]
  pipeline_stages:
  - docker: {}
  - json:
      expressions: { level: level }
  - labels: [level]     # 只把 level 提成 label
```

**验证方法**：

```bash
# ① Prometheus 抓得到吗
#    Grafana → Explore 跑：sum by(version) (rate(http_requests_total{app="order-api"}[5m]))
#    期望：**version 维度有多个值**（说明标签生效了）

# ② Grafana 面板出数
#    导入 dashboards/business.json，期望 QPS / 错误率 / P99 三个面板有数据

# ③ 告警真的能发出去
#    造负载触发 → 钉钉/电话收到

# ④ 告警风暴抑制

# ⑤ 日志管道验收（这是硬指标）
kubectl delete pod <某个 order-api Pod>
#    等新 Pod 起来后，在 Grafana 里查 {app="order-api"} 且时间窗覆盖删除前
#    期望：**还能查到已删除 Pod 的日志**（label 里能看到旧 pod 名）
#    查不到 = 还在依赖容器本地日志，管道没通

# ⑥ 版本关联验证（关键）
#    触发一次发布前后，对比 sum by(version) 的错误率
```

**看到什么算成功**：
- `sum by(version)(...)` 返回**多个版本值**——证明版本标签埋对了
- 删掉 Pod 后仍能查到它的历史日志
- 告警内容含 app / env / version / runbook
- 一次故障演练能在 **10 分钟内**从告警定位到具体 Pod 和具体日志行

**常见失败点**：

| 失败点 | 症状 | 真实原因 | 怎么修 |
|---|---|---|---|
| 版本标签没打 | `sum by(version)` 只有一个值 | Chart 模板里漏了 labels | 模板里集中定义（`_helpers.tpl`），不各处手写 |
| ServiceMonitor 没覆盖新环境 | 新 ns 上线了但没监控 | 按 ns 配的，新 ns 没加 | **改用 label 选择器**，覆盖全环境 |
| Loki 标签基数爆炸 | Loki OOM / 节点盘满 | 把 traceId、requestId、userId 打成 label | label 只放低基数（app/ns/pod/level），高基数字段留在日志正文，用 LogQL 的 json 解析器现场取 |
| 告警风暴 | 一晚上几百条 | 没分组没抑制 | `group_by` + `inhibit_rules` + `repeat_interval` + severity 分级路由 |
| 告警没人管 | 群里没人接 | 全推一个大群 | 按服务分群 + 值班表 + **升级规则**（15 分钟未响应升级） |
| Grafana 挂了告警也静默 | — | 告警挂在 Grafana Panel 上 | **生产告警一律走 PrometheusRule + Alertmanager**，Grafana 只做可视化 |
| 面板全空 | — | PromQL 对但数据源/时间窗/label 不对 | 先在 Explore 单跑 PromQL 验证，再贴面板 |

**这一步解决了基线里的哪条**：**故障恢复耗时（MTTR）**——把"靠人翻日志"变成"告警 → 看板 → 日志"三跳定位。

### 3.8 阶段 7 · 渐进发布

**目标**：让发布**先小流量试错**，指标不过就自动停。

**具体产物**：

```
deploy/rollouts/
├── rollout.yaml            # Rollout 资源
└── analysis.yaml           # AnalysisTemplate（接 Prometheus）
```

```yaml

metadata:
  name: order-api
spec:
  replicas: 4
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: { duration: 3m }
      - analysis: { templateName: order-api-slo }
      - setWeight: 50
      - pause: { duration: 5m }
      - analysis: { templateName: order-api-slo }
      - setWeight: 100

  template:
    metadata:

        app: order-api
        version: "{{ .Values.image.tag }}"

      containers:
      - name: order-api
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: order-api-slo
spec:
  metrics:
  - name: error-rate
    interval: 1m
    successCondition: result[0] < 0.01
    failureLimit: 3
    provider:
      prometheus:
        address: http://prom-kube-prometheus-stack-prometheus.monitoring:9090
        query: |
          sum(rate(http_requests_total{app="order-api",status=~"5.."}[5m]))
```

| 字段 | 含义 | 写错的后果 |
|---|---|---|
| `setWeight` | 每步放多少流量 | 灰度流量全是内部账号 → **覆盖不到真实场景，问题全量才暴露** |
| `pause.duration` | 观察窗口 | 2 分钟就放量 → 压力相关缺陷暴露不了 |
| `analysis.templateName` | 用哪个指标判定 | 指向不存在的模板 → **Analysis 一直 Pending，发布卡死** |
| `successCondition` | 通过条件 | 结果是 vector 却按标量比较 → 永远不通过 |
| `failureLimit` | 连续失败几次中止 | — |
| `provider.prometheus.address` | Prometheus 地址 | 填错 → Pending |

**验证方法**：

```bash
# ① 升级到新版本
kubectl argo rollouts set image order-api order-api=<新镜像>

# ② 观察步进
kubectl argo rollouts get rollout order-api

# ③ 故意造一个错误率超阈值的版本 → 应自动中止
kubectl argo rollouts abort order-api      # 手动中止
kubectl argo rollouts get rollout order-api  # 期望：回到稳定版本，无流量损失

# ④ 确认回到稳定版
kubectl get pods -l app=order-api -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image
```

**看到什么算成功**：
- 步进顺序是 10% → 50% → 100%，每步之间 Analysis 通过
- 故意超阈值时**自动中止并回到稳定版本**
- 中止后业务无流量损失（用户可感知）

**常见失败点**：

| 失败点 | 症状 | 真实原因 | 怎么修 |
|---|---|---|---|
| Analysis 一直 Pending | 发布卡住 | Prometheus 地址错 / PromQL 返回空 / 条件类型不对 | **先把 PromQL 在 Prometheus 里跑通再贴进来** |
| 灰度没发现问题，全量崩 | 事故 | 灰度只按比例，流量全是内部账号；观察窗口太短 | 按用户/地域分层；窗口覆盖一个完整峰谷周期 |
| 回滚了但数据已脏 | 二次故障 | 新版本写了不兼容的数据结构 | **三步发布法**：先兼容（双写/加字段不删字段）→ 再切流量 → 最后清理旧逻辑 |
| 蓝绿切完老连接不断 | 长连接还连老 Pod | 切了 Service selector，但没排空 | `preStop` + 优雅停机 + 连接排空时间 |
| Rollout 起来了但 ArgoCD 报漂移 | 一直 OutOfSync | Chart 里渲染的是 Deployment，集群里是 Rollout | **ArgoCD 管理的资源类型要和实际一致**（`kind: Rollout`） |

**这一步解决了基线里的哪条**：**故障恢复耗时**（把"发布引发的事故"拦在灰度阶段）、以及"发布一次耗时"里的**风险成本**（回滚从"分钟级人工"变成"秒级自动中止"）。

### 3.10 成本收益：给算法，不给数字

**这一节是本篇的方法论核心：教怎么算，而不是给一个看起来漂亮的百分比。**

#### 3.10.1 先算副本成本项

```
R  = QPS_peak / QPS_valley        # 峰谷倍率（必须用本项目实测流量）
C  = 单副本可承载 QPS              # 压测得到（不是估算）
N_fixed = ceil(QPS_peak / C)       # 固定副本策略下的副本数（按峰值常年备）

# 弹性策略下，一天内的副本数随时间变化：
N(t) = max(N_min, ceil(QPS(t) / C))

副本成本项节省比 = 1 - [ Σ_t N(t)·Δt ] / [ T × N_fixed ]
```

**关键提醒**：**D2 场景 A 里那张峰谷表（"早晚通勤双峰约为谷时 3–5 倍、OTA 推送瞬时 5–8 倍"）是行业口径的行业观测值，不是本项目的实测数据。** 用它做假设可以，**用它做结论不行**——必须用阶段 0 拉下来的 7 天实测曲线重算。

#### 3.10.2 再算节点成本项（副本降了不等于节点降了）

```
节点数 ≈ ceil( Σ(副本数 × 单副本 requests) / 节点可分配资源 )

节点成本项节省比 = 1 - ceil(N_elapsed / C_node) / ceil(N_fixed / C_node)
```

**为什么这一步经常算出来接近 0**：

| 原因 | 解释 | 怎么破 |
|---|---|---|
| requests 写得虚高 | 装箱率低，副本减半也减不了节点数 | 先做资源画像（用 Prometheus 的实际用量反推 requests） |
| 副本数不是节点数的整数倍 | 3 副本 → 2 副本，仍在同一个节点上 | 让 requests 与节点容量对齐 |
| 节点规格太大 | 单节点能装 20 个副本，8→4 不影响节点数 | **改规格或改节点池**，不是改副本数 |

> **这一条是很多"降本方案"翻车的地方**：**HPA 减副本 ≠ 云账单下降。** 只有当副本减少导致**所需节点数减少**时，节点成本才真的降下来。**"副本数降了 60% 但账单没变"是真实会发生的事**，面试时能讲清这一点，说明你懂 FinOps 而不是只会配 HPA。

#### 3.10.3 算发布效率收益

```
年节省人时 = 年发布次数 × 每次发布节省的分钟数 ÷ 60
```

**每次发布节省多少**：改造前是"人执行脚本 + 观察 + 确认"（分钟级），改造后是"合并 PR + 自动同步 + 看指标"（分钟级，但**风险成本下降**：灰度阶段发现问题，爆炸半径是 10% 而不是 100%）。

> **人时节省通常不是最大的收益项**（一个月发布 20 次、每次省 20 分钟，一年才 80 小时）。**真正的收益是爆炸半径**——发布出问题时，受影响用户从 100% 变成 10%，且回滚是秒级自动中止。**汇报时要分开讲这两项**，因为它们的量级完全不同。

#### 3.10.4 夜间缩容能省多少，取决于流量曲线

```
夜间节省 = (N_peak - N_valley) × 夜间时长 × 单副本资源成本 × (1 - HPA 生效延迟占比)
```

**必须扣掉两个损耗**：

| 损耗 | 量级 | 为什么 |
|---|---|---|
| HPA 生效延迟 | **1–2 分钟** | 采集 + 同步 + 调度 + 拉镜像 + 就绪探针 |
| 缩容稳定窗口 | **300s** | `scaleDown.stabilizationWindowSeconds` 默认值 |

**结论**：**夜间空窗窗口必须显著长于 300 秒 + 生效延迟**才有收益。如果业务夜间零流量但保留 2 个副本（`minReplicas=2`），**收益就是 0**——因为 `minReplicas` 是硬下限。**`minReplicas` 定多少，直接决定弹性收益的上限。**

> **这就是"成本收益的算法"里最容易漏的一环**：很多人算收益时忘了 `minReplicas` 这个地板。**弹性收益的上限 = 峰谷差 × (1 - minReplicas/N_peak)**。`minReplicas=1` 时理论上限最高，但生产上单副本意味着滚动更新期间容量减半——**这是个取舍，不是免费的**。

#### 3.10.5 成本收益的算法（不依赖峰谷假设的版本）

如果拿不到精确流量曲线（很多团队拿不到），用这个**只需要三组数**的版本：

```
可归因收益 = (改造前固定资源成本 − 改造后实测资源成本) / 改造前固定资源成本
```

**做法**：选一个**改造前后都稳定**的时间窗（比如"上线后第二周的同一周"），对比 ACK 账单里的节点费用。**注意用"账单"而不是"kubectl top"**——`kubectl top` 只看 Pod 用量，账单里还有节点管理费、系统盘、流量费、闲置预留。

> **这一条极其重要**：**"Pod CPU 利用率从 30% 降到 12%"不是省钱，"账单里节点费用降了 X"才是省钱。** 中间还隔着装箱率、节点规格、预留实例、云厂商的最低计费单位。**能把这两者区分开的人，才是真的懂 FinOps。**

### 3.11 端到端排障与运维命令速查（从代码到告警的全链路）

> **本节能做什么**：3.1–3.10 讲的是"八阶段怎么改造"，本节是"改造完上线后，**每天值班 / 面试都会敲的端到端排障命令**"——按全链路环节归类（代码提交 → CI 构建 → 镜像推 Harbor → ArgoCD 同步 → K8s 运行 → 监控告警），每条配真实例子。**整合项目比单工具难在"链路长、每段工具不同"，这一张表就是全链路的肌肉记忆。**

#### ① 代码提交与 CI 构建排障（链路最前端）

```bash
git rev-parse HEAD                              # 取当前 commit SHA（= 镜像 tag，全链路排障锚点）
git log --oneline -10                           # 看最近提交，确认本次提交在列
git status                                      # 看是否被 .gitignore 漏掉关键文件导致 CI 没触发
glab ci status                                  # GitLab CLI 看本次流水线状态（红/绿）
glab ci get-log <job-id>                        # 看某个 Job 日志（无 CLI 就用网页）
gitlab-runner verify                            # 私有 Runner 是否在线（流水线一直 Pending 先查这个）
kubectl get pods -n gitlab-runner               # Runner 以 Pod 形式跑时的状态
```

> **实战价值**：链路排障第一原则——**先用 `git rev-parse HEAD` 拿到 SHA，它就是贯穿 CI / Harbor / ArgoCD / K8s 的锚点**。流水线 Pending 不一定是代码问题，八成是 Runner 掉线或配额满；先看 `glab ci status` 再决定往哪段查。

#### ② 镜像推 Harbor / ACR 排障（制品这一环）

```bash
docker images | grep order-api                 # 确认本地镜像与 tag（tag 必须 = commit SHA）
docker tag order-api:<sha> registry.cn-hangzhou.aliyuncs.com/linux321-devops/order-api:<sha>
docker push registry.cn-hangzhou.aliyuncs.com/linux321-devops/order-api:<sha>
docker buildx build --platform linux/amd64 -t <repo>:<sha> --push .   # 跨平台构建直推
docker logout registry.cn-hangzhou.aliyuncs.com && docker login ...    # 401 先清登录态重登
cat ~/.docker/config.json | grep auth          # 看 ACR 凭据是否还在（401 先查这个）
crane digest <repo>:<sha>                      # 看 Harbor/ACR 里这个 SHA 的 digest 是否真存在
skopeo inspect docker://<repo>:<sha>           # 不拉全镜像只查 manifest（比对 size/config）
```

> **实战价值**：`ImagePullBackOff` 在整合项目里 80% 是"tag 不对 / 凭据过期 / 架构不匹配"三选一。`crane digest` 能在不拉镜像的前提下确认制品到底进没进仓库——**比盲目重推省十分钟**。架构坑：Mac 上是 arm64，生产节点是 amd64，必须 `buildx --platform linux/amd64`。

#### ③ ArgoCD 同步排障（GitOps 拉模型）

```bash
argocd app list                                # 看所有 App 的 SYNC / HEALTH 状态
argocd app get order-api                       # 看单个 App 的资源树与同步详情
argocd app sync order-api                      # 手动触发同步（PR 合并后没自动拉时）
argocd app diff order-api                      # 预览"Git 期望态 vs 集群实际态"差异（漂移检测第一招）
argocd app history order-api                   # 看部署历史（回滚用）
argocd app rollback order-api 3                # 回滚到历史版本 3
argocd app manifests order-api                 # 看 ArgoCD 最终会 apply 的渲染后清单
kubectl get app -n argocd order-api -o yaml    # 直接看 App CR（OUT_OF_SYNC 字段）
```

> **实战价值**：`Synced` 但 `OutOfSync` 反复横跳 = 有人在集群里手改（漂移）；`Synced` 但 `Not Healthy` = 应用起了但探针 / 依赖没就绪。**ArgoCD 排障先 `app get` 看状态，再 `app diff` 看差异，别一上来就手动 `kubectl`。**

#### ④ K8s 运行态排障（集群这一环）

```bash
kubectl get pods -n prod -o wide -l app=order-api     # 看 Pod 落在哪节点 / IP（NODE 列第一入口）
kubectl rollout status deploy/order-api -n prod       # 发布是否就绪
kubectl describe deploy/order-api -n prod             # 看新 ReplicaSet 为什么起不来
kubectl logs -f deploy/order-api -n prod --tail=100   # 跟应用日志
kubectl logs deploy/order-api -n prod -p --tail=50    # 看崩溃前日志（CrashLoop 必用 -p）
kubectl get events -n prod --sort-by=.lastTimestamp   # 看集群事件（OOMKilled / FailedScheduling）
kubectl top pods -n prod                             # 看资源占用（HPA 是否真生效）
kubectl get hpa -n prod                             # 看分母是否为 <unknown>（没写 requests）
```

> **实战价值**：整合项目里 `CrashLoopBackOff` 多半是"新镜像配置读不到 Secret"或"依赖的 Redis / DB 没起来"。**`logs -p` 拿崩溃瞬间日志，`describe` 的 Last State 拿退出码，两个一起看才准。** HPA 显示 `<unknown>` 就是忘了写 `resources.requests`，副本永远不扩。

#### ⑤ 监控告警排障（观测闭环这一环）

```bash
kubectl get pods -n monitoring | grep -E 'prometheus|grafana|loki|alertmanager'   # 组件是否活着
kubectl port-forward -n monitoring svc/prometheus 9090:9090   # 本地起 Prometheus 界面查 PromQL
promtool check rules /etc/rules/*.yaml             # 校验 PrometheusRule 语法（CI 门禁用）
kubectl get prometheusrule -n prod -o yaml         # 看告警规则是否加载
kubectl get servicemonitor -n prod                 # 看抓取目标是否注册（没它就没指标）
amtool alert query                                 # 查 Alertmanager 当前活跃告警
amtool silence add alertname=OrderErrorRate --duration=1h   # 维护窗口静默告警
kubectl logs -n monitoring deploy/loki -f          # Loki 卡住先查它自己
```

> **实战价值**："没告警"不一定是没问题——先 `amtool alert query` 确认告警真的发出来了，还是 Prometheus 根本没抓到指标（`ServiceMonitor` 没注册）。**观测闭环排障要分清"数据没采到"和"告警没路由"两件事。** `promtool` 把规则语法错误挡在 CI 阶段，比上线后发现强。

#### ⑥ 环境差异比对与配置漂移检测（面试高频）

```bash
# 配置漂移：Git 期望态 vs 集群实际态
argocd app diff order-api                          # ArgoCD 视角的漂移（最权威）
kubectl diff -f manifests/ -n prod                 # 本地清单 vs 集群实际态
# 环境差异：测试 vs 生产（逐字段比对）
kubectl get deploy/order-api -n test -o yaml > /tmp/test.yaml
kubectl get deploy/order-api -n prod -o yaml > /tmp/prod.yaml
diff /tmp/test.yaml /tmp/prod.yaml                 # 全量 diff
# 只比关键维度（副本数 / 镜像 / 资源 / 环境变量）
kubectl get deploy/order-api -n test -o jsonpath='{.spec.replicas}'; echo
kubectl get deploy/order-api -n prod -o jsonpath='{.spec.replicas}'; echo
kubectl get deploy/order-api -n prod -o jsonpath='{.spec.template.spec.containers[0].image}'; echo
# ConfigMap / Secret 漂移
kubectl get cm/order-api-config -n prod -o yaml    # 比对配置是否和 Git 里的一致
```

> **实战价值**：**"测试能过、生产挂"几乎都源于环境差异**——副本数、资源 limit、环境变量、镜像 tag 某一项没对齐。`diff` 两环境的 yaml 是最快定位法；`argocd app diff` 则直接告诉你"集群被手改了多少"。**面试能现场说出"怎么比对两环境差异、怎么检测漂移"，就是配置管理岗的加分项。**

#### ⑦ 回滚全链路（应用 + DB + 缓存）

```bash
# ① 应用层回滚（GitOps 托管的应用）
argocd app rollback order-api <last-good>          # ArgoCD 回滚到上一个健康版本
# 或直接 kubectl（非 GitOps 托管时）
kubectl rollout undo deploy/order-api -n prod
# ② DB 回滚（仅当本次发布含不兼容 schema 变更，且迁移脚本向下兼容、已提前备好）
kubectl exec -n prod deploy/order-api -- \
  flyway migrate -url=$DB_URL -user=$DB_USER -password=$DB_PWD -locations=filesystem:/db/rollback
# ③ 缓存处理（清脏缓存，避免读到旧结构；仅当缓存可安全重建）
kubectl exec -n prod deploy/redis -- redis-cli flushall
# ④ 回滚后验证三连
kubectl rollout status deploy/order-api -n prod
curl -s https://order.example.com/healthz          # 业务健康
argocd app get order-api                           # 确认 Healthy 且 Synced
# ⑤ 一致性校验：应用版本标签与 DB schema 版本对齐
kubectl get deploy/order-api -n prod -o jsonpath='{.spec.template.metadata.labels.version}'; echo
```

> **实战价值**：**回滚顺序 = 应用先回、依赖后回、缓存最后清**；DB 回滚是最后手段——优先用"向前兼容迁移"避免回滚数据（数据回滚的爆炸半径远大于应用）。**缓存能重建就 flush，不能重建就靠版本键隔离。** 这条顺序是面试里"发布翻车怎么救"的标准答案。

### 3.12 端到端排障实战（三个全链路场景串命令）

> **把 3.11 的命令用起来**：三个整合项目最典型的故障，按"现象 → 敲的命令 → 怎么读"走一遍。**都在 kind 集群 `day2` 上练，别在生产试。**

#### 场景 A：提交后一直没上线（链路断在 CI 或 ArgoCD）

```bash
git rev-parse HEAD                                 # ① 取本次提交 SHA（锚点）
glab ci status                                     # ② 看 CI 是否绿（红了 = 镜像没产出）
argocd app get order-api                           # ③ CI 绿了看 ArgoCD：SYNC 状态
# 现象：SYNC STATUS=OutOfSync 且没自动同步 → Webhook 没触发 / 自动同步关了
argocd app sync order-api                          # 手动补一次同步
argocd app wait order-api --health                 # 等它 Healthy
```

> **读法**：先定位断点在哪一段——`git rev-parse HEAD` 拿到 SHA，去 Harbor 看有没有这个 tag 的镜像：**没有 = CI 没推**（查 CI 日志）；**有镜像但 ArgoCD OutOfSync = 同步没触发**（查 Webhook / 自动同步）；**Synced 但不 Healthy = 集群里起不来**（跳到 ④）。**全链路排障第一原则：用 commit SHA 做贯穿各段的锚点，一段段往下验，不靠猜。**

#### 场景 B：上线了但镜像不是最新（制品 / 同步漂移）

```bash
kubectl get deploy/order-api -n prod -o jsonpath='{.spec.template.spec.containers[0].image}'   # 集群里实际镜像
argocd app diff order-api                          # Git 期望镜像 vs 集群实际镜像
docker images | grep order-api                     # 本地构建的 tag 是否等于想推的 SHA
crane digest <repo>:<sha>                          # Harbor 里这个 SHA 的 digest 是否真存在
argocd app rollback order-api <上一次正常版本>      # 确认漂移后先回滚止血
```

> **读法**：集群镜像 ≠ 期望镜像，就是漂移。`argocd app diff` 直接把差异打出来；**常见根因是"只 push 了 latest 没打 SHA tag"或"values 里写的 tag 没跟着 PR 改"。** 根治：镜像 tag 必须 = commit SHA，且 GitOps 仓库的 values 必须随 PR 一起改——这正是 L1 阶段 5/6 反复强调的纪律。**漂移的本质是"事实源不唯一"，回滚只是止血，修 Git 才是根因。**

#### 场景 C：发布翻车要全链路回滚（应用 + DB + 缓存）

```bash
# ① 先止血：应用回滚
argocd app rollback order-api <last-good>          # 或 kubectl rollout undo
# ② 判 DB 是否需回滚（本次发布是否含不兼容 schema 变更）
kubectl get cm/order-api-config -n prod -o yaml | grep DB_SCHEMA_VERSION   # 比对应用与 DB 版本
# 若含破坏性迁移 → 跑对应 rollback 脚本（前提：迁移向下兼容、已提前备好）
# ③ 清脏缓存，避免读到旧结构
kubectl exec -n prod deploy/redis -- redis-cli flushall     # 仅当缓存可安全重建
# ④ 回滚后三连验证
kubectl rollout status deploy/order-api -n prod
curl -s https://order.example.com/healthz
argocd app get order-api                           # 确认 Healthy 且 Synced
```

> **读法**：**回滚顺序 = 应用先回、依赖后回、缓存最后清**。DB 回滚是最后手段，优先用"向前兼容迁移"避免回滚数据（数据回滚风险远大于应用）。缓存能重建就 flush，不能重建就靠版本键隔离。**面试加分点：能说清"为什么 DB 不轻易回滚"和"回滚顺序为什么这样排"，比背命令值钱得多。**

> **三个场景的共同心法**：① **用 commit SHA 做全链路锚点**，一段段往下验；② **先定位断点在哪一段，再动手**，别在错的地方改；③ **回滚优先于修**，止血永远第一。整合项目的排障，比单工具排障难在"链路长、每段工具不同"——把 3.11 每段的高频命令练成肌肉记忆，面试时画得出"代码 → CI → Harbor → ArgoCD → K8s → 监控"这条链，就能覆盖 80% 的整合项目排障题。

## 5. 横向对比

### 5.1 一步到位改造 vs 分阶段改造

| 维度 | 一步到位（三个月一次上齐） | 分阶段（本篇八阶段） |
|---|---|---|
| **见效速度** | 三个月后才有第一个成果 | **阶段 1 两周就有可汇报的数字** |
| **故障归因** | 变量多，出问题不知道是探针/HPA/同步竞态 | 每阶段只引入一个新变量，归因范围小 |
| **失败代价** | 全盘皆输，前期投入全部沉没 | 停在哪个阶段就带走哪个阶段的成果 |
| **对团队的要求** | 需要一次投入 3 个熟练工 | 一个人也能推，每个阶段可独立验证 |
| **组织阻力** | 一次性大改，研发抵触最大 | 每阶段收益明确，抵触小 |
| **管理风险** | 领导看不到中间成果 → 中途砍预算 | 每阶段出数字 → 预算有依据 |
| **回滚成本** | 极高（配置、数据、流量全动过） | **随阶段递增，前期近乎免费** |
| **适合谁** | 有专职平台团队、有明确窗口期的大厂 | **10 几人团队、中小民企**（本篇定位） |

> **面试这么答**："云原生化不该是一次性工程，它是一次**有顺序的迁移**。我把它排成八个阶段，排序依据不是技术难度，是**回滚成本从低到高**。第一个阶段只做容器化，两周就能拿出镜像体积和构建耗时的对比；配置搬进 K8s 放在第五阶段之后，因为那之后回退成本开始指数上升。"

### 5.2 容器化 vs 原地改造

| 维度 | 容器化 + K8s（本篇路线） | 原地改造（在虚机上装 Docker / 改脚本） |
|---|---|---|
| **交付一致性** | 镜像即制品，**同一份镜像从 dev 到 prod** | 仍然"每台机器装一遍"，**漂移是常态** |
| **环境可重建** | 删了重建，一条命令 | 重建靠人，重建即引入新差异 |
| **弹性** | HPA + 弹性伸缩组 | 只能靠人加机器（**回到半夜叫人起床**） |
| **故障自愈** | Pod 挂了自动重建 | 挂了要人发现（靠 Zabbix 告警 + 人处理） |
| **回滚** | `helm rollback` / `git revert`，秒级 | 回滚靠人切脚本，分钟级且容易错 |
| **资源利用率** | requests 精确 + 装箱优化 | 每台虚机规格固定，**利用率天然浪费** |
| **对现有系统侵入** | 需要改部署方式、配置外置 | 侵入最小 |
| **团队学习成本** | 高（K8s / Helm / GitOps） | 低 |
| **适合什么阶段** | 有持续交付需求、想降本的组织 | **存量系统止血，或团队只有 1–2 人** |

> **"原地改造"不是没用的东西**——它是**阶段 1 的一个子集**：把 Dockerfile 做出来、在虚机上用 Docker 跑起来，本身就有价值（环境一致性 + 一份制品）。**问题只在于它到这一步就停了**，停在这里就永远拿不到弹性、自愈和 GitOps 的收益。

### 5.3 自建 K8s vs ACK 托管

**对本地民企的判断：几乎必然是 ACK（或同类托管），不是自建。** 理由是三条硬的：

| 维度 | 自建（kubeadm / kops） | ACK 托管版 |
|---|---|---|
| **控制面运维** | apiserver / etcd / scheduler 的 HA、升级、证书、备份**全要自己扛** | 托管 |
| **etcd 备份** | 自己写 `etcdctl snapshot save` + 验证 + 异地存（**做不好就是全集群没了**） | 托管侧负责 |
| **升级节奏** | 自己定，容易拖到版本落后 | 托管侧滚动升级 |
| **团队要求** | 至少 1–2 人全职懂控制面 | 1 人也能用 |
| **成本结构** | 控制面机器 + 运维人力 | **管理费 + 节点费**（管理费是固定支出） |
| **定制能力** | 完全可控 | 有限（网络插件、CNI 等受约束） |
| **适合谁** | 有专职基础架构团队、有特殊合规要求（信创、涉密） | **10 几人团队、民企（默认选这个）** |

**必须承认的代价**（不写这一段就变成了推销）：

- **管理费是固定支出**，用不满就是纯浪费。**kind 本地练、ACK 短跑验证，是性价比最高的组合**（本地练能力、ACK 验生产形态）
- **托管版限制了排障深度**：etcd 你不能随便登进去查，节点问题得提工单
- **版本可能落后于上游**几个小版本，**新特性要用得先看 ACK 的支持节奏**

> **面试这么答**："本地民企基本都用 ACK 托管版，我不会建议他们自建——**自建控制面需要的不是一台机器，是一个全职的人**。10 几人的团队没有这个人。但我要说清代价：**管理费是固定支出**，所以我建议先用 kind 在本地把能力练熟，再上 ACK 做短跑验证，**别一上来就开一个长期空转的托管集群**。"

### 5.4 阶段顺序的两条备选路径

**主路径**（本篇采用）：0 → 1 → 2 → 3 → 4 → 5 → 6 → 7

| 备选路径 | 顺序 | 优点 | 代价 | 什么时候选 |
|---|---|---|---|---|
| **可观测前置** | 0 → 1 → 2 → **6** → 3 → 4 → 5 → 7 | 一上来就有"看得见"，**排障成本低**，适合存量系统改造（故障多） | 监控要覆盖还没标准化的东西，**标签需要反复改** | **存量系统故障频发、团队不熟 K8s** |
| **交付前置** | 0 → 1 → 2 → **4 → 5** → 3 → 6 → 7 | 最快拿到"发布效率"提升（领导最关心） | 弹性收益来晚了，**"降本"这条线推迟** | **领导关注交付效率、成本不是主要诉求** |

> **怎么选**：**看公司当前最痛的是什么。** 痛点是"发布慢、老出事"→ 交付前置或可观测前置；痛点是"成本高、资源浪费"→ 主路径（弹性在第 3 阶段，尽早上）。**但 0 和 1 永远在最前面**——没基线、没制品，后面全是空转。

## 6. 踩坑与排障

| 你看到的（症状） | 状态 | 真实原因 | 怎么修 | 下次怎么防 |
|---|---|---|---|---|
| **改造做完了，汇报时说不出收益** | — | **基线没量**（阶段 0 跳过了，或表填了一半） | 立刻补测能测的（镜像体积、构建耗时用 CI 历史反推）；测不出来的标"估算"并写清方法 | **基线表和阶段表放同一个文件**，改一个必须改另一个；基线表进 Git，第一次提交即冻结 |
| **发布显示成功，访问却是 502** | Pod `Running` 但业务未就绪 | **没配 readinessProbe**（或探针只探端口不探业务） | 补 readinessProbe，探业务就绪接口；`kubectl describe pod` 看探针事件 | **没有 readinessProbe 的 Deployment 不允许上线**（CI 里加 policy 校验） |
| **HPA 永远 `<unknown>/50%`，大促不扩容** | — | **漏写 `resources.requests.cpu`**（分母不存在） | 补 `requests.cpu` | CI 里加必填字段校验；发布后必看 `kubectl get hpa` 的 TARGETS |
| **改一个超时参数要重新构建整个镜像、重新推仓库、重新发布** | — | **配置与镜像耦合**（`application.yml` 打进 jar / ConfigMap 改了不触发滚动） | 配置全部外置为 ConfigMap；Chart 里加 `checksum/config` 注解触发滚动 | Dockerfile 里不 COPY 配置文件；配置改动只走 Git 一次提交 |
| **ArgoCD 和手工 kubectl 互相打架：改了被改回去 / 改了集群同步又乱** | `OutOfSync` 反复 | **CI 或人手里还有集群写权限** | **写入口收敛成 Git 一个**；CI 只写 Git、不碰集群；人改集群必须补 PR | 集群 RBAC 收口：开发者只读 + 紧急通道留痕；把"集群写权限清单"当季度审计项 |
| **容器停不下来，每次都要等满 30 秒** | 停止慢 | **shell 形式 ENTRYPOINT**，sh 是 PID 1 不转发 SIGTERM | 改 exec 形式 `ENTRYPOINT ["java","-jar","/app.jar"]` | Dockerfile 模板里禁止 shell 形式；评审时看这一行 |
| **镜像能启动，但所有 HTTPS 调用报 `x509: certificate signed by unknown authority`** | 应用报错 | `scratch` **没有 `/etc/ssl/certs`** | `COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/` | Go 项目模板固定这一行；CI 里加"启动后发一次 HTTPS"的冒烟测试 |
| **Pod 起不来，日志首行 `exec format error`** | `CrashLoopBackOff` | 本地 Mac(arm64) 构建的镜像推到 amd64 节点 | CI 里 `buildx --platform linux/amd64` **单点构建** | **禁止本地 build 的镜像当制品**；`docker manifest inspect` 校验架构 |
| **推 ACR 报 `oci.empty` / `manifest invalid`** | 推送失败 | Docker 23+ 默认附 provenance/SBOM，ACR 个人版不认 | `--provenance=false --sbom=false` | CI 里固化 `BUILDX_PROVENANCE=false` |
| **HPA 扩了，Pod 全 `Pending`** | `Pending` | **HPA 只管 Pod 数不管节点**，集群没余量 | 配 cluster-autoscaler / ACK 弹性伸缩组；`requests` 要真实 | `maxReplicas` 按"单副本承载 QPS × 副本数 ≤ 集群余量"反推 |
| **副本数 1→3→1→3 来回抖** | — | 阈值卡在业务均值上 | `scaleDown.stabilizationWindowSeconds: 300` + 阈值放"日常峰值 × 1.2" | 阈值定完观察一周 flapping 次数再上线 |
| **Helm upgrade 之后副本数被重置，HPA 又调回去** | 反复抖 | **两个控制器抢同一个字段** | **replicas 归 HPA 独占**，Chart 里不设 `replicas`（或设 null） | Chart 模板里写死这个约定；或给 Deployment 加 `ignoreDifferences` |
| **缩容时用户看到 502、长连接被断** | 5xx 突增 | 缩容没有 `preStop` + 优雅停机；且 Exec 是 shell 形式 | `preStop: sleep 15` + `terminationGracePeriodSeconds` + PDB + exec 形式 ENTRYPOINT | 缩容演练：手动 scale down 观察网关 5xx，必须为 0 |
| **定时任务凌晨把在线服务拖慢** | 延迟升高 | 定时任务与 API 同副本同资源；`concurrencyPolicy` 默认 Allow | `Forbid` + 独立 requests + 错峰调度 | CronJob 单独一个 values，`resources` 与 API 不同 |
| **`helm upgrade` 显示成功，但 Pod 没起** | Pod 不 Ready | **Helm 默认不等就绪** | 加 `--wait --timeout 5m` | 所有部署命令统一带 `--wait`（否则"部署成功"是谎报） |
| **`helm rollback` 回到了错误的版本** | 版本不对 | 不指定 revision 时回退到"上一个"，中间失败过几次 revision 号会乱 | 先 `helm history <rel>` 看清，再 `helm rollback <rel> <明确 revision>` | 回滚记录进变更单，写明目标 revision |
| **ArgoCD 显示 `Synced` 但业务不通** | `Synced` / HEALTHY 不健康 | **Synced ≠ Healthy**——ArgoCD 只看资源 apply 成功 | 看 HEALTH 状态 + 就绪探针 + Pod 事件 | 应用级健康检查（不只资源级）写进 Application 定义 |
| **Prune 把数据库或关键中间件删了** | 资源消失 | Prune 无差别清理 Git 里不存在的资源 | 关键资源加 `argocd.argoproj.io/sync-options: Prune=false`；**停机用副本置 0，不要删 manifest** | Prune 按 App 分级；CRD 单独管 + `PruneLast=true` |
| **SelfHeal 把半夜的排障热修还原了，故障二次发生** | 参数莫名变回去 | 热修没进 Git | 热修也走加急 PR；实在不行先 `argocd app set --sync-policy none` 并**立刻登记** | 复盘时问"为什么当时必须手改"——答不出来就是流水线有瓶颈 |
| **告警一晚上几百条，手机被静音** | 告警风暴 | 没分组没抑制 | `group_by` 收敛 + `inhibit_rules` 抑制衍生告警 + `repeat_interval` 拉长 | 只推 main 分支失败 + 生产发布失败，其余进日报 |
| **告警发出去了但没人认领** | 无人响应 | 全推一个大群，没有归属 | 按服务分群 + 值班表 + **升级规则**（15 分钟未响应升级到负责人） | 告警 label 必须带 `app` 和 `env` |
| **Loki 内存打爆 / 节点盘被日志吃满** | OOM / 磁盘满 | **把 traceId、requestId、userId 打成 label** → 基数爆炸 | label 只放低基数（app/ns/pod/level），高基数字段留在日志正文，用 LogQL 的 json 解析器现场取 | 采集配置评审时专门查"哪些字段被提成了 label" |
| **Loki 里查不到已经删掉的 Pod 的日志** | 无数据 | 日志还在容器本地，Promtail 没采到 | 检查 Promtail 是否抓到 stdout；Helm 版 label 常是 `app_kubernetes_io_name` 而非 `app` | **验收标准就写死"删 Pod 后仍能查到"**，做不到就是管道没通 |
| **发布后指标劣化，但说不清是不是这次发布引起的** | — | **Pod 没打版本标签** | Chart 的 `_helpers.tpl` 里统一加 `version` 标签 | 模板里集中定义标签，不各处手写；发布后必看 `sum by(version)(...)` |
| **灰度 10% 没发现问题，全量后崩** | 事故 | 灰度流量全是内部账号；观察窗口太短 | 按用户/地域分层灰度；窗口覆盖一个完整峰谷周期 | 灰度步骤写进发布 SOP，不靠个人经验 |
| **回滚了但还是出事（数据不兼容）** | 二次故障 | 新版本写了旧版本读不了的数据结构 | **三步发布法**：先兼容 → 再切流 → 后清理 | 数据库变更必须有兼容窗口期，写进发布单 |
| **副本数降了 60%，账单没怎么变** | — | **副本减少没让节点数减少**（装箱率低 / requests 虚高 / 节点规格太大） | 先做资源画像，用实际用量反推 requests；再调节点规格或节点池 | 降本看**账单**不看 `kubectl top`；每月按标签出成本归集 |
| **弹性上了但夜间一点没省** | — | `minReplicas` 是硬下限；夜间窗口短于 300s 缩容窗口 + 生效延迟 | 业务允许时降 `minReplicas`；夜间窗口要显著长于缩容窗口 | 算收益时把 `minReplicas` 和 300s 窗口算进去 |
| **Docker 构建在 CI 里失败，本地能过** | 流水线红 | `cache:key` 只写分支名 → **跨分支命中脏缓存**；或 DinD 被集群策略禁特权 | key 绑 lockfile 哈希；无特权环境换 Kaniko | 缓存 key 与路径写成模板变量，不各写各的 |
| **CI 日志里出现 AK** | 泄露 | 变量没设 Masked/Protected，或被 echo 出来 | 改 Masked + Protected；严禁 echo | 流水线日志定期扫关键字 |
| **Terraform apply 报冲突，另一个人也 apply 了** | 锁等待/覆盖 | **本地 state 没有锁** | 换 OSS 远程后端（自带锁）；CI 统一执行 apply | 目录按环境分离；本地不 apply 生产 |
| **`terraform plan` 出现大量莫名变更** | plan 噪声 | provider 版本漂移 | `required_providers` 钉版本 + 提交 `.terraform.lock.hcl` | lock 文件进 Git；不在本地跑 `init -upgrade` |
| **operator 装完，CR 创建了但中间件行为不对** | 状态异常 | **既有 StatefulSet 没改成 Operator 管理的类型**（CRD 与既有资源冲突） | 先备份 → 在 Operator 里声明 → 校验数据 → 切读写 | 见 [`../06-云原生中间件/L2-中间件Operator选型.md`](../06-云原生中间件/L2-中间件Operator选型.md) |
| **中间件 Operator 升级后数据出问题** | 数据异常 | 升级前没做恢复演练，Operator 与中间件版本未钉 | 升级前**做一次恢复演练**并钉版本 | 恢复演练是必选项，见中间件篇 |

> **最后一条不是本项目的坑，但它是本项目的"下一步"**——阶段 8（中间件 Operator）的失败模式，和阶段 1–7 的失败模式**完全不同**：前面全是"应用层"问题（探针、标签、副本），中间件是"数据层"问题（备份能不能恢复、数据能不能迁移）。**数据层的错误不可回滚**，所以它的门槛更高。

## 8. 自测三问

1. **能说清输入输出吗？**
   - **输入**：一个巨石应用（Spring Boot 单体 + 定时任务 + Go 工具服务）+ 一张现状描述。
   - **输出**：一条八阶段的改造路径，每阶段有产物、验证命令、成功判据、失败点、回滚方案。
   - **中间**：阶段 0 量基线 → 阶段 1 让制品可识别（主线 A）→ 阶段 2 让运行态可声明（主线 B）→ 阶段 3/6/7 让运行可判定（主线 C），阶段 4/5 分别加固 A 与 B。
   - **再进一步**：输入"我要降本 30%"，输出是 3.10 节的算法和**需要补测的三个数**（峰谷倍率、单副本承载 QPS、实际账单口径），而不是一个百分比。

2. **能故意改坏再倒推吗？** —— 六个可执行实验（在 kind 集群 `day2` 上做，**别在生产做**）：

   | # | 改什么 | 会看到什么 | 倒推出的机制 |
   |---|---|---|---|
   | ① | 删掉 `resources.requests.cpu` | `kubectl get hpa` 显示 `<unknown>/50%`，压测时副本**一个都不涨** | HPA 分母是 requests；没有分母就退化为"退化成 limits"，两者都不写则无分母 |
   | ② | 删掉 `readinessProbe` | 发布瞬间 `kubectl get endpoints` 里立刻出现新 Pod，访问偶发 502 | readiness 决定是否进端点；liveness 才管重启——**两者混了就解释不清"假成功"** |
   | ③ | 把 `ENTRYPOINT` 改成 shell 形式 | `docker stop` 时容器**等满 grace period** 才退出，应用收不到 SIGTERM | PID 1 不转发信号 → 优雅停机失效 → 缩容必然 502 |
   | ④ | 删掉 `COPY ca-certificates.crt`（Go 镜像） | 容器起来但调外部 HTTPS 报 `x509: certificate signed by unknown authority` | `scratch` 没有 CA 目录 |
   | ⑤ | Helm 里给 `replicas` 写死 3，同时 HPA `minReplicas=1` | `helm upgrade` 后副本被拉回 3，HPA 再拉回，**两边来回抖** | 两个控制器抢同一个字段的所有权 |
   | ⑥ | 在 ArgoCD 开着的环境里手工 `kubectl scale` | App 变 `OutOfSync`，随后被 SelfHeal 拉回 | Git 是唯一事实源；**手改集群 = 制造漂移，下次同步被改回去** |

3. **能画上下游吗？** —— 画这条链，并在每两个环节之间标出"这一步失败会看到什么状态"：
