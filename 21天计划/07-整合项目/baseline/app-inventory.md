## 二、依赖关系（谁调谁）

```
                 ┌──────────┐
   外部流量 ───▶ │ order-api │ ──▶ ┌──────┐
                 └────┬─────┘     │  DB  │
                      │           └──────┘
                      ▼
                 ┌──────────┐
                 │settle-job│ ──▶ ┌──────┐
                 └──────────┘     │  MQ  │
                                   └──────┘
```

**要画出来，并标清楚三种边**：

| 边类型 | 含义 | 改造影响 |
|---|---|---|
| **强依赖**（同步调用） | 下游挂了上游就不可用 | 上游扩容要考虑下游容量；**下游缩容要看上游有没有重试风暴** |
| **弱依赖**（异步/最终一致） | 下游挂了上游还能跑 | 重试策略要测；**夜间缩容下游要看消息会不会积压** |
| **共享资源**（同一个 DB / MQ / 对象存储） | 互相影响但不是直接调用 | **最容易被忽略的一类**——共享一个 DB 的两个应用，缩容其中一个可能拖垮另一个 |

> **共享资源这一类必须单独标出来。** 面试讲「一个人干三份工」或讲多环境改造时，**能说出"这六个应用里有三个共用一个实例的 DB"是资历的标志**——它证明你真做过盘点，而不是照着架构图念。

给每个组件打分（1-5，5 最难），并写清**难在哪**：

| 组件 | 难度 | 难在哪 | 回滚成本 | 不可逆点 |
|---|---|---|---|---|
| | | | 低 / 中 / 高 | |
| | | | | |

**回滚成本**参考：

| 成本 | 判断依据 |
|---|---|
| 低 | 改个 yaml 就能回去，**无数据变更** |
| 中 | 需要重新部署旧版本 + 数据回填 |
| 高 | **有数据格式/结构变更**，回滚要先迁数据 |

**不可逆点**（勾出来就说明这一步要格外小心）：

- [ ] 镜像推成不可变 + 配置搬进 K8s（**过了这个点，回退成本上升一档**）
- [ ] 数据结构变更 / 加了不做兼容的字段
- [ ] 流量入口切到 Ingress / SLB
- [ ] 外部系统开始依赖新接口

## 四、必须问清的四件事

盘点时对着每个组件问：

1. **谁在用？**（内部几个系统 + 外部对接方，**外部对接方最容易被漏**）
2. **它能停多久？**（业务能容忍的最长不可用时间 → 决定 `maxUnavailable`）
3. **它的配置在哪？**（配置文件 / 硬编码 / 数据库 → 决定怎么拆 ConfigMap）
4. **它现在谁在维护？**（**维护者可能已变更**——这决定知识转移成本，也是"接替岗"风险）

> 第 4 问常被跳过但最关键：**上一任运维已经走了、配置只有他知道** —— 这种组件改造要排在最前面，因为它同时是"最痛"和"最容易出错"。
